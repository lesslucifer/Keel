Keel — architecture

What Keel is now: its commands, what setup installs, the policy keys, the evidence, the router tools and the close. Each rule lives in one skill or decision; this page points to it.

T1 · 2026-11-19 · Keel · current shape only; history is in git

The shape

Keel is one binary plus the rules it writes into a repository. The binary serves the CLI and the git hooks. The repository holds the policy (committed) and the evidence (git notes, which travel with the code).

Work moves from the owner to a router to a worker in one worktree. A worker commits on wu/<epic>/<slug> or epic/<epic>. Each WU and then the epic is gated at its merge into its target; the owner signs last. In Keel's own repository GitHub mirrors that flow: a router bot pushes work branches and opens pull requests, GitHub runs the same gate from main as required checks, the owner signs by approving a pull request and GitHub merges it, and the router hears the owner's comments and reviews (GitHub).

  E["epic/E"] -->|"epic gate"| M

The gate reads committed policy and notes; the hooks are the enforcement.

Docs have five tiers, T0 to T4 (skill keel-distill). This page is T1: it carries the shape and points at the skill or T2 page that owns each rule. Where it and the code disagree, the code wins (gaps).

Terms

EpicA user-visible change on epic/<slug>: one working unit or more, merged into main once.
WUA working unit: one independently shippable slice on wu/<epic>/<slug>, merged into its epic.
Gatekeel verify-dod at a merge boundary. It reads committed policy and notes, never an agent's word.
EvidenceThe notes a gate believes: test, doc, cr, mr, and the dod receipt the gate writes.
ExemptA range that changes no code_paths path. It owes no test, review or doc note; the sign-off still runs.

The seven git hooks

HookWhat it enforces
pre-commitNo non-merge commit on main; gates a conflicted merge finished by git commit; lints a staged code change.
commit-msgA staged rule_bearing path needs a Reviewed-By trailer naming a roster signer.
pre-merge-commitBy the target's committed policy: into epic/* the WU gate, into main the epic gate, then keel check.
pre-pushkeel check on every pushed tree; verify-dod range on main and epic/*; then pushes the notes.
post-checkoutSets merge.ff=false; copies .gitworktreecopy entries into a new worktree.
verify-doc-post, verify-doc-stopThe host's doc checks, per write and at turn end.

Each hook is a shim. It refuses when the first keel on PATH is missing or lacks Keel's marker, then runs the command; the two doc hooks exit 0 instead. The hooks: skill keel-workflow §7; the marker: install §1.

The config keys

.keel/config.toml is read twice. The pre-merge-commit hook reads the copy committed on the target, so a branch cannot change the rules that judge its own merge; by-hand commands read the working copy. Defaults and comments: templates/config.toml. [review] modules, rubric and [router] are read by the review skill and the launcher, never the CLI; the launcher reads [router] strictly, from HEAD (DEC-39).

The router tooling

The router coordinates the owner and the workers and never does the work (skill keel-router; decisions router and router hosts). Its tools are in scripts/. On Claude Code the guard is a fail-closed hook; on DeepSeek Harness no guard plugin exists, so the skill is the only guard (backlog D2).

The epic close

An epic closes on its own branch, then lands on main. The code enforces the evidence at each step; the owner signs, merges and pushes. In full: skill keel-workflow §2, and skill keel-distill for distilling.

  1. Merge main in if it moved.
  2. Distil each T3 doc into T1/T2, then git rm it; a copy stays in the ignored docs/.archive/.
  3. On that archive commit, write the epic's test (e2e) and doc notes, with no --target.
  4. Write the epic result pair into docs/.archive/.
  5. keel preflight epic, the epic code review, then keel verify-dod epic: only check 8 is red.
  6. The owner signs (keel mr confirm epic), merges --no-ff into main and pushes.

A close commit is judged by its epic-range notes

A plain commit whose notes name the epic's base is judged at the close level (checks 1, 2 with e2e, and 6) when it is the pushed tip or changes no code. That makes the archive commit pushable (skill keel-workflow §3, §4).

A bare tip is resolved, never guessed

A WU tip is measured against the epic its branch names. A tip with no branch takes the epic its wu/ holders name, else the one epic/ branch that holds it, else it is refused, naming --target; main is never a guess for a WU (skill keel-workflow §1, §4).

GitHub

This flow is dropped (owner ruling 2026-11-19, DEC-70): releases and the owner's own pushes stay on GitHub; everything else below stands until E-GHREVERT reverts it (backlog local-app A1), and the local app replaces it (local-app.html).

Keel's own repository only: keel init sets none of this up in another project. Every workflow runs from main, so a branch cannot change what judges it. The checks hold a merge only while the owner's keel-merge ruleset is on; the typed sign-off and local merges still work without GitHub.

What no gate reviews

  • Everything outside code_paths. Docs, skills, templates, .keel/ and scripts/ are not code to the gate. A rule-bearing commit needs the owner's trailer, which is typed text (DEC-47).
  • A docs/infra-only WU or epic. It owes no test, review or doc note; the hooks guard, an archived T3 doc's lineage and the owner's sign-off still run.
  • Whether a waiver's reason is true. Any non-blank reason passes.
  • Doc depth and claims. verify-doc checks form only; its Mermaid label scan is best-effort (backlog B21).
  • The dod/v1 receipt. Nothing reads it, or notices its loss.
  • Whether a follow-up names a real destination.
  • GitHub's settings. The checks hold a merge only while the owner's ruleset is on; gh-settings-check.sh reads them, but nothing makes it run. A check belongs to a commit, so a wu/ pull request into main is never approved (DEC-65).
  • An approval note's review. Only the sign-off writer reads the GitHub review; check 8 checks the note offline, so a same-user shell could write one (DEC-64, DEC-48).
  • The router guard on DeepSeek Harness. A skill rule only; the router must say enforcement is missing.
  • The keel binary itself. The hooks refuse an old or foreign one; nothing installs the right one for you.
