The problem

The epic splits each plan and result into a short page for you and a data file for agents and checks. It also slims today's long docs. Nobody has yet listed which docs that touches, what each keeps, or how short "short" is. The rest of the epic builds on that list, so you approve it first.

How you approve

  1. The worker writes the inventory page and the two example pages.
  2. You open the inventory page. The table comes first. The field lists, the slimming rules and the caps follow. Two links open the examples.
  3. You comment in the pages. The worker fixes each point and resolves the comment.
  4. You tell the router "W1 approved", or what to change.
  5. The worker records the decision and writes the result. You sign off this part. The next parts may then start.

A · The inventory table

In short: one row per doc kind. Each row says who reads it and what it becomes. The rows come from the code, not from memory.

  • Rows: epic plan, WU plan, WU result, epic result, decisions, use cases, backlog, the decision, use-case and backlog indexes, architecture, install, AGENTS.md, the report note, the Pages index. Plus any kind the code scan finds.
  • Columns: reader · tier · page part · data part · where the data part lives (a committed file or a git note) and why · word cap · slimming rule.
  • Open point 1 of the epic answered per row: a committed file beside the page, unless the row says why a note fits better.
  • Open point 5 of the epic carried in: the decision and use-case indexes become data files; the backlog order stays a short page.
  • The data file's name: the page's name with .yaml.

B · The data file's fields

In short: what today's tags hold becomes named fields, one table per role. W2's check reads these lists.

  • Shared fields: role, status, title, date, epic, WU id, page path.
  • Epic plan: the nine tags of today, with each WU as a list entry holding its summary, maps-to, expected and dependencies.
  • WU plan, WU result, epic result: their tags of today, one field each.
  • A field keeps its tag's name (maps-to, test-plan), so skills and agents change little.
  • For each field: required or optional, text or list, and which role a collapsed epic merges.
  • One example data file per example page, shown inline on the inventory page.

C · The two plan pages, redesigned

In short: for the epic plan and the WU plan, what the page shows you, in what order, and how long. Each comes with a real example, so you judge the shape, not a description of it.

  • Per page: the sections in order, what each holds, its cap. What moves to the data file (file lists, test lists, grounding) is named.
  • Example epic page: this epic's own plan, rewritten in the new shape. You have read the old one, so you can compare.
  • Example WU page: this W1 plan, rewritten the same way.
  • Both are plain pages with no checklist tags. Today's check reads only their links and diagram labels.
  • This epic's own plans keep today's tags until W2 reaches the epic branch (epic open point 7).

D · Slimming rules and word caps

In short: what each kept doc drops, and a cap per page kind. W5 and W6 apply the rules. W2 enforces the caps.

  • Rules: a replaced decision keeps its id and one line; use cases drop their build history; the backlog drops done and struck rows; architecture and install drop history and rules the skills already hold.
  • Caps: set from today's word counts per kind, measured over the docs on main and the archived plans in git history. The epic plan's 300-word top stays.
  • Each cap is shown beside today's median and largest doc of that kind.

E · The decision

In short: once you approve, the table's rules become one new decision. It amends the three decisions above.

  • The next free DEC id, checked on every branch first: E-GHSETUP and E-LOCALTOOL may mint ids too.
  • Written in docs/decisions/workflow-gates.html and the decision index, in today's form. W5 turns the index into data.
  • Written only after your approval: a decision records what you approved, not a proposal.

Details

Acceptance

  • docs/work/2026-11-18-e-docsplit-w1-inventory.html exists, approved by you: a row for every doc kind listed in part A and every kind the scan below finds, each column filled.
  • It lists the fields of all four roles. Every data-item tag in src/verify_doc.rs's checklists, plus data-wu, data-artifact and data-status, maps to exactly one field.
  • It shows a cap per page kind, beside today's median and largest of that kind.
  • Two example pages exist, the epic plan's and this plan's rewrite, each under its proposed cap, with an example data file for each shown inline.
  • The new decision is in docs/decisions/workflow-gates.html and the index, under an id no branch uses, naming the three it amends.
  • keel verify-doc is green on every doc W1 adds or edits.

How it is checked

  1. Coverage: a one-off scan of src/, scripts/, skills/ and templates/ for every doc path, role or note Keel reads or writes. Each hit maps to a row. The scan and its result go in the WU result.
  2. Tags to fields: the checklist tags in src/verify_doc.rs are compared with the field tables. None missing, none extra.
  3. Caps: word counts per kind, counted the way keel verify-doc counts the top, over main and the archived plans. Each example page counted against its cap.
  4. DEC id: a search of docs/decisions on every local and remote branch.
  5. Doc check: keel verify-doc on each page.
  6. You: the approval of step 4 above, quoted in the result.

Scripts run from a scratch directory and are not committed.

Unit, integration, e2e: none. W1 touches no code path (src/, tests/), so Keel exempts it from test, review and doc evidence. If a gate asks anyway, each layer is waived with the reason "docs-only WU: no code".

Stand-ins: the six checks above. The epic's end-to-end test (W2 to W4) proves the split in the tool.

Review: no code review: there is no code. Your read of the inventory is the review.

Sign-off: keel mr confirm wu on the tip with the WU result, as always.
