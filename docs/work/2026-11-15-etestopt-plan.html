E-TESTOPT · A full test run in half the time, green in a worker's sandbox

Epic plan for the owner's ask of 2026-11-15: "Init a new epic for test optimization, we've done the same thing on trawler, let's migrate it here, the tests currently take insanely long."

T3 · epic plan · 2026-11-15 · Keel · branch epic/E-TESTOPT off main 690aef1 · ready without owner review (owner ruling 2026-11-15: plans carry their recommended answers)

The problem

A full test run takes about a minute here, and longer when several workers test at once. Every gated step pays it: each review round, each push, the merge into main. Most of the time goes to starting programs: one run starts about 22,600 git processes. The test files also run one after another. One test waits out a 20-second timeout on purpose. And in a worker's sandbox, 12 tests fail for reasons that have nothing to do with Keel. This epic halves the run and makes it green in the sandbox, porting what sped up Trawler's suite.

Terms

SandboxThe limits a worker session runs under. It blocks some files and commands.

The work

W1 and W2 run in any order. W3 moves every test file, so it follows them. W4 follows W3. W5 closes.

W1 · The tests run the real git

In short: on macOS, /usr/bin/git is a small launcher (the xcrun shim) that finds the real git and starts it. In a worker's sandbox it also prints an error about its cache, and 12 router tests that compare git's output fail on that line. The shim also costs time: 8.4 ms per git call against 5.2 ms for the real git, over 22,600 calls a run. The test helpers put the real git first on every path a test hands to a child process, so keel, the hooks and the router scripts all use it.

  • tests/common/mod.rs resolves the real git's directory once per process (for example from git --exec-path) and common::cmd puts it first on PATH. Where no shim is in the way (Linux, or no real git found), nothing changes.
  • Every test that builds its own PATH (the router launcher's fast_path, the review and walk helpers that put keel's directory first) starts from that path.
  • A guard in the style of every_test_spawn_strips_gits_env: no test sets PATH except from the helper's.
  • Production code is unchanged: keel still runs whatever git the user's PATH names.

The owner's ask (2026-11-15) · backlog R43, first half (sandbox-only reds from the xcrun shim) · testing charter: tests are deterministic and hermetic.

Integration: with the stock PATH in a worker's sandbox, cargo test --test router has no xcrun cache failure (12 reds today); a test asserts the git a spawned test command resolves is not the shim when a real git exists. Unit: the directory resolver, including the case with no real git. Observable: the recipe's stock-PATH run matches the CLT-git run within noise.

W2 · A test that proves a timeout does not wait out the full bound

In short: the router tests bound every wait by one 10-second constant. watcher_run_is_bounded_when_the_watch_outpolls_its_releases proves that a watch that is never released makes the helpers give up, so it waits out that bound twice: 20.1 s alone, the longest test by four times. It also fails in the sandbox, because it lists processes with ps, which the sandbox blocks (R43, second half).

  • The stepped-watch helpers take their bound as an argument. A test that expects "never" passes a short bound; every wait for something that must happen keeps 10 s.
  • "The sleep shim has exited" is checked without ps, for example from a pid file the shim writes and a liveness check.
  • A sweep of the suite for other waits that run to their bound on purpose; the serial profile shows none above 5 s.

The owner's ask · backlog R43, second half (the watcher test in the sandbox) · testing charter: no sleep as synchronization; fast and isolated.

Integration: the watcher test still fails if the helpers stop bounding a never-released watch, kept by a mutant check (the helper's bound removed: the test must hang or fail, not pass); it runs under 3 s and is green in the sandbox. Unit: the bound helper. Observable: tests/router.rs's test program under cargo test drops from 23.9 s to its next-slowest test.

W3 · One test program

In short: Trawler's port (E-GATEPAR2.W4). The ten test files become modules of one program, so cargo test runs all 231 integration tests in one pool instead of ten in a row. A trial copy measured 61.3 s → 38.2 s with no other change, and 29.2 s at 8 threads with the watcher test left out. One program also ends the stop at the first failing file that hid five router reds in E-SEED2.W15.

  • git mv tests/<f>.rs tests/suite/<f>.rs; tests/suite/main.rs declares each module and #[path = "../common/mod.rs"] mod common;; each mod common; becomes use crate::common;. That is the whole change the trial needed: it compiled and passed first time.
  • A guard test: a .rs file directly under tests/ fails, naming the fix (open point 3).
  • The thread cap, if W3's own re-measure still shows it (open point 2): .cargo/config.toml [env] RUST_TEST_THREADS = "8". Checked: cargo hands [env] to the test programs.
  • [check] test stays cargo test: no change to .keel/config.toml, no new tool (open point 1).

The owner's ask · Trawler E-GATEPAR2.W4 "suite-cost" (34 test binaries → 9) · backlog e-seed-v2's E-SEED2.W15 lesson (cargo stops at the first failing binary).

Integration: cargo test lists exactly two test programs (the unit tests and suite); the passed count equals the count before the move (329 with W1 and W2 in); the guard fails on a planted top-level test file. Unit: waived, no production code. Observable: the recipe's cargo test wall time near the trial's 38 s (29 s with the cap).

W4 · Fewer spawns: fixtures built once, copied per test

In short: spawns are the cost, and they get dearer in parallel: kernel time is 60 s run one test at a time and 321 s at 14 threads. Many tests build the same scratch repo from scratch: init, config, keel mr setup, a commit, keel hooks install, branches, commits through the hooks. W4 measures where the 22,600 git calls come from, then builds each common fixture once per run and copies it per test, with no spawn.

  • First, the profile: git calls per test, split into fixture setup and the steps the test judges (recipe step 5, run per test). The fixtures that pay go first; today verify_dod (10,266 calls) and mr (5,909) hold 72%.
  • A template per fixture shape, built once (OnceLock) in its own temp dir and copied into each test's temp dir with std::fs. Each test still owns its copy.
  • A fixture whose repo records an absolute path (hooks, worktrees, a remote) is rebuilt or rewritten after the copy; the WU checks every shape it converts.
  • No test loses an assertion; table-driven tests that rebuild a repo per row may share one where rows do not write.

The owner's ask · testing charter: each test owns its state and runs in parallel · Trawler's shared fixtures (tests/suite/common.rs, E-GATEPAR2.W5's hermetic.rs).

Integration: a template copy is independent: a write in one test's copy is not seen by another's or by the template (asserted for each shape). The suite's git calls per run fall (recipe step 5), and the passed count is unchanged. Unit: the copy helper (a tree with a symlink, an empty directory, the file modes git needs). Observable: recipe steps 3 and 5, before and after, in the WU result.

Acceptance

  • The recipe's cargo test --no-fail-fast on the epic tip takes at most half of main's on the same machine in the same session, every test passing.
  • The suite is green in a worker's sandbox with the stock PATH.
  • cargo test builds two test programs: the unit tests and suite. A new top-level test file fails a test.
  • No single test takes more than 6 s in the serial run.
  • The passed count is 329 or more; no test was deleted to buy time.
  • The before/after table is in the epic result, with load and both git paths.

Use cases

  • None. A process epic: it changes only tests and test tooling. What keel check runs (UC-GATE-4) stays cargo test.

Out of scope

  • Keel's own git calls in src/ (open point 4: a backlog row).
  • A required test runner, or any change to .keel/config.toml.
  • Dropping or weakening a test to save time.
  • The router's other sandbox rows (R30 and the rest of R40–R46).
  • CI: Keel has only release.yml; no test workflow is added.

Epic test

Waiver intent (open point 5): no e2e test is added. The epic changes no product behaviour, and a test that runs the whole suite would run itself. In its place, at W5:

  1. A scratch clone with Keel's hooks installed (keel hooks install run there only) merges the epic into main with git merge --no-ff. The pre-merge-commit hook runs keel check on the merged tree: green. This is the E-SEED2.W15 lesson: a gate change is done when the real merge through the real hook passes.
  2. The recipe runs on main and on the epic tip, same machine and session. The epic result carries the table.
  3. The suite runs green in a worker's sandbox with the stock PATH.

Risks

  • Load cannot be controlled: the sandbox blocks ps, so a sibling worker's test run is invisible. Mitigation: load recorded, two samples, before and after in one session.
  • One program shares one process: a test that changes process-wide state (environment, current directory) would now reach tests from other files. A grep finds no set_var, remove_var or set_current_dir in tests/ today; W3 re-checks.
  • The stock-git cost outside the sandbox may be lower than 8.4 ms, since the shim can write its cache there. W1's gain outside the sandbox is measured, not assumed.
