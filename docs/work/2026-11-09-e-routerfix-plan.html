E-ROUTERFIX · Headless workers can build, test and gate

Collapsed epic + WU plan (one WU) for epic/E-ROUTERFIX: a router/meta-tooling hotfix. It gives launcher-spawned workers the cargo/keel commands their work needs, and lets the router choose a worker's permission mode per task.

T3 · epic plan + WU plan · 2026-11-09 · Keel · branch epic/E-ROUTERFIX off main 296fa97

Intent

Headless workers started by scripts/router-worker.sh cannot run cargo or keel. Three separate workers this session got "requires approval" on cargo/keel, and that answer is a refusal, because a claude -p session has nobody to approve. A worker therefore cannot run its own tests, write its test/v1/doc/v1 notes, run keel preflight or run the code review. That is the workflow every WU has to follow. The launcher also hardcodes --permission-mode acceptEdits, so the router has no way to start a read-only checker in a stricter mode. This epic gives every launcher-spawned worker a fixed, narrow grant for cargo and keel, and it explicitly denies the owner-only keel mr. It also adds an optional, validated --permission-mode to the launcher. Why now: backlog e-router-v2 R2 asked whether workers stall under acceptEdits. Real runs answered it: they are refused. Every multi-worker epic is currently blocked at its gate steps.

Design

Worker grants live on the launcher's command line, not in .claude/settings.json. The launcher adds a fixed --allowedTools list and a fixed --disallowedTools list to its claude -p call. The grant then reaches exactly the processes the launcher starts. It never reaches the router, the owner's interactive session in this repo, or another agent, and it lives in a file a worker can edit. That rules out settings.json (F2, F3).
ListEntries (each Bash(…); bare and " *" forms both listed, so a no-argument call matches too)Why not more
allow · cargocargo build, cargo test, cargo check, cargo clippy, cargo fmtNo cargo run: cargo run -- mr is keel mr. No install/publish/add/update: those touch the machine, the registry or the dependency set.
allow · keelkeel preflight, keel verify-doc, keel verify-dod, keel notes write, keel lint, keel checkExactly the subcommands a WU's gate steps use (src/main.rs dispatch). No init or hooks install: they write into the shared git common dir. No hook …: git invokes those.
denykeel mr, keel mr *, cargo run, cargo run *mr is the owner's manual review (AGENTS.md). A deny also beats the user-level allowlist.
Known ceiling, recorded as a DEC rather than hidden. cargo test runs code the worker wrote (tests, build.rs), so the grant amounts to code execution in the worktree. That is the same class as DEC-33's accepted risk. The keel mr deny states intent; it is not a sandbox.

Permission mode: spawn and resume take an optional trailing --permission-mode <m> after their positional arguments. Accepted values are acceptEdits (the default when omitted, so today's behaviour is unchanged) and plan (read-only checkers and reviewers). Anything else is refused with a message naming the set, including bypassPermissions, dontAsk, default, a missing value and an unknown option. The launcher, not the guard, is the boundary that keeps bypassPermissions out of the router's reach (F5). The chosen mode is written to the run dir (permission-mode) and printed on the RUNNING line. A resume does not inherit the mode: each run states its own or gets the default. A named option, not a sixth positional, so it composes with E-SEED2.W7's possible effort argument.

flowchart LR
  R[router session] -- "spawn … opus [--permission-mode plan]" --> G{router-guard.jq}
  G -- shape ok --> L[router-worker.sh]
  L -- "mode ∈ {acceptEdits, plan}?" --> X[refuse]
  L -- "claude -p --permission-mode m --allowedTools cargo/keel list --disallowedTools keel mr, cargo run" --> W[worker]
  W --> T[cargo test · keel preflight · keel notes write]
  R -. "cargo / keel" .-> G2[guard: deny]
Grants travel only on the launcher's command line. The router keeps its closed whitelist.

Use cases

Changes UC-ROUTE (worker modes and launcher). The launcher contract gains the worker grant lists and the optional --permission-mode. No product (UC-GATE/UC-MR/…) contract changes.

Expected

  • In tests/router.rs, the stub claude's recorded argv for a plain spawn shows --permission-mode acceptEdits, every allow entry from the table and every deny entry. A spawn with --permission-mode plan shows plan.
  • scripts/router-worker.sh spawn … opus --permission-mode bypassPermissions (and dontAsk, a missing value, an unknown option) exits non-zero with a "permission mode must be" message, and nothing starts.
  • The guard still allows the router scripts/router-worker.sh spawn n /w .router/briefs/n.md opus --permission-mode plan and still denies it cargo test and keel preflight.
  • .claude/settings.json is unchanged by this epic. cargo test is green.
  • Live (owner-run, evidence only, not a gate): a worker spawned through the new launcher runs cargo test, keel preflight and keel verify-doc without "requires approval". Its keel mr --help is refused.

Non-goals

  • Touching .claude/settings.json or the router's posture (DEC-30). The guard is unchanged.
  • Revisiting DEC-33 (workers' inherited user-level allowlist), or moving git grants into the repo.
  • bypassPermissions for workers in any form. Also auto mode (open question 3).
  • Backlog e-router-v2 R1 (persona missing), R3 (gating the router's security files) and the rest. E-SEED2.W7's opus-only policy.

Open questions

  1. Bootstrapping (open point 1). Default: option A, the owner adds the temporary user-level allow/deny entries listed there before W1 is spawned and removes them after the epic merges. Override: option B, the owner runs the four gate commands personally.
  2. Should the grant include more cargo subcommands (cargo doc, cargo tree, cargo metadata)? Default: no. Add one when a brief needs it.
  3. auto mode. Default: not accepted. It hands the approval to a classifier rather than a fixed list, and this CLI/account has not confirmed it exists. Add it when a task needs it and claude --help lists it.
  4. Ordering with E-SEED2. Default: E-ROUTERFIX merges first. It is small and it unblocks E-SEED2's own workers.
