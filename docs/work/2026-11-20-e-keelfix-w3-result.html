E-KEELFIX.W3 · The GitHub signer line removed

Keel knows three signer kinds now. A GitHub line, or any other kind, is refused by its line number.

T3 · WU result · 2026-11-20 · Keel · epic E-KEELFIX · delivered

What happened

Keel knows three signer kinds: email, user name and key. A signer-list line of any other kind is refused, with its line number. This covers setup, signing off, rule-file commits and the gate. Rules that name GitHub as a signer kind are refused as unknown. All tests pass.

The main case, run for real

From the test run, in a scratch project:

  1. The epic's signer list holds your user name on line 1 and a GitHub line on line 2.
  2. A sign-off as you is refused: "line 2: expected …, tier one of email, username, key". No sign-off is written.
  3. A rule-file commit with your name on it is refused the same way. No commit is made.
  4. The gate, given a sign-off, is red and names line 2.
  5. On a list with no GitHub line, the earlier revert's full test signs off by typing, merges and pushes as before.

Differences from the plan

  • "Names GitHub nowhere" was too strong. The install links point at github.com, and the plan kept them. The new tests feed keel a GitHub line to check it is refused.
  • One new test was not red before. An old GitHub-approval sign-off on a clean list already read "not listed". The old "GitHub only" wording needed a GitHub line in the list, which is now refused outright. The test stays, to hold the new wording.
  • Only a unit test catches a lone unknown kind. A GitHub line with two words also fails the line-shape check, so the larger tests stay green without the new rule. The unit test covers one-word lines and typos.
  • The example comes from the tests. A by-hand run was blocked: workers may not run the sign-off command.
