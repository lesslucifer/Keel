R1 · Worker persona missing in branches without it

--agent worker fails ("--agent 'worker' not found") when the launcher spawns into a worktree whose branch does not track .claude/agents/worker.md (smoke run into Keel-E-SEED). Once E-ROUTER is on main every new branch carries it; branches cut earlier do not. The intended fix branch wu/E-ROUTER/worker-persona-copy (worktree Keel-router-dev) has no commits of its own. Options: the launcher passes the persona inline or copies it in like the brief, or refuses early with a clear message. Source: worker-ops open issue 2.

R2 · Do headless workers stall under acceptEdits? · done

Answered and fixed in E-ROUTERFIX.W1. Workers are refused, not stalled: "requires approval" on cargo / keel is a refusal in claude -p. The launcher now grants the gate commands, denies keel mr, and takes a validated --permission-mode acceptEdits|plan: DEC-37.

Unverified whether a worker's Bash outside its allowlist stalls under --permission-mode acceptEdits (a headless session cannot answer a prompt). If it does, widen the worker's mode or the worker allowlist, never the router's (DEC-30). Since the router now has no Agent fallback (DEC-31), a stall blocks all helper work: prove it with a real worker before relying on the mode for a long fleet. Source: worker-ops open issue 3; plan rulings "not verified".

R3 · Put the router's security files under a gate

scripts/router-guard.jq, scripts/router-worker.sh and .claude/agents/ are neither code_paths nor rule_bearing in .keel/config.toml, so a commit changing them needs no review and no Reviewed-By; only tests/router.rs (a code path) guards their behaviour. Add them to rule_bearing (a .keel/ change: owner's keel mr commit). Related: Keel's own clone had no keel hooks install through E-ROUTER, so no commit-msg or merge hook ran on any of its commits. Source: E-ROUTER close review.

R4 · Revisit the accepted worker risk

Workers inherit the owner's user-level allowlist (rm, kill, curl, claude --dangerously-skip-permissions) and run any brief the router writes (DEC-33). Revisit before workers read untrusted input: a worker-scoped allowlist in .claude/settings.json, or a dedicated permission mode in the launcher. Same class (owner ruling 2026-11-10, E-SEED2.W7 review r1): a worker holding the owner's user-level Bash(git:*) can move the router checkout's branch ref (git update-ref runs no hook), so the launcher would read a wider DEC-39 [router] policy with no owner commit, just as it can already rewrite the launcher through that shared checkout. Source: plan ruling "worker permissions".

R5 · Epic e2e for the router

The plan's e2e (a scratch repo after keel init; a fresh session asked to "be the router for a new epic" loads keel-router and project-router, cuts and pushes the epic branch before any plan, stages rather than runs keel mr confirm with a watcher armed; refusals for a plan before the branch and for the router running keel mr) was never automated. W4 ran its try-recipe once by hand (skills listed and picked); tests/init.rs and tests/router.rs cover the installed files and the enforcement. Like B3: until built, an E-ROUTER-style epic test/v1 waives its e2e layer. E-ROUTERFIX's e2e (tests/router.rs epic_e2e_router_drives_a_granted_worker_in_a_seeded_worktree_to_its_end, UC-ROUTE-5) covers the launcher, guard and wait path, not this skill-loading session flow.

R8 · Router↔worker messaging: a fix owner ruling 2026-11-10: E-ROUTER3.W1

Upgraded 2026-11-10. The owner ruled that the guard's ban on router→worker messages is wrong: R8 is a fix, not an option, and it is E-ROUTER3's first WU. The ruling of 2026-11-09 below is kept as history. The "expired" subscription fallback (R12) merges into this fix.

Today's channel is accepted for now. The router subscribes to a worker's end (SendMessage notify_when_idle, DEC-36) and arms router-worker.sh wait, then reads .router/out/<name>.out. It is one-way: the router never sends a worker content. The owner ruled on 2026-11-09 that improving this channel is its own future epic. Until then the router's watch capability also stays as it is: a worker's end is watched with wait, and owner actions are not watched.

ItemSource
Watch gap: nothing watches an owner action (a staged keel mr, a merge, a push). The worker-ops recipe for it fails under the launcher (R7, first row), and wait covers only a worker's end. The router learns about owner actions only when the owner tells it or when its next git log shows them · done by E-SEED2.W12 (scripts/router-watch.sh, UC-ROUTE-1)R7; owner ruling 2026-11-09
Subscription denied in practice. On 2026-11-09 the router keel-fb sent SendMessage to a launcher-spawned worker's name with notify_when_idle: true, once with message empty and once without it. The guard denied both calls with "router guard: SendMessage only as a pure subscription: {to, notify_when_idle: true}, no message", although DEC-36 allows that shape. Cause (E-SEED2.W7 plan phase, from the source): that deny text comes only from the SendMessage branch of scripts/router-guard.jq. It fires when that branch's predicate fails: to is not a string, notify_when_idle is not exactly true, message is non-empty, or the input has a key outside the closed set to, notify_when_idle, message, summary. The predicate admits both shapes the router sent: tests/router.rs router_guard_allows_send_message_only_as_a_contentless_idle_subscription and the e2e epic_e2e_router_drives_a_granted_worker_in_a_seeded_worktree_to_its_end assert exactly those inputs, and main's guard is identical to the epic's. The denied calls therefore reached the hook with a different tool_input than the call as written. The likely case is a key that Claude Code adds or normalises before PreToolUse, which the closed key set rejects; the other possibility is notify_when_idle arriving as something other than boolean true. The synthetic test inputs never saw the real payload. Not confirmed: running the guard against sample payloads was refused in the W7 session ("jq command contains dangerous flags that could execute code or read arbitrary files"). Next step: capture one real router SendMessage PreToolUse payload in a scratch clone, add it as a test fixture, and then loosen that branch's closed key set to the harness's real keys without letting content through.
