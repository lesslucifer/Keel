E-GHFLOW2.W6 · Work that need not wait goes in its own pull request

A rule or skill edit that needs your yes goes in its own small pull request, and the code work goes on beside it. Your approval of the small one is its sign-off. When two pull requests clash, the router sends the second back to its worker.

Ready v1 (for your review) · 2026-11-16 · T3 · WU plan · Keel · off epic/E-GHFLOW2 366a9eb (after landing 3) · epic plan: git show 738c795:docs/work/2026-11-15-eghflow2-plan.html (archived), its W6 card and E-GHFLOW's §8

The problem

A change to a rule file needs your typed commit. So a worker that edits a skill or a rule in the middle of its work stops until you are at your Mac. A pull request with no code still needs a result report, which is paperwork for a three-line edit. And when two pull requests touch the same file, GitHub refuses the second merge, but nobody is told.

What changes for you

Example

  1. A worker building a feature finds a skill needs one more line.
  2. The router starts a second worker on a rules branch off the epic. It commits the line with no typed trailer. The commit check allows that on a rules branch only.
  3. The bot pushes the branch and opens its pull request. It changes no code, so it needs no review, no tests and no report. Only your sign-off is required.
  4. You read the diff and approve. GitHub merges it into the epic.
  5. The feature worker never stopped. Its own pull request merges later, by your approval.
  6. Had both edited one file, GitHub could not merge the second. The router would mark it a draft with a "conflict" label. Its worker merges the epic in, fixes the clash, and re-runs its checks. The router marks it ready, and you approve again.

The work

On a wu/<E>/rules-<slug> branch the commit-msg hook accepts a commit that changes a rule-bearing path and no code path without a Reviewed-By trailer, and on every other branch, or with a code path staged, refuses it as today; a WU or epic range that changes no code path is signed - typed, by approval, and at check 8 - without a result report under [mr] report = "required", while a range that changes code still needs one; and router-gh.sh draft <n> turns a bot pull request that GitHub reports as conflicted back to draft with the conflict label and changes nothing otherwise, while pr-ready removes that label.

1 · No trailer on a rules branch

In short: the commit check lets a rule-file commit through with no trailer when the branch is a rules branch and the commit stages no code. Your sign-off of that branch's pull request is the yes. Everywhere else the trailer rule stands.

  • src/mr.rs commit_msg: before reading the trailer, the current branch (git symbolic-ref --short -q HEAD) is read. When it is a rules branch and no staged path is a code path, the hook prints one line naming the rule-bearing paths and "its pull request's sign-off covers them", and allows the commit.
  • The branch-kind parser, next to the branch grammar in src/notes.rs: exactly <wu_prefix><E>/rules-<slug>, with E and slug plain words ([A-Za-z0-9][A-Za-z0-9._-]*). Anything else is not a rules branch: a detached HEAD, a third segment, an empty slug, another case, an epic branch. It refuses the unusual instead of modelling it.
  • A commit that stages a code path on a rules branch needs the trailer, as anywhere. A rules branch that carries code is then simply a code WU: tests, review and report, all required by the gate as today.
  • The relaxation lives in the keel binary, which every worktree's hook calls. It reaches a worktree when you install a keel built from main (the close, or a landing).

2 · No result report for a range without code

In short: [mr] report = "required" now asks for a report only when the range changes code. The test is the one the gate already uses to exempt a docs-only range. The sign-off itself is still required everywhere.

  • One helper in src/mr.rs: the policy that applies to a range is required turned to optional when notes::exempt holds for base..tip; optional and none are unchanged.
  • Used in the three places that read the policy: pick_report (the typed keel mr confirm and the approval writer) and manual_review (check 8). One rule, so a sign-off check 8 accepts is one the writers write.
  • Both levels. A report found in a range without code is still attested, as under optional.
  • Unchanged: check 8 is never exempt; a roster change still needs your typed sign-off with --roster-change; the approval writer's other refusals stand.

3 · Code that needs the rule change

In short: nothing new is built. The code branch starts from the rules branch's tip, and its notes and review are written after the rules pull request merges. A test proves that git then leaves the rules commits out of the code's range.

  • Once the rules pull request merges as a merge commit, the rules tip is in the epic. The code branch's merge-base with the epic is then that tip, so its range holds only its own commits.
  • Notes written before that merge name the old base; check 4 turns red after it, and the worker writes them again. The gate enforces the order.
  • The router never marks such a code pull request ready while its rules pull request is open (a skill rule, item 5). If the rules pull request is closed unmerged, the worker reverts the rule commits on its branch with a new commit, never a rebase.

4 · A conflict goes back to its worker

In short: a new bot command asks GitHub whether a pull request can merge. When GitHub says it conflicts, the command turns it back to draft and labels it. The worker fixes it on its own branch and re-runs its checks; then the router marks it ready again.

  • router-gh.sh draft <n>: only a bot pull request (the same bot_pr check as pr-ready). It reads the pull request once. When mergeable is false and mergeable_state is dirty, it converts it to draft (GraphQL convertPullRequestToDraft), adds the conflict label (created if missing, as issue creates its labels) and prints DRAFT pr=<n> head=… sha=… state=drafted. When mergeable is true it prints state=clean. Anything else prints state=pending and writes nothing; the router asks again later.
  • When the router runs it: after each merge into an epic, on every other open, ready bot pull request into that epic.
  • pr-ready also removes the conflict label; GitHub's "not there" is fine, any other refusal is a WARN line. It already turns auto-merge back on.
  • The router's guard (scripts/router-guard.jq) admits scripts/router-gh.sh draft [1-9][0-9]{0,6}; its deny message lists it.
  • The worker's side is today's flow: merge the synced epic into its branch (git merge --no-ff, never a rebase), resolve, re-gate (new notes, a new review when it has code), and the bot pushes. The walk skips the back-merge as a seam. You approve the new head again, because a push dismisses an approval. This also closes G7 N7's second half: a conflicted pull request has no merge commit, so the sign-off writer could not run; after the fix it can.

5 · The skills

In short: the router and its workers learn the two branch kinds and the conflict flow. Text only, staged for your typed commit.

  • keel-workflow (both trees, skills/ and .claude/skills/): rules and docs branches; no trailer on a rules branch commit without code; no report for a range without code; a rules or docs WU needs no plan or result doc, its pull request is the record; the stacked order (item 3); the conflict fix (item 4).
  • keel-router (both trees): when to split a rule or doc edit into its own branch; never mark ready a code pull request whose rules pull request is open; draft after each merge into an epic; pr-ready after the re-gate; the independent security review still runs on a rules pull request that changes a script or the guard.
  • project-router: the guard's new shape.

Details

What a reader can check when W6 is done:

  • On a scratch repo, an untrailered commit of a skill file is refused on wu/E/x and accepted on wu/E/rules-x; with a src/ file staged too it is refused on wu/E/rules-x.
  • A WU that changes only docs signs with keel mr confirm, and by the approval writer, with no report under report = "required"; verify-dod wu is green. A WU with code and no report is still refused at both and red at check 8.
  • A code branch started from a rules branch, gated after the rules merge, has a range without the rules commits and is green at check 4; notes written before that merge are red at check 4 after it.
  • router-gh.sh draft <n> on a conflicted bot pull request (recorded answer) sends the draft mutation and the label, and prints state=drafted; on a clean or a pending one it writes nothing. pr-ready removes the label.
  • The guard admits draft 12 and refuses draft 0, draft -1, draft 12 x, and pr-open wu/E/x --base epic/F.

Security review

router-gh.sh holds the App's token and gains a write (draft, label). The guard gains a shape. The hook relaxes a rule. All three go to the router's independent security review before your commit, against DEC-63's list, plus: draft acts only on a bot pull request from this repository; every GitHub value it reads is checked before use (mergeable a JSON boolean, mergeable_state compared as an exact word, the node id by its shape); nothing GitHub sends is printed unchecked.

Unverified, each failing safe

  • That an App with Pull requests write may run convertPullRequestToDraft. If refused, draft fails with GitHub's message and the router tells you.
  • That mergeable = false with mergeable_state = dirty is GitHub's word for a conflict, and null while it computes. Any other answer changes nothing.
  • Whether turning a pull request back to draft turns auto-merge off. pr-ready turns it on again either way.
  • Whether GitHub refuses the bot's push of a back-merge that brings in an epic's workflow change (the App has no Workflows permission). If so, you push that branch.
