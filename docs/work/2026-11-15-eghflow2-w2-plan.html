E-GHFLOW2.W2 · The router uses the GitHub flow

The router skills learn when to push, open and ready a pull request, how to arm the GitHub watches, and how to keep the tracking issue.

Ready v1 · 2026-11-15 · T3 · WU plan · Keel · epic plan: 2026-11-15-eghflow2-plan.html

The problem

The router bot and the GitHub watch exist, but the router's instructions never mention them. So the router still asks you to push, and it cannot hear your comments on GitHub. A gap in the sign-off command also stays open until W3 fixes it.

What changes for you

WhenTodayAfter W2 reaches main
A WU has its test evidenceThe router asks you to pushThe bot pushes it and opens a draft pull request
A WU passed its reviewA chat messageThe pull request turns ready and GitHub asks for your review; the typed sign-off still comes by chat and Telegram
You comment /keel go or a question on GitHubNobody hears itThe router hears it within a minute, like a chat message
You edit a comment—The router asks you to post it again; it never acts on an edit
GitHub is down—Chat and Telegram carry everything, as today
Before a typed sign-off in a work checkoutNothing checks the checkout's git linksThe router first reads the watchdog's latest check and stops on a problem

Nothing changes until this lands on main: the router runs in the main checkout.

Example

  1. A worker finishes a WU and writes its test evidence.
  2. The router has the bot push the branch and open a draft pull request into the epic. It updates the tracking issue.
  3. The review passes. The router marks the pull request ready; GitHub asks you to review.
  4. The router sends you the sign-off command by chat and Telegram, and watches the pull request.
  5. You comment "why is step 3 needed?". The router hears it and sends the question to the worker.
  6. You sign and merge. The bot pushes the epic; GitHub shows the pull request merged.

Terms

TermMeaning
the botThe GitHub App the router acts through (scripts/router-gh.sh).
the watchA background command that waits for one GitHub event and wakes the router (scripts/router-gh-watch.sh).
commanderA GitHub account the router listens to; for Keel, you alone.
tracking issueOne GitHub issue per epic, one sub-issue per WU, written by the bot from git.

The work

The keel-router skill (both trees, byte-identical) names every router-run shape of the project's GitHub bot and watch, says when the router runs each one, how it handles each event line the watch prints, that the push channel stays the fallback, and the R50 stopgap; and the project-router skill states Keel's facts for them, so that a router reading the two skills can take a WU from push to a merged pull request with no owner command but the sign-off and the merge.
