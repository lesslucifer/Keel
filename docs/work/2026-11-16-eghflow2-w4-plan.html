E-GHFLOW2.W4 · GitHub enforces the merge

Rules on GitHub make the merge button the gate. The checks that judge a pull request come from main, so a branch can no longer change them. A branch could still report a check under the same name from a workflow it adds, so the merge also needs your approval as code owner.

The problem

Today GitHub's checks are a signal only. The workflow and its script come from the pushed branch, so a branch can make its own run green (DEC-60). Nothing stops a red pull request from merging, and anyone with a push right can push main or an epic directly. You still merge by hand.

Example

  1. The bot pushes wu/E-GHFLOW2/w5-tryit and opens its pull request into the epic.
  2. "Keel gate" runs from main: one job builds keel from the epic, then keel/ci, keel/gate and keel/docs use that one build.
  3. The router marks the pull request ready; auto-merge goes on.
  4. You approve. The writer sets keel/sign-off. All four checks are green, so GitHub merges.
  5. The router syncs the epic from GitHub.

The work

With W4 on main, every pull-request check named keel/ci, keel/gate or keel/docs comes from main's workflow and script, runs head code only in keel/ci with a read-only token and no secret, is red (never skipped) when it cannot judge, and shares one keel built from the base whose hash each job checks; pr-ready turns on auto-merge as a merge commit when [github] merge_on_approve is on; scripts/gh-settings-check.sh reads the live settings, writes nothing, and is red on any difference from the list; and a merge commit made by GitHub walks green.

Why pull_request_target holds here

  • Every job's token is contents: read; no job names a secret; every checkout keeps no credential; every action is pinned; event values reach the script only through env:.
  • Only keel/ci runs head code. It holds the read token only, and its verdict is the head's own tests, which the head could always change.
  • What head code could still reach is the run's runtime token: the run's artifacts and the cache. The keel artifact is checked by hash. No workflow restores a cache, and a lock test keeps it so.
  • A fork's pull request runs no head code: the build and every job refuse it first.
  • The check names are new, so no older workflow a branch carries can report them. A workflow a head adds could (only you can push one: the bot has no Workflows permission), so your approval as code owner is required too.

Tests

Hermetic, no network:

  • The lock test pins pull_request_target, the push of main only, the read token, the four jobs and their names, no skip condition on a pull request, the hash check, and no cache in any workflow. It also pins no pull_request trigger in release.yml.
  • ci-gate.sh tests: the build prints a hash and a wrong hash is refused; a fork is refused; keel/ci tests the merged tree and a conflict is red; a back-merge of main is green on the gate and refused when the head is not on main.
  • The settings check on recorded answers: the full list green, writing nothing. A missing rule, a bypass actor, squash allowed, or a check from another source is red.
  • pr-ready sends the auto-merge request with MERGE, skips it when merge_on_approve = false, and prints a WARN on a refusal.
  • sync main is accepted by the script and the guard.
  • A GitHub-made merge commit walks green in verify-dod epic and the push range.

Unit: none new (the logic is shell and git). Integration: tests/suite/keel_gate.rs, ci_gate.rs, settings_check.rs (new), router_gh.rs, router.rs, close_walk.rs, release.rs. E2E: waived for this WU, because GitHub's settings cannot be tested hermetically. Live: the first WU merged through the button after the rules are on, recorded in its result.
