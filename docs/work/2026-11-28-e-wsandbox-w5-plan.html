E-WSANDBOX.W5 · Bring a stopped worker back, and reuse it when that is cheaper

A worker that knows the work answers the follow-up, instead of a fresh one reading everything again.

The problem

A stopped worker is never brought back, because a plain resume loses its safety settings. So each follow-up goes to a fresh worker, which spends about 36,000 tokens before it starts, then re-reads the files. The router also cannot see a worker's memory size or cache, so it cannot tell when reuse is cheaper.

How it works

  1. Resume. The launcher finds the named worker's last session and rebuilds every setting from the committed rules, with the code a new start uses. It refuses a running worker, a lost history, a moved worktree, a changed brief, a reviewer, or settings the rules no longer allow.
  2. Reuse. Reuse wins when the task is the worker's own or a follow-up, and its memory is under 200,000 tokens (cold cache) or 400,000 (warm). A reviewer is always fresh.

Your probe decides one design

Can a stopped and removed worker come back with its history? Your probe answers this first, before any build.

How you approve

  1. Run the probe and send its log.

  3. I commit tests and notes; scripts, settings and router skills are staged for your one commit.
  4. A fresh reviewer runs; you sign off and merge.
  5. At the epic's last check, you run a live stop and resume.

How you'll know it worked

  • A resumed worker's command line matches a new start's, plus its session.
  • Each refusal fires before a start.
  • The status read matches a recorded history at a fixed clock.
  • No router text still says "never revived", and the two fix rules agree.
  • Live: the resumed worker remembers a word and is still refused a write outside its worktree.
