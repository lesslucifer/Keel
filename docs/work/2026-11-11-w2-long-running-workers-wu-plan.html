E-ROUTER3.W2 · Workers are long-running sessions — plan

A worker stays alive between tasks. The router hands it the next brief with send, steers it with SendMessage, and closes it with stop. The router's own heartbeat is removed: the router only routes, and W9's watchdog worker reports progress.

T3 · WU plan · 2026-11-11 · Keel · branch wu/E-ROUTER3/w2-long-running-workers off epic/E-ROUTER3 (created after the owner's go) · epic E-ROUTER3 plan · owner rulings 2026-11-11

Requirement

A worker started by scripts/router-worker.sh spawn stays alive after it reports. send delivers its next brief, snapshotted and hashed, to the same session. wait prints IDLE at the end of each turn. stop ends the session after its current turn. The router guard admits send and stop, and nothing else changes in its posture.

Maps to

E-ROUTER3 (summary block W2) · owner rulings 2026-11-11 (workers are long-running, the router closes them; the router runs no loop) · backlog R15 (follow-ups continue the same session), R17 (the router heartbeat, struck and moved to W9) · UC-ROUTE-1, UC-ROUTE-5, UC-ROUTE-6 · DEC-32 and DEC-36 amended by a new DEC.

Today

A worker is claude -p "<fixed prompt>" … < /dev/null. It does one brief and exits. A follow-up starts a new process with resume <name> <session-uuid>, which reloads the whole session from disk each round. wait knows two ends, EXITED and STALLED. The skill also tells the router to run a 10-minute heartbeat that the guard has never allowed.

Design

sequenceDiagram
  participant R as Router
  participant L as router-worker.sh
  participant I as inbox (.router/inbox/name.jsonl)
  participant W as Worker (claude -p, stream-json in/out)

  L->>I: brief 1 as a user message
  I->>W: stdin (tail -f keeps it open)
  W-->>L: result event → .router/out/name.out
  R->>L: wait name  →  IDLE
  R->>W: SendMessage (steer: answer, clarify, stop)
  R->>L: send name brief-2.md  →  SENT sha256=…
  L->>I: brief 2 as a user message
  W-->>L: result event → .router/out/name.out
  R->>L: stop name  →  inbox closed
  W-->>L: EOF → exits after its turn  →  wait: EXITED
Proposed shape, to be confirmed by the probe (step 1). One process per worker for its whole life. Every task still travels as a snapshotted, hashed brief (DEC-32).
PieceChange
spawnStarts claude -p --input-format stream-json --output-format stream-json with stdin from tail -f .router/inbox/<name>.jsonl, and writes the first brief there. The grants, the worker policy, worktree checks and the snapshot are unchanged. The process stays alive after its first result.
send <name> <brief.md> (new)Refuses unless the worker is live. Snapshots and hashes the brief exactly as resume does, copies it into the worktree, and appends one user message pointing at the copy. Prints SENT name=… snapshot=… sha256=….
stop <name> (new)Closes the inbox (ends its tail). The session finishes its current turn, reads EOF and exits, and wait prints EXITED. It never kills a turn in progress.
waitAdds IDLE name=… turn=<n> out=… when a new result event arrives. STALLED now counts only inside a turn, so an idle worker waiting for input is never reported as stalled.
ReportThe launcher's output filter writes each turn's result text to .router/out/<name>.out, replacing the last one. Reading .out still gives the latest report. The raw stream goes to <name>.jsonl, which W9's watchdog reads.
resumeKept only to restart a dead session (a crash or a reboot), now into the same long-running shape.
GuardThe Bash whitelist's launcher alternation grows from spawn|resume|wait to spawn|resume|send|stop|wait. No other change.
Skill text (rule-bearing: owner keel mr commit)worker-ops Spawn, Follow-up, Report and Retire use send, IDLE and stop. The Heartbeat section and the SKILL.md heartbeat bullet go: the router arms one wait per worker, and W9's watchdog reports progress. Lessons C10 and C13 point there.
DEC (next free id)Workers are long-running and the router closes them. It amends DEC-32 (a brief per round, now delivered by send) and DEC-36 (the end of a turn, not of the process, is the signal).

Steps

  1. Probe first (throwaway repo, real claude, as in W1). Four questions:
    1. Does a stream-json -p session stay alive between turns while stdin is open, with one result event per turn?
    2. Does a SendMessage reach it while it is idle on stdin, and does it start a turn?
    3. Does notify_when_idle fire at each turn's end, or only at exit?
    4. Does ListAgents still list it by its -n name?
    The answers decide open points 1 and 2 before any code.
  2. Red: new launcher and guard tests against the current scripts. Then the launcher and the guard change, and the tests go green.
  3. Live run in a scratch clone at the WU tip: one real worker does two briefs in one session (spawn, IDLE, send, IDLE). A guarded router steers it once with SendMessage, and stop ends it. Recorded in the result.
  4. The DEC goes in docs/decisions/router.html. The skill text is staged as the owner's keel mr commit. Then the result, notes, preflight, the independent review, and the staged keel mr confirm wu.

Expected

  • With a stub claude that answers one result per stdin message, spawn leaves a live worker after its first report and wait prints IDLE.
  • send delivers a second brief to the same pid and session with a new snapshot and sha256, and .out then holds the second report.
  • send to a dead or unknown name and stop on an unknown name are refused with a named reason.
  • stop ends the worker, and wait prints EXITED.
  • The guard allows router-worker.sh send|stop in plain words and still denies any other script mode.
  • The live run shows two briefs in one real session, one steer while idle, and a clean stop.
  • The keel-router skill has no heartbeat or /loop instruction, and its mirror is byte-identical.
