E-ROUTER3.W4 · A worker can never sign as the owner; the router's security files are gated — result

The signer roster is .keel/mr-allowed as committed on the branch a change lands on; no keel command reads a roster from disk. A sign-off whose range changes the roster needs --roster-change. Keel's own policy gates the router's four security paths once the owner lands it. By owner ruling 2026-11-12 Keel's sign-offs stay name-based: key-only is deferred, so R14's signing half stays open (DEC-48 item 4). The owner's steps are still to do.

Result · 2026-11-12 · Keel · plan 2026-11-12-w4-owner-signing-wu-plan.html (v1, owner go 2026-11-12 on every default) · DEC-47, DEC-48

Outcome

Code and records delivered; owner steps pending. Every reader of the roster does what the plan's reader table says:

  • Check 8 at the merge hook reads HEAD's roster. Run by hand, it reads the resolved target's. At pre-push it reads the merge's first parent's.
  • keel mr confirm reads the target's roster, and so does its default signer.
  • keel mr commit and the commit-msg hook read HEAD's roster. With none at HEAD, they read the staged one.
  • On a target with no roster, the change's own roster judges and keel prints one bootstrap line. With none on either side the refusal names the keel mr setup fix.

The disk read and the tracked-refusal of .mr-allowed are deleted. In src/ the name survives only in that fix text. .keel/mr-allowed is rule-bearing whatever rule_bearing lists. keel mr setup writes the working .keel/mr-allowed, touches no info/exclude and prints the command that lands it. keel init's next steps put keel mr setup before the one-time first commit.
