Deviations

  • The plan's integration list said the script refuses bad input "before any git call that uses it"; the head branch is checked with git check-ref-format, a git call that only validates. Same intent.
  • The full-path run of the script against a real built keel (base = this tip) was not run: the sandbox's auto-mode refused the scratch commit it needed. The hermetic tests cover that path with the test build of keel.
  • The router's independent review of .github/ and the script (one important finding, five low) changed four things after the first report. (1) Keel is now built from inside the base worktree, so no .cargo/config.toml or rust-toolchain.toml of the head can steer the build. Before, cargo ran from the head checkout. (2) Only a push takes the "main" path; a fork's pull request from a branch named main builds keel from its base. (3) Each main commit has its own run group, and only work-branch runs are cancelled when superseded. (4) The evidence page caps each field at 500 characters, and failures and waived lines at 20 rows, so it stays under GitHub's 1 MiB step limit. Each fix has a test that was red first.
  • Code review round 1 (FAIL, five important findings) changed the Rust side. verify-dod and keel ci gate now share one gate function, so a check added to one reaches the other. The gate owns every check id, and the page reads ids from it; a failing check the page does not know shows as a red row. The page reads notes through their typed forms: a review waiver shows only on a WAIVED note, and a waiver where no review ran says "not reviewed". Each row says what actually ran: a docs-only range's skipped checks say "not run", while its epic layout and walk show their result. A fully green run is tested to write no receipt. Each correctness fix has a test that was red first.
  • Code review round 2 (FAIL, four important findings) found that the page still guessed which checks had run, so a missing note could show checks that never ran as green. The design now has the gate tell the page. As each check runs, the gate records its outcome under its own id: it ran, or part of it could not run because a note is missing. Each failure names the check it counts against, and each waiver the check it waives. The page shows only that record, and a check with no record says "not run", never green. Why this design: it removes the page's guessing as a class, so nothing in the page can drift from the gate again. Recording in the gate costs one line per check, at the place where the check already runs. A separate list of what runs, or parsing the gate's printed lines, would each be a second copy of the gate's rules. Every note is now read through one shared parser in notes.rs, used by the gate, the sign-off check and the page. Each fix has a test that was red first, plus new tests for a docs-only WU and for an archive.
  • Code review round 3 (FAIL, one important finding): two places decided whether a missing doc note was a missing input, and they disagreed for a commit that changes no doc. Now there is one rule: the note reader records a missing input on the checks a note feeds, and only when it required that note. A unit test at commit level, red first, proves a commit with no doc changed records none.
  • Code review round 4 (FAIL, one important finding, so the fix gets a fix-PASS): the checks a review note feeds were listed twice, once for "ran" and once for "missing". Now one list per note kind feeds both records, written in one place, and a unit test ties them.
  • The workflow's rustup component add step still runs in the head checkout. It adds rustfmt and clippy to whatever toolchain the head picks, and that is the toolchain the head's own keel check uses anyway. It never touches the keel that judges.
  • Otherwise none.
