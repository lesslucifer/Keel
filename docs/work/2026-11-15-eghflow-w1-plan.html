E-GHFLOW.W1 · GitHub runs the checks, as a signal

Every push of a work branch, and every pull request, runs the tests and the merge check on a GitHub machine.

Ready v1 · 2026-11-15 · T3 · WU plan · Keel · epic plan: 2026-11-15-eghflow-plan.html

The problem

Tests and the merge check run only on your Mac. Some tests fail only inside a worker's sandbox, so you re-run them by hand. A pull request on GitHub shows nothing about whether the work is ready.

What changes for you

WhenTodayAfter W1
A work branch is pushedNothing on GitHubThree checks run: tests, merge check, doc check
You want the evidenceYou ask a worker to run the gateThe merge check's run page lists the five notes and every check
A test is red only in the sandboxYou re-run it by handThe tests job runs it outside any sandbox
The work is not signed yetThe gate is red on the sign-offThe merge check is green on checks 0–7 and says "awaits sign-off"

Nothing is required yet. A red check blocks nothing; W5 makes the checks required.

Example

  1. You push wu/E-GHFLOW/w2-bot with its notes.
  2. GitHub starts "Keel gate": jobs ci, gate, docs.
  3. gate builds keel from epic/E-GHFLOW, not from the pushed branch, and runs the merge check on the pushed tip.
  4. The run page shows a table: test, doc and cr notes present, no sign-off yet, checks 1–7 green.
  5. You sign locally and push the notes; "Re-run jobs" shows the sign-off row filled.

Terms

The work

On every push of main, epic/** or wu/** and every pull request into main or epic/**, a GitHub workflow runs keel check, the merge check (verify-dod checks 0–8, judged green when only check 8 is red) with a five-note evidence table in the job summary, and keel verify-doc on the changed docs, each with a keel built from the base branch, a read-only token and no secret.

E-GHFLOW.W1 (epic plan, W1 card; §5 gates on GitHub; §7 C2, C11, C17, C20–C27, C33, C34). Use case UC-GATE: new row "the gate runs in CI, judged by a keel built from the base", written at the epic close. Backlog e-router-v2 R43 (sandbox-only reds) and R30.

.github/workflows/keel-gate.ymlTriggers: push on main, epic/**, wu/** (branches only, so no tag runs it); pull_request into main, epic/**. permissions: contents: read, no secrets., actions/checkout pinned to the commit dist pins, persist-credentials: false, fetch-depth: 0, ubuntu-24.04. scripts/ci-gate.sh ciBuilds keel from the base commit in a scratch worktree, then runs keel check in the checkout: the pushed commit, or the pull request's merged tree.
scripts/ci-gate.sh gateFetches refs/notes/*, makes local branches for head and base, adds a base worktree, installs Keel's hooks (check 0·hooks), and runs keel ci gate <wu|epic> <head> --target <base> --summary $GITHUB_STEP_SUMMARY from that worktree, so the policy is the base's committed .keel/config.toml. Skipped on a push to main (no head and base pair).
scripts/ci-gate.sh docsLists the docs/**.html files the range changed (deleted ones out) and runs keel verify-doc on them in a head worktree, so relative links resolve. Drafts stay silent, as at the write. A backstop for the write-time check, never a substitute (DEC-54).
keel ci gate (src/gate.rs, src/ci.rs)The same verify, hooks guard and check 8 as keel verify-dod, printed by the same code, so the FAIL blocks are byte-identical. Exit 0 when every failure is 8·manual-review. Writes no dod receipt (the runner's clone is thrown away). Appends the evidence to --summary: tip, base, the five notes (test, doc, cr, mr, dod) with their key fields, each check's state, and the failures. Recorded text is made inert, then every Markdown or HTML character becomes an entity, so a note cannot add a link, a mention, a table cell or a tag.

Bootstrap

The base builds the judge, so a base that predates W1 has no keel ci gate. The script then runs that base's plain keel verify-dod (the real local gate), says so in the summary, and takes its exit code: red until signed. This covers W1's own push (base epic/E-GHFLOW at cbbbcc3) and every epic/** push until E-GHFLOW reaches main. The full path first runs on GitHub for the first WU branch pushed after W1 merges into the epic.

Expected

  • Once the owner pushes this branch, the Actions tab shows "Keel gate" with jobs ci, gate and docs; ci runs cargo fmt, clippy and the full suite (the notify_owner tests included) and is green.
  • On that push, gate runs the bootstrap path and its summary says the base predates keel ci gate.
  • Locally and in tests: on a scratch repo with a bare origin, ci-gate.sh gate on a WU tip with test, doc and cr notes exits 0, prints 8·manual-review as the only FAIL, and its summary lists the five notes; with the cr note missing it exits 1 with the same FAIL block the local gate prints; no [check] command runs.
  • The workflow file has no tag trigger, no pull_request_target, no secret, a read-only token and pinned actions; a test fails when any of that changes.

Tests

Integration (W1's contract; tests/suite/ci_gate.rs), hermetic, a scratch repo with a bare origin and a runner clone of it, keel passed in by KEEL:

  • gate: a WU tip with test, doc and cr notes exits 0, 8·manual-review the only FAIL, summary lists the five notes; after keel mr confirm and a notes push, the re-run is fully green and the mr row names the signer.
  • gate: the cr note missing exits 1; its FAIL lines equal the local keel verify-dod ones byte for byte.
  • gate: [check] commands that touch a marker file never run; the runner clone's core.hooksPath is Keel's after the run and no 0·hooks FAIL prints.
  • gate: a keel without ci gate (a stub) takes the bootstrap path: plain verify-dod output, the bootstrap line in the summary, its exit code.
  • gate: an epic tip pushed to epic/e is judged at level epic against main.
  • docs: a changed red ready doc exits 1 naming it; a draft is silent; a deleted doc and an unchanged red doc are not read; no changed doc exits 0.
  • ci: keel check runs the checkout's [check]; a red test exits 1.
  • build: with no KEEL, a fake cargo on PATH records that it ran build --locked in a worktree at the base commit, and the script uses the binary it made.
  • arguments: a branch starting with -, holding .. or a space, a non-hex sha, an unknown job, or a head that is neither wu/<e>/<x> nor epic/<x> is refused with exit 2 before any git call that uses it.

Workflow lock (tests/suite/keel_gate.rs, like release.rs): the exact triggers and no others; permissions is contents: read only; no secrets.; no ${{ in a run: line; every uses: pinned to the dist pin's 40-hex commit; every checkout has persist-credentials: false and fetch-depth: 0; jobs ci, gate, docs each run scripts/ci-gate.sh with their own name; gate and docs skip a push to main and fork pull requests.

Unit (src/ci.rs, src/gate.rs): the Markdown escape (every active character, control characters, a fake row or link stays text); the renderer for a green, a red, an exempt and a bootstrap-free epic report, a missing, an unreadable and a wrong-tip note; the "only check 8 is red" rule; each failure's check mapped to its row (a walk failure 7·walk·3·review is check 7's).

E2E: not this WU's level (the epic test covers it). The live run on GitHub is evidence the owner unlocks by pushing; the result report gives the steps.

Details

  • Facts read for this plan (docs.github.com and github.blog, 2026-11-15): pull_request_target takes the workflow and checkout from the default branch since 2025-12-08; a step summary is at most 1 MiB and 20 are shown per job.
  • Untouched: release.yml and dist-workspace.toml (DEC-38). The new workflow never runs on a tag and publishes nothing.
  • No rule-bearing path changes: .github/ and scripts/ci-gate.sh are not in rule_bearing yet (W5 adds .github/). The router reviews both files independently.
  • Base for a push is origin/<base> now; for a pull request, the event's base commit. A base branch missing on origin is a red job naming it.
