E-ROUTER3.W2 · Workers are long-running sessions — result

A worker now stays alive between briefs. The router hands it the next brief with send, steers it with SendMessage even while it is idle, and closes it with stop. The router has no heartbeat.

T3 · WU result · 2026-11-11 · Keel · branch wu/E-ROUTER3/w2-long-running-workers off dda9ce0 · WU plan · epic plan

In one paragraph

Before this WU a worker was a one-turn claude -p: it did one brief and exited, and every follow-up started a new process. Now scripts/router-worker.sh starts it in stream-json mode, reading its turns from an inbox file that a tail -f feed keeps open, so the session waits for its next brief instead of exiting. Three launcher commands drive that life: send (next brief, snapshotted and hashed as before), stop (close the input, the worker exits after its turn), and wait, which now also prints IDLE when the worker has finished its turn. The router's 10-minute heartbeat is gone from the skill (owner ruling: the router only routes), and a watchdog worker (W9) will report progress instead.

How a worker lives now

stateDiagram-v2
  [*] --> Busy: spawn (brief 1 in the inbox)
  Busy --> Idle: result event (wait prints IDLE, writes .report)
  Idle --> Busy: send (next brief) or a SendMessage
  Busy --> Busy: SendMessage steers mid-turn
  Idle --> Stopping: stop (feed closed)
  Busy --> Stopping: stop (the turn finishes first)
  Stopping --> [*]: EOF, process exits (wait prints EXITED)
  Busy --> [*]: crash or reboot (wait prints EXITED; resume restarts it)
The worker's states as wait reports them. A stopping worker is never reported IDLE, and an idle one is never reported STALLED.
File under .router/out/Holds
<name>.inThe inbox: one stream-json user message per brief (spawn writes the first, send appends).
<name>.feedThe pid of the tail -f that keeps the worker's stdin open. stop kills it.
<name>.outThe raw stream-json output, truncated by each run of the name.
<name>.reportThe last result's text, written by wait on IDLE and EXITED. This is the report the router reads.

The idle rule (as fixed in review round 1). The worker runs with --replay-user-messages, so it echoes each brief when it takes it. wait counts typed events with jq, reading only the lines added since its last poll. A worker is idle when three things hold:

  • every brief in the inbox has been replayed;
  • every turn it opened (system/init) has closed (result);
  • its feed is still its own tail of the inbox.

Three facts make this the rule:

  • A turn the worker opens itself (a SendMessage) replays nothing, so it never answers an unread brief.
  • A brief sent mid-turn is folded into the running turn and answered by its one result.
  • Real sessions emit command_lifecycle after a result, so the last event is no signal.

Outcome

Delivered. The requirement holds: a spawned worker stays alive after it reports, send delivers its next brief, snapshotted and hashed, to the same session, wait prints IDLE at the end of each turn, stop ends the session after its turn, and the guard admits send and stop with no other posture change. Both plan unknowns came out on the default side: a stream-json -p session stays open between turns (open point 1), and a SendMessage reaches an idle worker, which opens a turn to answer (open point 2), so no pty fallback and no brief-only steering were needed.

Deviations

  • Report file. The plan had the launcher pipe output through a filter that writes each result to .out. A filter at the end of the pipeline would make $! the filter's pid, not the worker's. Instead .out stays the raw stream, and wait writes .report.
  • Idle rule. The plan said "when a new result event arrives". The live stream showed events after a result, and a turn with no inbox entry, so the rule counts turns, inbox entries and the open feed (above).
  • A reaper per run. This was not planned. A worker that dies on its own would leave its tail -f blocked forever, so each run starts a small loop that ends the feed when the worker exits. It holds the feed pid by value, because a later run of the name rewrites .feed. The tests caught a resume whose feed was killed by the old run's reaper before this change.
  • stop semantics, refined. It still never kills mid-turn. But the live run showed that a worker can end its turn early with work in a background task, and exiting cuts that task. The skill and DEC-43 now say this, and the router stops only idle, clean workers.
  • Settings allowlist. send and stop were added to permissions.allow in .claude/settings.json, so the router is not prompted for them. This was not in the plan; it landed in the owner's commit 6166848, staged as HEAD plus the two lines so the owner's uncommitted edit stayed untouched.
  • E2E touched here. The E-ROUTERFIX e2e asserted EXITED after the stub's release, which is now IDLE. Its flow gained send and stop in this WU rather than in W7.
  • Live-run harness. Both sessions ran through a wrapper adding --setting-sources project,local --strict-mcp-config, so no second Telegram poller started. That flag is W3's and W8's to put in the launcher. The launcher commands ran from a shell, as the router would issue them: a headless router in an untrusted scratch clone ignores the project allowlist, so it could not run them unprompted. The router session made the SendMessage call under the guard.
  • Review round 1 (FAIL, 3 blockers and 4 importants on cd852ae). Fixed in e64507c, with a regression test written first and shown red with the exact false IDLE.
    • B1: a self-opened turn let a fresh send read as answered.
    • B2: send to a stopping worker printed SENT for a brief no one would read.
    • B3: a brief folded into a running turn left wait unable to print IDLE. A probe showed real folding.
    • I4: the feed pid was killed without checking that it was still this worker's tail.
    • I5: every poll re-parsed the whole output.
    • I6: EXITED left an earlier brief's answer as the report.
    • I7: a duplicated bounded-wait helper.
    The fix made three changes beyond the plan: the replay flag, the feed-identity check, and the rule that an exit with an unanswered brief leaves no .report. The skill states the last one, and that a stopping worker refuses send, in a second owner commit.
  • Plan file. The first W2 plan (a router heartbeat) was rewritten after the owner's ruling and renamed from …-w2-heartbeat-…. The epic plan was amended in this WU (W2 rewritten, W9 added, open point 6 ruled).
  • Snapshot. docs/decisions/router.html's htmldoc id is still unknown to the server (as in W1), so its diff view has no baseline. Use git diff.
