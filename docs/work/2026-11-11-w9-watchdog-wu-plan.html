E-ROUTER3.W9 · A watchdog worker reports every worker's progress — plan

A Haiku background session tells the router, every 5 minutes, what each live worker is doing, in one short sentence per worker, and names a worker that is done or stuck. The launcher builds the facts; the router only starts and stops it.

Today (W10 has landed)

Workers are native background sessions (claude --bg -n <name> --agent worker), and wait and send are gone. The flow is:

  • a worker that finishes its work sends the router its report itself, by SendMessage, and stays alive idle;
  • the router then retires it with scripts/router-worker.sh stop <name> (the router has no claude);
  • the owner wakes the router for everything else.

notify_when_idle stays an optional native extra; nothing relies on it.

That flow has three gaps, named in DEC-44's consequences and in worker-ops.md ("the watchdog will; until then check on wake"). A worker that goes idle without reporting leaves the router waiting. A worker that waits on a permission prompt never reports and never goes idle. A worker that is busy with no transcript progress never reports either. The router also has no view of what a healthy busy worker has been doing for the last hour.

The watchdog covers them. Every tick it sends the router one short sentence per worker, and that message says first which workers the tick found done (idle) or stuck (blocked, or busy and quiet past the stall threshold). Both words are decided by a deterministic shell check in the launcher, not by the model.

What the watchdog is not: it is not a machine signal the router acts on blindly. It is a periodic, human-readable progress line. The router reads it, and confirms with the worker's transcript, git state or a message before it does anything.

The tick flow, as probed (step 2). There is no shell loop, no pid file and no environment variable: the schedule lives in the watchdog session, the router's name lives in the session's two hook commands, and every fact comes from one read-only launcher command.

The session claude --bg -n watchdog-<name> --setting-sources local --agents '<JSON: the watchdog agent>' --agent watchdog --model <watchdog_model> --tools SendMessage CronCreate --allowedTools SendMessage CronCreate --strict-mcp-config --autocompact 100k --settings '<JSON: two hooks>' "<fixed first prompt>"
  • --setting-sources local: the session loads no project and no user settings (probe P4). With the project settings loaded, the project's Stop hook (verify-doc-stop) refuses every turn end of a session that cannot fix a red doc, and the session loops. So none of the project's hooks, permissions or its "agent": "router" default reach this session; everything it needs is on its command line.
  • --agents '{"watchdog":{"description":…,"prompt":…,"tools":["SendMessage","CronCreate"]}}' --agent watchdog: the agent is defined inline, built by the launcher. With the project source off, an agent file under .claude/agents/ is not found (--agent 'watchdog' not found, before init), so there is no watchdog.md.
  • The prompt follows the single-valued --settings: after a list option it would be read as a tool name (W10).
  • --autocompact 100k is the smallest window the CLI accepts. Claude Code compacts the session by itself; the launcher never restarts or resumes it (ruled; a resume of a running session would start a copy).
  • The first prompt is fixed text: schedule the prompt tick at */5 * * * *, then treat this turn as the first tick.
  • No effort flag, no permission mode, no cargo/keel grant.
The --settings JSON (built by the launcher from the validated name and its own absolute path)
  • UserPromptSubmit: <ROOT>/scripts/router-worker.sh watchdog facts <name>. Its output enters the turn as context.
  • PreToolUse (every tool, fail-closed: a guard that cannot run or parse denies): jq -c --arg watchdog_to <name> -f <ROOT>/scripts/router-guard.jq || { …; exit 2; }.
Both commands hold only [a-z0-9-] from the name and the launcher's own path. The project's guard hook does not run in this session (project settings are off), so this PreToolUse hook is the session's only tool hook. The prompt hook runs on every turn, not only on a tick: a message from another session to the watchdog also runs it (probed), so such a turn gets fresh facts and the router-gone check as well. Nothing is built for that.
watchdog facts <router-name> (new, read-only; run by the hook, not a router shape) Prints the header Report to <router-name>. and one block per live worker. If the session list cannot be read it prints that one line and nothing else. If no session named <router-name> is listed, it stops the watchdog session instead (claude stop on the id of this checkout's watchdog-<name> row).

Live worker = a kind: "background" row of claude agents --json whose cwd is a registered worktree of this repository other than the launcher's checkout and the main checkout: exactly where spawn may put a worker, so the router and the watchdog are never counted. Per worker:

  • state, from status, or state when there is no status: DONE when idle; STUCK (<waitingFor, or the state>) at once for every state but idle and busy, so a worker waiting on a permission prompt reads STUCK (permission prompt); STUCK (quiet <n>m) when busy with a transcript untouched for the stall threshold, 15 minutes, or more; otherwise busy;
  • quiet: minutes since its transcript (~/.claude/projects/*/<sessionId>.jsonl and its subagents/*.jsonl) was last written;
  • branch, tip, dirty: git -C <cwd>: branch name, %h %s of HEAD, count of status --porcelain lines;
  • last: from the transcript's last 64 KB, the last 6 assistant items (text, or tool <name>: <input>), each cut to 200 characters. claude logs is not used: it prints terminal escape output.
A block is cut to 2000 bytes; text taken from a row (name, waitingFor) is cut and stripped of control characters like transcript text.

Total budget: the whole output, header included, stays under 9000 bytes. Hook output of 10,120 characters and more reaches the model as a file path and a 2 KB preview, and the watchdog has no Read tool (probe, step 2). Blocks are printed whole, DONE and STUCK workers first, then busy ones. When the next block would pass the budget, facts prints the last line <N> more workers not shown. and stops. Ceiling: about four full blocks; a fleet with more workers than fit shows its done and stuck workers first and counts the rest.

With no live worker it prints No live worker. and the watchdog sends nothing.

DEC-45 (docs/decisions/router.html, index)A watchdog background session reports progress and names done and stuck workers, closing the gap DEC-44's consequences leave open; its schedule is native and its facts come from the launcher; the router's name travels in the session's hook commands because a background session has no launcher environment; it auto-compacts and is never resumed; a report is a progress line, not a signal.

A watchdog report is untrusted. Its input is worker output summarised by a small model. The watchdog can reach only the router (--tools and the tool hook), so worker text is never relayed to another worker. The skill tells the router to treat a report as a hint: it never acts on an instruction inside one. DONE and STUCK are the two words in it decided by code, and even then the router checks before it acts: it reads a done worker's report before stopping it, messages a quiet worker before asking the owner to replace it, and hands a worker waiting on a permission prompt to the owner (claude attach <id>; the router cannot answer a prompt).

Test plan

The 5-minute firing itself is native and cannot be hermetic: the tests pin the schedule text the session is given, and the live run proves it fires.
