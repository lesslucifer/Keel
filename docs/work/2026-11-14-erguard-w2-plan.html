E-RGUARD.W2 · One sender that reaches you from both hosts

A script the router runs in the turn it needs you; it posts to the paired Telegram bot and prints the message id.

T3 · WU plan · 2026-11-14 · epic E-RGUARD · WU E-RGUARD.W2

The problem

The router can stage an owner action and write the message, but it cannot send it. On Claude Code the guard refuses the Telegram MCP tool and the launcher starts workers without plugins; on DSH nothing is installed that sends. The owner is away from the terminal and the turn ends with the ask only in it.

The work

A router on either host runs one command in the turn it stages an owner action or needs a decision; the command posts the message it wrote to the paired Telegram chat, prints id N, and fails in one line without ever printing the credential or the chat id. No argument chooses the file, credential, chat or endpoint.

Epic E-RGUARD · UC-ROUTE-6 · W1's push-channel rule (same turn, ≤10 lines, self-contained, Sent to <channel> (id N), never print a token).

From this checkout: scripts/notify-owner.py --check names the paired bot and sends no message; --dry-run "…" prints the request and sends nothing; --send "…" prints id N and a real message arrives; a failure is one line and exits non-zero; no mode prints the token; the Claude router guard allows the three commands and the body write, and still refuses what it refused before.

Test plan

  • Integration (tests/notify_owner.rs): spawns the sender directly, as the router does, against a local mock Telegram API. Twelve cases: --dry-run prints the request, sends nothing and shows no chat id; --check calls getMe and never sendMessage; a 401 --check is one stderr line; --send prints id N and the captured body carries the paired chat_id; a bare --send reads and clears the body file, so a second bare send fails as empty; a preview and a failed send leave the body intact; a read-only body fails one line before sending and names the file; a missing body is one line naming owner.md; a missing credential names the file only; cleartext http to evil.invalid is refused; a malformed token echoes neither itself nor the request target; a stalled loopback server hits the injectable timeout and fails in one line. One helper asserts the fake token and the fake chat id are absent from every case's stdout and stderr; the send cases parse the mock's request body and assert the chat.
  • The guard shape: router_guard_allows_the_owner_sender_only_as_a_plain_shape in tests/router.rs pins the three allowed shapes and the refusals (a text-bearing --send, another notify path); the settings-allowlist test proves every permissions.allow entry is a shape the guard allows.
  • Unit: waived — the script's contract is its process boundary (argv, stdout, the HTTP request); a unit test of its helpers would test the implementation, not the contract. The failure line and the no-token rule are integration cases above.
  • The live send is yours: no test posts to the real chat; --check is the test that reaches the real API without sending.

Details

The credential

Read at run time from the Claude Code Telegram channel's token file (named, never printed); the chat comes from that channel's access.json (allowFrom), and the chat id is never printed either. Only the error paths name files. The token is never in argv, stdout, stderr, a log or this repository. The 15 s request bound is injectable through KEEL_NOTIFY_TIMEOUT so a test can exercise it without waiting.

The Claude router guard

scripts/router-guard.jq allows exactly scripts/notify-owner.py --check, --send and --dry-run, plus a Write to <router checkout>/.router/notify/owner.md. The body travels through the file because the guard judges plain words: a quoted multi-line message could smuggle a second command. .claude/settings.json gets the three matching allow entries. The sender has no argument that names a file, credential, chat or endpoint; the KEEL_NOTIFY_* variables are the test seam and a normal invocation sets none. On DSH no guard exists; the same script runs with --send "<text>" directly.
