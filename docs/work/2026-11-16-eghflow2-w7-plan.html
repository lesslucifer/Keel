E-GHFLOW2.W7 · Waivers and roster changes from the pull request

Three sign-off decisions still need your Mac: waiving a review, accepting a waiver the review wrote, and signing a change to who may sign. After W7 you make each one on GitHub, in the text of your approval. You see the same preview the typed command shows, and you confirm it with its code.

The problem

Your approval signs most pull requests now. It cannot sign three kinds: one whose review did not pass, one whose review its round limit waived, and one that changes who may sign. For each, the approval's status turns red and tells you to type the sign-off at your Mac. So the decisions that most need your eyes are the ones you cannot make from your phone.

Nothing else changes. No new workflow, no new permission, no new GitHub setting. The typed commands stay as the fallback.

Example: you skip the review of a landing

  1. The epic's pull request into main is ready. You chose to skip its code review, so no review ran.
  2. You approve, and in the approval's text box you write /keel waive-review landing only; tested by hand.
  3. The sign-off runs. It writes nothing. Its status turns yellow: "Waiver preview (Details): approve with /keel confirm-waiver 3f2a9c01b7de".
  4. Details opens the run. Its log shows what the typed preview shows: your reason, what the review left open, and every review note on the branch.
  5. You approve again, with the text /keel confirm-waiver 3f2a9c01b7de.
  6. The sign-off writes the waiver and your sign-off together, and the status turns green. The router takes both notes and refreshes the pull request, so the gate runs again and turns green. GitHub merges.

The other two decisions start at step 3: your plain approval gets the preview and the line, /keel accept-waiver <code> or /keel roster-change <code>.

The work

On a Keel pull request on GitHub, a reviewer whose id the base's roster lists under the github tier can waive the head's review, accept a waiver the review's round limit wrote, or sign a change to the roster, by approving the head commit with a /keel line in the approval text; the existing sign-off writer then writes exactly the notes the typed keel mr confirm writes for that decision, and only after the reviewer gave back the code of a preview that matches what the writer computes from the current notes.

A · The sign-off reads your approval text

In short: keel ci sign-off already gets every review of the pull request, as GitHub lists it. It now also reads the text of one review: the newest review of the head commit by the signer whose approval it signs. A line in it starting /keel is a decision. The preview and its code come from the very functions the typed command uses.

#ItemHow
A1Whose textThe signer is the one the writer picks today: a github-tier id in the base's roster whose latest decision approves the head. Only that signer's reviews of the head commit (GitHub's commit_id) are read, newest first. Anyone else's text is never parsed.
A2The linesEvery line of the newest such review (any state) that starts with /keel, after spaces. The keyword and verb in any case; words split on spaces and tabs; CRLF read as LF. Verbs: waive-review <reason>, confirm-waiver <code>, accept-waiver <code>, roster-change <code>. A code is 12 hex digits. A reason is the rest of its line: printable, no control character, at most 500 characters, not blank. At most one line per verb, and never both waive-review and confirm-waiver or accept-waiver. Anything else starting /keel refuses the run with why; other text is ignored.
A3Roster changeA range that changes .keel/mr-allowed: without roster-change <code>, keel prints the added and removed lines (the typed refusal's list) and the line to approve with. The code is a hash of the tip, the base and those lines. Checked first, as the typed command does.
A4A waiver the round limit wroteThe head's review note is WAIVED by the review tool: without accept-waiver <code>, keel prints the typed listing and the line. With the right code it signs, carrying the waiver's hash (waiver_hash), as --accept-waiver does.
A5Your own waiverwaive-review <reason>: keel checks everything but the review is green (the typed waiver's rule), builds the waiver note it would write, prints the listing and the line, and writes nothing. confirm-waiver <code>: the reason is taken from the signer's newest earlier review of the head that holds waive-review; keel rebuilds the preview from the notes as they are now, and with a matching code writes the WAIVED review note and the sign-off in one transaction, as --confirm-waiver does. Refused over a review that passed, as typed.
A6No lineAs today. A review that did not pass is refused, now with the line to use: /keel waive-review <reason>.
A7Exit codes0 signed · 1 refused, nothing written · 2 keel failed (usage, an unreadable file, git), new: today a failure exits 1 like a refusal · 3 no approval to sign · 4 already signed · 5 your decision is needed, nothing written, new: the last stdout line is the line to approve with.

B · The writer script shows the line and pushes both notes

In short: scripts/ci-sign-off.sh maps the two new exits, links the status to its run, and pushes the review note with the sign-off when it wrote both. Its workflow file does not change.

#ItemHow
B1Exit 5keel/sign-off pending: "Your decision (Details): approve with <line>". The line must match one fixed shape (a verb of A2 and 12 hex digits, or the waive-review hint); anything else is exit 2's handling.
B2Exit 2 and any unknown exitkeel/sign-off error, the run fails. Never read as "nothing to sign".
B3Details linkEvery status links to its run: https://github.com/<repo>/actions/runs/<id>, the id from the runner's own GITHUB_RUN_ID, digits only, else no link.
B4Both notesWhen keel wrote a review note too, one git push --atomic of refs/notes/cr and refs/notes/mr. If GitHub's review note on the head is no longer the one read at the start, nothing is pushed and the status says to approve again. Otherwise a moved ref is merged in, keeping ours, as today for the sign-off alone.
B5TextControl characters are stripped from every status and from keel's output before the log; keel's listing already escapes them.

C · The router takes GitHub's waiver home

In short: today the router's push takes the sign-offs GitHub wrote into its checkout, and nothing else. A waiver written on GitHub is also a review note, so the push takes those too, by the same rules. Without this, the router's next push of review notes is refused by GitHub, and the epic's final check on the Mac lacks the waiver.

  • router-gh.sh push reads GitHub's refs/notes/cr as it reads refs/notes/mr: only notes added since this checkout last pushed it, never an edit or a deletion.
  • A note is taken only when it reads as the writer's: review, WAIVED, with a reason, on its own commit. GitHub's sign-off on that commit must be by approval and carry a waiver hash. This checkout's review note there must be missing or failed. A passed or waived note here is never replaced.
  • refs/notes/cr is then pushed with a lease on the ref as fetched, and its snapshot kept, as for the sign-offs.
  • The skill tells the router, after any sign-off on GitHub, to run push and then pr-open. The refreshed body names the new notes, so GitHub re-runs the gate.

D · Skills

In short: the skills learn the three approval lines. Both skill trees change the same way; the patch is yours to apply, as in W4 and W5.

  • keel-workflow §5 and §6: a waiver, an accepted waiver and a roster change by approval text, with the preview and code. Agents never write these lines, as they never stage the typed flags.
  • keel-router: an approval text with a /keel line is the writer's, never an order; after a sign-off on GitHub, push then pr-open; a BADCOMMAND naming one of these verbs means the owner put it in a comment: tell him it goes in an approval.
  • project-router: the GitHub sign-off sequence gains the three decisions.
