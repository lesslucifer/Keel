Outcome

Delivered. scripts/router-gh.sh has the five router shapes: push, pr-open, pr-ready, post and sync. It checks every argument before anything else. It acts as a GitHub App through a token minted on each call. No output, argv, environment or worker-reachable file carries the key, the JWT or the token, and git hands the token only to github.com over https. It never runs the code it pushes: the pre-push hook is skipped, and push does Keel's code-free checks itself. The router guard admits exactly these shapes. Workers cannot read the key directory (the sandbox's denyRead is the bound). The script is rule-bearing. Against GitHub itself it is unproven until your App exists; the hermetic tests cover every shape.

The first live run: what to look for

  1. The router runs the script from a checkout that holds this WU, because the guard and the script come from the router's own checkout. scripts/router-gh.sh push wu/E-GHFLOW/w3-… (or this branch) prints PUSHED branch=… sha=… state=new. On GitHub, the branch's push shows the bot as pusher, and "Keel gate" starts.
  2. scripts/router-gh.sh pr-open <branch> prints PR number=… url=…. The pull request is a draft, authored by <slug>[bot], into the epic, and its body has the tip, the doc table and the notes row.
  3. Three facts only the live run can prove: (1) GitHub accepts the token as x-access-token basic auth over https. The credential path itself is tested through git's own credential layer: the token goes once per git run, to github.com over https only, and no hook runs during the push, so nothing of the pushed code ever sees it. (2) GET /repos/…/git/ref/heads/wu/E/x takes a branch name with slashes. (3) The Pull requests permission lets the App comment (post). A failure of any one is a one-line error naming the request.

Deviations

  • The router's push no longer runs the pre-push hook. The epic plan said the hook "still runs on every router push". The independent security review (blocker B1) showed why it must not: the hook's keel check runs the pushed branch's own [check] commands, build scripts and tests with the router's rights, and the router can read the App key and write its own guard. So push runs with --no-verify and does Keel's code-free checks itself. A wu/ tip must carry its test/v1 note for that tip, which proves its worker ran keel check in its sandbox. An epic/ push that GitHub already holds must pass keel verify-dod range, as the hook would. The tests run in the worker's sandbox and in CI's ci job, never on the router's push. The notes ride the same push again, as the plan said; the second push of v1 existed only because of the hook.
  • The security review's other fixes:
    • B2: post reads the worker's file once. It enters .router-gh by its real path, opens the name without following a link, accepts only a regular file with one link, and checks and posts a copy. A link, a hard link, a FIFO or a moved directory is refused.
    • I1: git reads no global or system config, so no url.insteadOf, pushInsteadOf or push.followTags applies. Pushes pass --no-follow-tags, and the credential helper answers only protocol=https host=github.com.
    • I2: a test drives the https path through git's real credential layer.
    • N1: curl -q, so no ~/.curlrc is read.
    • N2: set -f, so no glob expansion.
    • N3: the comments no longer claim workers are denied the script; the denyRead of the key directory is the bound.
    • N4: the key directory must be the user's and writable by no one else, and the key must have one link.
  • The security review's second round:
    • X1: sync no longer runs git inside a worktree. A worker can write the shared git dir, so it could forge a worktree entry naming a repository whose filters and hooks it owns. So sync only fetches GitHub's branch into refs/remotes/origin/epic/<E>. When no worktree has the branch checked out, sync moves it by update-ref. When one does, it reports state=fetched, and that worktree's own session fast-forwards it. The plan said sync "fast-forwards the local epic/ branch"; it now does so only when no worktree holds it.
    • X2: the run's temp dir, which holds the token while the script runs, now lies under the key directory (~/.config/keel/router-gh/run/), which workers cannot read, never in the shared $TMPDIR. The credential helper accepts only a token file there.
    • N1: a worktree entry is believed only when git made it for this repository, by the launcher's rule. A forged entry can neither steer post nor block every call through the key-location check.
    • N2 and N4: the script's header says its checks on git data are policy, not a bound, because workers can write the shared git dir; CI's gate and your sign-off are the authority. Replace refs are ignored.
    • N3: push sends only Keel's five notes kinds.
  • .claude/settings.json's allow lines were not added. The worker file guard refuses that edit, by design, so they are owner step 1.
  • The epic plan named "a local mock of the GitHub API" in the notify_owner shape, a loopback server. The worker sandbox refuses every socket, loopback and Unix (probed), so the mock is a fake curl instead. That trade was decided in the WU plan, open point 1. One more test runs the real curl, to prove it reads the script's request config.
  • No manual scratch run. My shell refused a scratch git push and git notes, both on the worker deny list, so every behaviour was exercised only through cargo test. The tests make a throwaway RSA key in a temp home; no real key or token was created or read.
  • Otherwise none.
