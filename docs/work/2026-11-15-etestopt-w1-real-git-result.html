E-TESTOPT.W1 · The tests run the real git — result

Every program a test starts now runs the real git from inside its own installation, not the macOS launcher. The 11 sandbox failures it caused are gone, and the full run with the stock PATH is as fast as with the developer tools' git first.

T3 · WU result · 2026-11-15 · Keel · branch wu/E-TESTOPT/w1-real-git off epic/E-TESTOPT 1e1c6bc · WU plan · epic E-TESTOPT plan, block W1

What happened

Delivered, with one change of mechanism after review round 1. The test helpers ask the PATH's git once per test program where its installation keeps its own programs, and put that directory first on every PATH a test hands a child. Round 1 had linked the git into a directory of its own instead. Started from there, git could not work out which installation it belonged to and borrowed Xcode's; the review failed it, and the fix replaced the link. With the stock PATH in a worker's sandbox, the router tests went from 12 failures to 1. The one left was the watcher test, which W2 fixed. After W2 merged into the epic and was merged back here, the whole suite is green in the sandbox with the stock PATH: 334 pass, 0 fail. A full run with the stock PATH took 61.6 s, the same as with the developer tools' git first; the epic's baseline had it at 77 s. Keel's own code is unchanged.

Deviations

  • The before runs come from the epic's baseline, not from this session. A scratch clone of the base for a same-session run was refused twice by the session's permission check (git clone -q <this worktree> $TMPDIR/keel-before). The test code at the base 1e1c6bc equals the baseline's 690aef1 (that commit adds only the epic plan), on the same machine. This session also ran the router tests on the old code: 12 failures, 18 xcrun_db lines, 30.2 s.
  • A fix found by the recipe's own run. With the developer tools' git already first, the resolver made no link, so a PATH a test makes up (/usr/bin:/bin) fell back to the launcher, and the new test caught it. The link is now made whenever a real git is found. Only the shared PATH is left as inherited when its git already is that one (commit 9619347). Review round 1's fix replaced the link, and with it this case.
  • Review round 1 failed: 1 blocker, 2 importants. The fix changes the mechanism. The blocker: git finds its install prefix from the directory it was started from. A link in target/tmp sits in no install layout, so git fell back to its built-in prefix, Xcode's. With the Command Line Tools first, the children ran their git with Xcode's helpers. On a Mac with only the Command Line Tools, a local push would reach the launcher's git-receive-pack. Important 1: the contract test checked the resolved binary, not what the children run, so it could not see this. Important 2: one link per target/, repointed by every test program, let two overlapping runs redirect each other. The fix (069dc88) puts the PATH's git's own --exec-path first: its libexec/git-core, which holds git and git's own helper programs only. Git puts that same directory first on PATH for its own hooks and subcommands. Started from there, git resolves its own prefix (traced: resolved executable dir: …/CommandLineTools/usr/libexec/git-core). Nothing is written, so no run can repoint another's git.
  • The plan's "nothing changes where no launcher is in the way" no longer holds. On Linux, or with the developer tools' git first, git-core still goes first: one rule for every PATH, which also ends the case 9619347 fixed. A git whose exec-path holds no git, or no git at all, leaves every PATH as inherited.

How it works

  • tests/common/mod.rs: git_core(exec_path) is the exec-path when it is absolute and holds git, else none. git_dir(inherited) asks the inherited PATH's git for --exec-path; test_path_for(inherited) puts that directory first. path(), path_with(dir) and real_git_first(p) are the only ways a test builds a PATH, and cmd sets path() on every spawn.
  • This machine's real git is Xcode's (xcode-select -p is /Applications/Xcode.app/Contents/Developer), not the Command Line Tools'. Its usr/bin also holds python3, make, gcc and dozens more, so that directory never goes on PATH. Its libexec/git-core holds 172 entries, all git's own (git, git-*, scalar, mergetools).
  • Every std::env::var("PATH") in the test files became a helper call (cli, close_walk, init, mr, review, router, seed3_e2e, verify_doc, verify_dod). The one literal PATH, /usr/bin:/bin in installed_git_hook_without_keel_on_path_refuses_and_points_to_install_channels, goes through real_git_first.

Distillation

Nothing lands in T1/T2 at this WU. For DEC-84 at the epic close, the git-on-PATH rule for tests: "Every PATH a test hands a child comes from tests/common (path, path_with, real_git_first; guarded by every_test_path_comes_from_common). Its first directory is the PATH's git's own --exec-path (its libexec/git-core, the directory git itself puts first for its hooks), when that holds git: git started there resolves its own installation, and the macOS xcrun launcher never runs under a test. Keel itself runs whatever git its caller's PATH names." Rejected: a link to the real git in a directory of its own (git started outside its install falls back to a built-in prefix, another installation's: E-TESTOPT.W1 review round 1); the real git's own bin directory first (it shadows Xcode's python3, make and more); xcrun --find git (macOS only, and it is the program that fails in the sandbox).
