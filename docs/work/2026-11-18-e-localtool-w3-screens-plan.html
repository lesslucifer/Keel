How you approve it

  1. You read this plan and comment, or tell the router it is fine.
  2. The worker draws the screens in one result doc. It opens with the screens.
  3. The router tells you it is ready. You open it in your browser and comment on any screen or field.
  4. The router opens a pull request into the epic. You approve it on GitHub. Your approval is the sign-off, and GitHub merges it.

The form

  • Static HTML and CSS, inside the result doc. No script but the doc's usual two. Each screen sits in a plain window frame at desktop width.
  • Plain look. Grey frames, one colour per state (green, amber, red). Fonts and colours are the build's job.
  • Fields folded. Under each screen, a closed "Where each field comes from" table: field, source, the W2 part that reads it, mark. You open it only when you want it.
  • Each screen names the one window request it uses, from W2's list (the waiting list, the fleet, one epic, the projects). A screen that needs another request names it as new.

Details

Tests and checks

Unit and integration: waived. W3 changes only docs/work/, so no code path changes. The range is exempt from test, review and doc notes. Your sign-off still runs.

The checks the worker runs instead, by a script in a scratch folder, with the raw output in the result's evidence:

  1. Every must need shown. n1, n2 and n3 each name the screen and fields that show them. n4, n5 and n7 too. n6 and n8 to n10 are listed as not drawn, each with who takes it.
  2. Every field sourced. Each field's row names keel (a read command, or a file and line at cf4c752), git (a ref or a read command), or a session (a claude agents --json field, a run record, the inbox count), or the mark "new". Each names the W2 part that reads it.
  3. The app judges nothing. Every source is one of W2's read commands. A field that needs anything else is marked "new", and the result lists what keel would gain, as W2 listed K1 to K3.
  4. Every item kind drawn. Screen 2 has a row of each kind the epic names: a sign-off, a rule-file commit, a question from the router, a failed gate, a merge conflict. A kind the day did not have is drawn and marked "sample".
  5. Every sample value traced. Each value names its commit, note or file of 2026-11-18, or is marked "sample".
  6. W4's edge kept. Each waiting item has its two slots, empty and marked W4. No link target or command text is drawn by W3.
  7. Local sources exist. Every repository path cited passes git cat-file -e cf4c752:<path>.
  8. Static. The doc has no script but the mermaid one and htmldoc's.
  9. Doc check. keel verify-doc is green on the result.
  10. Scope. git diff --name-only cf4c752..<tip> lists only docs/work/ files.

Sign-off and merge

  • The WU reaches epic/E-LOCALTOOL as a pull request, opened by the router. Your approval of it signs it (the github tier), and auto-merge merges it.
  • The result report is in the range, so the sign-off attests its bytes.
  • GitHub's flow is still today's flow. W5 plans its retirement; nothing about it changes here.
