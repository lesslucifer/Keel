W2 · One sender that reaches you from both hosts

In short: one script the router runs in the same turn it stages an owner action or needs a decision. It posts the message the push rule already makes it write to the paired Telegram bot and prints the id the router records as Sent to <channel> (id N); the same code runs on DSH and Claude Code.

  • scripts/notify-owner.py (new, stdlib only): --send posts and prints id N, --dry-run validates and prints without sending, --check asks Telegram who the bot is and sends nothing. The credential is read from the channel's own token file and never printed.

  • tests/notify_owner.rs: the three modes against a local mock API, the --check failure line, and no credential on stdout.

Details

Acceptance

  • A router that reads the shipped skill meets "run START before your first tool call" and "WAKE on every wake", each one link away from the checklist.
  • The checklist fits one screen and every row says what skipping it cost.
  • A dispatch on any host writes the brief file first; a stale brief is a finding, not a template.
  • On DSH the router states that no worker's finish can wake it, and names the message the owner must send; no text claims a fleet wake is in force.
  • The router reaches the owner from either host with one command, and the message id it prints is the line it records.
  • keel init in a scratch repo plants checklists.md, byte-equal to the source; the two skill trees stay byte-identical.
  • No test in the repository goes red; clippy with -D warnings stays green.

Use cases

  • UC-ROUTE-6, amended: on DSH the skill is the only guard, so the router runs the checklists and names the gap; the owner is reached in the same turn from either host; no worker's finish can wake the router until W3 lands.
  • UC-ROUTE-1, amended: the moment of action carries the boundary — read tools for dispatch and verification, never for the work.
  • UC-ROUTE-5, amended: a DSH worker's report is its transcript; a dispatch writes a brief file on every host. W3, when it lands, makes the report a post that wakes the router.

Out of scope

  • The guard plugin (D2) and any plugin code.
  • An allow rule for the launcher in the DSH preset, and any change to the launcher, the hooks or the preset.
  • A second bot, token or notification service; the sender uses the chat you already paired.
  • Rewriting the router skill's long form; the checklists point to it, they do not replace it.
  • The inbox channel in this epic tip: W3 is parked on its branch, and a Claude Code worker posting is out of that WU too.

Epic test

This is a process epic, and each landed unit's end-to-end proof is its integration test on the shipped tree. W1: keel init in a scratch repo plants checklists.md byte-equal to the source, and the installed SKILL.md names it at the two points a router meets it. W2: the router's own command, scripts/notify-owner.py, is spawned against a local mock of the Telegram API and exercised in all three modes, including the failure line. W3's proof is tests/router_inbox.rs on its parked branch, not in this tip. The live send to your phone is an outward action you trigger, not a test. Waiver intent: stated here rather than as separate flows.

Test plan

  • Integration (tests/init.rs): the shipped-skill inventory stays exact — every reference file is named by SKILL.md and the reverse; the embed list matches skills/, so keel init plants checklists.md; a test asserts each of the three checklists exists with its trigger and that the four failures D2 will enforce each have a row.
  • Integration (tests/notify_owner.rs): the sender spawned as the router runs it, against a local mock API — the three modes, the failure line, the cleared and read-only body, the https rule, the injectable timeout, and no credential or chat id in any output.
  • Integration (W3, parked): tests/router_inbox.rs spawns the inbox script through its process boundary, one temp inbox per case.
  • Unit: waived — W1's code change is one entry in a constant list, and W2's is a script whose contract is its process boundary; the behaviour each buys is the integration test above.
  • Rule text: the existing rule-text tests in tests/init.rs and tests/router.rs stay green on the new wording, and W2's guard test pins the sender's shapes.
  • No live router session: a router's conduct on DSH is not observable from a test; the evidence is the checklist a session must read, and D2 is what makes it fail a call.
