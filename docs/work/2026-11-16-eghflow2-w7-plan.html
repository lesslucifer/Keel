E-GHFLOW2.W7 · Your approval accepts all

When you approve a WU's or an epic's pull request, that is the whole decision. A failed code review or a change to who may sign no longer sends you to your Mac.

Ready v3 · 2026-11-17 · T3 · WU plan · Keel · off epic/E-GHFLOW2 366a9eb (after landing 3) · matches W6 plan v5 (f3efcac) · plan only: no build before your go

The problem

Say W9's code review fails on one finding you think is wrong. You open its pull request on your phone and approve it. Today nothing happens: the sign-off refuses, and the pull request waits until you type a waiver at your Mac. The same happens when the round limit gave up on the review, and when the pull request changes who may sign. The decisions that most need you are the ones your phone cannot make.

The sign-off note records what you approved over, and the pull request's sign-off status says it. The typed commands at your Mac stay as they are.

Example

  1. W9's code review fails on one finding.
  2. The router tells you, and the bot asks for your review. On the pull request, the build, tests and docs are green. The gate is green too, and its page says "the review did not pass: your approval decides", with the finding.
  3. You read the finding and approve.
  4. Keel signs. The note says "approved over a failed review". The sign-off status turns green: "Signed by approval, over a review that did not pass".
  5. W9 merges into the epic, as any approved WU does today.

How it fits W6's tasks

  • A task's pull request (into its WU's branch): nothing changes. It has no review, no notes and no sign-off. You merge it, and your merge is the yes.
  • A WU's pull request (into the epic): the code review runs once per WU and is checked here only. Your approval of it accepts all, including every task already merged into the WU.
  • An epic's pull request (into main): the same. A WU inside it that you approved over a failed review does not turn the epic red.
  • Only you merge. The router keeps each pull request ready and tells you when a review failed. It never approves.

What still stops a merge

  • A red build, test run or doc check. These checks stay required on GitHub.
  • Any gate check other than the review: missing test or doc records, a WU inside an epic that never passed its own checks.
  • No approval yet, or an approval from someone the signer list does not name. Today that list names only you. The list on the target branch decides, so a pull request cannot add its own signer.
  • A change request from you.
  • A required result report that is missing (W6 asks for one only when the code changes).

The work

  1. The sign-off accepts your approval over the review and the signer list. It still needs everything else green. It records the review's state and any signer-list change in the note.
  2. The gate leaves the review to your approval. On GitHub it stays green when only the review fails, and says so on its page; the required sign-off status still holds the merge until you approve. On your Mac, and when an epic checks its WUs, a review is accepted when your approval signed that commit.
  3. The status says what you approved over. One line added to the sign-off script.
  4. The skills say that your approval accepts all, and that the router must tell you plainly when a review failed. A patch for you to apply.

Not in W7: the router's four commands (go, hold, retry, answer), which you decide on separately; tasks, which W6 owns.

Safety

  • No new workflow, permission, token or GitHub setting; the writer still runs main's code. keel/ci, keel/gate, keel/docs and keel/sign-off stay required.
  • With the gate green on a failed review, only keel/sign-off holds the merge. Its one setter is the writer, which turns it green only for a new approval, an approval GitHub still lists (6), or a typed sign-off with a green review (6). Tighter than today on GitHub.
  • On the Mac nothing new opens: a same-user shell could already write a github-tier note (G7) or a passing cr note.
