E-ROUTERFIX.W3 · Result

New worktrees of Keel's own tree inherit the main checkout's signer list (.mr-allowed), so the first keel mr in a fresh worktree is no longer refused for want of one.

T3 · WU result · 2026-11-09 · Keel · wu/E-ROUTERFIX/w3-worktree-seed · plan epic plan, W3 block

Outcome

Delivered against the plan. A tracked .gitworktreecopy lists .mr-allowed. keel's post-checkout hook (src/main.rs POST_CHECKOUT, unchanged) copies each listed file from the main checkout into a new worktree when the file exists there and the new worktree has no copy of its own.

Two preconditions sit outside this WU. (1) The hook reads .gitworktreecopy from the main checkout, which is on main. The seeding therefore starts when this epic lands on main. Until then, the owner can place the same one-line file, untracked, in the main checkout. (2) keel's hooks are not installed in this repo (empty core.hooksPath, no keel-hooks in the common git dir), so no hook runs at all until keel hooks install. Also, the main checkout's .mr-allowed is empty today, so the seeded copy would be empty until the owner runs keel mr setup there.

Evidence

  • New tests/init.rs self_hosting_new_worktree_inherits_the_signer_list. It clones Keel's own committed tree, installs hooks, writes an untracked .mr-allowed, runs git worktree add, and asserts that the new worktree holds the same bytes. The hook's general behaviour stays covered by tests/cli.rs new_worktree_is_seeded_from_gitworktreecopy.
  • Red before the tracked file was committed (the clone had no .gitworktreecopy, so the test failed with NotFound reading w/.mr-allowed). Green after: cargo test --test init self_hosting gave 2 passed.
