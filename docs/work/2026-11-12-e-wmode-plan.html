One-WU epic (E-WMODE.W1), epic and WU plan collapsed. The launcher stops hard-coding acceptEdits. It reads the mode from .keel/config.toml [router], as it already reads the model and the effort. Keel's own config sets Claude Code's auto mode.

Intent

The permission mode a background worker starts in becomes project policy. Today scripts/router-worker.sh hard-codes acceptEdits, and a trailing --permission-mode plan on spawn is the only override. After this epic the launcher reads worker_permission_mode from [router] in .keel/config.toml, as committed at the router checkout's HEAD. This is the same source and the same fail-closed reader that already decide the model and the effort (DEC-39). Keel's own config sets auto. Why now: during a worker run the owner had to answer permission prompts for plain reads. acceptEdits auto-accepts only edits inside the worktree. A Read outside it, a WebFetch, or a host outside the sandbox stops a background worker on a prompt that only the owner can answer through claude attach (DEC-44 consequences). In auto mode, Claude Code's classifier judges those calls instead of the owner. The owner wants this on main before E-CRCAP's WUs start, so E-WMODE is a separate one-WU epic.

Expected

  • With worker_permission_mode = "auto" committed in the router checkout, scripts/router-worker.sh spawn <name> <wt> <brief> opus passes --permission-mode auto to claude, writes auto to the run dir's permission-mode and prints permission-mode=auto on the RUNNING line. The same holds for acceptEdits and plan.
  • With no worker_permission_mode line, the mode is acceptEdits. A project that already has a [router] section keeps working unchanged.
  • --permission-mode X on spawn is accepted only when X is no wider than the committed mode (plan < acceptEdits < auto). Under auto, plan and acceptEdits are accepted. Under acceptEdits, auto is refused as wider than the policy, and nothing starts.
  • A committed value outside plan|acceptEdits|auto (bypassPermissions, dontAsk, default, Auto) is refused with worker_permission_mode must be one of: plan acceptEdits auto, and nothing starts. A malformed line (unquoted, a list, repeated, with junk after it) makes the whole policy fail with no worker policy, as any other malformed [router] line does. An uncommitted edit cannot widen the mode.
  • Keel's committed [router] holds worker_permission_mode = "auto", pinned by tests/router.rs.
  • The sandbox, the grant and deny lists, --setting-sources project,local, --strict-mcp-config and --agent worker reach the worker exactly as before, whatever the mode (the argv shape test is unchanged).

Design

PieceChange
read_policy (awk over git show HEAD:.keel/config.toml)One more accepted line: /^worker_permission_mode = "[A-Za-z]+"$/, at most once (a repeat falls through to bad, as a repeated key does today). It prints a fifth line: the value, or - when absent. The existing word grammar ([a-z][a-z0-9.-]*) cannot hold acceptEdits, hence its own pattern. Membership is checked by spawn, not by the reader, so a well-formed but refused value gets a message that names the key. A watchdog start, which does not use the mode, is not refused by it.
spawnpm starts empty. After read_policy: the policy mode is - → acceptEdits. If it is outside the set → die "worker_permission_mode must be one of: plan acceptEdits auto ([router] in .keel/config.toml)". Then a requested --permission-mode outside the set → die "permission mode must be plan|acceptEdits|auto". A request ranked above the policy's mode → die "permission mode <X> is wider than the policy's <Y> ([router] worker_permission_mode in .keel/config.toml)". All of this runs before the worktree checks, the lock, the snapshot and the start. The usage line becomes [--permission-mode plan|acceptEdits|auto].

Evidence that auto is an accepted --permission-mode value

This worker cannot run claude (it is on the deny list) and reads nothing outside its worktree, so it has no direct evidence. Indirect evidence: (1) DEC-37's Rejected row (2026-11-09) lists auto beside bypassPermissions, dontAsk and default as a worker mode the CLI offered. (2) This worker session (Claude Code, launched by this launcher on 2026-11-12) documents an auto mode in its own Bash tool (allowed_domains: "Auto mode only"). (3) Mid-run, this session observed a harness notice that auto mode was active. The cause is unknown: the launcher started the session in acceptEdits, and the router has asked the owner whether they switched it while attached. No claim rests on this observation. None of these proves that the launch flag claude --bg --permission-mode auto is accepted at the installed version, or that a background session keeps the mode. The router's first spawn after the merge is the live check (open point 9).
