What happened

Delivered. The cap, the whole-work rounds and the blocker-only round are three settings in the rules file of the branch the work merges into. A setting left out takes its default value, written in one place in the code. After your feedback, every test now works out what it expects from the settings under test. It runs the default values and at least three other schedules.

The main case, as the tests run it

A project sets a cap of 4, two whole-work rounds, and blocker-only from round 3.

  1. Rounds 1 and 2 read the whole work. Each finds a medium finding, so the next round runs.
  2. Round 3 reads only the last fix. It also finds a medium finding.
  3. The tool refuses round 4: only a blocker earns it from round 3 on. It names the way on: record the fix with no new round.
  4. That record is written, and the merge check reads it as a pass.
  5. Another work item on the same project finds a blocker in every round. Round 4 is the last, and the review ends in the cap's waiver, "review cap: 4 rounds".

The same tests run on the default values and on other schedules, through the real tool and hooks.

Differences from the plan

  • A wrong setting already landed blocks the review, never your sign-off. The sign-off then lists rounds by the default values and says so.
  • A refused setting names its own fix.
  • The first version of this plan and its tests were written around the default values. They were rewritten after your feedback. The tool's logic did not change.
  • The first code review found two test gaps and three small points. All five are fixed: the tests keep the default values in one place, and a setting above an unset cap now says the cap is the default one.
