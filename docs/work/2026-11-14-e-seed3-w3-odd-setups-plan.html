The problem

Three odd setups change what the gate or the tests see. Each one is a wrong answer that looks right.

  1. A push runs with GIT_INDEX_FILE set: its scratch checkout writes the pushed tree into your real index. You then see the pushed files as staged and deleted in your checkout.
  2. A WU is signed off or verified by a bare commit id. The gate cannot read a branch name, so it measures the WU against main, and a correct review turns red on 4·review-base.
  3. The test suite reads your global and system git config. A local signing key or log setting can make tests fail, or pass, only on your machine.

A real case, in steps

  1. A post-commit hook pushes for you, so the push inherits the index path git exported.
  2. pre-push proves a non-HEAD sha in a scratch worktree. git worktree add inherits GIT_INDEX_FILE and writes the pushed tree there.
  3. You copy a WU tip id from git log and run keel mr confirm wu <sha>.
  4. The tip names no branch. The gate falls back to main, and the merge-base with main differs from the one the review recorded: a false 4·review-base red.
  5. In a test, a fixture's git commit reads ~/.gitconfig, so your tag.gpgSign signs a tag the test never expected.
  6. After this WU: the scratch checkout starts from a clean index environment, the bare id finds its epic, and the fixture reads no global config.

Terms

Bare commit idA commit named by its sha, not by a branch, so no branch name tells the gate what a WU is measured against.
TargetThe branch a WU's changes are measured from: an epic branch for a WU, main for an epic.
Holder branchA local branch that has the commit in its history.
Scratch checkoutThe temporary worktree the push check creates to prove a pushed sha that is not HEAD.

The work

In short: each case gets a rule with one place that enforces it, and a regression test that fails without it. The three touch different code paths: the push check, the target resolution, and the test spawn helper.

flowchart TD
  A["Tip given to a WU gate"] --> B{"Names a local branch?"}
  B -->|"yes"| C["Its epic by the wu prefix, else main"]
  B -->|"no"| D["Branches that hold it"]
  D --> E{"A wu branch holds it?"}
  E -->|"yes, one epic"| F["That epic branch"]
  E -->|"yes, two epics"| G["Refuse: name --target"]
  E -->|"no"| H{"One epic branch holds it?"}
  H -->|"yes"| F
  H -->|"no"| G
How a WU target is resolved, and where it refuses instead of guessing main.
  1. B9, the push check: the two scratch worktree calls go through a spawn that strips GIT_INDEX_FILE. Every other keel git call keeps it, because git's commit hooks hand keel the index being committed (DEC-41).
  2. R7, the target: a WU tip that names no local branch resolves from the branches that hold it: the epic of a local wu/<e>/… holder, else the one local epic/<e> holder. No holder, no epic branch, or two epics: a refusal whose fix line names --target. Main is never a guess for a bare id.
  3. Explicit flags still win: --target is used as given, and a tip that names a branch keeps today's rule.
  4. B10, the test suite: tests/common's spawn helper sets GIT_CONFIG_GLOBAL=/dev/null and GIT_CONFIG_NOSYSTEM=1. The two files that set them by hand drop their copies.
  5. Tests: integration per case — the push with an inherited index path, the sign-off and the verify on a bare id, the hostile global config — and a unit test of the resolution over every holder combination.
  6. Rule text: no rule-bearing file is touched here. The wording for UC-NOTE-1, UC-GATE-2, DEC-15, DEC-41 and the keel-workflow rows goes in the result for the epic close, as W2 did for its use cases.

Details

A GIT_INDEX_FILE inherited by the push check never reaches its scratch worktree calls, so the real index is byte-identical after a push; keel verify-dod and keel mr confirm resolve a WU tip that names no local branch to the epic its holder branches name, and refuse with a --target fix line when none or more than one epic holds it; and every test spawn reads no global or system git config.

  • In a scratch repo, keel hook pre-push run with GIT_INDEX_FILE set at the real index leaves that file byte-identical, and git status unchanged.
  • A bare WU tip id, on an epic with a commit of its own, is green under verify-dod and signable with mr confirm; the review base is the epic's commit, not main's tip.
  • A bare id that no branch holds is refused with a fix line naming --target, and never reports 4·review-base.
  • A test spawn with a hostile ~/.gitconfig and a hostile system config selector reads neither.
  • The existing target rule for a branch name and for --target is unchanged: every existing test stays green.
  • Integration, tests/cli.rs: the push check with an inherited GIT_INDEX_FILE proves the pushed sha and leaves the real index byte-identical. Also the hostile-config spawn test.
  • Integration, tests/verify_dod.rs: the bare WU tip is green against its epic, and an id no branch holds is refused with --target and no 4·review-base.
  • Integration, tests/mr.rs: a sign-off on a bare WU tip id lands on the epic's base.
  • Unit, src/gate.rs: the target decision, over every combination of holders (none, main only, one wu branch, two wu branches of one epic, two epics, one epic branch) and with non-default prefixes.
