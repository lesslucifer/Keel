Decisions: the router

Why Keel's router has the posture, worker model and enforcement it has, and how E-ROUTER itself was run.

T2 · decisions · append-only · 2026-11-10 · Keel · DEC-30 – DEC-37, DEC-39, DEC-42 – DEC-45 · distilled from E-ROUTER (plan questions Q1–Q9, owner rulings 2026-11-08, close review), E-ROUTERFIX, E-SEED2.W7 and E-ROUTER3

"Lineage" names the E-ROUTER plan question or owner ruling (the plan, docs/work/2026-11-07-router-plan.html, is archived out of git; git show 9787799:docs/work/2026-11-07-router-plan.html recovers it) or the Trawler skill it ports. DEC-30 · The router has no general shell: a whitelist, a launcher and one fail-closed guard

ContextThe router reads untrusted text: the owner-facing chat and worker reports, one of which already carried an injected "stop and summarize" (lessons K1). Trawler's router ran git/gh/ps and spawned claude itself. The owner's own .claude/agents/router.md gave it no Bash at all.
ChoiceBash only for read-only git status|log|diff|show, git branch -v/-a variants, gh pr view|list|status, ps aux|-ef, and the two shapes of one committed launcher (scripts/router-worker.sh spawn|resume); Write only worker briefs; no Edit, Monitor, direct claude or kill. Enforced in Keel by "agent": "router" in .claude/settings.json, the agent file's tools:, and scripts/router-guard.jq run as the single PreToolUse hook on every tool for agent_type == "router", fail-closed (a jq error denies). The guard judges a command only after reducing it to plain words (a character whitelist), denies --ou*, gives gh only named query flags and bare words, caps length at 1000, and allows only the agent file's tools and the inline keel skills. The guard is the one source of the whitelist; tests/router.rs ties permissions.allow and router.md to it. keel init ships the skill, not the enforcement or the launcher: a project commits its own. Amended by E-SEED2.W12: the whitelist gains one more committed script, scripts/router-watch.sh commit|signed|merged|pushed|tagged <word>…, each word optional leading dots then [A-Za-z0-9_][A-Za-z0-9._/-]* (no leading -, no dots-only word, no ..). It only reads, except that pushed fetches exactly refs/remotes/origin/<b> (no tags, no FETCH_HEAD); its detail lines are untrusted text with control characters shown as ?.
RejectedA worker spawning on the router's behalf (owner chose to loosen the router's own whitelist by exactly the launcher shapes). Substring deny-lists on raw shell text and per-tool hooks keyed on the router's agent type alone: the close review bypassed both (DEC-35 consequences).
ConsequencesThe router cannot edit the launcher, the guard or the settings; only a reviewed worker commit can (scripts/ and .claude/agents/ are outside the cr gate's code_paths, but the guard and launcher are tested in tests/). Enforcement exists only in a checkout holding these files (lessons K11).
LineageQ2 (amended) and the owner's Q2 ruling 2026-11-08; hardened by the E-ROUTER close review (lessons K10).

DEC-31 · Headless workers are the standard; an enforced router has no Agent tool amended by DEC-44: workers are claude --bg sessions

ContextQ3 first answered "both modes, Agent-tool primary, headless for long fleets". In-session subagents die with the router session and are invisible to ps; the router also kept falling back to them for build work (lessons K4). The close review then showed an Agent subagent reports its own agent type, so it runs outside any hook keyed on the router's, in the router's checkout, with full tools.
ChoiceHeadless claude -p sessions, started only through the launcher (fixed prompt naming a brief, --agent worker --permission-mode acceptEdits --max-budget-usd 25, explicit model), are the standard worker mode. Keel's router has no Agent, SendMessage or TaskStop: every worker, checker and watcher is headless. The skill keeps the in-session recipe for projects that do not enforce the posture.
ConsequencesThe router's helper work (verify, watch, review) costs a headless spawn into a sibling worktree. Two launcher issues stay open: a branch without .claude/agents/worker.md cannot host a worker, and whether a worker stalls on Bash outside its allowlist under acceptEdits is unverified (backlog e-router-v2 R1, R2).
LineageQ3 (overridden by the owner 2026-11-08); E-ROUTER close review (Agent removed).

DEC-32 · The router writes worker briefs itself amended by DEC-42, DEC-43, DEC-44: snapshot and hash cover the spawn brief only

ContextUC-ROUTE-3 forbids the router authoring substance for a worker to paste. W1's first draft stretched it to briefs and had a worker write them.
ChoiceA brief is dispatch mechanics, like an Agent prompt: the router writes it directly (<router checkout>/.router/briefs/<name>.md, the only path it may Write). UC-ROUTE-3 covers content: doc prose, comment replies, status and "done" claims.
ConsequencesA brief is prompt text for a worker with edit and Bash power; the router must not paste untrusted report text into one (residual risk, DEC-33).
LineageOwner ruling 2026-11-08 ("who writes worker briefs"); corrects 4b6db50 (lessons K8).

DEC-33 · Accepted risk: workers inherit the owner's broad allowlist amended by DEC-44: the budget cap is gone

ContextHeadless workers run under the user-level ~/.claude/settings.json, whose Bash allowlist includes rm, kill, curl, python3 and claude (with --dangerously-skip-permissions). An independent security review raised it; the owner was shown the account-compromise severity.
ChoiceAccepted for now, not mitigated ("accept the risk for now"). Same for brief content: a compromised or injected router can still write a brief that a worker carries out in its own worktree. The launcher's fixed flags, the budget cap, the worktree refusals and the owner's merge sign-off bound the blast radius; they do not prevent a bad brief from running.
ConsequencesRevisit when workers read untrusted input (backlog e-router-v2 R4). Hardening the router (DEC-30) narrows what injected text can do directly; it does not make workers safe.
LineageOwner ruling 2026-11-08 ("worker permissions"); plan threat-model rows "workers' broad inherited Bash allowlist" and "brief content".

DEC-36 · The router may subscribe to a worker's end, never message it amended by DEC-42: the router may message a worker; DEC-43: a worker's turn end, not its exit, is the signal; DEC-44: the worker reports by message, wait is gone

ContextWithout Monitor or shell loops, the router learned that a headless worker ended only from a watch worker or the owner. Claude Code's cross-session SendMessage takes notify_when_idle: true with the message omitted: a one-shot notice when the target session next goes idle or exits. A live probe (E-ROUTERFIX.W2, 2026-11-09) subscribed a headless session to a launcher-spawned haiku worker by its -n name. The notice [Cross-session idle notice] "probe-notify" … is idle now was enqueued in the subscriber's queue at the second the worker exited. The subscriber was a headless session still mid-turn, and it did not see the notice during that turn. As soon as that turn ended, the queued notice started a new turn in the same session, and the notice arrived.
ChoiceThe router's tools gain ListAgents and SendMessage. The guard allows SendMessage only as a pure subscription: to a string, notify_when_idle exactly true, message absent or empty, and no other key besides the local summary label. The router subscribes right after a spawn or resume prints RUNNING. Amended by E-ROUTERFIX.W4: the router also arms scripts/router-worker.sh wait <name> [<stall-min>] as a background Bash command (the launcher's third shape; it only reads). The command ends with one EXITED line when the worker exits, or one STALLED line when the worker is still alive, no Bash-tool shell child is running, and its session transcripts are unchanged for stall-min minutes (default 15) on two polls in a row. The subscription covers a clean exit at no cost; wait adds the stall case.
RejectedLetting the router message workers: a worker has edit and Bash power, so router text would be a second brief with no snapshot or sha256 (DEC-32). Allow-listing keys by deny-list: a future content-bearing parameter would ride along.
ConsequencesThe notice carries a worker-written snippet (Its harness reports: «…»), so it is untrusted text, the same class as .router/out/<name>.out. The .out file stays the report of record. A router busy with a turn sees the notice only when that turn ends. The heartbeat stays, for a worker that hangs without exiting. Since W4, wait's STALLED line covers that hang, so the heartbeat's per-worker ps poll is a fallback for when no wait is armed. A background command is killed at its timeout (2 h at most), which wakes the router with no line, and the router re-arms. STALLED is a heuristic: a worker thinking quietly for longer than stall-min reads as stalled.
LineageE-ROUTERFIX.W2 (plan, result, live probe); amends DEC-30's tool list. E-ROUTERFIX.W4 (E-SEED2.W8's watchdog, moved here; its plan's Telegram-push design was dropped for wait, which needs no new channel).

DEC-37 · Worker grants travel on the launcher's command line; the router picks a worker's mode from a closed set

ContextBacklog e-router-v2 R2 asked whether headless workers stall under acceptEdits. Real runs answered it: they are refused. Three workers in one session got "requires approval" on cargo / keel, and in a claude -p session nobody can approve. No worker could run its tests, write its notes, run keel preflight or run the review. Neither allowlist a worker inherits has these commands: the owner's user-level one (DEC-33) and the project's, which is the router's own list (DEC-30). .claude/settings.json is rule-bearing, and Claude Code refuses a worker's write to it. The launcher also hardcoded acceptEdits, so a read-only checker could not be started in a stricter mode.
Choicescripts/router-worker.sh passes a fixed --allowedTools list to every claude -p it starts. The list holds Bash(c) and Bash(c *) for cargo build|test|check|clippy|fmt and keel preflight|verify-doc|verify-dod|notes write|lint|check. It also passes a fixed --disallowedTools list: keel mr, cargo run, bare and " *". A deny beats the user-level allowlist too. spawn and resume take an optional trailing --permission-mode acceptEdits|plan. It defaults to acceptEdits on every run, and a resume does not inherit it. Any other value is refused, as is a missing value or an unknown option. The mode is written to the run dir (permission-mode) and printed on the RUNNING line.
RejectedA worker allow-list in .claude/settings.json: it is shared with the router, rule-bearing and unwritable by workers. More cargo subcommands: no cargo run, since cargo run -- mr is keel mr, and no install, publish, add or update, since they touch the machine, the registry or the dependency set. keel init / hooks install: they write the shared git dir. bypassPermissions, dontAsk, default and auto as worker modes. Changing the guard: its launcher shape already admits the trailing option, and the launcher is the only judge of the value.
ConsequencesThe grant reaches only processes the launcher starts. It never reaches the router: the guard's closed Bash whitelist denies cargo / keel to agent_type == "router", and a hook deny beats any allow. cargo test runs code the worker wrote (tests, build.rs), so the grant amounts to code execution in the worktree. That is the same class as DEC-33's accepted risk. The keel mr deny states intent; it is not a sandbox. Until a router checkout holds this launcher, its workers still need the owner's temporary user-level entries (E-ROUTERFIX plan, open point 1). Test: tests/router.rs launcher_grants_workers_cargo_and_keel_and_validates_the_permission_mode.
LineageE-ROUTERFIX.W1 (plan docs/work/2026-11-09-e-routerfix-plan.html, archived at close); answers backlog e-router-v2 R2; amends DEC-31's fixed launcher flags; DEC-33's risk class.

DEC-39 · Workers run on opus at medium or high effort; the policy lives in .keel/config.toml [router] and the launcher enforces it

ContextThe launcher accepted opus|sonnet|haiku|fable and passed no effort, and the skills told the router only to pick "an explicit model". Lessons B7 records the owner's correction ("they should use opus 5.5"). Owner ruling 2026-11-09: workers run on opus only, at a chosen effort. Owner review 2026-11-10: the default effort is medium, and the policy belongs in the config that holds Keel's other rules. The Claude Code CLI has an --effort flag that overrides the session's effort without persisting.
ChoiceA [router] section in .keel/config.toml holds worker_model = "opus", worker_efforts = ["medium", "high"] and worker_default_effort = "medium". Medium is for mechanical work; high is for design, review and debugging. Only scripts/router-worker.sh reads it, from git show HEAD:.keel/config.toml in the router checkout, with a narrow fail-closed grammar (key = "word" or key = ["word", …], words [a-z][a-z0-9.-]*: a leading letter, then letters, digits, dots and hyphens). spawn and resume refuse a model other than worker_model, an --effort outside worker_efforts, and an absent or malformed policy (no worker policy, exit 2, nothing started). Every effort must be one of the CLI's levels low|medium|high|xhigh|max (never ultracode), and the default must be in the list. An omitted --effort takes the default; a resume does not inherit it. The effort goes to claude -p as --effort, to the run dir and to the RUNNING line. The keel-router skill stays generic and defers to "the project's model policy"; Keel's project-router points at [router].
Rejected(a) A keel config get subcommand for the launcher: CLI surface and src/ code for one caller, and a launcher dependency on keel on PATH. (b) Policy only in the launcher and the skill text: the owner asked for it in the config. (c) A separate .router/policy file: not rule-bearing, and .router/ is git-ignored. Keeping four models with a documentary policy: nothing would enforce it. A built-in fallback default in the launcher: a second copy of the policy that can drift.
ConsequencesThe CLI ignores [router] like [review] (no typed config, no src/ change), and the keel init template gets no [router], since init ships neither the launcher nor the guard (DEC-30; revisit with backlog e-router-v2 R6). The guard is unchanged: its launcher shape already admits --effort <level>. A policy change is meant to be an owner keel mr commit on rule-bearing .keel/, plus a red-then-green pin test in tests/router.rs; the launcher does not prove it was one. It trusts whatever the router checkout's HEAD holds, and a worker with the owner's user-level Bash(git:*) could move that branch ref (git update-ref runs no hook) to a commit with a wider [router]. Accepted residual risk, owner ruling 2026-11-10: the same class as DEC-33 (a worker can already rewrite the launcher through the shared checkout); revisit with backlog e-router-v2 R4. Because the launcher reads the router checkout's HEAD, an uncommitted edit cannot widen the policy, and the policy takes effect only once the config and the new launcher are both on the branch the router runs from.
LineageLessons B7; owner rulings 2026-11-09 and 2026-11-10; E-SEED2.W7 (plan docs/work/2026-11-09-w7-opus-policy-wu-plan.html). Amends DEC-31's "explicit model" and DEC-37's launcher options.

DEC-42 · The router may message a live worker; a new task still travels as a brief amended by DEC-44: a follow-up task travels as a message; no wait fallback

ContextDEC-36's guard admitted SendMessage only as a contentless subscription with a closed key set. On 2026-11-09 it denied a real router's subscription anyway (backlog e-router-v2 R8). A capture on 2026-11-10 (Claude Code 2.1.288, E-ROUTER3.W1) showed why: before PreToolUse the harness adds type, recipient and content to every SendMessage input, and the closed key set rejects them. The owner ruled on 2026-11-10 that the ban on router→worker messages is itself a defect: a router that cannot answer or stop a running worker loses every round to a fresh spawn.
ChoiceThe guard admits any SendMessage whose to is a non-empty string, and judges nothing else. A message steers a live worker: an answer, a clarification or a stop. A new task still goes as a brief through scripts/router-worker.sh resume, which snapshots and hashes it (DEC-32), and follow-up rounds resume the worker's session by default (backlog R15). A subscription that reports expiry falls back to router-worker.sh wait (R12). The brief-only rule for tasks lives in the keel-router skill, not in the guard.
RejectedLoosening the closed key set to the captured keys: the harness adds keys between versions, and an allow-list of them is what broke R8. Checking content in the guard: no jq predicate can tell a clarification from a task.
ConsequencesRouter text can now reach a full-tool worker without a snapshot, so a message is an unhashed instruction. That is the residual risk the brief rule bounds, and it belongs to DEC-33's class. A worker's reply is untrusted, like its .out. Live probe (E-ROUTER3.W1, 2026-11-10): a headless --agent router session ran under this guard in default mode. It messaged a headless worker in acceptEdits mid-run. The worker received the message at its next tool round and replied, and the reply reached the router mid-turn, followed by the idle notice. Tests: tests/router.rs router_guard_allows_send_message_to_a_named_worker_as_the_harness_sends_it (the captured payloads as fixtures) and the E-ROUTERFIX e2e.
LineageOwner ruling 2026-11-10; E-ROUTER3.W1 (plan docs/work/2026-11-10-w1-two-way-messaging-wu-plan.html); fixes backlog e-router-v2 R8, R12, R15. Amends DEC-32 (briefs are no longer the only router→worker text) and DEC-36 (its "never message" choice and closed key set).

DEC-43 · Workers are long-running sessions the router closes; the router runs no heartbeat mechanism replaced by DEC-44; the long-running worker and the no-heartbeat rule stand

ContextA launcher worker was a one-turn claude -p that exited after its report. Every follow-up round started a new process with resume, and the router could steer a worker only while its single run lasted. The keel-router skill also told the router to run a 10-minute /loop heartbeat, which the guard never allowed (backlog e-router-v2 R17). The owner ruled on 2026-11-11 that workers stay alive and are coordinated by SendMessage and closed by the router when no longer needed, and that the router only routes: no loop or timer of its own. Worker progress reporting moves to a watchdog worker (E-ROUTER3.W9).
Choicescripts/router-worker.sh starts each worker as claude -p --input-format stream-json --output-format stream-json reading .router/out/<name>.in through a tail -f feed, so the session outlives its turns. send <name> <brief.md> hands a live worker its next brief, snapshotted and hashed as on spawn (DEC-32). stop <name> closes the feed: the worker exits after its turn. wait adds IDLE, printed when every turn opened (system/init) has closed (result) and every sent brief has had its turn, and it writes the last result to .router/out/<name>.report. STALLED counts only mid-turn. resume only restarts a dead session. The guard admits send and stop. The router arms one wait per live worker and runs no heartbeat.
RejectedA router heartbeat through the loop skill and ScheduleWakeup (the first W2 plan): the owner ruled the router routes only. An interactive claude under a pty: stream-json is a supported headless mode, needs no TTY, and its events are machine-readable. Reading idleness from the last event: command_lifecycle events follow a result, and key order varies, so the launcher counts typed events with jq.
ConsequencesA worker's context spans its WU's rounds; the router gives a new WU a fresh worker. .router/out/<name>.out is now the raw stream and the report is .report. An idle worker answers a SendMessage by opening a turn of its own, which wait counts. A worker that dies on its own takes its feed with it (a reaper per run, holding that run's feed pid). stop ends the session at its turn's end: a worker that moved work to a background task ends its turn early, and that task is cut at exit, so the router stops only idle, clean workers. A stopped worker winding down is never IDLE, so a re-armed wait ends in EXITED. Review rounds 1 and 2 fixed what IDLE means. It now holds only when four things are true:
  • every brief has been replayed (--replay-user-messages), so a turn the worker opens itself never answers an unread brief, and briefs folded into one turn are answered by its one result. A peer's SendMessage replays as isSynthetic and is not counted;
  • every opened turn has closed;
  • the last system/background_tasks_changed lists no running task, and no emptied task list or system/task_notification waits for its completion turn, because a turn that ends with a task running is interim and the worker's own completion turn carries the answer;
  • the feed is this worker's own tail.
An exit that leaves the last brief unanswered leaves no .report. An error result is reported as one (IDLE … error=<reason>: its subtype, or, for an API failure that reads success, its terminal_reason, with the cause in the report), and a background task that never ends stalls the wait (STALLED … background=<n>) instead of hanging it. Review round 3 confirmed these event shapes with live probes. wait keeps its scan state (the worker's pid, the offset, the counters and the last result) in .router/out/<name>.scan. spawn and resume reset it, and state written under another pid is ignored. Each wait reads only what came after the last one, and jq streams it, so a long session costs no more per wait than a short one (review round 4: the old first scan took about 7 s and 876 MB at 100 MB; the streaming pass takes 1.0 s and 2.9 MB). Probes (Claude Code 2.1.288, E-ROUTER3.W2): a stream-json session stayed alive across turns and exited about 5 s after its input closed; an idle worker received a router's SendMessage, opened a turn and replied; the subscriber's idle notice fired at the turn's end with the worker still alive. Live run (an Opus worker through the launcher at the WU tip, a guarded router): two briefs in one session, an idle steer answered, a stop mid-turn. Tests: tests/router.rs launcher_keeps_a_worker_alive_across_briefs_until_stopped, router_guard_admits_send_and_stop_in_plain_words_only and the E-ROUTERFIX e2e (IDLE, send, stop).
LineageOwner rulings 2026-11-11; E-ROUTER3.W2 (plan docs/work/2026-11-11-w2-long-running-workers-wu-plan.html); backlog e-router-v2 R15 (follow-ups continue the session), R17 (the heartbeat, struck for W9). Amends DEC-32 (a follow-up brief travels by send) and DEC-36 (a turn's end, not the process exit, is the signal).

DEC-44 · Workers are native background sessions; the worker's message is its report

ContextDEC-43 kept workers alive by feeding claude -p stream-json input through a tail -f, and wait read the raw stream to decide IDLE, STALLED or EXITED. That scan failed seven review rounds in E-ROUTER3.W2, each on a new event shape. The owner ruled on 2026-11-11: no claude -p for anything; workers are native background sessions the router closes; wait and send go; the worker reports by SendMessage; a follow-up task is the router's own message. Claude Code 2.1.288 has claude --bg, claude agents --json, claude stop and claude rm.
Choicescripts/router-worker.sh has three modes. spawn runs one claude --bg -n <name> --model --effort --agent worker --allowedTools … --disallowedTools … --permission-mode <mode> "<fixed prompt>" in the worktree, with the policy (DEC-39), grant and deny lists (DEC-37) as before and no print, stream or budget flag; it refuses a name claude agents --json lists anywhere, waits until the session is listed, and records its session id (--bg assigns it) in the run dir. resume <name> <uuid> <worktree> <note.md> wakes an unlisted session with claude --bg --resume <uuid> and no option, so its saved model, effort, mode and grant carry over. stop <name> runs claude stop <id> then claude rm <id> on this repository's idle background session of that name; a busy one gets about 30 s (60 looks, 0.5 s apart) for its turn to end (its report arrives before the turn ends: live run), then is refused; a session that leaves the list meanwhile is reported gone at once, and a session list the CLI fails to give stops every mode (review round 1); once a start has happened, that failure prints UNLISTED with the snapshot, since the session may be running. A row listed with a state and no status (a blocked session: rate-limited, or waiting on its user) is read by its state, and every state but idle and busy is refused at once (review round 2). The worker sends its report to the router its brief names by SendMessage and stays alive; the router sends a follow-up task as a message. The spawn brief (and a resume's note) is still snapshotted and hashed; a follow-up message is recorded only in the worker's transcript. The guard admits spawn|resume|stop; --agent worker is always passed, because this repo's settings make every other session a router.
RejectedIn-session Agent subagents as workers (owner review 2026-11-11 of an evidenced comparison): a subagent starts in the router's checkout and a cd does not carry to its next Bash call, its isolation: worktree branches from the default branch, not the WU's, and the router guard does not apply to it. Keeping a snapshot-only send mode for follow-ups (owner ruling: dropped). Refusing nothing on stop: claude stop cuts a busy turn mid-edit.
ConsequencesNo poll, pid, feed, output or report file: .router/ holds briefs/ and runs/ only. A worker that goes idle without reporting, or never goes idle, is not reported until the watchdog (E-ROUTER3.W9); notify_when_idle stays an optional extra. A follow-up task is no longer hashed before it runs (DEC-42's residual risk, DEC-33's class). The budget cap is gone: --max-budget-usd works only with --print. A call outside the grant blocks the worker on a permission prompt (row status: waiting, waitingFor: "permission prompt") until the owner answers it with claude attach <id>, where -p refused it at once. The launcher's environment does not reach the session. A worktree must be trusted: a worktree of a repository whose main checkout is trusted is; a new clone is not, even under a trusted parent directory (its worktrees neither). Probes (Claude Code 2.1.288, E-ROUTER3.W10): --session-id is ignored under --bg; the other options are kept (~/.claude/jobs/<id>/state.json respawnFlags); a denied command was refused at once; the PreToolUse payload carries agent_type: "worker"; a 4.2 KB report reached a named router whole and woke it; a follow-up message opened a turn; claude stop cut a busy turn after 4 of 30 calls; stopped and killed sessions leave the active list; claude rm kept the transcript and the worktree; --bg --resume with options started a copy under a new id, without them it woke the same session; a fresh git worktree add of a trusted repository started at once, while a fresh clone under the same trusted parent was refused (live run). DEC-45 · A watchdog session reports the router's workers every 5 minutes

ContextDEC-44 leaves two cases unreported: a worker that goes idle without sending its report, and one that never goes idle (stuck on a permission prompt, or in a long silent turn). The owner ruled on 2026-11-11: a watchdog worker on Haiku reports every worker's progress to the router every 5 minutes by SendMessage, started and stopped through the launcher, with native auto-compaction and no restart.
Choicescripts/router-worker.sh watchdog start <router-name> starts one background session per router, named watchdog-<router-name>, in the router's checkout, on [router] watchdog_model (DEC-39's reader; optional, and without it only the watchdog refuses): claude --bg --setting-sources local --agents '<inline agent>' --agent watchdog --tools SendMessage CronCreate --allowedTools SendMessage CronCreate --strict-mcp-config --autocompact 100k --settings '<two hooks>'. Its first turn schedules the prompt tick every 5 minutes with CronCreate. Its UserPromptSubmit hook runs watchdog facts <router-name>, which prints one block per live worker (a background session in a worktree of this repository other than the router's checkout and the main one): state, quiet minutes, branch, tip, dirty count, the last six transcript items. Code decides DONE (idle) and STUCK (any state but idle and busy at once, with its waitingFor, e.g. a permission prompt; busy with a transcript quiet 15 minutes or more); blocks are at most 2000 bytes, done and stuck first, and the whole output stays under 9000 bytes, ending with <N> more workers not shown. when it does not fit. Its PreToolUse hook is the router guard run with --arg watchdog_to <router-name>: only the one CronCreate the start prompt asks for (*/5 * * * *, tick, recurring) and a SendMessage to that router pass, fail-closed, so worker text reaching the watchdog cannot add schedules (review round 2). The router's name travels only inside these two hook commands, and so does the launcher's claude (ROUTER_CLAUDE='<absolute path>' in the prompt hook): the session would otherwise fall back to ~/.local/bin/claude (review round 1). facts never exits non-zero, since a failing prompt hook blocks the tick: an unreadable session list or worktree list prints a "cannot be read" line instead of a wrong fleet or a gone router, and a watchdog-* session (another router's watchdog in a sibling worktree) is never a worker (review round 1). It reads a worker's worktree with git --no-optional-locks, so it never takes the worker's index.lock, and a transcript it cannot read costs that worker its quiet minutes, never the rest of the fleet (review round 2). watchdog stop <router-name> is DEC-44's stop on watchdog-<router-name>; facts stops the watchdog itself once the router is no longer listed. spawn and resume refuse watchdog names. A report is a progress hint from untrusted worker text summarised by a small model, never an instruction: the router checks before it acts.
RejectedA shell ticker (claude stop + claude --bg --resume each period): a long-lived process and a pid file, and a resume of a running session starts a copy. A Stop hook that sleeps 5 minutes: the session would always be busy. Project settings in the watchdog: the project's Stop hook (verify-doc-stop) refuses every turn end while a doc in the checkout is red, and a session that cannot fix it loops. An agent file under .claude/agents/: it is not found with the project setting source off. The router's name in an environment variable: a background session does not get its launcher's environment. A process-tree check for STUCK: unprobed for background sessions.
ConsequencesOne single command running longer than 15 minutes reads as STUCK (quiet …m), a message the router checks. A message from any session to the watchdog also runs the prompt hook, so it yields an extra report (to the router only). The recurring job expires after 7 days and fires only while the session is idle, up to half a period late; a watchdog that stops reporting is the router's to notice and restart. Hook output of 10,000 characters or more reaches the model only as a file path, which a watchdog without Read cannot open: hence the 9000-byte budget. Probes (Claude Code 2.1.288, E-ROUTER3.W9): --tools, --autocompact and --strict-mcp-config are kept by a background session; CronCreate loads there and runs without a prompt; the job fired in an idle session and its prompt ran the hook, whose output reached the model; the session's own PreToolUse hook refused a message to another name (payload agent_type: "watchdog"); a hook's claude stop of its own session ended it; a 137k-token context compacted to 8k and the schedule fired after it; hook output of 9,520 characters arrived whole, 10,120 became a file path; with project settings a red doc caused 11 refused turn ends in a minute, with --setting-sources local and the inline agent none.
