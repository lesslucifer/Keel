Why pull_request_target holds

  • No job holds a write token or a secret: contents: read everywhere, no secrets., no token passed, persist-credentials: false, pinned actions, event values through env: only. The lock test pins each.
  • Every checkout is github.sha, main's commit; the head is git data in scratch worktrees. Only keel/ci runs it, and that verdict is the head's own tests.
  • What head code in keel/ci could still take is the run's runtime token. With it, it could write the run's artifacts or a cache scoped to main. The keel artifact is refused unless its SHA-256 equals build's job output, which no other job can change. No workflow reads a cache, and the lock test keeps it so for every file in .github/workflows.
  • A fork's pull request runs nothing of its own: the script refuses it before any git call, in every job.
  • A pull request retargeted to another level (a WU into main) is red in every job of its own run: the workflow runs on edited and the script refuses any base but the head's own. pr-open and the guard refuse a WU into main. But a check belongs to the commit, not the pull request. A second pull request with the same head into its own epic makes the same head's required checks green again. Any of its edited or synchronize events does it, the bot's pr-open refresh included. So does a re-run of an older run. Residual, below; your approval is the backstop.
  • The required names are new, so no workflow a branch carries from before W4 can report them. One added by a head could; the bot cannot push one, and the ruleset requires your approval as code owner.
  • Residual, checks per commit: the WU-into-main pull request above. Its checks can go green from the WU's own pull request into its epic. Required checks alone do not stop it. Your code-owner approval does, since it is given per pull request: never approve a wu/ pull request into main.
  • Residual, from before W4: an old release.yml still runs on a pull request in two cases. The pull request's base still holds the old file, or the head edits it, which only you can push. It holds contents: write. If the head's dist-workspace.toml sets pr-run-mode = "upload", it builds head code with that token. That code can forge refs/notes/*, which keel/gate reads. It cannot move a protected branch, set keel/sign-off, or merge without your approval. So W4 must be back-merged into every live epic before step 6: today only E-GHFLOW2, which carries it. Open point 2.
  • A second reason to back-merge W4 into every live epic: GitHub reads CODEOWNERS from each pull request's base branch. An epic without .github/CODEOWNERS has no code owner, so no code-owner approval is required there. gh-settings-check.sh reads the default branch's file only.
