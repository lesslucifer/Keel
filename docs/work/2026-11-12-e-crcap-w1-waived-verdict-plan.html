The design

The writer

CallResult
keel notes write cr --verdict WAIVED --reason "<reason>" [--blockers n] [--importants n] [--target R]cr/v1 note: verdict: "WAIVED", waiver: "<reason, trimmed>", blockers/importants = the findings left open (default 0), code_diff_hash exactly as a review's. Older readers ignore the new field; an older keel reads WAIVED as "not PASS" and stays red (fails safe)
--verdict WAIVED with no --reason, or a blank onerefused, nothing written
--verdict PASS|FAIL --reason …refused: a reason belongs to a waiver only
Anything elseas today; the usage line names WAIVED

Open point 15: the open findings' texts ride the note as an extra field the gate ignores, open_findings: [{"severity": "blocker|important", "finding": "<summary>"}], added by the skill's jq step exactly as nits are. W1 fixes the field name and prints it at sign-off; W2's cap fills it. The cap reason review cap: 5 rounds, <n> blockers open is an ordinary reason to this writer: W1 needs no cap-specific code.

The merge check

WhereChange

Checks 4 and 5Unchanged: a WAIVED note is bound to its base and to the code diff hash like a review, so a code commit after the waiver leaves the new tip with no note, and a note carried onto it fails 5·diff-binding

The sign-off

flowchart TD
  C["keel mr confirm wu|epic tip"] --> S{"checks 1-7 green?"}
  S -->|no| X["refused: sign last"]
  S -->|yes| R{"roster, roster change"}
  R --> W{"cr note on tip is WAIVED?"}
  W -->|no| G["sign exactly as today"]
  W -->|yes| P["print the waiver, open findings, review history"]
  P --> F{"--accept-waiver?"}
  F -->|no| Y["refused, nothing written"]
  F -->|yes| H["mr/v1 + waiver_hash; key tier signs the extra line"]
The waiver is shown after every other refusal that could stop the sign-off, so the owner is asked once, at the right moment.
PieceRule
What is printedThe waiver reason, the open counts, each open_findings entry when recorded, and the review history: every cr note on a first-parent commit of base..tip, newest first, one line each (short sha, verdict, blockers, importants, and the reason on a WAIVED one). W2 adds round, scope and fix-PASS to these lines
The flag--accept-waiver, no value. Without it on a waived tip: refused with a fix -> line, nothing written. On a tip with no waiver it is ignored, as --roster-change is
The notemr/v1 gains waiver_hash: "sha256:<hex of the reason's bytes>", present only on an accepted waiver. This is what binds an identity-tier sign-off, which has no signature
The signed text (key tier)The keel-mr/v2 payload gains a last line review: WAIVED sha256:<hex> on a waived tip only. With no waiver the bytes are exactly today's, so every existing signature stays valid. The header stays v2: the line appears only where no older signature can exist
Check 8Rebuilds the waiver hash from the tip's current cr note and compares it with the note's waiver_hash before any signature check: reworded (hashes differ), a signed PASS later turned into a waiver (current has one, note has none), or a signed waiver later turned into something else (note has one, current has none) are each red with their own cause. A key-backed signature is then verified over the payload rebuilt with the current line

Who writes the waiver (router input, owner feedback 2026-11-12)

Today a waived review needs a review session to write a PASS it never reviewed. W1 removes the lie whatever the option: the note says WAIVED. What remains open is whose act records it.

OptionHowCosts
(a) An agent records the owner's ruling; the owner accepts at sign-off — recommended, built hereThe WU's own session (on the router's relay of the ruling, quoted as the reason) runs keel notes write cr --verdict WAIVED --reason "…". No review session is spawned: the session judges nothing, it records. The owner's own act is keel mr confirm … --accept-waiver, which shows the reason and signs its hashThe reason text is typed by an agent. Bounded: nothing merges until the owner reads it at sign-off and accepts it explicitly, and an agent that writes WAIVED without a ruling only reaches that same question. Inside the epic contract
(b) The owner's sign-off writes itkeel mr confirm … --waive-review "<reason>" writes the WAIVED cr note, then signs with the acceptance impliedA sign-off then writes a cr note too (two note kinds, one command). The sign-last check must accept a tip with no cr note or a FAIL one, for check 3 only, a new path through the gate. The cap (W2) still needs (a)'s writer, so the surface doubles. Widens W1 beyond the epic contract, which lists "a new owner command for any step" as out of scope
(c) Both(a) for the cap and relayed rulings, (b) for the owner's direct waiverThe sum of both; two ways to reach one record

Recommendation: (a). It already removes the review session from the waiver path and the false PASS from the record, and the owner's yes is the act that lets the work merge. (b) saves the owner one relayed step at the cost of a second writer and a new gate path; if the owner wants it, it is a small follow-up on top of W1 (open point 1 below), not built here without that go.

Expected

  • A waiver without a reason, or a reason on PASS or FAIL, is refused and writes nothing.
  • With one, keel verify-dod wu prints WAIVED 3·review: <reason> and is red only on 8·manual-review; a code commit after the waiver leaves no valid review on the new tip, and a note carried onto it is red on 5·diff-binding.
  • keel mr confirm on a waived tip prints the reason, the open findings and the review history, and without --accept-waiver refuses and writes nothing; with it, it signs and the merge check is green, its receipt saying review: WAIVED.
  • After signing, rewording the waiver, or turning a signed PASS into a waiver, is red on 8·manual-review in both identity and key tiers.
  • A tip with no waiver signs byte-for-byte as today: a note written with today's payload still verifies.
  • The epic walk passes a waived WU and prints it; an epic's own review can be waived.
  • skills/ and .claude/skills/ stay byte-identical, staged for the owner's commit.
