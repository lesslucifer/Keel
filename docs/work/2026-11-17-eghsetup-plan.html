E-GHSETUP · Set the GitHub flow up in any project

Today only Keel's own repository has the GitHub flow, set up by hand. After this epic, keel sets it up in any project, with two clicks in a browser.

Ready v2 · 2026-11-17 · T3 · epic plan · Keel · off main 6cf3127 · carries backlog github-flow G10 (open steps, live facts), parts of G4 and G5

The problem

The GitHub flow (GitHub runs the checks, a bot pushes work, you sign by approving, GitHub merges) works only in Keel's own repository. It took you a page of web steps and two loose scripts, and still hit a refused push. Another project gets nothing: its checks would build Keel from source, and the scripts live only in Keel. This epic makes keel set the flow up in any project, as automatically as GitHub allows.

Example: a new project

  1. You run the setup in your project. It says jq is missing. You install it and run again.
  2. A browser page opens. You click "Create GitHub App", then "Install".
  3. The setup writes the files and prints your one commit.
  4. You commit and push. The setup applies the settings and prints green.

W3 · keel writes the project's GitHub files

In short: keel carries the workflows, CODEOWNERS and the scripts, and writes them into a project. Its checks install a released keel at a pinned version instead of building Keel's source.

  • Embedded like the skills, with lock entries, so an upgrade replaces only unedited files.
  • A workflow downloads the keel version named in the base's committed config and checks its SHA-256 before running it. Keel's own repository keeps building from the base.
  • The printable-ASCII guard covers every workflow (G10, W4's residual). Pages ships only when chosen.

W4 · The App in two clicks

In short: keel opens a one-time local page that sends GitHub the App's description. You click "Create" and "Install". keel stores the key and reads the ids from GitHub.

  • GitHub's manifest flow: a page posts the manifest; GitHub returns a one-hour code; keel trades it for the App id, slug and key (POST /app-manifests/{code}/conversions).
  • The key goes to ~/.config/keel/router-gh/, mode 0600, under the rules router-gh.sh checks. keel reads the installation id with the App's own token, never from the redirect.
  • A second project reuses the App: one click adds the repository. router-gh.sh learns which installation serves which repository.
  • Takes G5's router_gh.rs nits.

Your brief: "the GitHub App stays required; automate everything around it" · UC-INIT-2 · DEC-61 amended.

Integration: against a fake GitHub, the flow stores a 0600 key and the three ids; a wrong mode, a second link or an expired code is refused; a second repository reuses the key. Unit: the manifest and the id parsing.

Details

Acceptance

  • In a fresh repository, one command lists any missing tool before changing anything.
  • The App is made and installed with two clicks; the key is stored mode 0600 and never printed.
  • The workflows, CODEOWNERS, scripts, [github] and the roster line are written; your one commit lands them.
  • The settings are applied in GitHub's order. The check prints SETTINGS green with no hand-checked line left.
  • A rerun on a set-up repository writes nothing.
  • The bot's first push of a new epic branch is accepted (do_not_enforce_on_create).
  • An epic's plan and close reach it by pull request and pass the epic gate.
  • The epic test passes.

Use cases

  • UC-INIT-2, new: keel sets the GitHub flow up in a project (W3 – W6).
  • UC-GATE-7 and UC-MR-3, amended: an epic's plan and close come in by pull request (W2).

Out of scope

  • A GitHub flow without an App, GitHub Enterprise Server, other forges.
  • Changing what the gate or the sign-off judges. G7's walk-waiver item stays in the backlog.
  • Claude reviews inside Actions; G4's range walk on main.
  • Any change to the /keel commands (open point 7).
  • The docs split (E-DOCSPLIT).

  • GitHub's manifest flow (docs, read 2026-11-17): a browser form posts the manifest; the code lasts one hour; the conversion returns the id and the key. Installing is a separate step. The setup page's installation_id may be spoofed, so keel reads it from the API. Whether GitHub takes a localhost redirect is W1's to confirm.
