E-SEED2.W8 · Worker watchdog with Telegram push

A headless watchdog worker polls the other running workers and messages the owner on Telegram when one finishes or stalls, so the router no longer has to be asked.

T3 · WU plan · 2026-11-09 · Keel · branch wu/E-SEED2/w8-worker-watchdog off epic/E-SEED2 2183539 · epic plan E-SEED2 W8 · scope flagged

Scope flag. This is router/meta-tooling. It properly belongs with E-ROUTER's backlog (e-router-v2.html), not an E-SEED product feature. The owner asked for it under E-SEED2 explicitly; it proceeds here and a cross-reference row goes into the E-ROUTER v2 backlog at distillation.

Requirement

scripts/router-watch.sh, given the router's .router/out directory, one or more worker names and a stall threshold, blocks until the first watched worker finishes (its pid is gone or a zombie) or stalls (its session transcript has not changed for longer than the threshold), prints exactly one event line naming the worker, and exits 0; a watchdog worker running it in a re-armed background loop sends one Telegram message to the owner per event.

Maps to

Epic E-SEED2.W8 · UC-ROUTE (new behaviour: proactive worker status; use-cases/router.html) · generalises the keel-router skill's existing "watch worker" pattern (one background until <probe>; do sleep N; done; echo <EVENT>) from owner actions to workers.

Design

sequenceDiagram
  participant R as Router
  participant L as router-worker.sh
  participant W as Watchdog worker (opus, medium)
  participant S as router-watch.sh
  participant T as Telegram reply tool
  R->>L: spawn e-seed2-watchdog (brief: names, chat id, out dir)
  L->>W: claude -p
  loop until every watched worker has finished
    W->>S: background Bash: router-watch.sh OUT names… --stall-min 15
    S-->>W: FINISHED name=… | STALLED name=… idle=…m
    W->>T: reply(chat_id, "<event> + last 5 lines of .out")
    W->>W: drop finished name (stalled: mark, keep watching), re-arm
  end
  W-->>R: final report (.router/out/e-seed2-watchdog.out)
The shell loop does the polling, so the model only wakes on an event.
PieceChoice
Finished probeSame predicate as the launcher's one-live-run check: <name>.pid read, ps -o stat=,command= -p $pid not a zombie and its command contains -n <name> ; otherwise finished.
Stall probeNot .out: claude -p with text output writes .out only at exit, so its mtime never moves while the worker runs. The session transcript does, on every turn: ~/.claude/projects/<worktree path with / → ->/<session>.jsonl, with the session id from the newest .router/runs/<name>-*/session and the worktree from its worktree file. Idle longer than --stall-min (default 15) ⇒ STALLED. Missing transcript ⇒ fall back to the newest mtime under the worktree.
PushThe Telegram channel plugin's reply tool, available in headless workers (it is loaded in this worker's own session). The watchdog never reads the bot token or access files (project-router "Never touch").
PathsA worker may only read its own worktree, so the out dir is an explicit argument to the script (absolute path to the router checkout's .router/out), never derived from $0.
Modelopus, medium effort (W7 ruling); the shell loop keeps token use near zero between events.

Expected result

  • With a fake worker (a sh -c 'sleep 60' -n fake-shaped process whose pid is in fake.pid), killing it makes router-watch.sh OUT fake print FINISHED name=fake within one poll interval and exit 0.
  • With a live fake worker and a transcript file older than the threshold, it prints STALLED name=fake idle=<m>m once and exits 0.
  • With two names, the first event wins and names only that worker.
  • Bad name, missing out dir, or non-numeric threshold ⇒ exit 2 with a message, before any polling.
  • A real run: the watchdog worker watching two headless workers sends one Telegram message per event and its final report lists every event it sent.
  • keel-router worker-ops.md "Watch" section and project-router "Workers" describe the watchdog; a struck cross-reference row exists in e-router-v2.html.

Test plan

LevelWhat
UnitThe script is a single shell file with no callable seam below the process boundary; its probes are exercised one per test at the integration level, which is the smallest level that can run them. Named waiver: no separate unit layer, for that reason.
Integrationtests/router.rs (the existing launcher test file; the cr gate covers it): temp dir as out dir, fake worker process, short poll interval via an env override (ROUTER_WATCH_POLL, seconds) and a fixture transcript with a set mtime. Cases: finished, zombie counted as finished, stalled, transcript missing ⇒ worktree-mtime fallback, first-of-two wins, each argument refusal. Deterministic: no real claude, no network, every sleep bounded.
E2EOne recorded real run (router spawns the watchdog plus two short workers; owner confirms receipt of the Telegram messages). Not hermetic — Telegram and real sessions — so recorded as WU evidence and waived as an automated layer for that reason.

Open points

#PointWhat was decided here
1Scope: router/meta-tooling, properly E-ROUTER v2 backlog, not an E-SEED product feature.Tracked here by explicit owner request; cross-reference row in e-router-v2.html at distillation.
2Push channel: native cross-session tools the router tried (ScheduleWakeup, ListAgents) are not available in this environment.Telegram channel reply tool is the only real push channel: the watchdog polls, then messages the owner directly on finish or stall.
3Telegram chat_id.The owner (or router) puts it in the watchdog's brief; the watchdog never reads the plugin's access files to find it.
4Several sessions loading the Telegram plugin at once may contend for inbound polling.The watchdog only sends; it ignores inbound messages. If sends fail under contention, it records the event in its report and the router relays.
5Stall signal.Transcript mtime, threshold 15 min default (.out cannot signal a stall, see Design). On STALLED the watchdog reports and keeps watching that worker; it never kills or resumes it — that stays the router's call.
6Where the watchdog runs.Spawned through the existing launcher into any non-router worktree (e.g. this WU's); no new launcher mode. If read access to the router's .router/out or ~/.claude/projects is refused in a headless session (see R2 in the E-ROUTER v2 backlog: unverified permission stalls), add an --add-dir to the launcher for the watchdog only — decided in the WU, recorded in its result.
7Stop condition.Exit when every watched worker has finished; a hard ceiling from --max-budget-usd 25 applies anyway.
