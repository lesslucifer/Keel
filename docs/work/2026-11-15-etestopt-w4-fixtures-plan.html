E-TESTOPT.W4 · Fixtures built once, copied per test

The scratch repos that many tests build the same way are built once per run and copied into each test with plain file copies, so fewer git and keel processes start.

The problem

A test run starts about 29,500 git processes (counted per test on 5d2ab18, below). Starting a process is the run's main cost, and it gets dearer when many run at once. Many tests begin by building the same scratch repo from nothing: git init, config, keel mr setup, a commit, keel hooks install, branches, more commits. That setup is repeated in every test that needs it.

What the profile says

Each test was run alone through a git shim that logs every git process and who started it, with each fixture builder marked. 88 % of git processes come from keel and the hooks, 12 % from the test code itself. Fixture setup is 4,865 of 29,524 (16 %). Four builders hold 94 % of it: verify_dod's (1,824), close_walk's (1,204), mr's (1,022) and router's launcher and watcher (515). The other builders (cli, init, verify_doc, seed3_e2e) hold 300 together and stay as they are.

The work

The fixtures of verify_dod, mr, close_walk and router are each built once per run as a template and copied into each test with std::fs, each copy independent of the template and of every other copy, with every test and assertion kept.

Epic E-TESTOPT, its W4 block and open points 4 and 7 · testing charter: each test owns its state and runs in parallel.

The suite's git processes per run fall by about the fixture share of the four converted files (recipe step 5); cargo test passes the 350 tests from before plus this WU's new ones, with 0 failures; recipe steps 2, 3 and 5 before and after are in the result, with load.

  • tests/common/mod.rs: fixture(key, build) and fixture_parts(key, parts, build). The first call for a key builds its template in a directory of its own (OnceLock per key); every call returns a fresh copy. copy_tree copies directories (empty ones too), files with their modes, and links as links.
  • Absolute paths: any file or link in the copy that names the template gets the copy's path instead, in both the written and the resolved form (/var/… and /private/var/… on macOS). That covers core.hooksPath, a remote's URL, a linked worktree's gitdir files and keel.signingkey.
  • The four files' builders build into the template; their signatures stay, so no test body changes.

Test plan

  • Integration, one per converted file, each shape: two copies and the template. No file of a copy names the template; core.hooksPath is the copy's own; a commit in one copy reaches neither the other nor the template. close_walk: the copy's origin is its own remote copy, and a push from it reaches no other remote. mr: keel.signingkey names the copy's key, still mode 600. router: the worktree list names the copy's three checkouts, and the watcher's origin is its own. A generic shape in tests/suite/fixtures.rs holds hooks, a worktree and a remote at once.
  • Unit (tests/suite/fixtures.rs): the copy keeps an empty directory, an executable hook, a 600 key, a directory's mode, relative, absolute and dangling links; a rewritten file keeps its mode; the byte rewrite; the resolved form first; the sweep removes only old template directories.
  • Red first, by mutants of the helper: no rewrite; a rewritten file's mode dropped; empty directories dropped; links followed; directory modes dropped; the resolved form not rewritten. Each must turn a test red.
  • No test lost: the passed count before (98 + 252) and after; no test body changed.
  • Observable: recipe steps 2 (cargo test --no-fail-fast, stock and CLT git), 3 (nextest -j 8 and -j 14, wall and kernel time) and 5 (git processes per test), before and after, twice each, load recorded.
