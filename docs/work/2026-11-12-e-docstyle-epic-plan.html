The problem

You found the first E-CRCAP epic plan hard to understand. Its rewrite, with the same facts, was much better. Today nothing tells an agent to write the second way. The plan skill lists the sections a plan must contain, and agents write them in that order: commands, ids and check numbers start in the first paragraph. In the first E-CRCAP plan, the part above the work list held 48 code snippets and about 40 internal ids. In the rewrite it held 5 and about 4. This epic writes down what made the rewrite better, as a skill every agent loads before it writes a doc you read. The tool then checks the two parts a tool can check.

The rules the skill will teach

These come from comparing the two versions line by line (the evidence is under Details). Your comments here change what the skill says.

  1. A doc has two readers. You read the top. The agent that does the work reads the details. Write the top for you and the details for the agent.
  2. Start with the problem. Say what goes wrong today, with a real case, then in one sentence what the work changes. Do not open with the solution or the mechanism.
  3. Say what changes for you. A table with one row per situation you meet: today, and after.
  4. Draw the flow once, in plain words. Every diagram label in quotes, with no code in it.
  5. Use few terms, and define each one. A short "Terms" table, or a definition where the term first appears. Above the work list, say what an id or check means ("fails only on the missing sign-off") instead of naming it ("red on 8·manual-review").
  6. One idea per paragraph, row or list item. Short sentences help, but the evidence shows they were not what made the difference.
  7. Each piece of work: "In short", then mechanics. Two or three plain sentences, then a list with one fact per item.
  8. Open points are questions. Each one is a question you can answer, with the recommendation first and the options after. Say once that the recommendation is the default.
  9. Reference material goes last, under "Details". Acceptance criteria, contracts, scope limits, research, design choices, tests, and where the knowledge goes. The checklist tags go wherever the reader needs them. The order of the tags is not the order of the doc.
  10. History goes last too. What a doc replaces, and how it was researched, come after everything else.
  11. Check before marking it ready. Read the first screen as the owner. Can you say the problem, what changes for you, and what you must decide, without reading any code?

W2 · The doc check tests what it can

In short: the doc check refuses a diagram label that is not in quotes, in any finished doc. It also refuses an epic plan that does not say what changes for you. Everything else in the rules stays judgment, yours and the author's.

Mechanics:

  • Diagram labels. In every non-draft doc, governed or not (as links are checked today), each <pre class="mermaid"> flowchart has every node label and every edge label in double quotes. The error names the label and its line. Other Mermaid diagram kinds are skipped, and the skill says so.
  • What changes for you. The epic plan checklist gains one item, owner-changes (working name). An epic that changes nothing for the owner says so in that section, as an epic with no use cases already does.
  • keel-plan §3 and §4 list the new item and the label check; the writing skill's rules 3 and 4 point at them.
  • A ready epic plan written before this lands goes red when its branch merges main, until it adds the one tag (open point 7).
  • Rule-bearing: the keel-plan and writing-skill text and their mirrors, in one owner keel mr commit.
  • Not reviewed by any gate: that text and the WU docs. The code review covers src/verify_doc.rs and tests/.

Epic end-to-end test

epic_e2e_a_new_project_gets_the_writing_skill_and_its_doc_hooks_hold_a_plan_to_it in tests/verify_doc.rs, added by W2. It builds a scratch repo in a temp dir, runs keel init there, and needs no network.

  1. keel init writes the writing skill and its example, and the AGENTS.md it writes names the skill.
  2. The installed example is copied into docs/work/ as a plan. The installed after-write hook, fed a write event for it, exits 0.
  3. One diagram label is made unquoted, with a "|" in it. The after-write hook exits 2 and names the label.
  4. The label is fixed and the "what changes for you" tag is removed. The end-of-turn hook exits 2 and names the missing item.
  5. The tag is put back. The end-of-turn hook exits 0.

No test layer is waived. If you choose "rules only" (open point 4), W2 is dropped and W1 adds a shorter version: steps 1 and 2.
