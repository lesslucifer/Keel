E-DSH · The same rules on DeepSeek Harness

Keel's rulebook reaches an agent through the files it writes for one host. This epic plants one skill root that every host reads, gives DeepSeek Harness the same rules beside Claude Code, and runs the doc check when a doc is written, not two steps later.

T3 · epic plan · 2026-11-13 · epic/E-DSH · owner review rounds 1–3, 2026-11-14

The problem

Keel's rules reach an agent only through the files it writes for one host. In a DeepSeek Harness (DSH) session on a Keel project an agent sees no skills, no doc check, no worker recipe: the rulebook is silent. This epic plants one skill root every host reads, puts the same rules in front of a DSH agent beside Claude Code, and runs the doc check right after a doc is written.

A plan written in a DSH session

  1. A worker in a DSH session writes a plan doc and misses one item.
  2. Claude Code's hook fails the write; DSH has no hook at all.
  3. The DSH doc-gate plugin runs the check on that write, feeds the missing item back, and the turn does not close on a broken doc.
  4. The worker fixes it in the same turn; notes, review, sign-off and merge run as today.

W1 · One shared skill root

In short: init plants a relative link at .agents/skills pointing at .claude/skills, so the host that reads .agents and the host that reads .claude read the same files. One copy, no drift. The hand-off names the three DSH plugins.

  • Init creates .agents/ and the link skills -> ../.claude/skills; a real .agents/skills directory, or a different link, is kept and reported, never replaced.
  • A second run changes nothing, and the relative link survives git worktree add.
  • The link is the only sharing step: init does not render or copy a per-host variant; the six skills are the same bytes for every host.
  • The hand-off prints the three profile install lines — Auto Review, worker sessions, doc gate — and says a plugin lives in the DSH profile, never in the project.
  • The test that asserted "init creates no .agents" flips to assert the link and its target.

W2 · The doc check runs at the write

In short: on a host with no shell hooks a plugin runs the doc check right after a doc is written, fails that write's result with the problems, and keeps the turn open until the doc is green. A review or a merge is too late.

  • Contract: after every first-party write/edit under the docs root the plugin runs keel verify-doc <path> on tools/post-execute; a red doc turns that call into a failed result carrying the problem lines, though the file has already landed. At turn end agent/turn-stopping runs keel verify-doc over all docs and steers the problems back, so the turn takes another step instead of closing. Exit 0 is silent; a draft is silent by construction.
  • The standard says so: the workflow skill's hook table gains the no-hook row and the no-substitute rule, and the plan skill stops naming one host as the trigger.
  • The plugin's code lives in its own repo in the desktop-dsh project, beside Auto Review and the worker sessions; this repo carries the contract and the install line.

W3 · The DSH router's worker recipe

In short: the router skill learns the DSH transport, report and persona rules, and the project template gains the slots a project fills in. Claude Code's recipe stays as it is.

  • One table in keel-router/SKILL.md maps each mechanism — dispatch, follow-up, report, fleet list, status, stop, permissions — one row per mechanism, one column per host; the DSH cells name worker_spawn, worker_send, worker_output, worker_list, worker_status, worker_stop.
  • The table is dated and says to re-check the host's tool list: DSH's worker tools are new. It is the only per-host prose in the shipped skills; the rest names mechanisms, not tools.
  • The description drops "Claude Code only", and a content test asserts no other shipped skill names a host tool beyond the router's table and the two lines W2 rewrites.
  • A DSH worker does not message the router: its report is its transcript, read at each wake and before each ask. A DSH subagent is not a worker, because it inherits the router's directory.
  • The persona on DSH is the worktree's AGENTS.md plus the skills plus the brief; there is no project-scoped agent definition and no preset to pick.

What the host makes true

These facts shape the plan and are not up for design here.

  • A DSH session's sandbox root is the directory it was created in, and it never changes; a subagent always inherits its parent's directory. So a worker cannot be a subagent: the worker-session plugin creates the session itself, with the worktree as its directory (ruling R3).
  • DSH has no shell-hook surface: no host setting runs a command on a tool call or at turn end. The doc check therefore ships as a host plugin on tools/post-execute and agent/turn-stopping: it fails the write's result with the problems and keeps the turn open, but the bytes have already landed. A review or a merge is too late. Without the plugin nothing checks doc form — the merge never did either.
  • DSH follows a symlinked skill root: with .agents/skills a relative link to ../.claude/skills, a worker's catalog listed the skill, the load worked, and the resource base resolved through the link (a .dsh/skills link behaves the same).
  • .agents is a shared convention, not a DSH path: DSH calls ~/.agents its shared agent config root and reads CLAUDE.md as instructions, while it never scans .claude/skills for skills.
  • With approvals off, a medium call is rejected unless something decides it. Auto Review is how a stock install lets an unattended session add, commit or mint, and denies what it calls high risk; every Keel DSH session runs under it (ruling R4 and the owner's review).

The plugin seam, read from the installed API

The tool pipeline is tools/pre-execute → tools/execute → tools/post-execute → tools/result, with agent/turn-stopping before a finished turn closes (installed dsh-tools and dsh-agent).

SurfaceWhat it can doFor the doc gate
tools/pre-executeAllow, deny or ask before the body runs; cannot rewrite arguments.No: a write could be vetoed, but an edit would need the plugin to re-run the edit and validate the result.
tools/post-executeMay replace content/value, attach contexts, or return {kind:'block', feedback}, which turns a successful call into an error result carrying the feedback.Yes: the write has landed; the call returns failed with the problem lines.
tools/resultObserve-only; the outcome is immutable.No.
agent/turn-stoppingRuns before an otherwise finished turn closes; a listener that objects calls agent.steer(...), and fresh steering runs another step.Yes: a red doc steers the problems back; the turn does not close.

So the contract is: the check runs at the write, and a red doc cannot pass as a successful write or a closed turn. It cannot stop the bytes landing — no post-write surface can — so the agent gets the problem lines on the failed write and fixes it in the same turn. dsh-auto-review proves the plugin path on tools/pre-execute; the doc gate uses the post-execute block and the turn-stopping steer.

One skill set, or one per host?

Two questions. (a) One tree: does one root, read through a link, work? Yes — round 2's probe listed, loaded and resolved the base dir through .agents/skills, and init writes one set. (b) One body: does the same prose work when the tools it names differ? The audit says yes for five of six skills and for the sixth with one table.

Bottom line. The divergence is confined to keel-router: it is the one body whose subject is transport, and it already owns the "how a worker is reached" section. Every other skill carries at most one line, and W2 rewrites two of those. A body is not "the same prose everywhere" — it is the same rules, with host facts in the one place that already holds them.

All three hosts read the same shape: a directory named after the skill holding SKILL.md, with YAML frontmatter whose required fields are name and description. The six shipped skills and the project-router file use only those two, so the same file parses everywhere; the optional keys differ, and Keel's portability rule is to keep using none of them.
