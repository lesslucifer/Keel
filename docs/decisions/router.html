Decisions: the router and its workers

Why Keel's router has the posture it has, how its workers are started, bounded and watched, and what risk the owner accepted.

T2 · decisions · current truth · 2026-11-18 · Keel · DEC-30 – DEC-37, DEC-39, DEC-42 – DEC-46, DEC-48

Current truth: each record says what stands today, why, and what was rejected. A later decision that changes one is folded in and named. A record replaced whole keeps its id and one line. Ids are never reused; git keeps the history. The router's host (DeepSeek Harness) and its inbox are in router-hosts.html; the standard itself is the keel-router skill.

The router

DEC-30 · The router has no general shell: a whitelist, a launcher and one fail-closed guard

ChoiceThe router reads untrusted text (chat, worker reports), so Bash is limited to read-only git status|log|diff|show, git branch -v/-a variants, gh pr view|list|status, ps aux|-ef, and the shapes of one committed launcher, scripts/router-worker.sh (since DEC-46: spawn, stop, worktree add|remove, watchdog start|stop; since E-WSANDBOX.W5 also resume <name> and the read-only status [<name>], each a name and nothing more). Write is for worker briefs only. The router has no Edit, Monitor, direct claude or kill. It is enforced by "agent": "router" in .claude/settings.json, the agent file's tools:, and scripts/router-guard.jq run as a fail-closed PreToolUse hook (a jq error denies). The guard reduces a command to plain words (a character whitelist) before judging it, denies --ou*, gives gh only named query flags and bare words, caps length at 1000, and allows only the agent file's tools and the inline keel skills. It is the one source of the whitelist: tests/suite/router.rs ties permissions.allow and router.md to it. The whitelist also holds the read-only scripts/router-watch.sh commit|signed|merged|pushed|tagged <word>… (pushed fetches exactly refs/remotes/origin/<b>; its detail lines are untrusted text) and the shapes DEC-58 adds. keel init ships the skill, not the enforcement or the launcher: a project commits its own. The router cannot edit the launcher, the guard or the settings; only a reviewed worker commit can (DEC-48). Enforcement exists only in a checkout that holds these files. E-WSANDBOX.W7 (owner, 2026-11-28): the whitelist adds read-only git grep (never -O or --open-files-in-pager, which run a command), git ls-tree, git worktree list and git branch --list <names>, and the launcher's prune; permissions.allow lists router-watch.sh by its five kinds, as the guard does; router.md lists no shapes and points to the guard and UC-ROUTE-6. A red doc holds the router's turn end once: keel's turn-end hook (verify-doc-stop) tells it to send the worker that owns the doc, and lets its next turn end pass (stop_hook_active); every other session is held as before. The router and the watchdog stay outside a sandbox: a sandbox bounds only the Bash tool, which the watchdog lacks, and the router's Bash runs only these shapes.
WhyOne worker report already carried an injected "stop and summarize"; a router with a general shell would have acted on it. The owner's own router agent file gave it no Bash at all, and Trawler's ran git, gh and ps and spawned claude itself.
RejectedA worker spawning on the router's behalf (the whitelist is loosened by exactly the launcher shapes instead). Substring deny-lists on raw shell text, and per-tool hooks keyed on the router's agent type alone: the close review bypassed both.

DEC-31 · Headless workers are the standard; an enforced router has no Agent tool

ChoiceWorkers are separate sessions started only through the launcher, never in-session subagents. Since DEC-44 they are claude --bg sessions (the first form, claude -p with a budget cap, is gone with its cap). Keel's router has no Agent and no TaskStop; it has ListAgents and SendMessage (DEC-36, DEC-42). The skill keeps the in-session recipe for projects that do not enforce the posture. The launcher's flags, grant and mode are in DEC-37.
WhySubagents die with the router session and are invisible to ps. A subagent reports its own agent type, so it runs outside any hook keyed on the router's, in the router's checkout, with full tools.

DEC-32 · The router writes worker briefs itself

ChoiceA brief is dispatch mechanics: the router writes it directly at <router checkout>/.router/briefs/<name>.md, the only path it may Write. UC-ROUTE-3 (the router authors no content for others) covers doc prose, comment replies, status and "done" claims. The launcher snapshots and hashes the spawn brief only; a follow-up message is not hashed (DEC-42, DEC-44). The router must not paste untrusted report text into a brief.
WhyA brief is prompt text for a worker with edit and Bash power, like an Agent prompt. A worker writing its own brief would defeat the point.

DEC-33 · Accepted risk: workers inherit the owner's broad allowlist

ChoiceAccepted, not mitigated ("accept the risk for now", owner, 2026-11-08). Workers run as the owner's OS user, and an injected or compromised router can still write a brief that a worker carries out in its worktree. The launcher's fixed flags, the worktree refusals and the owner's merge sign-off bound the blast radius; they do not stop a bad brief. DEC-48 records what a same-user worker can still do; OS-level isolation is the upgrade path.
WhyHardening the router (DEC-30) narrows what injected text does directly, but not what a worker does. The owner was shown the account-compromise severity and chose to accept it. Revisit when workers read untrusted input (backlog R4).

DEC-34 · E-ROUTER's WUs ran ungated; its close carries walk waivers

ChoiceE-ROUTER's WUs ran as plain commits on wu/E-ROUTER/<slug>, merged --no-ff into the epic by their worker, with no test, doc or cr notes and no sign-off (owner, 2026-11-08, option C). Main was merged in at 888bb54 after E-SEED closed. The epic close ran one review over the whole epic (base e5a04cf), fixed its 4 blockers and 7 importants with regression tests, and waived the three WU seams that change code paths (1002f5b, 0e9da4e, ba239f4) on the epic tip's cr note, citing this record. Seams that touch no code path are exempt anyway.
WhyE-ROUTER needed E-SEED's packaging on main to prove invocation. Waiting meant idle WUs; starting ungated and merging main in later did not.
RejectedWaiting for E-SEED and running fully gated.

DEC-35 · Router skill shape: the remaining plan defaults

ChoiceA generic push channel with Telegram as the worked example, its token and access files never touched. Trawler incident details stay in lessons.md as lineage, plus a Keel section (K1–K11). worker-ops.md stays macOS/zsh-first, labelled. Claude Code only, until Codex has a skill path. The skill is keel-router (the DEC-2 prefix) and project-router unprefixed; the plugin and the keel:router name are moot under DEC-2.

DEC-36 · The router may subscribe to a worker's end, never message it

ChoiceThe router has ListAgents and SendMessage. A subscription (notify_when_idle: true, no message) gives one notice when a worker next goes idle or exits. A worker's turn end, not its exit, is the signal (DEC-43), and the worker reports by message, so the wait command of the first form is gone (DEC-44). The "never message" half is reversed by DEC-42: the guard now admits any SendMessage to a named session. The notice carries a worker-written snippet, so it is untrusted text. A router busy in a turn sees it only when that turn ends.
WhyWithout Monitor or shell loops the router otherwise learns that a worker ended only from a watch worker or the owner. Verified by a live probe (E-ROUTERFIX.W2, 2026-11-09).
RejectedLetting the router message workers (reversed by DEC-42). Allow-listing keys by deny-list: a new content-bearing parameter would ride along.

Workers: model, messages, sessions, watchdog

DEC-39 · Workers run on opus at low or high effort by role; the policy lives in .keel/config.toml [router] and the launcher enforces it

ChoiceA [router] section in .keel/config.toml holds worker_model = "opus", worker_efforts = ["low", "high"], worker_default_effort = "low" and planner_effort = "high" (E-WSANDBOX.W9, owner ruling 2026-11-26). A worker runs low; a planner, whose deliverable is a plan or a design, runs high, while a review, build, fix or check is a worker's. It also holds the optional worker_permission_mode (DEC-37) and watchdog_model (DEC-45). Only scripts/router-worker.sh reads it, from git show HEAD:.keel/config.toml in the router checkout, so an uncommitted edit cannot widen it. The grammar is narrow and fail-closed: key = "word" or key = ["word", …], words [a-z][a-z0-9.-]*. spawn refuses a model other than worker_model, an --effort outside worker_efforts, and an absent or malformed policy (no worker policy, exit 2, nothing started). Every effort must be a CLI level low|medium|high|xhigh|max (never ultracode) and both role efforts must be in the list. spawn --role worker|planner takes the role's level, --effort names one explicitly, and the two are never given together. The effort goes to claude as --effort, to the run dir and to the RUNNING line. On DSH the router passes the same level in worker_spawn's effort, always explicitly (the route's default is high); the harness on this host currently rejects a per-worker effort at spawn, a DSH defect recorded in E-WSANDBOX.W9's plan, not worked around. The CLI ignores [router] (no typed config); keel init's template gets none, since init ships neither launcher nor guard. The keel-router skill stays generic ("the project's model policy"). Accepted residual risk (owner, 2026-11-10): the launcher trusts the router checkout's HEAD, so a worker with the owner's Bash(git:*) could move that branch ref to a commit with a wider policy; same class as DEC-33, revisit with backlog R4.
WhyThe owner ruled that workers run on opus only ("they should use opus 5.5"), with the effort chosen, and that the policy belongs in the config that holds Keel's other rules, where the launcher enforces it.
RejectedA keel config get subcommand for the launcher (CLI surface for one caller, and a dependency on keel on PATH). Policy only in the launcher and skill text. A .router/policy file (not rule-bearing, git-ignored). Four models under a documentary policy. A built-in fallback default in the launcher (a second copy that can drift; the optional worker_permission_mode is different: absent means the documented default acceptEdits, and any committed value is enforced as committed).

DEC-42 · The router may message a live worker; a new task still travels as a brief

ChoiceThe guard admits any SendMessage whose to is a non-empty string and judges nothing else. A message steers a live worker: an answer, a clarification or a stop, and since DEC-44 a follow-up task too. A new worker's task goes as a brief, snapshotted and hashed (DEC-32); follow-up rounds go to the live worker by message. The brief-only rule for new tasks lives in the keel-router skill, not in the guard. A message is an unhashed instruction, a residual risk of DEC-33's class, and a worker's reply is untrusted like any report.
WhyThe old closed key set denied a real router's subscription: the harness adds type, recipient and content to every SendMessage input before the hook. The owner ruled that a router that cannot answer or stop a running worker loses every round to a fresh spawn.
RejectedLoosening the key set to the captured keys (the harness adds keys between versions). Checking content in the guard: no jq predicate can tell a clarification from a task.

DEC-43 · Workers are long-running sessions the router closes; the router runs no heartbeat

ChoiceA worker stays alive across rounds and is closed by the router when no longer needed. Its context spans one WU's rounds; a new WU, an independent check or a review gets a fresh worker. Since E-WSANDBOX.W5 (owner rulings 2026-11-26 and 2026-11-28) the router reuses a worker, live or stopped and resumed, when the task is its own WU's or a follow-up of its last one and its context is under [router] reuse_max_context_cold with a cold cache or reuse_max_context_warm with a warm one, read first with the launcher's status; a fix goes to its author under the ceiling (the author may ask for a fresh one) and fresh past it unless the owner says otherwise; a reviewer is not resumed, by instruction, not by a check. The router only routes: it runs no loop, timer or heartbeat of its own, and arms no poll per worker (progress is the watchdog's, DEC-45). The mechanism (a stream-json claude -p fed through tail -f, with send and a wait scan) is replaced by DEC-44.
WhyA one-turn claude -p worker meant a new process per round, and the router could steer a worker only while its single run lasted. The owner ruled on 2026-11-11 that workers stay alive and the router closes them.
RejectedA router heartbeat through the loop skill and ScheduleWakeup (the owner: the router routes only). An interactive claude under a pty.

DEC-44 · Workers are native background sessions; the worker's message is its report

ChoiceNo claude -p for anything. scripts/router-worker.sh spawn runs claude --bg -n <name> --model --effort --agent worker --allowedTools … --disallowedTools … --permission-mode <mode> "<fixed prompt>" in the worktree, with the policy (DEC-39), grant and deny lists (DEC-37, DEC-46) and no print, stream or budget flag (--max-budget-usd needs --print, so the cap is gone). It refuses a name claude agents --json lists anywhere, waits until the session is listed, and records its id in the run dir. stop <name> runs claude stop then claude rm on this repository's idle session of that name; a busy one gets about 30 s to end its turn, then is refused. A session list the CLI fails to give stops every mode. Every state but idle and busy was refused; since E-WSANDBOX.W7 (owner, 2026-11-28) such a dead worker is stopped at once, its STOPPED line naming the state, and a busy one stays the owner's. prune clears what gone workers and removed worktrees leave: git's record of a worktree whose directory is gone, the brief copies of sessions no longer listed, and launch locks older than 10 minutes; it never deletes a worktree, a branch or a transcript. The worker reports by SendMessage to the router its brief names and stays alive; a follow-up task is the router's own message, recorded only in the worker's transcript. wait and send are gone. DEC-46 deleted the old resume; E-WSANDBOX.W5 brought back resume <name>: the newest run of that name gives the session id, the worktree, the branch, the effort, the mode and the review grant; the spawn's checks and its one flag builder run again with every flag from the committed policy, plus --resume <id> and a resume prompt, and it prints RESUMED. It refuses a live session of the name, no transcript, a changed brief snapshot, a worktree off the run's branch, and an effort, mode or model the policy no longer admits. status [<name>] prints, per worker, its context, peak, idle minutes, warm or cold cache and fits from its transcript's usage records and timestamps only. --agent worker is always passed, because this repository's settings make every other session a router. A call outside the grant leaves the worker on a permission prompt until the owner answers with claude attach <id>. A worktree must be trusted (a worktree of a trusted checkout is; a fresh clone is not). The guard admits spawn|stop; .router/ holds briefs/ and runs/ only.
WhyThe wait scan of the raw stream failed seven review rounds, each on a new event shape. The owner ruled on 2026-11-11 for native sessions that the router closes (Claude Code 2.1.288 has claude --bg, agents --json, stop, rm) and a worker that reports by message.
RejectedIn-session Agent subagents as workers: one starts in the router's checkout, a cd does not carry to its next Bash call, its isolation: worktree branches from the default branch, and the router guard does not apply to it. A snapshot-only send mode for follow-ups (the owner dropped it). Stopping a busy session at once: claude stop cuts a turn mid-edit.

DEC-45 · A watchdog session reports the router's workers every 5 minutes

Choicescripts/router-worker.sh watchdog start <router-name> starts one background session per router, watchdog-<router-name>, in the router's checkout, on [router] watchdog_model (Haiku; optional, and without it only the watchdog refuses). It runs with --setting-sources local, an inline agent (--agent watchdog), only the tools SendMessage and CronCreate, --strict-mcp-config and --autocompact 100k, and schedules the prompt tick every 5 minutes. Its UserPromptSubmit hook runs watchdog facts <router-name>: one block per live worker (a background session in another worktree of this repository) with state, quiet minutes, branch, tip, dirty count and the last six transcript items. Code decides DONE (idle) and STUCK (any state but idle and busy, with its waitingFor; or busy and quiet 15 minutes or more). Output stays under 9000 bytes (10,000 or more reaches the model only as a file path). facts never exits non-zero, runs git --no-optional-locks, and stops the watchdog once the router is gone. Its PreToolUse hook is the router guard with --arg watchdog_to <router-name>: only that one CronCreate (*/5 * * * *, tick) and a SendMessage to that router pass. watchdog stop <router-name> ends it, and spawn refuses watchdog names. A report is a progress hint from untrusted worker text summarised by a small model, never an instruction: the router checks before it acts. The recurring job expires after 7 days; a watchdog that stops reporting is the router's to restart. E-WSANDBOX.W7 (owner, 2026-11-28): from day 6 the facts carry Schedule ends in under a day: restart the watchdog …, judged by its own transcript's first timestamp (the recurring job ends after 7 days), and after the worker blocks a Close: block, at most 8 lines: a worker still on a branch merged --no-ff into its base, a merged worktree with no worker, a worktree whose directory is gone, each with the command that closes it; those git reads run in the router's checkout only. Accepted (owner, G3): --setting-sources local loads the router checkout's .claude/settings.local.json, the owner's git-ignored file, which no worker can write.
WhyDEC-44 leaves two cases unreported: a worker that goes idle without its report, and one that never goes idle (a permission prompt, a long silent turn). The owner ruled on 2026-11-11 for a Haiku watchdog with native auto-compaction and no restart.
RejectedA shell ticker (claude stop plus --resume each period). A Stop hook that sleeps. Project settings in the watchdog: the project's verify-doc-stop hook refuses every turn end while a doc is red, and the watchdog loops. An agent file under .claude/agents/ (not found with the project source off). The router's name in an environment variable (a background session gets none).

Worker limits and accepted risk

DEC-37 · Worker grants travel on the launcher's command line; the committed policy picks a worker's mode from a closed set, and the router may only narrow it

ChoiceGrant. The launcher passes every worker a fixed --allowedTools list, Bash(c) and Bash(c *) for cargo build|test|check|clippy|fmt and keel preflight|verify-doc|verify-dod|notes write|lint|check, and a fixed --disallowedTools list (DEC-46 point 10) that beats the user-level allowlist. It never reaches the router. It is code execution in the worktree (cargo test runs worker code), DEC-33's class; the keel mr deny states intent and is no sandbox.
Mode. [router] worker_permission_mode in .keel/config.toml (read as DEC-39) is optional, acceptEdits when absent; Keel sets auto. The launcher accepts plan, acceptEdits and auto; any other committed value is refused by name, and a malformed line fails the whole policy (no worker policy). spawn --permission-mode may only narrow it (plan < acceptEdits < auto, else wider than the policy's), before any run dir or start. A review worker takes the same mode. plan stays valid for read-only checkers. The shipped skill recommends acceptEdits, with auto opt-in.
File guard. The Bash sandbox bounds only the shell, so every worker's --settings carry a fail-closed PreToolUse hook on every tool, scripts/router-file-guard.sh <worktree> <home>, judging the resolved path. Edit, Write, MultiEdit and NotebookEdit pass only under the worktree, never on its .git, .claude/settings.json or settings.local.json, and not on a file with several hard links, a relative path or a ./.. component. Read passes anywhere but ~/.ssh and ~/.claude/channels, which Grep and Glob may not search either. spawn also refuses a worktree inside the router's or main checkout, and paths with a quote, backslash or newline.
Worktree link. spawn, stop, worktree remove and facts first check that <wt>/.git is a regular file reading gitdir: <git dir>/worktrees/<name>, whose admin dir holds commondir ../.. and a gitdir naming that worktree; the git dir comes from the router's checkout. facts reports unlinked .git, not read, stop prints drift=unlinked, the others refuse. Their git reads run with -c core.fsmonitor=false. The shell is denied <wt>/.git, the two settings files, the admin dir's commondir and gitdir, and ~/.claude.json. Since E-GHFLOW.W3, kept by E-GHREVERT, it is also denied writing <git dir>/commondir and config.worktree, and every admin dir's commondir, gitdir and config.worktree, by name and by glob (the old H-3, backlog R33, is fixed). Every launcher run checks every admin dir under <git dir>/worktrees (a real directory, commondir exactly ../.., no config.worktree, a gitdir naming a .git) and stops every mode on a mismatch before any session starts; the watchdog's facts report it instead. It also refuses a commondir or config.worktree file in the main git dir.
~/.cargo. The sandbox allowWrite names only registry/, git/, .package-cache, .package-cache-mutate and .global-cache (with -journal, -wal, -shm), not env, config.toml, credentials or bin. Under auto the sandbox, deny list, file guard and every git-side gate stay; the live check of auto is backlog R40.
Accepted. Owner code execution through the worktree's own .claude/agents/worker.md and .claude/skills/, code the owner runs from it (tests, build.rs), and other worktrees' admin dirs; under auto what a worker may read it may send (backlog R41). Owner-waived after review round 3, not fixed (backlog R31–R39): the guard lowercases ASCII only, so U+017F (ſ) for "s" escapes it; ~/.cargo/registry/src and git/checkouts stay shell-writable, so a dependency's build.rs can be edited; the guard passes tools it does not name (Artifact, ArtifactData, Workflow, EnterWorktree); a path ending in a newline, a swap between hook and open, a symlink in a non-last path component, and git worktree remove without the fsmonitor flag also get past it.
WhyWorkers were refused cargo and keel in a claude -p session, where nobody can approve. Under acceptEdits the owner answered prompts for plain reads outside the worktree, so the mode became project policy. One classifier-approved Edit could otherwise change the launcher, guard or settings, which run from disk on every spawn, with no gate.
RejectedA worker allow-list in .claude/settings.json (shared with the router, unwritable by workers). cargo run (cargo run -- mr is keel mr), install, publish, add, update; keel init, hooks install. bypassPermissions (no check), dontAsk (denies the worker's own edits), default (a prompt per edit stalls a background worker). Edit(//…/**) deny rules for the guard: Claude Code feeds them to the sandbox's denyWrite, so one on the main checkout would deny the git dir and every commit.

DEC-46 · Router and worker scope; a worker's environment and limits

ChoicePoint numbers are the W8 plan's; tests cite DEC-46 "point n".
Point 1. No worker pushes: the owner pushes, the router stages git push -u origin epic/<E> and arms the pushed watch.
Point 2. The router creates worktrees through the launcher: worktree add <epic/E | wu/E/slug> cuts the branch off its fixed base (main, or epic/E, which must exist; an existing branch is used as it is) at <main checkout>-<branch without its prefix, / as ->. No path or base argument.
Point 3. One worktree per epic branch and per WU branch, its branch never changed.
Point 4. A review runs in a fresh worker, spawn … --review, in the author's worktree while the author is idle, one per round. Only it is granted keel notes write cr, and it is denied Edit, Write, NotebookEdit, git add and git commit; every other worker is denied the cr note.
Point 5. worktree remove <branch> takes only a clean worktree whose branch is merged into its base, with no session in it, never the router's or main checkout, never --force; the branch is kept.
Point 6. --setting-sources project,local: the user source is off; the worktree's .claude/settings.local.json stays the owner's per-worktree knob.
Point 7. --strict-mcp-config with no MCP config.
Point 8. The brief names ~/.claude/skills/htmldoc/SKILL.md to read, since the user-level skill is gone with the user source.
Point 9. --settings carries Claude Code's Bash sandbox: enabled, auto-allowed, no unsandboxed retry; writes to the worktree, the git dir (--git-common-dir, absolute) and ~/.cargo (narrowed by DEC-37); no read of ~/.ssh or ~/.claude/channels; hosts htmldoc.wfomobile.com, crates.io, index.crates.io, static.crates.io, github.com. A host outside it waits as blocked · sandbox request. The prompt tells a worker to give network commands a timeout.
Point 10. The deny list (each Bash(x) and Bash(x *)): keel mr|init|hooks, cargo run|install|publish|login, git push|config|update-ref|symbolic-ref|stash|notes|switch|checkout|rebase, git worktree add|remove|move|prune, git -C|--git-dir|--work-tree (and the = spellings), claude, scripts/router-worker.sh. It states intent and refuses at once with a reason; the sandbox is the bound.
Point 12. The launcher unsets every GIT_* first, and the worker's first action checks that git rev-parse --show-toplevel prints its worktree.
Point 13. The sandbox denies writes to the git dir's config, hooks, keel-hooks and info and to ~/.cargo/bin; since E-GHFLOW.W3, kept by E-GHREVERT, also commondir and config.worktree in the git dir and every admin dir, and the launcher checks every admin dir on every run (DEC-37).
Point 14. Refs and notes stay writable (a commit must write the git dir), so a worker can move another branch or write a notes ref. The merge gate and the owner's signature bound it; accepted (DEC-48).
Point 15. spawn refuses a worktree without .claude/agents/worker.md or on a detached HEAD, before any run dir or brief copy; holds .router/runs/.lock-<name> over the live check and start; records branch, brief-copy and review in the run dir and prints branch=. stop removes the brief copies its session recorded (a real .router-brief.XXXXXX directly under the worktree) and prints drift=<branch> when the worktree left the spawn's branch.
Point 16. A worker can still edit its own worktree's settings or hooks, the remaining way around the sandbox.
A stopped worker comes back only by resume <name>, with every flag rebuilt (DEC-44; E-WSANDBOX.W5): the owner's probe of 2026-11-28 showed a claude --bg --resume <id> after claude stop and claude rm keeps the history and the session id, so stop stays claude stop then claude rm. claude respawn is never used: its saved flags follow what the session itself changed. gh does not work in a worker (keychain, api.github.com).
WhyAn exported GIT_DIR reached a --bg worker and silenced its doc hook; the sandbox held under --bg; a plain --bg --resume lost every launch flag (probes, 2026-11-11). The old roles also contradicted themselves: a worker pushing the epic branch, nobody able to create or remove a worktree, the author reviewing its own diff.
Rejected--setting-sources project alone. --restricted, --safe-mode (drop the project's settings, skills and hooks), --bare (no OAuth), keeping the user source and subtracting from it, claude -w (its own branch name). Granting rm, sed, curl by name instead of the sandbox. A ref snapshot compared at stop. A resume taking a session id, a worktree or a brief (E-WSANDBOX.W5 takes a name only and reads the rest from the run). A path or base argument for worktree add, --force removal, branch deletion, stale-lock recovery. The author orchestrating its own review.

DEC-48 · Accepted risk re-recorded: what a same-user worker can still do after the committed roster

ChoiceKeel keeps [mr] tiers = ["username", "key"] (the key-only flip is deferred, owner, 2026-11-12). scripts/router-guard.jq, scripts/router-worker.sh, scripts/router-watch.sh and .claude/agents/ are rule-bearing: a change is an owner keel mr commit inside a signed WU diff. The roster is the target's committed one (DEC-47), so a worker's key in its own roster does not count, and a roster change waiting for the owner's signature is refused without --roster-change. The owner's signing key needs a touch or typed passphrase, is never in ssh-agent, and is unreadable to a worker (~/.ssh: sandbox denyRead, and the file guard of DEC-37). Accepted, still open: (1) a typed Reviewed-By trailer or --no-verify on a rule-bearing commit (DEC-24), bounded by the WU and epic sign-offs. (2) A same-user shell rewriting the target branch: refs are writable in the sandbox (DEC-46), so a worker can commit its key onto epic/<E> with plumbing, merge its WU with --no-verify or a signature the rewritten roster accepts, then remove the key. An inner WU merge can be forged; the epic sign-off cannot (verified against main's roster, needs the presence key, covers the whole epic diff). (3) Deleting or overwriting mr notes can destroy a sign-off, never make one.
