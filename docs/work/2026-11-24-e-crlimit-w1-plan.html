E-CRLIMIT.W1 · The review schedule as three settings

The tool runs your 3-round review, and each project can set its own.

T3 · WU plan · 2026-11-24 · Keel · its data file, 2026-11-24-e-crlimit-w1-plan.yaml, sits beside this page · the epic plan is here

The problem

The tool counts review rounds on the old 5-round table. Its numbers are fixed in the code: a project can move only the cap. A wrong cap is found only when a review starts.

What you get

  • Round 1 reads the whole work. Round 2 reads only the fix.
  • Round 3 runs only after round 2 found a blocker. Medium findings in round 2 are fixed and recorded, with no new round.
  • A blocker still open in round 3 ends in the cap's waiver, which you accept or not at sign-off.
  • Three settings in the project's rules file change this: the cap, how many rounds read the whole work, and from which round only a blocker earns another.
  • A wrong setting is refused at the commit that adds it, and when a review starts.

How it works

  1. Tests are written first and fail on today's tool.
  2. The tool reads the three settings from the rules file committed on the branch the work merges into, never from the work itself. A setting left out takes its default.
  3. One rule checks the settings, in four places: the review start, the review record, the commit hook and the owner's rule-file commit.
  4. Old review records stay valid. Nothing is rewritten.
  5. The use case and the decision are updated in place.

What it makes

A change in the tool's review code and its tests, the epic's end-to-end test moved to the new schedule, two use cases and one decision updated, and this plan and its result. No instruction file changes: that is the next part.

What you decide

Nothing blocks the work.

How you'll know it worked

  • With no setting, a review runs at most 3 rounds, as above.
  • A project with its own settings gets exactly that schedule.
  • Each wrong setting is refused, and names itself.
  • Reviews recorded under the old table still pass.
  • Keel's checks pass.
