E-GHFLOW2 · The rest of the GitHub flow

Run the three GitHub pieces live, teach the router to use them, then move your sign-off, the merge, manual tests, rule edits, waivers and doc pages to GitHub.

Ready v1 · 2026-11-15 · T3 · epic plan · Keel · off main 72cae9d · carries E-GHFLOW W4 – W9 (backlog github-flow G1 – G5)

The problem

You still sign, merge and give orders at your Mac. The last epic put three pieces on GitHub: it runs the checks, a bot pushes work and opens pull requests, and the router can hear your comments. None has run against GitHub yet, and the router does not use them. This epic runs them live, teaches the router, then moves the rest of your actions to GitHub. It runs through that flow itself, switching each step on as it lands.

Example: one piece of work, at the end

  1. A worker finishes. The bot pushes its branch and opens a pull request.
  2. GitHub's checks turn green. You get a review request.
  3. You try the change on your Mac and comment that it passed.
  4. You approve. That signs it, and GitHub merges it.
  5. The router hears the merge and starts the next worker.

Terms

Pull request: GitHub's page for one branch waiting to merge. Landing: this epic merged into main before it closes, because GitHub runs some steps only from main. You rule on when: open point 1.

W3 · Your approval is the sign-off

In short: a new signer tier, github. When you approve a pull request, a workflow from main checks that you are in the committed roster and approved exactly the head commit. It then writes the same sign-off note your typed command writes, and sets a keel/sign-off status. The typed sign-off stays as the fallback.

  • Changed from E-GHFLOW's plan: GitHub takes a pull_request_review workflow from the pull request's merge commit, not from main, so a pull request could edit its own sign-off. So the review event only starts a run with no permissions; the writer runs on workflow_run, which GitHub takes from main. It trusts nothing from the run that started it: it re-reads the review by id (approver id, state, commit equal to the head).
  • The writer builds keel from the pull request's base and reads the base's roster and policy, as the gate does (DEC-60). It writes mr/v1, pushes refs/notes/mr, sets keel/sign-off. Its token: contents and statuses write, nothing else.
  • Roster line github: <user-id> <login> in .keel/mr-allowed; [mr] tiers must list github. This WU changes the roster, so it is signed with --roster-change.
  • mr/v1 gains review (id, URL, approved commit). Check 8 learns the tier: offline it checks the note's bindings; in CI it re-reads the review.
  • Both levels. For an epic, the result report rides as refs/notes/report on the epic tip, written by the closing worker; router-gh.sh push pushes it with the other notes, and check 8 hashes it from there.
  • Notes written on GitHub reach the Mac: router-gh.sh fetches and merges GitHub's notes before each notes push (DEC-61's open consequence).
  • R50: keel mr checks its own checkout's .git link and admin dir, as the launcher does, before any git call.
  • G5's W2 test nits, since this WU edits tests/suite/router_gh.rs.

W4 · GitHub enforces the merge

In short: rules on GitHub make the merge button the gate: main and every epic branch change only by a pull request whose checks are green, merged as a merge commit. Nobody bypasses, you included. The checks that judge a pull request come from main, so a branch can no longer turn its own checks green.

  • Base-defined checks. Main now holds the gate, so the pull-request jobs move to pull_request_target, which GitHub takes from main for every base (DEC-60). Same rules as today: read-only token, no secret, actions pinned, credentials not kept. No cache a pull request's run can write. .github/ and scripts/ci-gate.sh become rule-bearing.
  • Rules (you set them once; the WU gives the exact list): a pull request for main and epic/*; required checks ci, gate, docs, keel/sign-off, each pinned to GitHub Actions as its source; merge commits only; no force push or deletion; an empty bypass list. DEC-38's tag rule: only you create version tags.
  • Auto-merge: [github] merge_on_approve, default on; pr-ready turns on GitHub's auto-merge (merge commit), so your approval lands a green pull request.
  • After the rules: WU merges happen on GitHub; the router's sync brings them back; sync main fetches main. The close's own commits, and any merge of main into an epic, go through a pull request too.
  • A merge commit GitHub makes passes the epic's range walk.
  • A read-only script prints the live settings against the expected list.
  • G4: the base keel is built once per run and shared between the jobs.

W5 · A test you run on your Mac, from the pull request

In short: the worker writes try-it steps into its result report: where to check out, how to build, each step with what you should see, how to undo real changes. The pull request shows them as a checklist. You run them and comment the result; a keel/tried status records it on the exact commit, and the sign-off carries it.

  • A tagged section of the WU result report, data-item="try-it", optional, checked by keel verify-doc when present: each step has a command and an expected result; real state needs a restore step.
  • pr-open copies the steps into the pull-request body as a checklist, with the head sha to test.
  • You comment /keel tried pass, /keel tried fail <step>: <what you saw> or /keel tried skip <reason>. A workflow on issue_comment, which GitHub takes from main, checks your id against the roster's github lines and the head sha, then sets keel/tried. With no try-it section it sets success, "nothing to try", so the check can always be required.
  • The command joins the router's grammar (scripts/router-gh-command.jq), so the watch prints it; on a fail the router sends the worker your text as data.
  • W3's sign-off copies it into mr/v1 as tried; a typed sign-off passes --tried pass|skip. keel/tried joins W4's required checks.
  • G5's W3 test nits, since this WU edits the watch's tests.

W6 · Work that need not wait goes in its own pull request

In short: a rule-text or T1 doc edit that needs your yes goes into a small pull request off the epic, while the code work goes on in its own. Your approval of the small one is its sign-off, so no typed commit stops a worker.

  • New branch kinds under the WU prefix: wu/<E>/rules-<slug> (rule-bearing paths only) and wu/<E>/docs-<slug> (docs only). Each is a WU to the gate.
  • The commit-msg hook accepts a rule-bearing commit without a Reviewed-By trailer on a rules- branch only; that branch's sign-off is your review.
  • A docs-only or rules-only range needs no result report ([mr] report applies to ranges that change code).
  • When the code needs the rule change, its branch starts from the rules branch; its notes come only after the rules pull request merges.
  • Conflicts: GitHub refuses a conflicted merge; the router turns the pull request back to draft (a new router-gh.sh draft <n>, label conflict); the worker merges the synced epic into its branch, never a rebase, and re-gates.
  • The hook change reaches every worktree when you install a keel built from main, so it lands at the close or a landing.

W7 · Waivers and roster changes from the pull request

In short: the two-step decisions you type today become two comments. The first gets back exactly what the typed command shows; the second, with the code it printed, records it. You are told each time on GitHub.

  • The writer builds keel from the base and never runs the head's code.
