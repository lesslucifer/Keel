E-CRCAP.W2 · The 5-round review schedule — plan

The tool counts review rounds from the cr notes already on the branch. Preflight tells the reviewer which round it is and what to review. A fix that only answers allowed findings gets a PASS without a new round. Round 5 is the last; a blocker there ends in a WAIVED note that the owner accepts, or not, at sign-off.

Requirement

keel preflight wu|epic prints review round n of N and the scope (the whole range in rounds 1–2, the code changed since the last reviewed commit from round 3), counted from the reviewed cr notes on the branch's own first-parent line, and refuses with 0·review-cap a round past the cap or a round 5 after a round 4 with no blocker; keel notes write cr stamps that round and scope, enforces the same refusals, takes the round's findings, refuted candidates, nits and fleet itself, writes a fix-PASS (--verdict PASS --fixes <reviewed commit>) only after a round whose findings may be fixed without a new round, and writes the cap's WAIVED note with a reason the tool fixes; and keel mr confirm shows each round, its scope and each fix-PASS with the files it changed.

The design

What counts as a round

Note on a first-parent commit of base..tipCounts as
PASS or FAIL written by a reviewa round
WAIVED that kept a reviewed round of this range (the cap, or the owner over a FAIL)that round
fix-PASS, or a WAIVED marked unreviewednot a round
a note that does not parserefused: preflight and the writer stop and name the commit; the owner repairs it in place

The round about to run is one more than the rounds below the tip. The tip's own note never counts, so a re-run on the same commit is the same round. An epic reads only its own line, so its WUs' rounds (on their own tips) never count.

The CLI

CommandDoes
keel preflight wu|epic <tip>After its checks, prints review round n of N - scope: the whole range, <base>..<tip>, or from round 3 scope: the last fix, <since>..<tip> on the code paths (full SHAs; since is the last reviewed commit). Red 0·review-cap for round N+1, for round 5 or later when the round before found no blocker, and for an unreadable earlier note
keel notes write cr --verdict PASS|FAILSame refusals. Writes round and scope ("full" or "since <sha>"). Still binds the whole range's code hash, so checks 4–5 do not change. Prints the next step of the schedule. A FAIL with a blocker in round N says the cap is reached and names the WAIVED step
… --findings <json> --refuted <json> --nits <json> --fleet <json>Router item 1. The round's lists go on the note in the same call: arrays (fleet an object), refused otherwise, nothing written. With --findings, the counts come from it (entries without a waived reason); a typed --blockers/--importants that disagrees is refused. Only on a reviewed PASS or FAIL
keel notes write cr --verdict PASS --fixes <rev>The fix-PASS. Allowed when <rev> is the commit of the latest round below the tip, no fix-PASS sits between it and the tip unless no code path changed since the newest one (open point 7), and that round may be fixed without a new round: a PASS (nits), or a FAIL with importants and no blocker in round 4 or later (or in the cap round, when N is below 4). Writes fixes, round (the round it answers), fix_diff_hash (the code diff from the reviewed commit to the tip) and answers (its importants and nits). Not a round
keel notes write cr --verdict WAIVED (no --reason)The cap. Only when the tip's own note is round N's FAIL with a blocker. The tool writes the reason review cap: N rounds, <b> blockers open through W1's one waiver writer, so the FAIL's findings stay on the note. Anywhere else it is refused, as a waiver with no reason is today
keel mr confirmThe history rows gain [round n, full], [round n, since <sha>] and [fix-PASS of round n on <sha>; no reviewers ran; changed: <files>]. A sign-off whose line holds a fix-PASS prints the history too (open point 13), with no new flag

The cap is [review] max_rounds in the target's committed .keel/config.toml, default 5, like every other policy the gate reads: an edit in the branch or the working tree cannot raise it. Keel's own config stays unset. From round 4 only a blocker earns another round, whatever N is.

Expected

  • Preflight prints review round 1 of 5 and round 2 with the whole range, and from round 3 the range since the last reviewed commit.
  • A fix-PASS after a nits-only round is written and the merge check is green on it (red only on 8·manual-review before the sign-off). It is refused after a round-2 FAIL with importants, after any blocker, and on top of another fix-PASS when code changed since it. After a round-4 FAIL with importants and no blocker it is written.
  • Round 5 is refused after a round 4 with no blocker. Round 6 is refused. A round-5 FAIL with a blocker leads to the WAIVED note with the cap reason, and the owner's --accept-waiver signs it.
  • A merged WU's rounds do not count for its epic. Re-running a review on the same commit is the same round. max_rounds = 6 on the target moves the cap.
  • The writer stores findings, refuted, nits and fleet given as flags, and refuses a non-array list.
  • An unreadable earlier note refuses preflight and the writer; a notes ref git cannot list is an error, never "no note".
  • The epic e2e passes: a fix-PASS WU and a capped, waived WU merge through the real hook, and the epic merges into main.

Open points (decided here; the owner may overrule by comment)

#PointDecided here
1Does this plan need an owner go first?No. Neither keel-workflow nor the epic plan asks for one.
2W1's --verdict WAIVED --reason "…" still writes any reason. Restrict it to the cap?Keep it as W1 built it: W1's tests pin the waiver's behaviour through it, and the owner still accepts any waiver at sign-off. The skill uses only the reasonless cap form. Restricting it is a small follow-up if the owner wants it.
3Which config holds max_rounds?The target's committed config (above). The working tree's is never read for it.
4A FAIL with 0 blockers and 0 importants (e.g. keel check red)No fix-PASS after it: something other than findings failed the round, so it needs a round.
5Field and flag names (working names in the epic plan)round, scope, --fixes, fixes, fix_diff_hash, answers, --findings, --refuted, --nits, --fleet, 0·review-cap.
7What does a later commit that changes no code get, such as the result report after a fix-PASS, or the owner's skill commit? (independent text review round 1, I)No new round and no reviewers. A fix-PASS answering the same round, where the schedule allows one, even on top of a fix-PASS when no code path changed since the newest fix-PASS: nothing reviewable changed. Otherwise the round preflight names. A docs-only commit after a failed round still gets no PASS: it fixed nothing. Without this, a docs commit after a fix-PASS, or after round 4, had no path but a waiver. This amends the epic plan: its W2 block ("on top of another fix-PASS it is refused") and open point 13 ("no fix-PASS on a fix-PASS") now hold only when code changed since that fix-PASS.
8From round 4 (or at the cap), a second code fix after a fix-PASS: the fix-PASS is refused and no round follows a round without a blocker (independent text review round 2, I1)No new path. The refusal names the owner's waiver (never a round preflight refuses), and the skill says to write the fix-PASS only on the final fix. A rule letting fix-PASSes stack over new code would let unreviewed code pile up with no reviewer and no owner step. Before round 4 a second fix still gets its round.
6Does the merge check verify a fix-PASS?No: it reads PASS as today (checks 3–5). The rules live in the writer, and the owner sees each fix-PASS and its files at sign-off (epic open point 13).
