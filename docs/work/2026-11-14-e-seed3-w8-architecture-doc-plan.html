The problem

The epic moved the CLI, what setup installs, the config keys, the evidence and the epic close. The router tooling stays in its own scripts. A reader who wants the final shape must read the code and six T2 pages and join them. One T1 page should carry that shape.

How it is read

  1. An agent meets an unfamiliar subcommand or config key. It opens the page's table, finds the key and the code that reads it.
  2. A gate prints a check id. It opens the evidence table, finds which note feeds that check and who writes it.
  3. A close worker needs the order. It opens the close section and sees what the code enforces and what no gate sees.

The work

In short: one page written last, so it describes what W1–W7 built. Every claim comes from the code at this tip, not from a skill's summary.

  • The CLI: every subcommand, its arguments and what it does, including the hook entry points.
  • What setup installs: git hooks, settings, skills, .keel/, the notes refspec and the skills lock. Say what the code does not install.
  • The config keys: every key in templates/config.toml and every key the code reads, with the reader named. This includes the keys the CLI never reads ([review] modules/rubric, [router]).
  • The evidence set: each note kind, what writes it, what reads it and which gate check depends on it.
  • The router tooling: launcher, watch, guard and the worker plugin's tools; for each, what it may and may not do.
  • The close: the sequence the code enforces after W2 and W3, including the close level, the epic-range note rule and the bare-tip target rule.
  • Disagreements: where the code and a skill say different things, both sides are named.
