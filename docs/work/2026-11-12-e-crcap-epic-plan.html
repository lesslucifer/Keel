E-CRCAP · Code review stops after 3 failed rounds, and a waived review says so

Epic plan for backlog rows B8 and B12, within the owner's scope ruling of 2026-11-12.

T3 · epic plan · 2026-11-12 · Keel · branch epic/E-CRCAP off main 1f303dc · plan only; no work starts before the owner's go

The problem

Two things go wrong today. First, a code review can loop without end. Each round finds something, the author fixes it, and the next round finds something else. E-ROUTER3.W2 ran 7 rounds before the owner stopped it by hand, and E-SEED2.W12 was stopped by hand the day before. The 3-round limit the owner set exists only as a ruling that agents must remember. Second, when the owner waives a review, the record still says PASS. Three merged tips say "reviewed, PASS" when the truth is "the owner skipped the review". This epic makes the limit part of the tool, and makes a waiver look like a waiver.

"Continue" buys exactly one more round. If it fails too, the owner is asked again. The owner can also waive a review before any round runs.

W1 · A waived review is recorded as WAIVED B12

In short: when the owner waives a review, the agent records it as WAIVED with the owner's reason. The merge check accepts it and prints it. Sign-off shows it and needs the owner's explicit yes.

Mechanics:

  • keel notes write cr --verdict WAIVED --reason "<owner's ruling>" [--blockers n] [--importants n] writes the cr note with verdict: WAIVED, waiver: <reason>, and the same code hash as any review. An empty reason is refused. A reason on PASS or FAIL is refused.
  • The merge check's review step (check 3) accepts WAIVED and prints WAIVED 3·review: <reason>. The base and code-hash checks (4, 5) are unchanged, so a code change after the waiver still invalidates it.
  • The epic's walk over its merged WUs passes a waived WU and prints it. The dod/v1 receipt records review: WAIVED.
  • keel mr confirm on a waived commit prints the waiver and every review round, then refuses without an acceptance flag (working name --accept-waiver). With the flag, the signed text gains a line review: WAIVED sha256:<hash of the reason>. The sign-off check (check 8) rebuilds that line from the current note. Commits with no waiver sign exactly as today, so existing signatures stay valid.
  • Skill text: keel-code-review §5–§7 (an agent writes a waiver only on the owner's ruling), keel-workflow §3–§6.
  • Rule-bearing: skills/ and its .claude/skills/ mirror, in one owner keel mr commit that the worker stages and prints.
  • Not reviewed by any gate: that skill text and this WU's plan and result. The code (src/notes.rs, src/gate.rs, src/mr.rs) and tests/ go through the code review.

W2 · The 3-round limit B8 · rounds owner 2026-11-11

In short: preflight counts the failed reviews already recorded on the branch. After 3 it refuses a 4th and lists the owner's three choices. The count comes from the notes git already holds, so nobody has to remember it.

Mechanics:

  • A round is a FAIL cr note on a commit of the branch's own line of history (first-parent commits of base..tip). One rev-list --first-parent and one git notes list; no new state.
  • keel preflight wu|epic prints review round n of N. N is [review] max_rounds in .keel/config.toml, default 3. At the limit it refuses with 0·review-cap, naming the count and the three choices.
  • The owner's "continue" is passed as --continue "<ruling>" (working name). It allows exactly one more round, and that round's note stores the ruling as continued.
  • keel notes write cr uses the same count. It stamps round on the note and refuses a PASS or FAIL past the limit unless the ruling is given. A WAIVED note is never refused.
  • W1's sign-off listing adds the count and any "continue" rulings.
  • Skill text: keel-code-review §2 and §7 (the loop ends at PASS or at the limit, then stop and ask the owner), the keel-workflow check table, keel-router's review-worker brief row. templates/config.toml's [review] comment changes, because the CLI now reads that section too.
  • Rule-bearing: skills/, .claude/skills/ and templates/, in one owner keel mr commit. Keel's own .keel/config.toml is not changed: the default applies.
  • Not reviewed by any gate: that text, the template and the WU docs.

Backlog B8 (rounds) · owner rulings of 2026-11-10 (E-SEED2.W12) and 2026-11-11 (E-ROUTER3: 3 rounds per WU, the owner decides past that) · UC-REV-3 (new) · one new decision record, amending DEC-26 (the CLI now reads [review] max_rounds).

Integration tests (tests/verify_dod.rs, scratch repo): after 3 FAIL notes on 3 commits, preflight refuses with 0·review-cap and lists the choices. Rounds 1–3 print n of 3. A merged WU's failures do not count for its epic. Re-running a review on the same commit is one round. A PASS is not a round. --continue allows exactly one round and its note records the ruling. A FAIL note past the limit is refused; a WAIVED one is not. max_rounds = 5 moves the limit. Unit tests cover the count.

W3 · What counts as a nit B8 · scope

In short: the review rules name two cases as nits, so they never fail a review: a missing test for a case the code already handles correctly, and a tidy-up of test helpers. The router's own extra reviews get the same 3-round limit. Text only, no code.

Mechanics:

  • The shipped rubric.md severity rows: if the code is right on an untested case, the missing test is a nit. If the code is wrong on that case, that is a blocker against the code, never against the test.
  • A test-harness tidy-up that changes no test's result (helpers, duplicated fixtures, hermeticity polish no test observes) is a nit. Whether the WU's own contract is tested stays a question for its test note.
  • keel-code-review §5 and §7: a nit never triggers a fix round, and it is recorded on the cr note with its disposition.
  • keel-router: its triage line, and its rule "re-review security paths until a round finds nothing above low", get the 3-round limit as text (open point 9).
  • Rule-bearing: skills/ and the mirror, in one owner keel mr commit.
  • Not reviewed by any gate: the whole WU. It changes no code, so it needs no test, review or doc notes, but it still needs the owner's sign-off. The router's read-only extra review reads the text.

Details

The rest of the plan is reference: acceptance criteria, contracts, scope limits, design choices, tests and where the knowledge goes at the close.

Acceptance criteria

  • A waiver: keel notes write cr --verdict WAIVED --reason "<ruling>" writes a cr note with the reason and the code hash. With no reason, it is refused.
  • The merge check on a waived WU prints WAIVED 3·review: <reason> and fails only on the missing sign-off. A code commit after the waiver invalidates it, as it invalidates a review.
  • Sign-off on a waived WU prints the waiver and the rounds, and refuses without the acceptance flag. With the flag it signs, and the signature covers the waiver. Rewording the waiver, or turning a PASS into a waiver after signing, fails the merge.
  • An epic passes a waived WU in its walk and prints it as WAIVED. An epic's own review can be waived too (the E-SEED2 close case).
  • The limit: with 3 FAIL notes on the WU's branch, preflight refuses with 0·review-cap and names the choices. Rounds 1–3 print review round n of 3.
  • An epic counts only its own rounds, never its WUs'. Re-running a review on the same commit is one round. A PASS is not a round.
  • "Continue" allows exactly one more round, recorded on its note. The next one is refused again. The cr writer applies the same count.
  • [review] max_rounds = 5 in the committed config moves the limit. Unset means 3.
  • The rubric and skill name the two nit cases, and keep "the code is wrong on an untested case" a blocker. skills/ and .claude/skills/ stay byte-identical.
  • The epic test below passes through the real merge hook in a scratch repo.

Epic end-to-end test

epic_e2e_a_capped_review_loop_ends_in_an_owner_waiver_the_gate_accepts in a new tests/review.rs, added by W2 (the last code WU). It builds a scratch repo in a temp dir, runs keel init with hooks there only, uses a test signer, and needs no network.

  1. An epic branch with a plan, and a WU branch with code, tests, a result report, and test and doc notes.
  2. Three review rounds fail on three commits (keel notes write cr --verdict FAIL, the only review output the merge check reads). The fourth preflight is refused.
  3. The owner's "continue": one more round fails and records the ruling. The next preflight is refused again.
  4. The owner's "waive": a WAIVED note. The merge check fails only on the missing sign-off. Sign-off without the flag is refused; with it, it signs. The real git merge --no-ff into the epic passes the hook.
  5. The epic: its own review passes, its walk prints the WU as WAIVED, it is signed, and the merge into main passes the hook.
  6. A failure case: rewording the WU's waiver after signing fails the sign-off check.

No test layer is waived. Lesson from E-SEED2.W15: the test runs the real merge through the real hook.
