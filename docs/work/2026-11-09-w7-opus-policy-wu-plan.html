Requirement

scripts/router-worker.sh spawn|resume reads [router] worker_model, worker_efforts and worker_default_effort from .keel/config.toml as committed at the router checkout's HEAD. It refuses the run if that policy is absent or malformed. It refuses any model other than worker_model (opus), and any --effort value not in worker_efforts (medium, high). When --effort is omitted it uses worker_default_effort (medium), and it passes the effort to claude -p as --effort. After this WU, no tracked file outside docs/work/ and the lessons' history offers a non-opus worker model.

An uncommitted edit to the config has no effect.

Where the policy lives

Choice. A new [router] section in .keel/config.toml, read only by scripts/router-worker.sh. The CLI ignores it, the same way it ignores [review] (F6).

[router]   # read by scripts/router-worker.sh, not by the CLI (DEC-39)
worker_model = "opus"
worker_efforts = ["medium", "high"]
worker_default_effort = "medium"
QuestionDecisionReason
Keys and section[router] with worker_model (one string), worker_efforts (a string array) and worker_default_effort (one string)The ruling allows one model, so a list of models would be speculative. The default effort is its own key, not "the first entry in the list", which would be an implicit rule.
Who reads itThe launcher, from git -C "$ROOT" show HEAD:.keel/config.toml, where ROOT is the router checkout. A dedicated sed/grep reads only the [router] section and accepts exactly these forms: key = "word" and key = ["word", …], where a word is [a-z0-9.-]+, with an optional trailing # comment. Anything else in the section is a refusal. tests/router.rs also pins the committed values, so a change needs the owner's commit and a red-then-green test.The launcher is the only enforcer. Reading HEAD mirrors the merge gate (F7): an uncommitted edit, which a worker or a stray edit could make, cannot widen the policy. The launcher is POSIX sh with no TOML parser. The narrow grammar fails closed, so a form it does not understand denies the run instead of being misread.
Key absentRefuse: router-worker: no worker policy: [router] worker_model / worker_efforts / worker_default_effort in .keel/config.toml at HEAD of <ROOT>, exit 2, nothing spawned.One source of truth. A built-in fallback default would be a second copy of the policy in the launcher, and it could drift from the config unnoticed.
Config holds another modelThe launcher enforces whatever the committed config says (for example, worker_model = "sonnet" admits only sonnet). Each value must match [a-z0-9.-]+. Every effort must be one of the CLI's levels (low|medium|high|xhigh|max; ultracode is refused because it turns on extra orchestration), and the default must be in the list. Otherwise the run is refused.Changing the policy is an owner keel mr commit on a rule-bearing file, which is the point of the move. Hardcoding opus in the launcher as well would make two sources of truth. Shape checks catch typos at spawn time instead of passing them to claude.
src/ config parsingUnchanged; the keys stay launcher-only.No CLI command acts on them. A typed RouterCfg would be code with no caller, and a typo inside [router] is already caught at spawn time by the launcher's strict reader.
keel init templateNot changed: templates/config.toml gets no [router].Init ships neither the launcher nor the guard (F7). A section that nothing in an adopting project reads would be dead config. Revisit together with R6 ("ship the enforcement with keel init").

Rejected: (a) a keel config get <key> subcommand that the launcher calls. It gives typed parsing, but it adds CLI surface and src/ code for a single caller, and it makes the launcher depend on a keel binary on PATH, which the launcher does not need today. (b) Policy only in the launcher and the skill text (r1): the owner asked for it in the config that holds Keel's other rules. (c) A separate .router/policy file: it would not be rule-bearing, and .router/ is git-ignored.
