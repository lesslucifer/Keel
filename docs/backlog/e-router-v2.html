R2 · Do headless workers stall under acceptEdits? · done

Answered and fixed in E-ROUTERFIX.W1. Workers are refused, not stalled: "requires approval" on cargo / keel is a refusal in claude -p. The launcher now grants the gate commands, denies keel mr, and takes a validated --permission-mode acceptEdits|plan: DEC-37.

Unverified whether a worker's Bash outside its allowlist stalls under --permission-mode acceptEdits (a headless session cannot answer a prompt). R3 · Put the router's security files under a gate

scripts/router-guard.jq, scripts/router-worker.sh and .claude/agents/ are neither code_paths nor rule_bearing in .keel/config.toml, so a commit changing them needs no review and no Reviewed-By; only tests/router.rs (a code path) guards their behaviour. Add them to rule_bearing (a .keel/ change: owner's keel mr commit). Related: Keel's own clone had no keel hooks install through E-ROUTER, so no commit-msg or merge hook ran on any of its commits. Source: E-ROUTER close review.

R4 · Revisit the accepted worker risk

Workers inherit the owner's user-level allowlist (rm, kill, curl, claude --dangerously-skip-permissions) and run any brief the router writes (DEC-33). Revisit before workers read untrusted input: a worker-scoped allowlist in .claude/settings.json, or a dedicated permission mode in the launcher. Same class (owner ruling 2026-11-10, E-SEED2.W7 review r1): a worker holding the owner's user-level Bash(git:*) can move the router checkout's branch ref (git update-ref runs no hook), so the launcher would read a wider DEC-39 [router] policy with no owner commit, just as it can already rewrite the launcher through that shared checkout. Source: plan ruling "worker permissions".

R8 · Router↔worker messaging redesign own epic, owner ruling 2026-11-09

Today's channel is accepted for now. The router subscribes to a worker's end (SendMessage notify_when_idle, DEC-36) and arms router-worker.sh wait, then reads .router/out/<name>.out. It is one-way: the router never sends a worker content. The owner ruled on 2026-11-09 that improving this channel is its own future epic. Until then the router's watch capability also stays as it is: a worker's end is watched with wait, and owner actions are not watched.

ItemSource
Watch gap: nothing watches an owner action (a staged keel mr, a merge, a push). The worker-ops recipe for it fails under the launcher (R7, first row), and wait covers only a worker's end. The router learns about owner actions only when the owner tells it or when its next git log shows themR7; owner ruling 2026-11-09
Subscription denied in practice. On 2026-11-09 the router keel-fb sent SendMessage to a launcher-spawned worker's name with notify_when_idle: true, once with message empty and once without it. The guard denied both calls with "router guard: SendMessage only as a pure subscription: {to, notify_when_idle: true}, no message", although DEC-36 allows that shape. Cause (E-SEED2.W7 plan phase, from the source): that text comes only from scripts/router-guard.jq:54. It fires when the predicate at :52–53 fails: to is not a string, notify_when_idle is not exactly true, message is non-empty, or the input has a key outside the closed set to, notify_when_idle, message, summary (:53). The predicate admits both shapes the router sent: tests/router.rs router_guard_allows_send_message_only_as_a_contentless_idle_subscription and the e2e epic_e2e_router_drives_a_granted_worker_in_a_seeded_worktree_to_its_end assert exactly those inputs, and main's guard is identical to the epic's. The denied calls therefore reached the hook with a different tool_input than the call as written. The likely case is a key that Claude Code adds or normalises before PreToolUse, which the closed key set at :53 rejects; the other possibility is notify_when_idle arriving as something other than boolean true (:52). The synthetic test inputs never saw the real payload. Not confirmed: running the guard against sample payloads was refused in the W7 session ("jq command contains dangerous flags that could execute code or read arbitrary files"). Next step: capture one real router SendMessage PreToolUse payload in a scratch clone, add it as a test fixture, and then loosen :53 to the harness's real keys without letting content through.
