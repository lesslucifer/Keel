E-ROUTER3.W10 · Workers are native background sessions

WU plan: the launcher starts workers with claude --bg, the worker reports by SendMessage, and wait with its stream machinery is deleted.

T3 · WU plan · 2026-11-11 · Keel · branch wu/E-ROUTER3/w10-bg-workers off epic/E-ROUTER3 ee34a85 · plan only: no code before the owner's go

Requirement

scripts/router-worker.sh spawn starts a worker as a native background session (claude --bg -n <name> --agent worker on the policy's model and effort, with the fixed grant and deny lists and no print-mode or stream flag) and refuses a name that claude agents --json already lists; the worker sends its report to the router by SendMessage; a follow-up task is the router's own SendMessage, with no launcher step; stop runs claude stop then claude rm on that worker's id; and the launcher has only spawn, resume and stop: wait, send and every feed, stream, scan and report file are gone from the launcher, the guard and the settings.

Today (W2, at ee34a85)

A worker is claude -p in stream-json mode. Its stdin is a tail -f of .router/out/<name>.in, kept open by a feed process, with a reaper loop beside it. send appends a turn to the inbox, stop kills the feed, and wait polls the raw output: about 90 lines of shell and jq that count typed stream events to decide IDLE, STALLED or EXITED and write <name>.report. That scan failed seven review rounds in W2, each on a new event shape.

Claude Code 2.1.288 has the whole thing natively: claude --bg starts a session that stays alive idle, claude agents --json lists it, SendMessage opens a turn in it, and claude stop and claude rm end it.

A worker's life. The launcher runs each command to its end and keeps no process, pid file or output file. The worker tells the router it is done; nothing polls. A follow-up task never passes through the launcher.

.claude/agents/worker.mdThe body says: when your work is finished, send one self-contained report to the router named in your brief with SendMessage, then end your turn; you stay alive for follow-ups. The .out sentence and the word "headless" go.
scripts/router-guard.jqThe launcher alternation becomes (spawn|resume|stop), and the deny text follows. Nothing else changes.

The worker command. claude --bg --session-id <uuid> -n <name> --model <model> --effort <effort> --agent worker --allowedTools <grant…> --disallowedTools <deny…> --permission-mode <mode> "<fixed prompt>", run with the worktree as its working directory.

  • --agent worker is always passed: .claude/settings.json sets "agent": "router", and a background session started here without it loaded the router persona (observed 2026-11-11).
  • The prompt is the last argument and follows a single-valued option. --allowedTools and --disallowedTools take a list, so a prompt placed right after one of them would be read as a tool name.
  • The prompt stays fixed text naming only the in-worktree copy of the brief, as today, plus one sentence: report to the router named in the brief by SendMessage when finished.
  • Gone: -p, --input-format, --output-format, --verbose, --replay-user-messages, --max-budget-usd.

Expected

  • With the stub claude, spawn runs exactly one claude --bg in the worktree. Its options are, once each, --bg, --session-id, -n, --model, --effort, --agent worker, --allowedTools with the fixed grant, --disallowedTools with the fixed deny list and --permission-mode; its last argument is the fixed prompt naming the brief copy. It has no -p, no stream flag and no --max-budget-usd. spawn prints RUNNING with the id and session.
  • A spawn or resume of a name the session list already holds is refused with a named reason. A start the CLI refuses prints DEAD with the CLI's text and exits 1.
  • The launcher has exactly three modes, spawn, resume and stop. A follow-up task needs no launcher command.
  • stop runs claude stop <id> then claude rm <id> for that worker's id and no other. It refuses an unlisted name, a session outside this repository's worktrees and a busy worker.
  • scripts/router-worker.sh wait x and send x b.md are refused by the launcher and by the guard. After a spawn and a stop, .router/out/ does not exist and no launcher process is left.
  • The guard admits spawn, resume and stop in plain words. .claude/settings.json allows exactly those three launcher shapes.
  • Live: one real worker reports to a named router by SendMessage, takes a follow-up task by message, reports again, and is stopped; claude agents --json then lists no worker and its worktree is untouched.
  • The keel-router skill, its mirror and project-router describe this flow and name neither wait nor .report. DEC-44 is recorded.
