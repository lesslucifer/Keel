B9 · Strip GIT_INDEX_FILE in check_push's scratch path proposed: E-SEED3

Pre-existing; found by the E-SEED2.W13 review r2 verifier. If keel inherits GIT_INDEX_FILE when pre-push starts (the user's own post-commit hook runs git push, or the user exported it), the pre-push scratch path's git worktree add forwards it. With an absolute path that can overwrite the main index with the pushed tree; with a relative one the push is refused for an unrelated reason. The verdict stays correct either way. Fix: strip GIT_INDEX_FILE in src/gate.rs check_push's scratch calls only (keel's other git calls keep it, DEC-41).

B13 · Check 8 passes when an archived epic report is missing proposed: E-GATEFIX blocker, waived once for the E-SEED2 close

FindingWhen an epic's attested report is untracked or archived (docs/.archive/) and the local file is missing or unreadable, src/mr.rs report_hash returns Ok(None). manual_review's match has three arms: Ok(Some(h)) if h != hash (red), Err (red) and a catch-all _, which returns Ok(Some((path, hash))). So check 8·manual-review passes without re-hashing anything. src/gate.rs then copies that report and hash into the dod/v1 receipt as attested, although nothing was verified on this machine. Editing an archived report turns check 8 red (tests/mr.rs), but deleting it turns check 8 green. That breaks the stated contract: the comment above the match says "an attestation is never ignored", and DEC-40 says a report in a note is re-hashed whatever the policy.
OriginPre-existing on main 0dad93f: report_hash already returned Ok(None), and the arm was _ => Ok(()). E-SEED2.W2 rewrote that match and widened the gap into the new dod/v1 receipt. Found by the E-SEED2 epic review (one round, epic tip e184f1e, correctness finder; a fresh verifier confirmed it and raised it to blocker).
WaiverOwner ruling 2026-11-10, one time, the E-SEED2 close only: the blocker is waived, not fixed, and the epic's cr/v1 records PASS by this waiver. keel notes write cr takes only the verdict and counts, so the waiver lives here (and in the archived E-SEED2 epic result), not on the note (see B12). Until the fix lands, an archived epic report must stay on disk at its path until the epic merges, because the gate would not notice it missing.
Fix sketchA missing or unreadable local report is red at check 8, with a fix -> line naming the path. Regression test first: delete an archived epic report after mr confirm, and verify-dod epic turns red on 8·manual-review, writing no dod/v1.
Review nits (same round, not fixed)(1) src/mr.rs report_candidates runs one git show <tip>:<path> per changed .html, deleted paths included, at sign-off; one git cat-file --batch or a --diff-filter=d pre-filter would do. (2) src/main.rs hook_conflicts / hooks_problem_of call a stale Keel core.hooksPath (the repo was moved or renamed) "another tool's setup". The refusal is the DEC-23 contract and --force is the documented recovery, but the message is wrong for that case.

B12 · The cr note cannot carry a waiver proposed: E-SEED3

keel notes write cr takes only --verdict, --blockers and --importants, so a review round the owner waives cannot be recorded on the note itself. The E-SEED2 epic review's blocker, waived for the close, is the second such case (B13). The first: on 2026-11-10 the owner waived the review round after the C-locale fix 519c2cc in E-SEED2.W12 (W12 only, a one-time ruling). The cr/v1 PASS on W12's tip 90135b7 therefore records no review of that last change: it is a waiver, not a reviewed verdict. W12's round history (archived result, git show f059eb4:docs/work/2026-11-10-w12-owner-watch-wu-result.html): reviews over 7c26a43, 07c9ce0 and e8dcc49 FAIL and fixed; the round over f68f18c abandoned under the review cap, its real bug fixed in d42dcfd; the capped round over 854d334 FAIL (one blocker, one important), fixed in 519c2cc; the final round waived. Fix: a waiver field (with the owner's reason) on cr/v1, checked at the gate.
