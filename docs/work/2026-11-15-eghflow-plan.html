E-GHFLOW · Run the flow from GitHub

A direction-finding plan: which of your actions can move to GitHub, how, and what must stay on your Mac.

Draft v3 · 2026-11-15 · T3 · epic plan · Keel · v3.1: your comments answered; docs on GitHub Pages by your ruling

The problem

Today you drive the flow from your terminal. You prompt the router, sign, merge and push by typed commands, and get pings on Telegram. So you must be at your Mac, and a rule or doc edit that needs your yes stops the work until you type it. This epic moves your actions to GitHub: you comment, approve and press merge on a pull request (GitHub's page for one branch waiting to merge). Work that need not wait goes in its own pull request. The router stays on your Mac; the same checks guard every merge.

Example: one piece of work

  1. A worker finishes. The router pushes its branch and opens a pull request.
  2. GitHub runs the tests and the merge check. Both turn green.
  3. You follow the pull request's test steps on your Mac and comment "tried: pass".
  4. You approve. That is the sign-off; GitHub merges once green.
  5. The router sees the merge within a minute and starts the next worker.

The work

Each step lands alone; the local flow keeps working.

W1 · GitHub runs the checks, as a signal

In short: every push of a work branch, and every pull request, runs the full test suite and the merge check on a GitHub-hosted machine. Nothing is required yet; the results are a signal and a readable evidence page. This alone ends the sandbox-only reds.

  • A workflow .github/workflows/keel-gate.yml with two jobs. ci (pull_request and push on wu/**, epic/**): keel check on the merged tree, read-only token, no secrets. gate: fetches refs/notes/*, makes local branches for head and base, installs the hooks in the runner's clone, runs keel verify-dod wu|epic <head> --target <base> and writes the five notes as a table into the job summary.
  • The gate's keel is built from the base branch, never from the pull request's head: the code under review must not build its own judge.
  • The gate reads git data only; a test proves verify-dod runs no project command ([check]), so it is safe under a base-defined trigger.
  • Everything the jobs do lives in one script (scripts/ci-gate.sh), so it runs the same on a laptop and is testable hermetically.
  • The runner's clone has no Keel hooks, so the script installs them before the gate (check 0·hooks would be red otherwise); keel check's cache is not used there.
  • A third, cheap job runs keel verify-doc on the changed docs: a backstop for the write-time check, never a substitute (DEC-54). §7 audits every check this way.

W2 · The router bot pushes work branches and opens pull requests

In short: a GitHub App acts for the router. Through one fixed-shape script, the router pushes wu/ and epic/ branches (never main) and opens a draft pull request per WU (into its epic) and per epic (into main). Workers still never push and never touch GitHub.

  • scripts/router-gh.sh push <branch> · pr-open <branch> [--base <branch>] · pr-ready <n> · post <n> <body-name> · sync <branch> (fetch, then fast-forward the local epic/ branch to what GitHub merged; refuses anything but a fast-forward, so local worktrees see merges made on GitHub); every argument validated like the launcher's; the App's private key is read only by this script, never printed, never in a worktree.
  • A pull request's body is built by code from the plan and result docs (links, tip, gate state). Free text it posts comes from a file a worker wrote (UC-ROUTE-3: substance comes from workers).
  • The local pre-push hook still runs on every router push: keel check, the range walk, and the notes push.
  • The router guard admits these shapes; scripts/router-gh.sh becomes rule-bearing.
  • Needs your ruling: DEC-46's "no worker pushes; the owner pushes" becomes "the router bot pushes non-main branches" (open point 1).

Owner ask (actions through git/GitHub) · UC-ROUTE-1 and UC-ROUTE-6 (amended) · DEC-46 (amended).

Integration: against a local mock of the GitHub API and a bare origin: push refuses main, a tag, an unknown branch and any argument starting with -; pr-open sends the expected request with base and head derived from the branch name; no output carries the key or the token. W3 · The router hears you through GitHub

In short: a read-only watch, like today's owner-action watch, polls GitHub and wakes the router when you comment, review, approve or merge. Only your GitHub account is heard; everyone else's text is never read as an order.

  • scripts/router-gh-watch.sh review|comment|merged|checks <pr|issue> [since <id>]: checks at once, polls about every 60 s, prints one event line plus escaped detail, exits; TIMEOUT and UNREACHABLE as today.
  • Your identity is your numeric GitHub user id, committed in the repo (a login can be renamed; the id cannot). Events from any other id print as a count only.
  • A comment's first line may be a command from a closed list (/keel go, /keel hold, /keel retry, /keel answer <n> <A|B>); the rest is your message to the router, treated like a chat prompt today. Edited comments are not re-read as orders.
  • The router's status board becomes one tracking issue per epic (one sub-issue per WU), edited by the router bot.

Owner ask (you stop prompting the router) · UC-ROUTE-1 (amended: watch kinds) · new UC-ROUTE row (the GitHub command channel).

Integration: against the mock API: your approval prints APPROVED pr= sha=; a stranger's comment holding a command prints IGNORED from=other count=1, never its text; an edited comment is not a new command; control characters print as ?; the watch keeps no state between runs. Unit: the command grammar.

W2

W4 · Your approval is the sign-off

In short: a new signer tier, github. When you approve a pull request, a workflow defined on the base branch checks that the approver is in the committed roster and approved exactly the head commit, then writes the same mr/v1 note your typed sign-off writes today, and sets a keel/sign-off status.

  • Roster line github: <user-id> <login>; [mr] tiers must list github to accept it.
  • mr/v1 gains review (id, URL, approved commit). Everything else is as today: base, tip, level, diff hash, the result report's hash.
  • Check 8 learns the tier: offline it checks the note's bindings; in CI it also re-reads the review from the API.
  • The workflow runs on pull_request_review, which GitHub runs from the default branch, so a pull request cannot change its own sign-off logic.
  • Both levels: a WU's pull request into its epic and the epic's pull request into main (open point 10). For the epic, the result report is read from refs/notes/report on the epic tip, written by the closing worker; check 8 hashes it from there.
  • keel mr confirm stays, unchanged, as the fallback when GitHub is down.

Owner ask (sign-off through GitHub) · UC-MR (new row: a sign-off by pull-request approval) · DEC-47, DEC-48 (amended: what the github tier proves).

Integration: scratch repo plus a recorded review payload: an approval by a listed id on the head sha writes mr/v1 and the gate goes green; an approval on an older sha, by an unlisted id, or a "comment" review writes nothing; a code commit after the approval turns check 8 red, as today; an epic approval binds the report note's bytes, and a changed note turns check 8 red. Unit: the roster line parser, the note fields.

W1, W2

W5 · GitHub enforces the merge

In short: rules on GitHub make the merge button the gate: main and every epic branch change only by a pull request whose three checks are green, merged as a merge commit. Nobody bypasses, you included. The local hooks keep guarding local merges as the fallback.

  • Rules (you set them once in the repo settings; the WU gives the exact list): require a pull request; required checks ci, gate, docs, keel/sign-off, and keel/tried when the report has try-it steps; merge commits only; no linear-history rule; block force pushes and deletions; an empty bypass list. Plus DEC-38's owed tag rule (only you create version tags).
  • .github/ becomes rule-bearing, so a workflow change needs your review.
  • Once the CI checks are required, the local pre-push hook stops re-running the whole suite on every pushed tree: it keeps lint and the notes push (open point 17, §7).
  • A read-only check script prints the live settings against the expected list; a worker runs it.

W4

W6 · A test you run on your Mac, started from the pull request

In short: the worker that did the work writes a try-it instruction into its result report: where to check out, how to build and run, each step with what you should see, how to undo real changes. The pull request shows it as a checklist. You run it on your Mac and comment the result; a keel/tried status records it on the exact commit, and the sign-off carries it. §6 defines the instruction.

  • The instruction is a tagged section of the WU result report (data-item="try-it", optional, checked by keel verify-doc when present: every step has a command and an expected result, a restore step when real state is touched). The report's bytes are what your sign-off already attests, so the steps you followed are bound to the commit.
  • router-gh.sh pr-open copies the steps into the pull-request body as a checklist, with the head sha you must test.
  • You report with a comment: /keel tried pass, /keel tried fail <step>: <what you saw> or /keel tried skip <reason>. A base-defined workflow on issue_comment checks your user id and the head sha, then sets keel/tried (success, failure, or neutral with the reason). The router hears the same comment (W3) and, on a fail, sends the worker your text as untrusted data.
  • W4's sign-off copies the result into mr/v1 as tried (pass or skip with reason, and the comment's id). A typed sign-off can pass --tried pass|skip the same way.

Owner ask (manual testing done locally, from the pull request) · UC-ROUTE-1 (the ask's "try in the real app") · UC-DOC (new: the try-it section) · UC-MR (the sign-off records it).

Integration: keel verify-doc on report fixtures: a step without an expected result, or real state without a restore step, is red; a report with no try-it section is green. The comment reader on recorded payloads: your /keel tried pass on the head sets success; on an older sha, or from another id, sets nothing; a skip without a reason is refused. The sign-off writes tried. Unit: the comment grammar, the checklist renderer.

W7 · Work that need not wait goes in its own pull request

In short: a rule-text or T1 doc edit that needs your yes goes into a small pull request off the epic; the code work goes on in its own pull request at the same time. Your approval of the small pull request is the sign-off, so no typed commit stops a worker. §8 has the model and the options.

  • New branch kind under the WU prefix: wu/<E>/rules-<slug> (rule-bearing paths only) and wu/<E>/docs-<slug> (docs only). Each is a WU to the gate: same checks, same sign-off.
  • The commit-msg hook accepts a rule-bearing commit without a Reviewed-By trailer on a rules- branch only; that branch's sign-off (check 8, never exempt) is the owner's review. Every other branch keeps the trailer rule.
  • A docs-only or rules-only WU needs no separate result report: the pull request page is the record ([mr] report applies to ranges that change code).
  • When the code needs the rule change, the code branch starts from the rules branch; its notes and review are written only after the rules pull request has merged, so its range excludes the rules commits.
  • Parallel pull requests may touch the same file. A conflicted one goes back to draft with a conflict label; its worker merges the epic into the branch, resolves, re-gates, and the router marks it ready again (open point 18).

Owner ask (a T1 doc change must not block the work) · UC-MR-1 (amended: the trailer on rules branches) · UC-GATE (amended: report policy for docs-only ranges) · DEC-24 (amended).

Integration: scratch repo: a rule-bearing commit with no trailer is refused on wu/E/x and accepted on wu/E/rules-x; a rules branch carrying a code path is refused at its gate; a docs-only WU signs without a result report; a code branch started from a rules branch, gated after the rules merge, has a range without the rules commits and passes check 4. Unit: the branch-kind parser.

W2, W4

W8 · Waivers and roster changes from the pull request

In short: the two-step owner decisions that are typed today become two comments on the pull request. The first shows you exactly what the typed command shows; the second, with the code it printed, records it. You are told each time on GitHub.

  • /keel waive-review <reason>: a base-defined workflow posts the preview the typed --waive-review prints (your reason, open findings, every review note on the branch) with a confirm code. /keel confirm-waiver <code>, then your approval, writes the WAIVED review note and the sign-off in one transaction, as today.
  • /keel accept-waiver <code> accepts the waiver a review's round cap wrote, after the same preview.
  • A pull request that changes .keel/mr-allowed: the bot posts the added and removed lines; the sign-off is refused until your /keel roster-change comment after that preview.
  • How you hear of it: the bot's comment mentions you and requests your review (both reach GitHub Mobile as push), labels the pull request needs-owner, and lists it on the epic's tracking issue under "waiting on you"; once recorded, it posts the result and clears the label.

Your comment on open point 12 · UC-MR (amended: waivers and roster changes by comment) · DEC-49, DEC-47 (amended).

Integration: recorded payloads on a scratch repo: a waive request posts a preview carrying the same lines the typed preview prints; a confirm with a wrong code, from another id or on an older sha writes nothing; the right one writes both notes or neither; a roster change without /keel roster-change is refused. Unit: the command grammar, the preview renderer.

W3, W4

W9 · Docs as web pages on GitHub Pages

In short: every push rebuilds one GitHub Pages site holding the docs of each live branch, so a plan or report is a link you can open anywhere. Comments and diffs stay in htmldoc, whose script loads on any host.

  • First, before any build work, two checks: (1) Pages is available and free for this public personal-account repo (turn it on in a scratch public repo, or read the plan page for GitHub Free); (2) the htmldoc server accepts its comment and snapshot calls from the Pages origin (a test page on the scratch site, with a doc id minted only for this check, loads the comment layer and posts one comment, which is then resolved, never deleted). Either failing stops W9 and comes back to you with the htmldoc-server "view" endpoint as the fallback.
  • A workflow on pushes to main, epic/** and wu/** builds the site from every live branch's docs/ (one folder per branch) plus each epic tip's report note, and deploys it with Pages' own Actions deploy.
  • The pull request body links each changed doc's page.
  • Limits (verified): a site of at most 1 GB; a deploy times out after 10 minutes; a custom Actions workflow is not held to the 10-builds-an-hour soft limit. The pages are public, like the repo.

Your ruling on open point 5 (2026-11-15: "ok, go with Pages") · UC-DOC (new row: where a doc is read).

Integration: the site builder on a scratch repo with two branches: each branch's docs land under its folder, relative links resolve, a deleted branch's folder is gone on the next build, the report note renders. Unit: branch-to-folder naming.

Details

Acceptance

  • A push of any wu/ or epic/ branch shows two checks on GitHub; the gate's job summary lists the tip's five notes.
  • The router opens a pull request for a finished WU with no owner command typed.
  • Your approval on the head commit writes a sign-off note the local keel verify-dod accepts; an approval on an older commit writes nothing.
  • With W5's rules on, the merge button refuses a pull request whose gate is red, and a direct push to main is refused, for you too.
  • A comment from another account never reaches the router as text.
  • When a result report has try-it steps, the merge waits for your /keel tried comment on the head commit, and the sign-off records it.
  • A rule-text edit lands through its own pull request while the code pull request it came from keeps moving; no typed commit stops a worker.
  • With GitHub unreachable, the whole local flow (typed sign-off, local merge, hooks) still works.
  • Approving the epic's pull request signs the epic: the sign-off binds the report note's bytes, and no typed sign-off is needed.
  • With merge_on_approve on, your approval alone lands a green pull request; with it off, nothing merges until you press merge.
  • A conflicted pull request goes back to draft, is fixed on its own branch and re-gated, then marked ready again.
  • A review waiver or a roster change is recorded only after its preview is posted and you confirm it by comment; you are mentioned each time.
  • The epic test passes.

Out of scope

  • Running the router or workers on GitHub: they stay Claude sessions on your Mac.
  • Code reviews run by Claude inside GitHub Actions (needs a model key in GitHub; a later epic if wanted).
  • Moving release tags off your terminal.
  • Built binaries, artifacts and Codespaces as the way to test by hand (rejected: open point 9, §6).
  • A self-hosted runner, webhooks to your Mac, merge queue (not available on a personal-account repo).
  • Setting the GitHub flow up in other projects: Keel's own repo only (open point 8); a backlog row for a later review epic.
  • Changing what the gate checks: the checks stay as they are; only where they run moves.

Recommendation: A. It adds nothing that listens, and it is the shape the router already trusts. B is a later upgrade if a minute is too slow; it should never accept a job from a pull_request event.

Trust model.

  • Who may command: one GitHub user id, committed in the repo (with the roster). GitHub authenticates the account; your 2FA (ideally a passkey) is now the router's front door.
  • Every comment is untrusted input. From any other id the watch prints a count, never the text. From you, the first line is matched against the closed command list; the rest reaches the router as your message, the same trust as a chat prompt today. Edits do not re-issue a command.
  • Prompt injection. Pull requests from forks are ignored; the router reads only pull requests its bot opened. Workers never read GitHub, so no public text reaches a worker except through a brief the router writes, which never pastes untrusted text (UC-ROUTE-3).
  • The bot's power. The App can push work branches, open pull requests, comment and set statuses. W5's rules stop it from changing main or merging; it cannot approve its own pull request.
  • What the guard and launcher need: the guard admits router-gh.sh and router-gh-watch.sh in fixed shapes; the App key lives outside every worktree and outside the worker sandbox's reads; the worker deny list adds the two scripts; .github/ and both scripts become rule-bearing.

Settings (your comments on open points 6 and 11). One committed section, read by the router's GitHub scripts and by the base-defined workflows from the target's committed copy, never from a branch under review. It is in .keel/, so a change needs your approval.

6 · Manual testing: you test on your Mac, from the pull request

The work and its real state are on your Mac, so the test is too. GitHub carries the instruction and your result; it does not run the test.

  • Who writes it: the worker that did the work, in its WU result report, as the try-it section. It runs every step once itself before it reports (the router's existing rule for try-it helpers).
  • Where it lives: the result report (its bytes are what you sign). The pull request copies the steps as a checklist, names the head sha to test, and links the report on htmldoc.
  • How you report: one comment on the pull request: /keel tried pass · /keel tried fail <step>: <what you saw> · /keel tried skip <reason>. Ticking the checklist is optional, a way to keep your place.
  • How the gate knows: a base-defined workflow reads your comment (your user id, the current head sha) and sets keel/tried: success, failure, or neutral with your skip reason. It is a required check when the report has a try-it section (open point 9). The sign-off copies it into mr/v1. A new commit resets it, as it does every check.
The instruction must holdWhat that means
What you checkOne line in your words: the behaviour you will see work.
WhereThe absolute path of the WU's worktree and the head sha, with the two commands that prove it: cd <abs worktree> && git rev-parse HEAD (expect the sha) and git status --short (expect nothing). The router has the worker idle first. A step that writes real state uses a scratch worktree or repo the helper makes, never your main checkout.
Build and runThe exact build command and what "done" looks like (cargo build → Finished), then the built binary by path (./target/debug/keel …). Never an install over the keel your hooks run.
StepsNumbered. Each: one command, the output to expect (exact lines, or what to look for), and what a failure looks like.
Real stateEverything a step touches outside a temp dir (a repo's hooks, ~/.claude, Telegram, a running session), with backup and restore commands. Prefer a temp home; say "touches nothing real" when that is so.
CleanupHow to remove what the steps made.
ReportThe three comment forms above, with the step numbers.

Example. W3's watch: 1) cd <worktree> && git rev-parse HEAD shows the sha. 2) cargo build ends with Finished. 3) Run the helper; it arms the watch on a scratch pull request and prints WAITING. 4) Comment /keel go there from your phone; within a minute the terminal prints COMMAND from=owner verb=go. 5) Comment from a second account; nothing prints. 6) The helper's cleanup closes the scratch pull request. Then you comment /keel tried pass on the WU's pull request.

Rejected: built binaries, artifacts, pre-releases and Codespaces as the main route: they test a different machine and setup than the one the work runs on, and cannot run the router tooling at all.

The work never waits for a sign-off; only the gate of a dependent pull request does.

Dependencies.

  • None (the usual case): sibling pull requests, merged in any order. No evidence crosses between them; the epic walk joins them at the end.
  • Code needs the rule or doc change: the code branch starts from the rules branch's tip and the worker keeps working. Once the rules pull request merges with --no-ff, the rules tip is part of the epic, so the code branch's merge-base with the epic is that tip and its range holds only its own commits. Notes and review are written after that merge; written earlier, check 4 (the review's base) and the notes' base no longer match, and they are rewritten. Reasoned from how git computes a merge-base; a scratch probe of it was denied in this session, so W7's integration test is the proof. Until the rules merge, GitHub's diff of the code pull request also shows the rules commits; cosmetic.
  • The rule or doc describes the code (an architecture row for a new command): it follows the code, as a docs pull request after the code merges; it never holds the code.

Conflict risk. Two open pull requests editing one file conflict at the second merge, and GitHub refuses that merge. The router then turns the pull request back to draft with a conflict label, and that WU's worker merges the epic into the branch and resolves it there (never a rebase). The walk skips that back-merge as a seam, but the tip changes, so the branch's notes and sign-off are redone before the router marks it ready again (open point 18). Rejected: one open pull request per shared file (work waits), stacking every pull request on the last (one slow item holds all), and leaving rule edits inside code WUs (today's stop).

Options weighed (answers in open points 14–16, 18): separate sibling pull requests (recommended), stacked pull requests (only when the code needs the change), one docs pull request per epic collecting every doc edit (fewer pull requests, but it waits for the slowest edit). Conflicts are fixed on the conflicted branch, not prevented by waiting.

Incremental path

  1. W1 first: pure signal, no rule changes, no new credential. If it is all you keep, sandbox reds are gone.
  2. W2, then W3: the bot and the watch. You can still sign and merge locally; pull requests are a view.
  3. W4: your approval becomes a sign-off; the typed sign-off still works.
  4. W5 last: only then does GitHub refuse a red merge. Turning its rules off returns you to today's flow.
  5. W8 after W4; W9 any time after W2, starting with its two checks (Pages here, comments from a Pages page).
  6. W6 after W3; W7 after W4, and first among the rest if rule edits keep stopping workers: it removes the one check that blocks work (§7, C8).

Fallback, always: every gate still runs locally; a typed sign-off and a local --no-ff merge pushed by you remain valid, because the gate judges notes, not where the merge happened.
