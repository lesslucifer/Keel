How you approve it

  1. You read this plan and comment, or tell the router it is fine.
  2. The worker reads the code and W1 to W3, and writes one result doc. It opens with a picture.
  3. The router tells you it is ready. You open it in your browser and comment.
  4. The router opens a pull request into the epic. You approve it on GitHub. Your approval is the sign-off, and auto-merge merges it.

Terms

Waiting itemOne thing that needs you: a plan to approve, a result to sign, a merge, a rule-file commit, a question.
Hand-offWhat the item gives you: a doc to open, a button that runs its command, or both.
Done-signalWhat the app sees once you acted, such as your sign-off on the tip in git. Then the item leaves.
Run buttonA button that runs one fixed command of keel or git for you, after you confirm it. The command is the one you would type; the app adds no logic to it.
DiffThe code changes of a work unit or an epic.

The risks of keeping "sent" in memory only

Your question on point 2. The short answer: the risk is small, and smaller than a file would be. In order of weight:

#RiskWhat happensHow W4 keeps it small

Tests and checks

Unit and integration: waived. W4 changes only docs/work/, so no code path changes. The range is exempt from test, review and doc notes. Your sign-off still runs.

The checks the worker runs instead, by a script in a scratch folder, with raw output in the result's evidence:

  1. Every item covered. Each W1 "a button" job (j9, j10, j12, j22), each must or should need that waits on you (n1, n2, n3, n6), and each item the epic's W4 and W3 blocks name (plan, result, rule-file commit, question, failed gate, merge conflict) has a row, or a line saying who acts instead.
  2. Every command real. Each run command's subcommand and flags appear in keel's usage text at cf4c752 (src/mr.rs), or are plain git. The order matches the skills' sign-off sequence.
  3. Every run is today's command. Each button names one program, its list of values and its folder; no shell, no step of the app's own between your confirm and the command. The text shown is the text run, so the same line works in your terminal. Only keel mr confirm, keel mr commit and git merge --no-ff are run; each other writing command in W2's table stays never run.
  4. Every value checked. Each placeholder in a command names its source and its check, such as a full commit id or a branch name of the expected shape.
  5. Every done-signal read-only. Each is read by a command on W2's list of commands that write nothing. A "sent" mark lives in the app's memory only, and no item leaves on it alone.
  6. The diff compared. Three places, the same yardsticks, one recommendation.
  7. Local sources exist. Every repository path cited passes git cat-file -e cf4c752:<path>.
  8. Doc check. keel verify-doc is green on the result.
  9. Scope. git diff --name-only cf4c752..<tip> lists only docs/work/ files.
