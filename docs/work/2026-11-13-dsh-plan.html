E-DSH · The same rules on DeepSeek Harness

Keel's rulebook reaches an agent through the files it writes for one host. This epic writes them for DeepSeek Harness too, beside Claude Code, and gives a host without doc hooks a place where a broken doc still stops.

T3 · epic plan · 2026-11-13 · epic/E-DSH · Keel

The problem

Keel's rules reach an agent only through the files it writes for one host. In a DeepSeek Harness (DSH) session on a Keel project an agent sees no skills, no doc check, no worker recipe: the rulebook is silent. This epic puts the same rules in front of a DSH agent, beside Claude Code, and stops a broken doc at the review on a host with no doc hook.

W1 · The initialiser gives DSH the rules

In short: one embedded list writes both skill roots. A repo initialised by Keel also carries the skills a DSH session loads. Nothing written for Claude Code or Codex changes.

  • Init writes .dsh/skills/keel-* and the project-owned project-router beside .claude/skills/: same bytes, same create-or-keep and -f ask.
  • The printed next steps name the DSH root, and say a host plugin is installed in the DSH profile, never in the project.
  • Keel's own policy lists .dsh/skills/ as rule-bearing, so this repo's DSH copy is protected like its Claude Code copy.

R1 (beside, not instead) · UC-INIT-1 amended, UC-DSH-1 new · DEC-53.

Integration: after keel init in a temp repo both roots hold the same bytes, the router template sits in both, a second run adds nothing, and every shipped skill's frontmatter is the shape DSH parses: a closed block, a one-line name in kebab-case matching its directory, a one-line description, and no nested SKILL.md under a skill. Unit: the DSH root list and the conformance scan.

W2 · The rules say what a host without hooks does

In short: the standard tells an agent to verify a doc after writing it, because a hook does that on Claude Code. On DSH no shell hook exists, so the standard says who runs the check and where a miss is caught.

  • The workflow skill keeps its two hook rows and adds the no-hook case: the check is a command you run, and the review's first step refuses a red doc.
  • The plan skill stops naming one host as the trigger of that check.
  • A host-only fact stays out of the standard: it belongs in the router skill's project section.

UC-DOC-1 amended, UC-DSH-2 new · DEC-54.

Integration: a content test reads the shipped skills and asserts the no-hook paragraph names the doc check and the review step, and that no shipped skill claims the gate needs Claude Code. Unit: waived, text only.

W1

W3 · A DSH router has a worker recipe

In short: the router skill learns the DSH way to dispatch, read and retire a worker, and the project template gains the slots a project fills in. The Claude Code recipe stays as it is.

  • One table maps each mechanism: dispatch, follow-up, report, fleet list, stop, and the preset that lets an unattended worker commit.
  • A DSH worker does not message the router: its report is its transcript, read at each wake and before each ask. A DSH subagent is not a worker, because it inherits the router's directory.
  • The persona on DSH is the worktree's AGENTS.md plus the skills plus the brief; the project records which preset its router selects.

UC-ROUTE-5 and UC-ROUTE-6 amended, UC-DSH-3 and UC-DSH-4 new · DEC-55, DEC-56 · rulings R0, R2, R4.

Integration: a content test asserts the transport table names every DSH worker tool, the template carries the harness and preset slots, and the skill description no longer says Claude Code only. Unit: waived, text only.

W1

W4 · A red doc stops the review on any host

In short: the review's first step verifies every doc the range changed. A red doc stops it and names the problems, so a host with no doc hook cannot reach a review with a broken doc.

  • New check 0·doc beside 0·tree; it reads each changed doc at the tip and applies the same rules as keel verify-doc.
  • The merge gate keeps reading doc facts only: form is checked when authoring (the hook) and when a review starts.
  • Drafts stay silent, as they are today.

UC-DOC-1 amended, UC-DSH-2 new · DEC-54.

Integration: on a WU branch, a ready doc missing one item makes preflight red 0·doc naming that item; the fixed doc is green; a draft is silent; a range with no doc is green. Unit: the changed-doc selection (docs root, a deleted doc, a doc outside the root).

Details

Acceptance

  • A fresh repo after keel init carries both skill roots; a DSH session lists the six keel-* skills and the project's router skill, and a worker reads its worktree's AGENTS.md.
  • Every Claude Code and Codex artifact is byte-identical to before this epic, and the existing tests stay green.
  • A ready doc with a problem is refused by keel verify-doc and by the review's first step, on any host.
  • A DSH router dispatches one worker per worktree, reads its report from the transcript, sends follow-ups and stops it.
  • Under the Auto Review preset a worker's medium call (an add, a commit, a minting request) runs; a high-risk call is denied.
  • The epic test passes, and the live DSH run is recorded as evidence.

Out of scope

  • Replacing Claude Code, or changing any artifact, hook or test it uses.
  • Shipping a host plugin inside the keel binary; there is no channel for one. The epic ships the contract and the install line.
  • Re-implementing the Auto Review preset, the worker-session plugin, or any DSH UI.
  • Worker cold resume, out-of-process workers, a watchdog on DSH.

What the host makes true

Three facts shape the plan and are not up for design here.

  • A DSH session's sandbox root is the directory it was created in, and it never changes; a subagent always inherits its parent's directory. So a worker cannot be a subagent: the worker-session plugin creates the session itself, with the worktree as its directory (ruling R3).
  • DSH has no shell-hook surface: no host setting runs a command on a tool call or at turn end. What replaces Keel's two doc hooks is therefore either a host plugin or a check on a path every host shares (W4) — verified from the installed packages, not from memory.
  • With approvals off, a medium call is rejected unless something decides it. The Auto Review preset is how a stock install lets an unattended worker add, commit or mint, and denies what it calls high risk (ruling R4).
