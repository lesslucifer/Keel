E-ROUTERFIX.W2 · Router subscribes to a worker's end

The WU plan for wu/E-ROUTERFIX/w2-router-notify. The router can ask to be notified when a headless worker exits, and it can never send that worker text.

T3 · WU plan · 2026-11-09 · Keel · off epic/E-ROUTERFIX 07b4940 · epic plan E-ROUTERFIX

Why

The enforced router has no Monitor, no shell loops and no Agent (DEC-30, DEC-31). It currently learns that a worker has ended only through a watch worker, the 10-minute heartbeat or the owner. Claude Code's cross-session SendMessage takes notify_when_idle: true with the message omitted. That is a pure subscription: one notice when the target session next goes idle or exits, at no cost to the target. Earlier research saw the idle-to-worker direction work live. The direction this WU needs, the router hearing about a worker's exit, had not been observed.

Findings (from the tool's real schema)

#Fact
F1SendMessage parameters: to (required), message (string or a protocol object, default ""), notify_when_idle (boolean), summary (a label for the sender's own transcript, not transmitted). With the message omitted, it is a pure subscription. notify_when_idle works from the main conversation only, and the enforced router is a main conversation ("agent": "router").
F2ListAgents takes no usable parameters (channel/q are "not available in this build"). It is read-only.
F3A launcher worker runs as claude -p … -n <name>, and <name> is its SendMessage address (confirmed live: to: "probe-notify" resolved).
F4A worker is a full-tool session. Router text delivered to it would act as a second brief, with no snapshot or sha256 (DEC-32). So the guard must refuse any message content, not just discourage it.

Requirement

For agent_type == "router", the guard allows ListAgents, and allows SendMessage only when its input is an object with a string to, notify_when_idle exactly true, message absent or empty, and no key outside to/notify_when_idle/message/summary. It denies every other SendMessage, and the router's tools: line lists both tools.

E-ROUTERFIX.W2 (epic plan summary) → UC-ROUTE-6 (the posture's tool list), UC-ROUTE-5 (the launcher worker recipe gains "subscribe after RUNNING") · new DEC-36.

Design

  • scripts/router-guard.jq: tools gains SendMessage and ListAgents. A new SendMessage branch implements the requirement. Keys are an allow-list, so a content-bearing parameter added later is denied by default.
  • .claude/agents/router.md: the tools: line gains both tools (tests/router.rs asserts it equals the guard's list), plus one posture bullet.
  • scripts/router-worker.sh: the header comment names the subscribe step. The code is unchanged.
  • skills/keel-router/references/worker-ops.md (and its .claude/skills/ copy): a "Notify" step in Mode 2. This is rule-bearing and goes in the owner's keel mr commit.

Expected

  • The guard returns nothing (allow) for {"to":"e-x-w1","notify_when_idle":true}, and for the same input plus "message":"" and a summary.
  • The guard denies a non-empty message, a protocol-object message, notify_when_idle false, missing or a string, a missing to, an unknown key, and a non-object input.
  • The guard allows ListAgents. Other agent types still pass untouched.
  • Live (evidence, not a gate): a launcher-spawned haiku worker, subscribed right after RUNNING, produces an idle notice for the subscriber when it exits. The actual outcome is recorded either way.
