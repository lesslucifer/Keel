The run buttons: five lines, three commands

In short: each button runs one program with a fixed list of values, in one folder. The shown line is the run line, so it also works in your terminal. Nothing else is ever run.

#ButtonProgram and valuesFolder
R1Sign off… (a work unit)keel mr confirm wu <tip> --as <id> --target <epic> --report <report><epic folder>
R2Merge… (a work unit)git merge --no-ff --no-edit <wu branch><epic folder>
R3Sign off… (an epic)keel mr confirm epic <tip> --as <id> --report <report><epic folder>
R4Merge into main…git merge --no-ff --no-edit <epic><main folder>
R5Commit… (a rule file)keel mr commit -m <message> --as <id><branch folder>

How one run goes, R1 as the example:

  1. You click "Sign off…". The window asks the hidden part to run item E-DOCSPLIT.W2. It sends the item's name, never a command.
  2. The hidden part re-reads every value from git and rebuilds the line. If the tip moved since you saw it, the item is redrawn and nothing runs.
  3. It shows the macOS dialog: the folder and the full line. You confirm once.
  4. It runs keel with its list of values in that folder, with no shell. A branch name or a message is one value; it cannot become a second command.
  5. Keel's words appear under the item as text, control characters blanked. The app reads nothing into the exit code.
  6. The watcher sees the sign-off note; the item moves to its merge step.
  • No logic of the app's own between your confirm and the command. Keel's checks run inside keel; the merge's gate runs in keel's git hook, as when you type it.
  • One run at a time per project. No timeout and no stop button: a merge stopped half-way leaves git mid-merge. A merge into main runs keel's tests in its hook, so it can take minutes.
  • The terminal line is shown under each button: cd '<folder>' && <the line>, the message in single quotes. It works without the app.
  • Never run: every other writing command in W2's table (keel verify-dod, keel preflight, keel notes write, the inbox's consume, notify-owner's send, git fetch, git push), and any worker's command.
  • Signing with a key is not designed: keel asks ssh-keygen to sign, which may ask for a passphrase the app has no terminal for. Your username signs today (DEC-48 deferred key-only).

Details

The commands, checked against keel's code at cf4c752

  • Usage. keel mr confirm <wu|epic> [<tip>] [--as <identity>] [--target R] [--report <path>] … (src/mr.rs l.607); keel mr commit -m <msg> [--as <identity>] (l.581); the mr usage (l.1346). R1, R3 and R5 use only those flags. R2 and R4 use plain git: --no-ff and --no-edit are in git merge -h (git 2.50.1).
  • Order. Sign, then merge: skill keel-workflow, the lifecycle (steps 5 and 6), and skill project-router, the sign-off sequences.
  • Folder. keel mr runs only from a checkout's root holding .git (src/main.rs l.634–639). Its rules come from that folder's .keel/config.toml file (l.112, l.668). The merge's hook judges by the target's committed rules instead (l.122, l.662), and runs keel by PATH (l.393–416).
  • Values. A flag's value is the next word (src/mr.rs l.488), and a word starting with - is taken as a flag (l.323): hence the tip, report and message checks. Identities: l.45. A report path with a newline is refused (l.672). An epic report outside git is hashed from the folder's file (l.410–433). The target must be a local branch (src/gate.rs l.887–897).
  • Output. A sign-off prints mr/v1 on <10 characters> - <tier> <id> attests <report> (src/mr.rs l.782); a refusal prints the gate's FAIL lines (src/gate.rs l.490–504) and keel's "refused" line (src/mr.rs l.636).
  • Editor. Without --no-edit, a merge typed in a terminal opens an editor; run from the app it would not. --no-edit makes both the same (git help merge).

A risk found on the way, older than the app

keel mr commit runs git commit in the worker's folder. Git's pre-commit hook then reads that folder's .keel/config.toml file, which the worker can edit without committing. If it says the commit touches code, the hook runs its lint setting as a shell command, as you (src/main.rs l.657, l.582–598, l.276–277). This is true when you type the line today. The app does not add to it. Its dialog lists every unstaged file, so an edited .keel/ file shows. The fix is a keel change: the commit hooks read the committed rules (follow-ups).
