E-SEED.W9 — Report binding rework + hooks follow-up

Two items the owner deferred out of W4. First, drop the fixed or inferred report path from keel mr confirm, make the report requirement configurable, and treat the report as a receipt (W4 open point 11). Second, settle how Keel's hooks coexist with other git hook tooling (W4 open point 19).

v1 · 2026-11-07 · Keel · T2 WU plan · epic: E-SEED · depends on: W4 manual review · status: ready (dispatch does not wait on sign-off; the owner reviews asynchronously)

Requirement

Report binding (W4 point 11). Every mr/v1 sign-off today attests exactly one report, chosen by path. The owner's decision on W4 point 11: "let's drop the report path, report requirement can be configurable; and it's a receipt as well." After this WU, whether a sign-off must attest a report is project policy in .keel/config.toml. The report is found without a hard-coded file name. A missing report is reported as missing evidence, with a fix -> line, like any other missing receipt. It is not a usage error from mr confirm.

Hooks follow-up (W4 point 19). The hole point 19 recorded (a branch shipping a no-op .keel/hooks/pre-merge-commit that ran for its own merge) is already fixed, by commit 0412b3c. This WU does not reopen it. What is still open is the question behind the owner's comment that a fix "may conflict with another git-based hook": Keel's hook install takes over core.hooksPath for the whole repo. This WU decides, with the owner, how that coexists with other hook tooling, and then implements the decision.

Scope

Part 1 — the report binding today

As built in W4 (src/mr.rs):

WhereWhat it does now
confirm(), lines 311–328The report is --report <path>. Otherwise it is the single changed file in base..tip that starts with docs.root and ends with -result.html. Zero or several such files means mr confirm exits with "N result reports changed in the range - pass --report". The report is always required. There is no way to sign off without one.

manual_review() (check 8), lines 404 and 411–415The payload is rebuilt with the note's report/report_hash, and the signature is verified over it. The report is then re-hashed at the note's path. A mismatch is red, and an epic report found nowhere is accepted on the signature alone.
Docs that state the ruleSeed plan UC-MR-1 ("attests the result report's bytes"), skills/workflow/SKILL.md (§2 sign order, §3 notes table, check 8 row, §6 sign-off table), skills/plan/SKILL.md (result-report rows).

So the path is either typed by the human or inferred from a file-name convention (*-result.html). Neither is configured anywhere, and the requirement itself is hard-wired.

Part 1 — proposed change

  1. Configurable requirement. New optional key in the existing [mr] table, next to tiers, following the same style: a serde default that keeps today's behavior, and an unknown value is an error naming the key. 
    [mr]
tiers  = ["email", "username", "key"]
# Must a wu/epic sign-off attest a result report?
#   "required" - mr confirm refuses and check 8 is red without one (default: today's rule)
#   "optional" - attested when one is found; a sign-off without one is valid
#   "none"     - never attested; mr/v1 binds the diff only
report = "required"
    A per-level form (report = { wu = "required", epic = "optional" }) is open point 2. It is not built unless the owner wants it.
  2. No path convention. The report is found by what it is, not by its file name. It is the changed doc whose data-artifact carries the level's result role (wu-result for a WU, epic-result for an epic). That is the same markup keel verify-doc already checks (src/verify_doc.rs checklist()). --report stays as an explicit override. The -result.html suffix filter is deleted. The epic case needs a decision, because its report is archived out of git by gate time and so is not in base..tip (open point 3).
  3. The report as a receipt. Recommended reading of the owner's "it's a receipt as well" (open point 1 asks the owner to confirm it): the result report is evidence of the work, in the same family as test/v1, doc/v1 and cr/v1. So (a) when policy requires it and it is missing, the gate says so as a named check failure with a fix -> line, and sign-last refuses mr confirm before the human is asked to sign, rather than confirm failing on argument parsing; and (b) what was attested is recorded in the receipt chain. mr/v1 keeps the report's path and blob hash inside the signed bytes when there is one. The dod/v1 receipt then records which report the gate saw attested, so the receipt names the report and not only the diff.
  4. Format change. With report = "none" or "optional", report/report_hash can be absent. The MrNote fields become Option. The payload omits both lines when there is no report, so the signature never covers an empty placeholder, and the header goes to keel-mr/v2. Whether the note schema also moves to mr/v2 or mr/v1 is changed in place (nothing has shipped, and E-SEED runs ungated) is open point 4.
  5. Check 8. It reads the policy from the config it is handed. On the merge hook that is already HEAD's committed config (W4 point 14), so a branch cannot flip report to "none" for its own merge. "required" with no report in the note → red. A report in the note is always re-hashed and verified, whatever the policy.
  6. Docs. Amend seed-plan UC-MR-1 to "attests the result report's bytes when [mr] report requires one". Update the skills text listed in the table above and templates/config.toml.

Part 2 — the hooks, current state

Re-examined against the code on epic/E-SEED:

  • Fixed: the hook-tampering hole of W4 point 19. hooks_install() (src/main.rs, lines 318–347) writes every hook to <git-common-dir>/keel-hooks/ and sets git config --local core.hooksPath to that absolute path. Nothing under .keel/hooks is read any more. A branch's files cannot change which hook runs. Test: a_branch_shipping_neutered_hooks_cannot_skip_the_merge_gate (tests/verify_dod.rs). The skills, keel init and the Codex hook template already use the new location. Nothing in this part needs redoing.
  • Open: Keel takes over every other hook in the repo. hooks_install() overwrites any existing core.hooksPath without reading it. While core.hooksPath is set, git ignores .git/hooks/ entirely. I checked this on git 2.50.1: a .git/hooks/pre-commit that ran before the install no longer runs afterwards. So hooks installed by pre-commit, lefthook, husky v4 or by hand stop running silently once keel hooks install (or keel init) runs. Git 2.50 has no multi-hook-per-event mechanism to fall back on (git hook offers only run).
  • Open: the reverse is silent too. Tools that set core.hooksPath themselves (for example husky v5+, typically from an npm prepare script) overwrite Keel's value. Every Keel hook then stops running, including the pre-merge-commit gate, and no Keel command notices: nothing outside hooks_install() reads core.hooksPath. If such a tool points it at a tracked directory, the original point-19 hole is back.
  • Open: this reverses a Trawler decision. Trawler DEC-72 ("git runs the tracked hooks") chose a relative, tracked core.hooksPath and rejected an absolute one, because installed copies drift from the hooks the branch carries. Its gate entrypoints also refuse a checkout whose core.hooksPath is unset, absolute or points elsewhere. Keel deliberately went the other way to close the tampering hole. The drift risk is small, because Keel's hooks are three-line exec keel … shims and the logic lives in the binary. But DEC-72's "refuse when hooksPath is not ours" guard was not carried over. The epic's distillation plan re-records DEC-72, so Keel's own decision record must state the reversal and its reason.

Part 2 — options for the owner

OptionWhat it doesCost / conflict
A · leave as is, document itThe current behavior, plus one line in the install output and the workflow skill: "replaces any other hook manager".No code. Other tools stay silently off, and a tool resetting core.hooksPath silently disables the gate.
B · install refuses to clobberhooks install refuses when core.hooksPath is already set to something else, or .git/hooks/ holds non-.sample hooks. It lists them and offers a --force.Small. It makes the conflict visible at install time only.
C · chain the previous hooksEach Keel shim runs Keel first (fail closed), then the hook of the same name from the previous core.hooksPath or .git/hooks/, recorded at install.Real coexistence, at the price of Keel executing other tools' scripts, and those may be tracked (husky's .husky/). That re-imports branch-controlled code into the merge hook, after Keel's gate has passed. This is the conflict the owner flagged.
D · DEC-72-style guardkeel check, keel preflight and keel verify-dod wu|epic refuse (or warn) when core.hooksPath is not this repo's keel-hooks directory, and print keel hooks install.Small. It catches the silent-disable case the next time any Keel command runs. Combines with A, B or C.

Recommendation: B + D, with D as a hard refusal in verify-dod/preflight and a warning in check. Plus the Keel decision record for the DEC-72 reversal. C only if the owner needs another hook manager to run alongside Keel, and then only after deciding whether chained hooks may be tracked. Open point 5.

Expected result

With no [mr] report key, every W4 test still passes unchanged (the default is "required"). With report = "none", a WU with no result doc signs and merges green, and its mr/v1 carries no report fields. With "required", a WU with no wu-result doc is refused at mr confirm before signing, and at the merge as a named check failure with a fix -> line. A WU result doc named anything (not *-result.html) is found by its data-artifact. A branch that sets report = "none" on itself is still judged by the target's committed policy. For the hooks: the behavior the owner picks in open point 5 is enforced, and the DEC-72 reversal is written down.

Test plan

Extend tests/mr.rs and tests/verify_dod.rs (same fixture style: temp repo, real keel binary, throwaway ed25519 key, SSH_AUTH_SOCK removed):

  • Policy matrix: required / optional / none × report present / absent, at WU level. Each cell asserts confirm's outcome and check 8's.
  • Found by role, not name: a wu-result doc named docs/work/outcome.html is attested. Two wu-result docs in one range are refused with a fix naming both.
  • Policy from HEAD: a WU branch that sets report = "none" while the epic requires one is red at the merge hook.
  • Tamper still caught: under "optional", a note whose report hash is forged is red. An epic report edited after signing is still re-hashed red (the W4 test keeps passing).
  • Hooks (per the chosen option): for B, install over a foreign core.hooksPath and over a non-sample .git/hooks/pre-commit is refused, and passes with --force. For D, after git config core.hooksPath .husky, keel verify-dod wu refuses with the keel hooks install fix.
