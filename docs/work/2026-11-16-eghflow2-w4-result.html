Why pull_request_target holds

  • No job holds a write token or a secret: contents: read everywhere, no secrets., no token passed, persist-credentials: false, pinned actions, event values through env: only. The lock test pins each.
  • Every checkout is github.sha, main's commit; the head is git data in scratch worktrees. Only keel/ci runs it, and that verdict is the head's own tests.
  • What head code in keel/ci could still take is the run's runtime token. With it, it could write the run's artifacts or a cache scoped to main. The keel artifact is refused unless its SHA-256 equals build's job output, which no other job can change. No workflow reads a cache, and the lock test keeps it so for every file in .github/workflows.
  • A fork's pull request runs nothing of its own: the script refuses it before any git call, in every job.
  • The required names are new. A branch cut before W4 still runs its old ci, gate and docs with head code, but it can never report keel/ci, keel/gate or keel/docs.
  • Residual, from before W4: an old commit's release.yml still runs on that branch's pull request, holding contents: write. If the head's dist-workspace.toml sets pr-run-mode = "upload", it builds head code with that token. Such code could write refs/notes/* on GitHub, but it cannot set keel/sign-off or move a protected branch. Open point 2 below.
