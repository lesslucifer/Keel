E-SEED2.W13 · Hook environment leak and landed-tip sign-off

Keel stops passing git's repository-locating environment variables to the lint and test commands it runs, and to its own git calls. Every test spawn helper strips the same variables. keel mr confirm refuses a tip that its target already contains.

T3 · WU plan · 2026-11-10 · Keel · branch wu/E-SEED2/w13-hook-env off epic/E-SEED2 36cd14d · epic plan E-SEED2 W13 · owner ruling 2026-11-10

Requirement

Keel locates the repository only from its working directory. It runs git and the configured check.lint / check.test commands without the inherited variables that git rev-parse --local-env-vars lists. The one exception is GIT_INDEX_FILE, which keel's own git calls keep. As a result, keel check, run with GIT_DIR pointing at another repository, checks and changes only its own repository. The pre-push scratch worktree checks the pushed sha. Every test spawn removes the same variables. keel mr confirm refuses, and writes nothing, when the tip is already an ancestor of its target.

Epic E-SEED2.W13 (owner ruling 2026-11-10) · UC-GATE, the pre-push check and keel check (use-cases/workflow.html) · UC-MR-1, sign-off (UC-MR-1) · testing charter rule "Hermetic".

Problem and evidence

Incident, 2026-11-10 13:24 and 13:36. Someone ran git push from the linked worktree Keel-E-SEED2. The push started the pre-push hook, which runs keel hook pre-push, then keel check, then lint and cargo test. For a linked worktree, git exports an absolute GIT_DIR (…/.git/worktrees/<name>) to its hooks. sh() (src/main.rs ~148) passes its whole environment on to the child process, so cargo test inherited that GIT_DIR. The fixtures in tests/cli.rs then ran git inside their TempDir, and git followed GIT_DIR to the real repository instead. The fixture spawn helper is run() at cli.rs ~10. The fixture steps that wrote to the real repository:

  • git init (~29) set core.bare=true in the shared .git/config.
  • The user config steps (~30-31) set the identity to t / t@t.
  • The fixture commits (~72-74) moved epic/E-SEED2 onto a fixture commit.
  • git switch -c work (~77 and ~138) created a branch named work.
  • A test note was added.
  • keel hooks install rewrote .git/keel-hooks/*.

The owner restored the repository by hand. In the main checkout, git exports the relative GIT_DIR=.git. That value resolves to the TempDir's own .git, so it does no harm. Only linked worktrees leak.

The same class of bug elsewhere (read-only audit, re-derived for this plan):

  • Test helpers. No test spawn helper removes the variables. The sites are cli.rs 11, 119, 291; init.rs 7, 44, 61, 70, 129, 135, 267, 362, 368, 387; mr.rs 10, 125; router.rs 262, 341, 1055, 1061, 1072 (and the /bin/sh spawns at 240 and 1028, whose scripts call git); verify_doc.rs 12; verify_dod.rs 14.
  • Clones. init.rs 398 and 436 run git clone with no current_dir. Under an inherited GIT_DIR, git clone uses that directory as the destination's git dir. These are the most dangerous calls in the suite.
  • Product: check_push. The scratch-worktree branch (main.rs ~223-230) calls check(&dir, …). That runs tree_key, git_dir and sh() with current_dir(scratch) but with the inherited GIT_DIR. So the cache key, the cache file and the test run all target the hook's worktree, not the pushed sha. The proof for a non-HEAD push is therefore false.
  • Product: git(). Every keel git call goes through git() in main.rs ~124 (gate.rs and mr.rs use it too). repo_root() goes through it as well. The only other spawn in src/ is init.rs:255 (sh -c "command -v keel"), which never touches git.

A separate finding (item 3). keel mr confirm wu <tip> --target <epic> was run on a tip that was already merged into the target. Then merge-base(target, tip) = tip, so the range is empty and has no code paths. The diff is exempt, so sign-last (gate::sign_ready) is green. Keel then signed base = tip with the empty change hash and overwrote the valid mr/v1 note from the real sign-off.

Design

(1) Product: keel never forwards git's local environment

  • One list. Add const GIT_LOCAL_ENV: [&str; 15] in src/main.rs. It holds exactly what git rev-parse --local-env-vars prints on the installed git: GIT_ALTERNATE_OBJECT_DIRECTORIES GIT_CONFIG GIT_CONFIG_PARAMETERS GIT_CONFIG_COUNT GIT_OBJECT_DIRECTORY GIT_DIR GIT_WORK_TREE GIT_IMPLICIT_WORK_TREE GIT_GRAFT_FILE GIT_INDEX_FILE GIT_NO_REPLACE_OBJECTS GIT_REPLACE_REF_BASE GIT_PREFIX GIT_SHALLOW_FILE GIT_COMMON_DIR. The list is hardcoded so that there is no extra git spawn per call. A test checks that it covers git's own list (see the test plan).
  • One helper. fn no_git_env(c: &mut Command, keep_index: bool) -> &mut Command calls env_remove on every name in the list. It skips GIT_INDEX_FILE when keep_index is set.
  • sh() calls no_git_env(&mut c, false). A configured lint or test command finds its repository from its working directory and nothing else. This alone closes the incident path.
  • git() calls no_git_env(&mut c, true) before it applies its own envs. The explicit GIT_INDEX_FILE that tree_key sets is applied last, so it still wins. Because repo_root() uses git(), the whole binary now locates the repository from its working directory. Git runs hooks at the worktree root, and discovery from there finds the same git dir that git exported, in both the main checkout and linked worktrees.
  • Why GIT_INDEX_FILE is kept in git(). Git's commit hooks (pre-commit, commit-msg, pre-merge-commit) get GIT_INDEX_FILE. For git commit -a or git commit <paths>, it names a temporary index (index.lock or next-index-*.lock), and only that index holds what is being committed. mr::commit_msg reads git diff --cached. If it stripped the variable, it would read the stale real index and miss a rule-bearing change, which would bypass the Reviewed-By check. sh() still strips the variable, because a test suite should never see the caller's index.
  • check_push's scratch path needs no code of its own. Every call it makes (git(), git_dir(), tree_key(), sh()) is now cleaned, and each runs with current_dir(scratch), so each one resolves to the scratch worktree. Pre-push hooks never receive GIT_INDEX_FILE, so keeping it in git() cannot reach this path. This is stated as a risk below.
  • Not stripped: GIT_CONFIG_GLOBAL, GIT_CONFIG_SYSTEM, GIT_CONFIG_NOSYSTEM, HOME, GIT_AUTHOR_*, GIT_COMMITTER_*, GIT_REFLOG_ACTION. These variables do not locate a repository. They carry the user's own scope or identity, and the gate reads GIT_REFLOG_ACTION from keel's own environment, not a child's. GIT_CONFIG_PARAMETERS and GIT_CONFIG_COUNT (from git -c) are in git's list, so they are stripped. Without GIT_CONFIG_COUNT, git ignores the GIT_CONFIG_KEY_n / GIT_CONFIG_VALUE_n pairs, so those need no entry (open question 1).

(2) Tests: every spawn helper strips the same variables

  • New module: tests/common/mod.rs, with pub const GIT_LOCAL_ENV (the same 15 names; a test crate cannot import from the binary) and pub fn no_git_env(c: &mut Command) -> &mut Command, which strips all 15 names, GIT_INDEX_FILE included. Each test file adds mod common;. Cargo does not build tests/common/mod.rs as a test crate of its own.
  • Every spawn that can reach git goes through it. That covers each helper listed in the audit above, plus the sh spawns in router.rs and init.rs whose scripts call git. Spawns of jq, ps and kill cannot reach git and stay as they are. Where several call sites in a file share a helper, the helper is changed once.
  • The clones at init.rs 398 and 436 gain .current_dir(d.path()), on top of the stripping.
  • W12 (wu/E-SEED2/w12-owner-watch) will call common::no_git_env from its own hermetic() after it back-merges the epic. The name no_git_env is chosen so it does not clash with W12's hermetic().

(3) keel mr confirm refuses a tip that has already landed

  • sign_ready already returns (tip, base) with base = merge-base(target, tip). base == tip holds exactly when the tip is an ancestor of its target, the tip and the target being equal included. So no extra git call is needed.
  • Add fn landed(tip: &str, base: &str, target: &str) -> Option<String> in src/mr.rs. It returns the refusal text when tip == base, otherwise None.
  • Call it in confirm straight after sign_ready, before pick_report and before anything is hashed, signed or written. When it returns text, print it and exit 1. The text: mr confirm refused - <tip> is already contained in <target> (merge-base = tip): the range is empty, so a sign-off here would bind the empty diff and replace the note that attests the real change\n fix -> nothing to sign; the existing sign-off stands. To sign new work, commit it on the branch and confirm the new tip.
  • The target name comes from the same gate::target_of that sign_ready uses. The fix exposes it through the sign_ready return value (a triple) so the refusal can name it. Both levels are covered: a WU against its epic, and an epic against main.
  • Out of scope: making verify-dod red on an empty range. An already-merged tip is legitimately exempt there (open question 4).

Expected result

  • keel check, run in fixture repo A with GIT_DIR=<B>/.git (B is a second temp repo), runs A's test command against A: the command's probe records A's absolute git dir, and A's keel-check-green cache exists. Every file under B's .git is byte-identical before and after, and its file list is unchanged.
  • keel hook pre-push, run from a linked worktree with git's absolute GIT_DIR and a pushed sha that is not HEAD, runs the test command in the scratch worktree with HEAD = the pushed sha.
  • In a linked worktree, a pathspec commit (git commit -m … docs/rules.html, which uses a temporary index) that touches a rule-bearing path and has no trailer is still refused by commit-msg.
  • Every test spawn that can reach git goes through common::no_git_env, and both clones set current_dir.
  • keel mr confirm wu <tip> on a tip already merged into its epic exits 1 with the "already contained" refusal. The tip's mr/v1 note is byte-identical afterwards. The same holds for an epic tip already in main.

How the regression test stays hermetic. Both repositories and the probe file are TempDirs. The test first strips its own inherited variables (no_git_env) and only then sets the decoy GIT_DIR, which points at temp repo B. The real repository is never reachable, even when cargo test itself runs under a leaked GIT_DIR. The snapshot comparison shows that B, the stand-in for "the real repo", is unchanged. The worker proves each new integration test red against the unfixed binary before the fix lands, and records that in the result report.

Commit order. c1: no_git_env, git(), sh(), with their unit tests and the two cli.rs regression tests. c2: tests/common and every helper and clone. c3: the mr confirm refusal, its unit test and its integration test, plus the pathspec-commit extension. c4: distillation (DEC-41 and UC text). c5: the result report. Each commit carries unit tests for all the code it changes.

Risks

#RiskMitigation
R1The fix is not live until the installed binary is replaced. The hooks run keel from PATH. A push from a linked worktree keeps leaking until the owner installs the fixed build. The worker cannot do that.The worker reports this to the owner. Until the new binary is installed, push from the main checkout, where git exports the relative GIT_DIR=.git. Never use --no-verify.
R2Keeping GIT_INDEX_FILE in git() would mis-point a call on another repository if a hook that exports it reached such a call.Only check_push works on another directory, and pre-push never receives GIT_INDEX_FILE. The unit test locks the exception to that one name.
R3Behaviour change: GIT_DIR=/x keel … run from an unrelated directory no longer reaches /x.Deliberate: keel's contract is "run inside the checkout". DEC-41 records it.
R4A future test adds a spawn and forgets the helper.Open question 2 (source scan). With (1) in place, the hook path is safe whatever the test helpers do.
R5Text conflict with W12 in tests/router.rs.W13 edits only the spawn lines. W12 back-merges the epic and resolves the conflict on its own side.
R6The worker runs cargo test during development under some hook.Developers run cargo test from a plain shell. After c2, even a leaked GIT_DIR can no longer reach the real repository through the tests.

Open questions (decided here, owner may override)

#PointRecommendation (the default this WU proceeds on)
1GIT_CONFIG* scopeStrip only what git lists (GIT_CONFIG, GIT_CONFIG_PARAMETERS, GIT_CONFIG_COUNT). Leave GIT_CONFIG_GLOBAL, GIT_CONFIG_SYSTEM and GIT_CONFIG_NOSYSTEM: they select the user's scope, not a repository. Isolating the test suite from the developer's ~/.gitconfig is a separate hermeticity item; it goes to the backlog, not here.
2Guarding the helpers against regressionsAdd one cheap source-scan test (tests/cli.rs). It fails when a Command::new("git"|"sh"|"/bin/sh"|CARGO_BIN_EXE_keel) in tests/*.rs does not go through no_git_env. It is deterministic and reads only the repository's own test sources.
3Hardcoded list vs asking git at runtimeHardcode it, with the coverage test. Asking git at runtime costs one extra spawn per keel process and per test helper, for no gain the test does not already give.
4Should verify-dod also go red on an empty range?No. A merged tip is legitimately exempt at the gate, and the walk re-judges seams. Only signing an empty range is wrong, so the refusal lives in mr confirm.
5GIT_INDEX_FILE in git()Keep it in git() and strip it in sh() (design 1). Stripping it in git() as well would open a Reviewed-By bypass through git commit -a or a pathspec commit.
