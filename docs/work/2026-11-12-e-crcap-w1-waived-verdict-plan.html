E-CRCAP.W1 · A waived review is recorded as WAIVED — plan

The cr note gains a third verdict, WAIVED, with the reason. The merge check accepts it and prints it. Sign-off shows it with the review history and needs the owner's explicit yes, and the sign-off covers the waiver, so a later edit is caught.

Requirement

keel notes write cr --verdict WAIVED --reason "<reason>" writes a cr/v1 note with verdict: WAIVED, the reason in waiver and the same code binding as a review, and refuses an empty reason or a reason on PASS or FAIL; keel mr confirm … --waive-review "<reason>" lets the owner waive a review in the sign-off itself, writing that note together with the signature, so no session writes a waiver for the owner; the merge check accepts that note in check 3, prints WAIVED 3·review: <reason>, passes a waived WU in the epic walk and records review: WAIVED in the dod/v1 receipt; keel mr confirm on a waived tip prints the waiver and the branch's review history and refuses, writing nothing, without --accept-waiver; with it, the sign-off carries the waiver's hash (and a key-backed signature signs it), check 8 rebuilds that from the current cr note so a reworded waiver, or a signed PASS turned into a waiver, fails the merge; and a tip with no waiver signs exactly as today.

The design

The writer

Older readers ignore the new field; an older keel reads WAIVED as "not PASS" and stays red (fails safe)
--verdict WAIVED with no --reason, or a blank onerefused, nothing written
--verdict PASS|FAIL --reason …refused: a reason belongs to a waiver only
Anything elseas today; the usage line names WAIVED

Open point 15 (v3): the open findings are W3's findings entries on the note ({location, claim, severity, evidence}) that carry no waived. The skill's jq step already records them for every round. v1's separate open_findings field is dropped: it duplicated that schema, and nothing after W3 would write it. The cap reason review cap: 5 rounds, <n> blockers open is an ordinary reason to this writer: W1 needs no cap-specific code.

The sign-off

flowchart TD
  C["keel mr confirm wu or epic tip"] --> Q{"waive review given?"}
  Q -->|"no"| S{"checks 1 to 7 green?"}
  Q -->|"yes"| SW{"everything but the review green?"}
  S -->|"no"| X["refused: sign last"]
  SW -->|"no"| X
  S -->|"yes"| W{"cr note on the tip is WAIVED?"}
  W -->|"no"| G["sign exactly as today"]
  W -->|"yes"| P["show the waiver, what is open, every round"]
  P --> F{"accept waiver given?"}
  F -->|"no"| Y["refused, nothing written"]
  F -->|"yes"| H["sign, with the waiver hash"]
  SW -->|"yes"| PV["show the waiver and a code, write nothing"]
  PV --> CC{"run again with that confirm code?"}
  CC -->|"no, or what is shown changed"| Y
  CC -->|"yes"| HW["write the WAIVED cr note, then sign with its hash"]
The roster, roster-change and report refusals run before the waiver is shown, so the owner is asked once, at the right moment. Both waiver paths end in the same note and the same signed line.
PieceRule
What is printedThe waiver reason, the open counts, each open (unwaived) findings entry and each walk waiver, "not reviewed" in place of 0/0 when no review ran on the tip, and the review history: every cr note on a first-parent commit of base..tip, newest first, one line each (short sha, verdict, blockers, importants, and the reason on a WAIVED one). W2 adds round, scope and fix-PASS to these lines
The flag--accept-waiver, no value. Without it on a waived tip: refused with a fix -> line, nothing written. On a tip with no waiver it is ignored, as --roster-change is
The notemr/v1 gains waiver_hash: "sha256:<hex of the reason's bytes>", present only on an accepted waiver. This is what binds an identity-tier sign-off, which has no signature
The signed text (key tier)The keel-mr/v2 payload gains a last line review: WAIVED sha256:<hex> on a waived tip only. With no waiver the bytes are exactly today's, so every existing signature stays valid. The header stays v2: the line appears only where no older signature can exist
Check 8Rebuilds the waiver hash from the tip's current cr note and compares it with the note's waiver_hash before any signature check: reworded (hashes differ), a signed PASS later turned into a waiver (current has one, note has none), or a signed waiver later turned into something else (note has one, current has none) are each red with their own cause. A key-backed signature is then verified over the payload rebuilt with the current line

Round 2: the owner's waiver at sign-off (option b), router decision 2026-11-12

Decision. Router keel-77, 2026-11-12, after the owner left open point 1 unanswered twice: build (b). Reason: (a) cannot run as built. The launcher denies keel notes write cr to every worker but a --review one (scripts/router-worker.sh, DEC-46), so the WU's own session can never write the waiver. This widens W1 past the epic plan's out-of-scope line ("a new owner command for any step of the schedule"). It is a flag on the existing sign-off, not a new command. It is the router's decision taken on the default; the owner's sign-off of this WU is where the owner rules on it.

Expected

  • A waiver without a reason, or a reason on PASS or FAIL, is refused and writes nothing.
  • With one, keel verify-dod wu prints WAIVED 3·review: <reason> and is red only on 8·manual-review; a code commit after the waiver leaves no valid review on the new tip, and a note carried onto it is red on 5·diff-binding.
  • keel mr confirm on a waived tip prints the reason, the open findings and the review history, and without --accept-waiver refuses and writes nothing; with it, it signs and the merge check is green, its receipt saying review: WAIVED.
  • After signing, rewording the waiver, or turning a signed PASS into a waiver, is red on 8·manual-review in both identity and key tiers.
  • A tip with no waiver signs byte-for-byte as today: a note written with today's payload still verifies.
  • The epic walk passes a waived WU and prints it; an epic's own review can be waived.
  • keel mr confirm … --waive-review "<reason>" on an unreviewed or failed tip writes the WAIVED note and the sign-off together, and the merge goes through the real hook. It is refused over a PASS, with a blank reason, or while any other check is red, and then writes nothing.
  • skills/ and .claude/skills/ stay byte-identical, staged for the owner's commit.
