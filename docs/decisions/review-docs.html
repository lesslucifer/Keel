Decisions: reviews and docs

How code is reviewed (scope, waivers, the 5-round schedule, nits) and how docs are written, checked and kept short. Check here before "fixing" anything that looks deliberate.

T2 · decisions · current truth · 2026-11-18 · Keel · DEC-26 – DEC-28, DEC-49 – DEC-52, DEC-54, DEC-68, DEC-69

Current truth: each record says what stands today, why, and what was rejected. A later decision that changes one is folded in and named. A record replaced whole keeps its id and one line. Ids are never reused; git keeps the history.

Code review

DEC-26 · Review scope, nits and modules

ChoiceA standalone code commit gets no review of its own; the epic review covers it (Trawler DEC-51 not restored). [review] modules globs define a module for the altitude finder (each * match is one module) and [review] rubric points at an optional project-local rubric. The skill reads [review]; the CLI reads [review] max_rounds from the target's committed config (DEC-50). The cr writer takes a third verdict, WAIVED (DEC-49), and the round's lists (--findings, --refuted, --nits, --fleet) go on the note through its flags, not a jq step (DEC-50). The gate reads none of them, and no disposition check will be built. The shipped rubric holds dimensions, severities, principles P1–P5 in general form, the DEC-50 corpus numbers as lineage, and the nit cases and repeat-finding rule of DEC-51; project instances go in the project rubric.
WhyOne epic review sees every commit; reviewing each costs more. Nits and the fleet bill are record, not gate.

DEC-49 · A waived review is its own verdict, and only the owner accepts it

Choiceverdict: "WAIVED" with waiver: "<reason>" in cr/v1, bound to the code like a review. Check 3 accepts it with a non-blank reason; the walk carries a waived WU up; dod/v1 records it. The owner waives in the sign-off, in two steps: --waive-review "<reason>" previews, --confirm-waiver <code> writes the cr note and the sign-off together in one ref transaction (the code hashes what was shown). A waiver the tool wrote (the cap, DEC-50) is signed only with --accept-waiver <code>. The sign-off covers the whole waiver: waiver_hash on mr/v1 and a signed payload line (DEC-40); the hash covers the reason, open counts, unreviewed, open findings and walk waivers, so any change turns check 8 red. One writer, notes::waive, never over a PASS; the cr writer takes no --reason. Every cr note is read through plumbing (notes list, cat-file), so no git setting alters a row. A GitHub approval signs over a review in any state, with no waiver written (DEC-66).
WhyA waived review could only be written as PASS, so records said "reviewed, PASS" where the owner skipped it (backlog B12).
RejectedPASS plus a waiver field (an older keel passes it silently; WAIVED fails safe as "not PASS"). A separate CAPPED verdict. Print-only consent or a bare flag (no proof the owner saw it). A session recording the owner's ruling with the WAIVED writer (only a review worker may write cr notes, DEC-46).

DEC-50 · The review follows a 5-round schedule the tool derives from the notes

ChoiceRounds 1–2 review the whole range, rounds 3–5 only the code since the last reviewed commit; nits are fixed after the verdict under a fix-PASS (--fixes); from round 4 importants with no blocker too; only a blocker earns round 5, and a blocker in round 5 ends in the cap's WAIVED. The round is derived from the cr notes on the branch's own first-parent line, never typed. Preflight and the writer enforce it (0·review-cap), and the writer stamps round and scope. A narrow round still binds the whole range's code hash. [review] max_rounds comes from the target's committed config (default 5), so a branch cannot raise its own cap. A commit that changes no code path carries a fix-PASS for the same round, even over a fix-PASS; a docs-only commit after a failed round fixes nothing; a FAIL with nothing counted is recorded and needs a round; a second code fix from round 4 ends in the owner's waiver. "Changed since a round" counts only the branch's own changes: each first-parent commit of since..tip against its parent; a merge against git's automatic merge of its parents (merge-tree --write-tree, attributes from the first parent's tree); an octopus merge whole. It needs git 2.40; a git error refuses.
WhyReviews looped: each round found something and the fix reopened the WU.
RejectedSchedule in skill text only. A typed round number. Binding a narrow round to its narrow diff. A new owner command. A one-verifier check of each fix-PASS. Stacking fix-PASSes. A merge check on nit dispositions (DEC-26).

DEC-51 · Two nit cases, and a later round refutes a repeat of an earlier finding

ChoiceThe shipped rubric names two nits: a missing test for an edge case the code already handles correctly, and a test-harness tidy-up that changes no test's result. Wrong code on an untested case stays a blocker. From round 2 the orchestrator gives verifiers (not finders) every earlier cr note on the branch's line. A claim is a repeat only when it is surely the same defect in the same code. A repeat of a fixed finding is refuted unless the verifier names a failing case at the tip that shows the fix does not hold; then it is judged as a finding against that fix. A repeat of a waived or refuted entry is refuted only while the code it judged, and every file its reason names, is unchanged; in doubt the claim is new. The router's own extra reviews follow the same schedule (1–4 severity: blocker/high, medium, low).
WhyReviews reopened work over a missing edge-case test or a harness tidy-up, and later rounds re-judged defects an earlier round had found and the author fixed.
RejectedAlways refuting a repeat (a fix that did not work passes unseen). Re-judging repeats normally (what looped). Giving finders the list too (it would change what reviewers look for).

Documentation

DEC-27 · Doc tiers by config globs; archiving needs lineage

ChoiceTiers come from [docs.tiers] globs (default: Trawler's layout under docs.root, design-rules dropped), matched T3 → T2 → T1 → T0 so a broad glob never hides a working doc. "Archived" means deleted in the range and absent at the tip; the local copy in gitignored docs/.archive/ is not checked. An archived T3 doc needs distilled_to: T1/T2 docs tracked at the tip (not necessarily changed in the same range), or "none: <why>". A page and its data file are one doc for tiers and lineage (DEC-69): one --distill naming either file gives both the same distilled_to, each keeps its own when both are named, and a pair archived by half (one file gone, the other still at the tip) is refused by the doc writer and red at check 6, naming the file left. A doc matching no glob is red. The doc set includes T0 files, so an AGENTS.md edit needs a doc note. Only verify-dod enforces this; verify-doc has no range.
RejectedA per-doc data-tier tag (a T3 doc could relabel itself to escape archiving). Trawler's t2_waived and distills sentence (judgment text the gate can only check for non-emptiness).

DEC-28 · verify-doc: drafts fully silent

ChoiceA draft (or status-less) governed doc is silent on its checklist and its relative links, unlike Trawler. Since DEC-69 the checklist is read from the data file, keyed by its role; collapsed roles need the union. The Codex apply_patch payload parsing in verify-doc-post is ported from Trawler, not verified against Codex docs (backlog B7).

DEC-52 · Docs are written by a shipped writing skill; the tool checks only what it can count

ChoiceA shipped skill, keel-write, holds nine writing rules, each with a before/after, a self-check and one short epic plan as example. keel init installs it; keel-plan, keel-distill, AGENTS.md and its template point to it. It covers every doc a person reads, not skill files or agent messages. Existing docs are rewritten only when edited. keel verify-doc checks only what a tool can judge: the checklist from the data file, where owner-changes is required in an epic plan (DEC-69); every Mermaid flowchart label in a non-draft page in quotes (best effort: refusing a valid diagram is a bug, a missed label a known limit; backlog B21); and the page's word cap (DEC-69): by its data file's role, else by path from [docs.caps] in .keel/config.toml. An epic plan's top (at most 300 words, diagram source and ids counted) ends at the heading with id work; with no such heading the whole page is the top. A page with no data file gets links, labels and its path cap only.
WhyAgents wrote long, dense plans: one epic plan had 1,575 words above its work. The owner wanted docs "short, direct and easy to understand". The router skill and briefs are not yet covered (backlog R46).
RejectedRules as a keel-plan section or in AGENTS.md alone (no room for examples). A length cap on every doc. A label check that must catch every label.

DEC-54 · The doc check runs at the write, from a host plugin; a review or a merge is no substitute

ChoiceThe trigger is the write, on any host. A host with shell hooks (Claude Code, DEC-5) runs keel verify-doc <path> on each first-party write or edit and keel verify-doc over all docs at turn end. DeepSeek Harness (DSH) has no shell-hook surface, so a plugin reaches the same two points: tools/post-execute runs the per-path check after the bytes land and returns {kind:'block', feedback} on a red doc; agent/turn-stopping runs the whole-tree check and calls agent.steer() with the problems, so the turn takes another step instead of closing. Exit 0 and a draft are silent; flipping to ready is the checkpoint. The check fails the write; it cannot prevent it. The gate stays facts-only: it never reads a document's form.
WhyOn DSH nothing ran keel verify-doc, and a broken doc surfaced at a review or never. A red doc's bytes still land; the cost is one fixing turn. The plugin lives in its own repo (the desktop-dsh project), a profile dependency named by the install line; without it nothing checks doc form in a DSH session. Shipped skills are tested for this text (tests/suite/init.rs).
RejectedVetoing at tools/pre-execute (it cannot rewrite arguments, and a veto loses the work). tools/result (observe-only). Checking at the review or the merge (too late; the merge never checked form). A project-side script on DSH. The plugin's code in this repo.

DEC-68 · Docs are read as web pages, built from every live branch

Choice.github/workflows/pages.yml runs on workflow_run of "Keel gate" and "Keel main", from main. Its build job (contents: read) runs scripts/pages-build.sh: each live branch's tracked docs land under <branch>/docs/ byte for byte, an epic tip's report note at <branch>/docs/_report/report.html; only doc file types (html, css, png, jpg, jpeg, gif, webp, svg, drawio), every file a blob, no branch code run, a path part at most 200 bytes, a branch over its size budget skipped whole. Each build starts empty, so a deleted branch disappears. The deploy job (pages: write, id-token: write) runs only actions/deploy-pages; a fork's run is skipped. The bot's pull request and tracking issue link each doc's page.
WhyThe owner ruled for docs as pages on GitHub Pages (2026-11-15): he read plans as files on his Mac, not readable on the phone. The builder reads GitHub without credentials, so the repository must stay public. The owner sets Pages' source to "GitHub Actions" and limits the github-pages environment to main (backlog G10).
RejectedA site per branch or per pull request (one site per repository). Rendering on the owner's Mac.

DEC-69 · Docs split: a short page for the owner, a data file for agents and checks

ChoiceEach plan and result is a page plus a YAML data file beside it, named like the page and ending .yaml. The data file holds the checklist as fields named like the old tags (data-wu becomes wu), plus artifact, status, id, epic (WU roles), title, date (a quoted string) and page; extra facts go under one free field, details, and any other unknown field is red. An epic plan's data file repeats its today/after table. The doc check reads the data file (a draft is silent); the page carries no checklist tags and is checked for links, diagram labels and its word cap. An epic plan's top (problem, what changes, an example, terms) is at most 300 words and ends at the heading with id work; a result page marks each "how you'll know" check met or not and runs the main case for real. Word caps for a ready page: epic plan 700, WU plan 500, WU result 500, epic result 700 (a one-part epic takes the epic caps), a decision file 5,000 (a record about 250), architecture 3,000, install 1,500; other work pages none. A plan or result finds its cap by its data file's role, any other page by path. The sign-off still attests the page; the data file is in the signed diff. An epic result's data file sits beside its page in docs/.archive/, untracked. Data, no page: the decision and use-case indexes, the use cases (contracts, no build history), the backlog (open rows only) and its order. Current truth only: a replaced decision keeps "DEC-n · title · replaced by DEC-m", lineage rows go; architecture and install drop history and the rules a skill holds; a decision file over its cap is split by topic. Ids are never reused, and every id cited in code, skills or docs still resolves.
WhyOne HTML file served the owner, agents and keel verify-doc badly: long pages full of checklist tags. The owner asked (2026-11-17) for a short doc for him and a data file for agents. A data file has no htmldoc id; the owner comments on the page and asks an agent about use cases and backlog.
RejectedThe data in git notes (a plan exists before any commit to hang a note on). One doc generated from the other. Dropping the use cases (code, reviews and plans cite their ids). Reading the old tags for a while (no other project yet).
