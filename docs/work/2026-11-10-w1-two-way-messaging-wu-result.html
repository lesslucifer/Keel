E-ROUTER3.W1 · Router↔worker messaging works both ways — result

What was wrong, what changed, how it works now, and how it was proven. This covers both the technical design and the outcome.

T3 · WU result · 2026-11-10 · Keel · branch wu/E-ROUTER3/w1-two-way-messaging off e421b20 · WU plan · epic plan

In one paragraph

The router session is a coordinator that drives worker sessions. It talks to them with Claude Code's SendMessage tool. A safety hook, the router guard, inspects every tool call the router makes and blocks anything outside its whitelist. Until now the guard blocked every SendMessage that carried text, by design. In practice it also blocked the one kind it was meant to allow, a bare "tell me when you finish" subscription (backlog R8). This WU found why: Claude Code silently adds three fields to every SendMessage call before the guard sees it, and the guard rejected unknown fields. The guard now asks one question, "is there a named recipient?". The router can therefore message a running worker and get its reply. A real two-session run proved both directions.

The problem, and how it was found

Before: the guard allowed SendMessage only when it met all of these at once:

  • notify_when_idle was exactly true.
  • message was empty.
  • The input had no key other than to, notify_when_idle, message and summary.

The tests passed because they fed the guard hand-written inputs. Real routers were still denied.

The capture: to see what the guard actually receives, a throwaway repo was set up with a hook that only writes its input to a file. A headless --agent router session there made two calls, and the hook recorded them:

{"to":"e-x-w1","message":"ping…","summary":"ping"}{"to":"e-x-w1","summary":"ping","message":"ping…","type":"message","recipient":"e-x-w1","content":"ping…"}

The bold keys are added by Claude Code (2.1.288). The old guard's closed key list rejected type, recipient and content, so even the bare subscription was denied. Running the old guard on these two captures confirms it: both are denied.

Why a guard change is the whole fix

Two-way messaging needs a transport and permission to use it.

  • Transport: Claude Code already provides it. SendMessage delivers text from any session to any other named session on the machine, in both directions. Keel builds nothing here, and the live probe below shows it working unmodified.
  • Permission: the router guard was the only thing standing in the way. It runs only for agent_type == "router", so it never judged a worker's calls. It blocked exactly one direction, router→worker, and in practice also the router's subscription.
DirectionBefore W1After W1
Router → worker, text (an answer, a clarification, a stop)Denied by design (DEC-36)Allowed
Router → worker, "notify me when you finish" subscriptionDenied in practice (R8: the harness-added keys)Allowed
Worker → router, textNot blocked: the guard ignores worker sessions. Of little use, though: a question got no answer, because the router could not reply.Allowed, and the router can now answer

Lifting that one block completes the loop. The worker sends a question or report, and the router answers or redirects it. The worker replies to the from address on the message it received, and an unprompted report goes to the router's name, which every brief already carries ("report to the router's current name"). That is why the code diff is a few lines of jq. The rest of the WU is proof (the capture, tests and the live probe) and rules: the skill text decides what the router may say in a message (DEC-42).

The guard rule, old and new, on a text message

The guard does not allow or forbid fields. It reads a call's whole argument list (tool_input) and answers allow or deny. A router's text message reaches it as {"to":"w1","message":"use the old flag","type":"message","recipient":"w1","content":"use the old flag"}. The text rides in message, and content is the harness's copy of it.

Old rule: allow only if all holdNew rule
Conditions
  1. to is a string.
  2. notify_when_idle is true.
  3. message is empty (the "no text" ban).
  4. There are no keys besides to, notify_when_idle, message and summary.
The arguments are an object, and to is a non-empty string. The text is never read.
Text messageDenied by conditions 2, 3 and 4.Allowed
SubscriptionDenied by condition 4, because of the harness keys (R8).Allowed
No recipientDeniedDenied

Text gets through because the conditions that inspected it were deleted. The remaining to check only rejects a malformed call. What the router may say lives in the skill text (DEC-42), because code cannot tell a clarification from a new task.

Why the guard checks so little now.

  • An allow-list of keys is what broke R8, and the harness can add keys in any release.
  • No jq rule can tell "clarify step 3" from "now also push to main". The difference is semantic, so the brief-only rule for new tasks lives in the router's skill text, not the guard.

The accepted residual is that router text can now reach a full-tool worker without a hashed snapshot. That is DEC-33's risk class, and DEC-42 records it.

Outcome

Delivered. The requirement holds. The guard allows a router's SendMessage exactly when to is a non-empty string, including the harness's real payloads for a subscription and for a content message. Every tool outside the router's list is still denied. Two-way delivery between a guarded router and a launcher-style worker was shown live. The skill text change landed as the owner's commit 66588aa.

Live probe (2026-11-10)

Two real headless sessions ran in throwaway repos, both with --setting-sources project,local --strict-mcp-config, so no Telegram poller started:

  1. probe-w (the worker): permission mode acceptEdits, as the launcher runs workers. It ran sleep 20 in a loop and waited for a message.
  2. probe-r (the router): agent: router, with this branch's guard wired exactly as .claude/settings.json wires it. It ran ListAgents, which found probe-w live and busy. It then sent SendMessage {to: "probe-w", message: "ping-7731 from the router", notify_when_idle: true}.
  3. Guard: it allowed the call. The router transcript has no "router guard" denial, and the input it judged carried the harness's extra keys.
  4. Router → worker: the worker received ping-7731 from the router from probe-r between two of its sleep calls, mid-run.
  5. Worker → router: the worker replied pong: ping-7731 from the router. The reply reached the router mid-turn, between its tool calls. The [Cross-session idle notice] for probe-w followed when the worker finished.

The router ran in default mode and the worker in acceptEdits. The message was not held for approval despite the different modes, which the SendMessage tool text warns can happen.
