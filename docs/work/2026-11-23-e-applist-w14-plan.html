E-APPLIST.W14 · Bindings that survive git's longer short hashes

A review or sign-off must not go stale because the repository grew.

T3 · WU plan · 2026-11-23 · Keel · its data file, 2026-11-23-e-applist-w14-plan.yaml, sits beside this page · the epic plan is archived

The problem

A review and a sign-off are tied to the exact text of the change. That text holds short ids of the files. Git makes those ids longer as the repository grows.

On 23 November the repository passed 16,384 objects. Git's ids went from 7 to 8 characters. Every review and sign-off written before then now reads as stale, though nothing changed. The epic's gate shows 10 such red steps.

What you get

  • New reviews and sign-offs use full ids, so the repository's size no longer matters.
  • Old ones still count: keel also accepts the short form, 7 to 12 characters.
  • A real change to the code still turns them red.
  • The epic's 10 stale steps go green with no waiver.

How it works

  1. A test grows a scratch repository past 16,384 objects between the sign-off and the check. It fails on today's keel.
  2. Keel writes the change's text with full ids.
  3. To check, keel tries the full form first, then each short length from 7 to 12. One rule serves the review, the receipt and your sign-off.
  4. Keel's own gate is run on the epic, read only, to show the 10 steps green.

What it makes

A change in keel's note code, its tests, a line in the review use case, the backlog row closed, and this plan and its result. The app does not change.
