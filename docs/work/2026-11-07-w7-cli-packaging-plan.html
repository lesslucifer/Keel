E-SEED.W7 (v2) — CLI packaging, self-delivered skills, self-hosting

Keel ships as a plain CLI binary, not a Claude Code plugin. keel init writes the five Keel skills into the adopting project's .claude/skills/keel-* and merges two harness hooks into .claude/settings.json. When a skill file on disk differs from the one in the binary, it asks before overwriting, unless --force / -f is given. Keel then adopts itself and its gates turn on.

Requirement

No plugin. The owner decided Keel is not distributed as a Claude Code plugin or marketplace entry. A plugin would add a second install step, a second version (the plugin's skills against the binary's gate), and a plugin runtime. The project would not control which rules it runs under. Instead, there is one artifact, the keel binary. It carries the gate and the rules. Today it installs with cargo install --git https://github.com/lesslucifer/Keel. GitHub Releases and npm come later, in W10.

Skills are delivered by keel init. The binary embeds every file under skills/ and writes them into the adopting project at .claude/skills/keel-<name>/. The project commits them, so the skills are versioned with the project's gate. Every teammate and every worktree sees the same rules, with nothing installed at user level. init also merges two Claude Code harness hooks into the project's .claude/settings.json: PostToolUse Write|Edit runs verify-doc-post, and Stop runs verify-doc-stop. These are the same scripts that .codex/hooks.json already calls.

Re-running init upgrades with confirmation. When a Keel-owned skill file in the project differs from the copy in the running binary, init asks the user before overwriting it, on every run, unless --force / -f is passed. It never overwrites silently and never skips silently. Automation that cannot answer a prompt must pass -f.

Keel adopts itself. Keel's repo carries its own keel init output. Once the owner installs the hooks on the real checkout, a direct commit on main is refused and every merge into main goes through keel verify-dod, as Q12 promised.

3 · Merging .claude/settings.json

This is a merge, never an overwrite. A project may already have its own settings. Keel's own repo is an example: "agent": "router", a permissions whitelist, and a PreToolUse Bash hook. It uses serde_json, which is already a dependency.

  1. Read .claude/settings.json. If the file is absent, start from {}. If it does not parse as a JSON object, leave it untouched, print kept .claude/settings.json (not valid JSON - add the Keel hooks by hand: …) with the two entries, and continue. Data loss is never acceptable here.
  2. For each of the two entries, look under hooks.<Event>[*].hooks[*].command for the exact Keel command string. If it is there, do nothing (idempotent, and safe if the user moved it into another matcher group). If it is not, append a new group: {"matcher": "Write|Edit", "hooks": [{"type": "command", "command": …}]} for PostToolUse, or the same without a matcher for Stop.
  3. Write the file back only if something was added, pretty-printed with a trailing newline, and report merged, unchanged or kept. Keys keep their original order through serde_json's preserve_order feature (open point 11).
PostToolUse (matcher "Write|Edit"):
  f="$(git rev-parse --git-common-dir 2>/dev/null)/keel-hooks/verify-doc-post"; [ -f "$f" ] || exit 0; sh "$f"
Stop:
  f="$(git rev-parse --git-common-dir 2>/dev/null)/keel-hooks/verify-doc-stop"; [ -f "$f" ] || exit 0; sh "$f"

Because the file is committed, every teammate and every worktree gets these entries. The [ -f "$f" ] || exit 0 guard means a clone that never ran keel hooks install stays silent and is not broken. Outside a git repo, f becomes /keel-hooks/…, which does not exist, so the hook also exits 0. The scripts themselves are W5's DOC_POST/DOC_STOP strings in src/main.rs, unchanged. They already exit 0 when keel is not on PATH (open point 8). The decision of the first W7 plan about where the hook script text lives still holds: the hooks call the installed scripts, so there is one source of truth.

4 · Re-running init: confirm before overwriting

flowchart TD
  A["for each keel-* skill dir in the binary"] --> B{"every file on disk == embedded?"}
  B -->|"yes"| U["unchanged"]
  B -->|"some file missing, none differ"| C["create the missing files, no prompt"]
  B -->|"one or more differ"| M{"mode"}
  M -->|"--force / -f"| W["overwrite the differing files, no prompt"]
  M -->|"no -f (TTY or not)"| P["prompt for each differing file: overwrite? [y/N]"]

  P -->|"N / Enter / EOF (stdin cannot answer)"| K["keep; print 'differs' + how to update"]
Prompted per differing file. Missing files are always created, because creating a file destroys nothing.
  • What the prompt covers: files under .claude/skills/keel-*/ only. .keel/config.toml, AGENTS.md, .codex/hooks.json and project-router are project-owned once written, and they keep the existing "kept, differs from the default" rule (open point 14).
  • Prompt text (proposed, open point 2): 
    .claude/skills/keel-workflow/SKILL.md differs from this keel build (0.2.0).
Local edits or an older Keel version - keel cannot tell which.
Overwrite with this build's version? [y/N]  (-f overwrites without asking)
    When every differing file is tracked and clean in git, the prompt adds "(committed - recoverable with git checkout)". A file with uncommitted changes adds "(UNCOMMITTED changes will be lost)".
  • Upstream update or hand edit? init cannot tell these apart without a record of what it last wrote. It does not keep one: it asks the same question either way, which is the owner's ruling (decision 5). A .keel/skills.lock with the hashes of the last written files would let it tell the cases apart. That is listed as a possible later addition, not built (open point 4).
  • Force flag (owner decision, open point 3): a single --force / -f flag replaces the earlier three-tier design (--yes, --no, TTY detection). Without -f, init prompts for every differing skill file on every run. With -f, it overwrites every differing file without asking. There is no --yes, no --no, and no TTY branching. CI and other non-interactive callers must pass -f: a run without it reads its prompt answers from stdin, and EOF counts as N (keep, print one differs line, exit 0), so an unattended run without -f never destroys anything but also never updates. -f only affects differing files. Missing files are created either way, and project-owned files keep their rule.
  • Files the build no longer ships (for example, a reference removed upstream) or files a user added inside a keel-* directory are left in place and reported as extra (not in this keel build). They are never deleted (open point 5).
  • Dispatch: the ["init"] match arm in src/main.rs becomes ["init", flags @ ..], accepting only --force / -f (anything else is a usage error). The prompt logic is a function over a BufRead plus a Write, so it can be unit-tested with a Cursor.

Expected result

In a fresh temp repo, keel init writes all 10 skill files byte-for-byte under .claude/skills/keel-*/, plus project-router. It creates .claude/settings.json with the two guarded hooks, or merges them into an existing file with every other key kept in order. A second init leaves the tree byte-identical. After a skill file is edited, init with a non-terminal stdin keeps it and says differs, an interactive y or -f restores the embedded bytes, and N keeps it. No skill or AGENTS.md refers to a Keel skill by its bare name, and no install hint says cargo install keel. In a clone of the W7 branch with hooks installed, a commit on main is refused and keel init </dev/null changes nothing. cargo build, cargo test and cargo clippy --all-targets -- -D warnings are clean.

Test plan

Integration tests in tests/init.rs run the real binary in temp repos, in the existing fixture style. Unit tests sit next to the prompt and merge code.

  • Embedding completeness: walk Keel's skills/ tree. After init, every file exists at .claude/skills/<same relative path> with identical bytes, and no file exists under .claude/skills/keel-* that is not in skills/. A file added to skills/ but missing from the SKILLS list fails this test.
  • Prefix correctness: every directory directly under skills/ starts with keel-, and its SKILL.md frontmatter name: equals the directory name. A regex over skills/**/*.md and templates/AGENTS.md finds no bare Keel skill name in "skill X", "the X skill" or "**X** skill" form (X in workflow, plan, code-review, distill, router). The existing every_keel_command_a_skill_names_exists test keeps passing over the renamed tree.
  • settings.json merge: (a) no file: created with exactly the two entries. (b) Keel's own settings shape (agent, permissions, a PreToolUse hook): every original key and value kept in its original order, two groups added. (c) A second init leaves the file byte-identical. (d) The Keel command already present under a different matcher group: not added again. (e) Invalid JSON: the file is unchanged and a warning is printed. (f) Each merged command, run through sh -c with a Claude payload on stdin: no keel-hooks → exit 0 and silent; hooks installed and a red ready doc → exit 2 with the verify-doc error; a green doc → 0.
  • Upgrade confirmation: unit tests over the prompt function with Cursor input, one prompt per differing file: y → overwrite, n/empty/EOF → keep, garbage → re-ask once, then keep. Integration, with a skill file edited after the first init: piped empty stdin without -f → kept + differs line + exit 0; piped y without -f → overwritten; -f → embedded bytes restored with no prompt; unknown flag (--yes) → usage error; a deleted skill file → recreated without a prompt; an extra file in keel-router/ → still there + extra line. The interactive TTY path itself is covered by the unit tests, not by a pty in cargo test.
  • Install hints: no string cargo install keel remains in src/. The hook shims print the --git line.
  • Self-hosting (ported from the orphaned branch): clone HEAD into a temp dir, run keel hooks install, and check that git commit --allow-empty on main is refused as merge-only, that keel init </dev/null reports nothing created/differs/merged and leaves git status clean, and that a --no-ff merge of an evidence-less branch into main is refused by verify-dod.
