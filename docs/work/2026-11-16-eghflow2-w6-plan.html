E-GHFLOW2.W6 · Work that need not wait goes in its own pull request

When part of a WU waits, for your yes, a decision or anything else, that part becomes a task: its own branch and pull request into the WU's branch. The rest of the WU goes on. You merge a task into its WU on GitHub; nobody else merges. The WU still reaches the epic as one pull request, reviewed and signed on its last commit. The router checks every open pull request regularly and sends any problem, such as a clash, back to its worker.

The problem

Say W9 adds a keel export command. Halfway through, its worker sees that the workflow skill must tell workers when to run it. That is one line, but it is a rule edit, so it needs your yes, typed on your Mac.

Today the worker stops there. The export code, its tests and its review all wait for that one line, until you are back at your Mac. Or the line waits for the end, and all of W9 waits for your one approval of everything.

After W6 the line goes on a branch of its own, a task, with its own small pull request: one file, one line. You merge it from your phone. W9's worker takes it in and goes on. W9's own pull request comes later, as today.

The same works for any wait: a script change waiting for the security review, a step waiting for a GitHub setting only you can make. Two smaller problems go too: a WU with no code needs no result report, and when a pull request clashes with its target, the router tells the worker who must fix it, so every pull request stays ready for you to merge.

1 · Tasks: one WU, several pull requests

In short: when part of a WU waits, that part becomes a task with its own pull request into the WU branch, and the rest goes on. You merge the task into the WU on GitHub; nobody else merges. The WU keeps one set of commits to judge, one set of notes on its last commit, and one pull request into the epic, so the gate changes nothing. What is built is the task's branch name and the bot's handling of it.

  • What can wait: anything outside the worker's hands. Your typed commit or approval, an open point only you answer, the router's security review, a GitHub setting, another WU's merge. A piece of work that would wait goes in a task; the rest goes on, on the WU branch or in another task.
  • A task is a branch wu/<E>/<wu>_<task> off its WU branch, in its own worktree with its own worker. Today's branch words are [A-Za-z0-9][A-Za-z0-9._-]*, so no WU name holds a _; the WU of a task is the name before its first _. The parser sits next to the branch grammar in src/notes.rs, and the scripts' grammar matches it (the guard-agreement corpus). Anything else is not a task: an empty side, a fourth segment, an epic branch, a detached HEAD.
  • A task's pull request goes into its WU branch. No gate runs on it (keel-gate.yml runs only for pull requests into main and epic/**), and no notes, code review or report are written on it. Your merge is the yes.
  • You merge the task's pull request on GitHub. The router sees it (router-gh-watch.sh merged), fetches the WU branch (router-gh.sh sync), and tells the WU's worker, who takes it into its own branch before the bot's next push. Neither the router nor a worker ever merges a pull request (open point 9).
  • The WU's tests, review, report and sign-off go on the WU branch's last commit, and the WU reaches the epic in one pull request, signed by your approval, as today. Code review runs here only: the review notes are checked on the WU's pull request into the epic. That pull request holds every task's commits, so nothing escapes the gate. A test proves it: two tasks merged into a WU, the WU gated and signed on its last commit, then the epic is green.
  • The WU's plan lists the tasks known up front; a task split off later is named in the result. One result report per WU, as today. The WU is done when its pull request into the epic merges.

2 · The bot and the worktrees know tasks

In short: the router can push a task, open its pull request into its WU branch, and make its worktree off that branch. Auto-merge is never turned on for a task: you merge it yourself.

  • router-gh.sh push <task>: as for a WU branch.
  • router-gh.sh pr-open <task>: the base is always its WU branch, which must already be on GitHub; --base is refused for a task. The title is the task's branch name unless its range carries a plan.
  • router-gh.sh pr-ready <n> on a task's pull request asks for your review and leaves auto-merge off: no ruleset covers wu/ branches, so GitHub would merge at once or refuse.
  • router-gh.sh sync <WU branch>: as for an epic. It fast-forwards the local branch when no worktree has it; else it fetches and names the ref, and the WU's worker merges it in. Should the bot push first, GitHub refuses a push that is not a fast-forward, so nothing is lost.
  • router-gh.sh issue refuses a task: the WU's sub-issue is the record, and its result names its tasks. The epic's issue already skips names that are not plain words.
  • router-worker.sh worktree add <task> cuts the task off its WU branch (refused when that branch does not exist), at ../Keel-<E>-<wu>_<task>.
  • The router's guard (scripts/router-guard.jq) admits the task shape for push, pr-open (with no --base) and worktree add|remove, and a WU branch for sync; its deny message lists them.

3 · No trailer on a task commit without code

In short: a rule edit waits on your yes, so it is the task most often split off. The commit check lets a rule-file commit through with no trailer when the branch is a task and the commit stages no code. Your merge of the task's pull request is the yes. Everywhere else the trailer rule stands.

  • src/mr.rs commit_msg: before reading the trailer, the current branch (git symbolic-ref --short -q HEAD) is read. When it is a task branch and no staged path is a code path or the roster (.keel/mr-allowed), the hook prints one line naming the rule-bearing paths and "your merge of the task covers them", and allows the commit.
  • A task commit that stages code or the roster with a rule-bearing path needs the trailer, as anywhere. On the WU branch itself the trailer rule is unchanged.
  • The relaxation lives in the keel binary, which every worktree's hook calls. It reaches a worktree when you install a keel built from main (the close, or a landing).

4 · No result report for a range without code

In short: [mr] report = "required" now asks for a report only when the range changes code. The test is the one the gate already uses to exempt a docs-only range. The sign-off itself is still required everywhere. A task never has a report; this is for a WU, or an epic, with no code.

  • One helper in src/mr.rs: the policy that applies to a range is required turned to optional when notes::exempt holds for base..tip; optional and none are unchanged.
  • Used in the three places that read the policy: pick_report (the typed keel mr confirm and the approval writer) and manual_review (check 8). One rule, so a sign-off check 8 accepts is one the writers write.
  • Both levels. A report found in a range without code is still attested, as under optional.
  • Check 8 is never exempt. What your approval signs over (a failed review, a roster change) is W7's, by your ruling that your approval accepts everything; this rule only stops asking for a report where there is no code, and holds the same way under it.

5 · A task that needs another task

In short: nothing new is built. A task that needs another task's work starts from the WU branch after that task has been merged into it. No notes are written on a task, so there is no range to fix.

  • If it must start sooner, it starts from the other task's tip; its pull request then shows both until the first is merged into the WU.
  • The router never marks a task's pull request ready while a task it needs is open (a skill rule, item 7). If the needed task is closed unmerged, the worker reverts its commits on its branch with a new commit, never a rebase.

6 · The router keeps every pull request ready to merge

In short: only you merge. The router checks every open pull request regularly, tasks and WUs alike, and sends each problem to its worker: a conflict, a red check, your review comments. A new read-only watch tells it of a conflict.

  • router-gh-watch.sh conflict <n>, read through router-gh.sh watch-read like the other watches: only a bot pull request. It polls the pull request and ends with CONFLICT pr=<n> head=… sha=… at=… once mergeable is false and mergeable_state is dirty, or with MERGED or CLOSED if it leaves first. It writes nothing: GitHub itself shows "This branch has conflicts" and blocks the merge.
  • When: the router keeps one running for every open bot pull request, as it does checks and review today.
  • The router sends the problem to the worker of that branch. The worker brings the target branch into its own (the epic, or for a task its WU branch; git merge --no-ff, never a rebase), resolves, re-gates a WU (new notes, a new review when it has code), and the bot pushes. A push dismisses an approval, so you approve a WU again.
  • The guard admits scripts/router-gh-watch.sh conflict [1-9][0-9]{0,6}; its deny message lists it.
  • This also closes G7 N7's second half: a conflicted pull request has no merge commit, so the sign-off writer could not run; after the fix it can.

7 · The skills

In short: the router and its workers learn tasks and the conflict flow. Text only, staged for your typed commit.

  • keel-workflow (both trees, skills/ and .claude/skills/): tasks (item 1): when a piece waits, it goes in a task and the rest goes on; the name; no gate, notes or report on a task; the WU's notes, review and sign-off on its last commit; taking in the WU branch after you merge a task; no trailer on a task commit without code; no report for a range without code; the task order (item 5); the conflict fix (item 6); never merge a pull request.
  • keel-router (both trees): when to split a task off; a worker per task, in its own worktree; after you merge a task, sync the WU branch and tell its worker; keep conflict, checks and review watches on every open pull request and send each problem to its worker; never merge; never mark ready a task whose needed task is open; pr-ready after the fix; the independent security review still runs on a task that changes a script or the guard.
  • project-router: the guard's new shapes; a worktree per task.
