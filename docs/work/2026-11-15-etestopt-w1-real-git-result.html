E-TESTOPT.W1 · The tests run the real git — result

Every program a test starts now runs the real git, not the macOS launcher. The 11 sandbox failures it caused are gone, and the full run with the stock PATH is as fast as with the developer tools' git first.

T3 · WU result · 2026-11-15 · Keel · branch wu/E-TESTOPT/w1-real-git off epic/E-TESTOPT 1e1c6bc · WU plan · epic E-TESTOPT plan, block W1

What happened

Delivered as planned. The test helpers find the real git once per test program and put a directory holding only it first on every PATH a test hands a child. With the stock PATH in a worker's sandbox, the router tests went from 12 failures to 1. The one left is the watcher test, which W2 owns. A full run with the stock PATH took 61.6 s, the same as with the developer tools' git first; the epic's baseline had it at 77 s. Keel's own code is unchanged.

Deviations

  • The before runs come from the epic's baseline, not from this session. A scratch clone of the base for a same-session run was refused twice by the session's permission check (git clone -q <this worktree> $TMPDIR/keel-before). The test code at the base 1e1c6bc equals the baseline's 690aef1 (that commit adds only the epic plan), on the same machine. This session also ran the router tests on the old code: 12 failures, 18 xcrun_db lines, 30.2 s.
  • A fix found by the recipe's own run. With the developer tools' git already first, the resolver made no link, so a PATH a test makes up (/usr/bin:/bin) fell back to the launcher, and the new test caught it. The link is now made whenever a real git is found. Only the shared PATH is left as inherited when its git already is that one (commit 9619347).
  • The requirement's fallback reads slightly wider. The plan said the test PATH is unchanged when the PATH's git is the real one. That holds for the shared PATH. A PATH a test makes up still gets the link first, so it never reaches the launcher.

How it works

  • tests/common/mod.rs: real_git(exec_path) takes <prefix>/bin/git beside <prefix>/libexec/git-core, else git-core/git; a relative or empty exec-path is none. real_git_dir asks the PATH's git for --exec-path once and links the real git into target/tmp/real-git/git, under a staged name, then renamed. shared_path leaves the inherited PATH alone when its git already is the linked one. path(), path_with(dir) and real_git_first(p) are the only ways a test builds a PATH, and cmd sets path() on every spawn.
  • This machine's real git is Xcode's (xcode-select -p is /Applications/Xcode.app/Contents/Developer), not the Command Line Tools'. Its directory also holds python3, make, gcc and dozens more, which is why only git is linked.
  • Every std::env::var("PATH") in the test files became a helper call (cli, close_walk, init, mr, review, router, seed3_e2e, verify_doc, verify_dod). The one literal PATH, /usr/bin:/bin in installed_git_hook_without_keel_on_path_refuses_and_points_to_install_channels, goes through real_git_first.
  • Known limit: the link sits in the shared target/tmp. Two test runs in one worktree with different git paths re-point it in turn. Each target is a real git, and one worktree runs one test run at a time.

Distillation

Nothing lands in T1/T2 at this WU. For DEC-84 at the epic close, the git-on-PATH rule for tests: "Every PATH a test hands a child comes from tests/common (path, path_with, real_git_first; guarded by every_test_path_comes_from_common). It has a directory holding only the real git first, found from the PATH's git's --exec-path, so the macOS xcrun launcher never runs under a test. Where the PATH's git already is the real one, the shared PATH is the inherited one. Keel itself runs whatever git its caller's PATH names." Rejected: the real git's own directory first (it shadows Xcode's python3, make and more); xcrun --find git (macOS only, and it is the program that fails in the sandbox). Backlog R43's first half is done by this WU; R43 closes at the epic close with W2.
