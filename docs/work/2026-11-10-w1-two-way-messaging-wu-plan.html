E-ROUTER3.W1 · Router↔worker messaging works both ways — plan

Admit the real SendMessage payload in the router guard, let the router steer a live worker with content, make resume the default follow-up, and record DEC-42.

T3 · WU plan · 2026-11-10 · Keel · branch wu/E-ROUTER3/w1-two-way-messaging off e421b20 · epic E-ROUTER3 plan

Requirement

A router session's SendMessage is allowed by scripts/router-guard.jq exactly when its tool_input is an object whose to is a non-empty string, whatever else the harness adds. This covers the harness's real payload for both a bare subscription and a content message. Every tool outside the router's list is still denied.

Finding: the real payload (captured before this plan)

Captured on 2026-11-10 from Claude Code 2.1.288. The run was a headless --agent router session in a scratch repo whose only PreToolUse hook appends its stdin to a file. The router wrote {to, notify_when_idle: true}, and the hook received this tool_input:

{"to":"e-x-w1","message":"","notify_when_idle":true,"type":"message","recipient":"e-x-w1","content":""}

A content message {to, message, summary} arrived with the same three extra keys, type, recipient and content (a copy of message). The guard's closed key set (to, notify_when_idle, message, summary) rejects those keys. That explains R8's denied subscription of 2026-11-09: the synthetic test inputs never carried the harness's keys. The event also carries agent_type: "router", so the guard's router test holds for real sessions.

Expected

  • The guard's SendMessage branch is one predicate: tool_input is an object and to is a non-empty string. Its deny text names that rule.
  • tests/router.rs holds both captured payloads as fixtures, and both pass the guard. The test also covers a hand-written content message and a bare subscription. It denies a missing, empty or non-string to and a non-object input, and every tool outside the list is still denied.
  • The E-ROUTERFIX e2e no longer asserts that a content message is denied. It asserts that the guard admits one through the settings-wired hook.
  • keel-router skill and its .claude/skills/ mirror, byte-identical:
    • A message may steer a live worker: an answer, a clarification or a stop.
    • A new task still goes as a brief through router-worker.sh resume, which snapshots and hashes it.
    • Follow-up rounds resume the worker's session by default.
    • A subscription that reports the worker as unreachable or expired falls back to wait.
    The skill change is staged as an owner keel mr commit.
  • docs/decisions/router.html carries DEC-42, and DEC-32 and DEC-36 are marked amended by it. The decisions index names DEC-42, and its next free id is DEC-43.
  • A live probe is recorded in the WU result with one message delivered in each direction (router→worker and worker→router), and the real guard admits the router's call.

Test plan

  • Integration (tests/router.rs): the guard is run as a real jq process on whole PreToolUse events, which is its contract boundary.
    • router_guard_allows_send_message_to_a_named_worker_as_the_harness_sends_it replaces router_guard_allows_send_message_only_as_a_contentless_idle_subscription. It feeds both captured events verbatim and checks the allow and deny shapes listed in Expected.
    • The e2e epic_e2e_router_drives_a_granted_worker_in_a_seeded_worktree_to_its_end sends the captured content payload through the settings-wired hook and expects an allow.
    • router_guard_confines_the_router_to_its_tools_and_leaves_other_agents_alone drops SendMessage from its list of denied tools, because an empty input is now denied for the missing to and not for being off the list. The other tools stay in that list.
  • Unit: the guard is the only changed code, and it is a jq filter with no Rust surface. The guard tests above run it in isolation on fabricated inputs, which is what a unit test does here, so they cover both layers.
  • Mirror: the existing skill-mirror test keeps skills/keel-router and .claude/skills/keel-router byte-identical.
  • Live probe (manual, recorded in the result; it cannot be hermetic because it needs real sessions):
    1. A headless worker started with -n <name> is kept running.
    2. A headless --agent router session, in a scratch repo wired with this branch's guard, sends it a message. The guard admits it.
    3. The worker reports the text it received and sends a reply with SendMessage.
    4. The reply is seen arriving at a live session.
    The run is started with --setting-sources project,local --strict-mcp-config, so no second Telegram poller starts (R7).
