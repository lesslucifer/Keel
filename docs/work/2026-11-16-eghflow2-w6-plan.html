E-GHFLOW2.W6 · Work that need not wait goes in its own pull request

When part of a WU waits, for your yes, a decision or anything else, that part becomes a task: its own branch and pull request into the WU's branch. The rest of the WU goes on. Your approval lets a task into its WU. The WU still reaches the epic as one pull request, with its notes and sign-off on its last commit. When two pull requests clash, the router sends the second back to its worker.

The problem

A WU is one branch and one pull request today. So when any part of it waits, for your yes, an answer, a review or another WU, the whole WU waits. The most common wait: a change to a rule file needs your typed commit. So a worker that edits a skill or a rule in the middle of its work stops until you are at your Mac. A WU with no code still needs a result report, which is paperwork for a three-line edit. And when two pull requests touch the same file, GitHub refuses the second merge, but nobody is told.

Example

  1. A worker building W9 on wu/E/w9-export finds a skill needs one more line.
  2. The router starts a second worker on a task branch, wu/E/w9-export_skill-line, off the WU branch. It commits the line with no typed trailer. The commit check allows that on a task branch, for a commit with no code.
  3. The bot pushes the task and opens its pull request into wu/E/w9-export. No gate runs on a task and it carries no notes: only your approval is asked for.
  4. You read the diff and approve. The W9 worker merges the task into its branch, and the bot pushes it; GitHub shows the task merged.
  5. The W9 worker never stopped. When W9 is done, its tests, review, report and sign-off go on the WU branch's last commit, and its one pull request into the epic merges by your approval, as today.
  6. Had the task and the WU edited one file, the task could not merge. The router would mark the task's pull request a draft with a "conflict" label. Its worker merges the WU branch in and fixes the clash. The router marks it ready, and you approve again.

The same holds for any wait. Say part of W9 waits for a GitHub setting only you can make. That part goes up as a task when it is ready, and the rest of W9 goes on without it.

The work

A branch wu/<E>/<wu>_<task> is a task of the WU branch wu/<E>/<wu>: router-gh.sh pushes it, opens its pull request into that WU branch only and never turns on auto-merge for it, and router-worker.sh worktree add cuts it off that WU branch; on a task branch the commit-msg hook accepts a commit that changes a rule-bearing path other than the roster and no code path without a Reviewed-By trailer, and on every other branch, or with a code path or the roster staged, refuses it as today; a WU whose tasks were merged into it is gated and signed on its own last commit as one range, and the epic is green after it merges; a WU or epic range that changes no code path is signed - typed, by approval, and at check 8 - without a result report under [mr] report = "required", while a range that changes code still needs one; and router-gh.sh draft <n> turns a bot pull request that GitHub reports as conflicted back to draft with the conflict label and changes nothing otherwise, while pr-ready removes that label.

1 · Tasks: one WU, several pull requests

In short: when part of a WU waits, that part becomes a task with its own pull request into the WU branch, and the rest goes on. Your approval lets the task in. The WU keeps one range, one set of notes on its last commit, and one pull request into the epic, so the gate changes nothing. What is built is the task's branch name and the bot's handling of it.

  • What can wait: anything outside the worker's hands. Your typed commit or approval, an open point only you answer, the router's security review, a GitHub setting, another WU's merge. A piece of work that would wait goes in a task; the rest goes on, on the WU branch or in another task.
  • A task is a branch wu/<E>/<wu>_<task> off its WU branch, in its own worktree with its own worker. Today's branch words are [A-Za-z0-9][A-Za-z0-9._-]*, so no WU name holds a _; the WU of a task is the name before its first _. The parser sits next to the branch grammar in src/notes.rs, and the scripts' grammar matches it (the guard-agreement corpus). Anything else is not a task: an empty side, a fourth segment, an epic branch, a detached HEAD.
  • A task's pull request goes into its WU branch. No gate runs on it (keel-gate.yml runs only for pull requests into main and epic/**), and no notes, review or report are written on it. Your approval is the yes.
  • After your approval, the WU's worker merges the head you approved into the WU branch (git merge --no-ff <sha>; the merge hook gates only merges into an epic or main, and the commit check passes a merge), and the bot pushes the WU branch. GitHub then shows the task's pull request merged. Open point 9 says why the merge is local.
  • The WU's tests, review, report and sign-off go on the WU branch's last commit, and the WU reaches the epic in one pull request, signed by your approval, as today. Its range holds every task's commits, so nothing escapes the gate. A test proves it: two tasks merged into a WU, the WU gated and signed on its last commit, then the epic is green.
  • The WU's plan lists the tasks known up front; a task split off later is named in the result. One result report per WU, as today. The WU is done when its pull request into the epic merges.

2 · The bot and the worktrees know tasks

In short: the router can push a task, open its pull request into its WU branch, and make its worktree off that branch. Auto-merge is never turned on for a task, because the WU's worker merges it.

  • router-gh.sh push <task>: as for a WU branch.
  • router-gh.sh pr-open <task>: the base is always its WU branch, which must already be on GitHub; --base is refused for a task. The title is the task's branch name unless its range carries a plan.
  • router-gh.sh pr-ready <n> on a task's pull request asks for your review and leaves auto-merge off: no ruleset covers wu/ branches, so GitHub would merge at once or refuse.
  • router-gh.sh issue refuses a task: the WU's sub-issue is the record, and its result names its tasks. The epic's issue already skips names that are not plain words.
  • router-worker.sh worktree add <task> cuts the task off its WU branch (refused when that branch does not exist), at ../Keel-<E>-<wu>_<task>.
  • The router's guard (scripts/router-guard.jq) admits the task shape for push, pr-open (with no --base) and worktree add|remove; its deny message lists them.

3 · No trailer on a task commit without code

In short: a rule edit waits on your yes, so it is the task most often split off. The commit check lets a rule-file commit through with no trailer when the branch is a task and the commit stages no code. Your approval of the task's pull request is the yes. Everywhere else the trailer rule stands.

  • src/mr.rs commit_msg: before reading the trailer, the current branch (git symbolic-ref --short -q HEAD) is read. When it is a task branch and no staged path is a code path or the roster (.keel/mr-allowed), the hook prints one line naming the rule-bearing paths and "the task's approval covers them", and allows the commit.
  • A task commit that stages code or the roster with a rule-bearing path needs the trailer, as anywhere. On the WU branch itself the trailer rule is unchanged.
  • The relaxation lives in the keel binary, which every worktree's hook calls. It reaches a worktree when you install a keel built from main (the close, or a landing).

4 · No result report for a range without code

In short: [mr] report = "required" now asks for a report only when the range changes code. The test is the one the gate already uses to exempt a docs-only range. The sign-off itself is still required everywhere. A task never has a report; this is for a WU, or an epic, with no code.

  • One helper in src/mr.rs: the policy that applies to a range is required turned to optional when notes::exempt holds for base..tip; optional and none are unchanged.
  • Used in the three places that read the policy: pick_report (the typed keel mr confirm and the approval writer) and manual_review (check 8). One rule, so a sign-off check 8 accepts is one the writers write.
  • Both levels. A report found in a range without code is still attested, as under optional.
  • Check 8 is never exempt. What your approval signs over (a failed review, a roster change) is W7's, by your ruling that your approval accepts everything; this rule only stops asking for a report where there is no code, and holds the same way under it.

5 · A task that needs another task

In short: nothing new is built. A task that needs another task's work starts from the WU branch after that task has been merged into it. No notes are written on a task, so there is no range to fix.

  • If it must start sooner, it starts from the other task's tip; its pull request then shows both until the first is merged into the WU.
  • The router never marks a task's pull request ready while a task it needs is open (a skill rule, item 7). If the needed task is closed unmerged, the worker reverts its commits on its branch with a new commit, never a rebase.

6 · A conflict goes back to its worker

In short: a new bot command asks GitHub whether a pull request can merge. When GitHub says it conflicts, the command turns it back to draft and labels it. The worker fixes it on its own branch; then the router marks it ready again. This holds for a WU's pull request into the epic and for a task's into its WU.

  • router-gh.sh draft <n>: only a bot pull request (the same bot_pr check as pr-ready). It reads the pull request once. When mergeable is false and mergeable_state is dirty, it converts it to draft (GraphQL convertPullRequestToDraft), adds the conflict label (created if missing, as issue creates its labels) and prints DRAFT pr=<n> head=… sha=… state=drafted. When mergeable is true it prints state=clean. Anything else prints state=pending and writes nothing; the router asks again later.
  • When the router runs it: after each merge into an epic, on every other open, ready bot pull request into that epic; after each push of a WU branch that took a task, on that WU's other open task pull requests.
  • pr-ready also removes the conflict label; GitHub's "not there" is fine, any other refusal is a WARN line. For a WU it already turns auto-merge back on.
  • The guard admits scripts/router-gh.sh draft [1-9][0-9]{0,6}; its deny message lists it.
  • The worker's side is today's flow: merge the synced epic (for a task, its WU branch) into its branch (git merge --no-ff, never a rebase), resolve, re-gate a WU (new notes, a new review when it has code), and the bot pushes. You approve the new head again, because a push dismisses an approval. This also closes G7 N7's second half: a conflicted pull request has no merge commit, so the sign-off writer could not run; after the fix it can.

7 · The skills

In short: the router and its workers learn tasks and the conflict flow. Text only, staged for your typed commit.

  • keel-workflow (both trees, skills/ and .claude/skills/): tasks (item 1): when a piece waits, it goes in a task and the rest goes on; the name; no gate, notes or report on a task; the WU's notes and sign-off on its last commit; merging the approved head of a task; no trailer on a task commit without code; no report for a range without code; the task order (item 5); the conflict fix (item 6).
  • keel-router (both trees): when to split a task off; a worker per task, in its own worktree; after your approval, tell the WU's worker to merge that head, then push the WU branch; never mark ready a task whose needed task is open; draft after each merge into an epic and each task taken into a WU; pr-ready after the fix; the independent security review still runs on a task that changes a script or the guard.
  • project-router: the guard's new shapes; a worktree per task.

Security review

router-gh.sh holds the App's token and gains a write (draft, label) and a new branch shape; router-worker.sh makes a worktree off a WU branch. The guard gains shapes. The hook relaxes a rule. All go to the router's independent security review before your commit, against DEC-63's list, plus: draft acts only on a bot pull request from this repository; every GitHub value it reads is checked before use (mergeable a JSON boolean, mergeable_state compared as an exact word, the node id by its shape); nothing GitHub sends is printed unchecked; a task's pull request can only go into its own WU branch. That a task is merged only after your approval is a router rule, not a GitHub one (open point 9); the bound is your approval of the WU's pull request.

Unverified, each failing safe

  • That an App with Pull requests write may run convertPullRequestToDraft. If refused, draft fails with GitHub's message and the router tells you.
  • That mergeable = false with mergeable_state = dirty is GitHub's word for a conflict, and null while it computes. Any other answer changes nothing.
  • Whether turning a pull request back to draft turns auto-merge off. pr-ready turns it on again either way.
  • That GitHub marks a task's pull request merged once its head is pushed into the WU branch. If not, it stays open and you close it.
  • Whether GitHub refuses the bot's push of a back-merge that brings in an epic's workflow change (the App has no Workflows permission). If so, you push that branch.
