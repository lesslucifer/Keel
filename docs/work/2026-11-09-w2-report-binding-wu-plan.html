E-SEED2.W2 · Report binding and hook coexistence

Builds the never-started E-SEED.W9: a configurable result-report requirement for the human sign-off, reports found by role instead of file name, SHA-256 sign-off hashes, and Keel's hooks that refuse to clobber or be silently clobbered.

T3 · WU plan · 2026-11-09 · Keel · branch wu/E-SEED2/w2-report-binding off epic/E-SEED2 ef9ee75 · epic E-SEED2 plan · runs in parallel with W7 (owner ruling 2026-11-09, option A) · open questions 1–5 proceed on their defaults (owner ruling 2026-11-09)

Requirement

Whether a WU or epic sign-off must attest a result report is set by [mr] report = "required" | "optional" | "none" in the target's committed .keel/config.toml (default "required"). The report is found by its data-artifact role, with --report as an override. A required report that is missing is refused at keel mr confirm before signing and is a named 8·manual-review failure with a fix -> line at the merge. The signed payload is keel-mr/v2 with SHA-256 change and report hashes, and dod/v1 names the attested report. keel hooks install refuses to replace a foreign core.hooksPath or non-sample .git/hooks without --force, and keel preflight and keel verify-dod wu|epic refuse while core.hooksPath is not Keel's (keel check warns).

Expected

  • Every existing tests/mr.rs and tests/verify_dod.rs scenario passes with no [mr] report key. The only fixture changes are a data-artifact on the fixture result doc and a keel hooks install before gate commands (see risks).
  • report = "none": a WU with no result doc signs and merges green. Its mr/v1 note has no report or report_hash field.
  • report = "required": a WU with no wu-result doc is refused at mr confirm and writes no note. A hand-written note with no report is red at the merge as 8·manual-review, with a fix -> line.
  • A wu-result doc with any file name (e.g. docs/work/outcome.html) is found and attested. An ungoverned x-result.html is not attested.
  • A WU branch that sets report = "none" on itself is still judged at the merge hook by the epic's committed "required".
  • mr/v1 change_hash and report_hash read sha256:<64 hex>. The dod/v1 receipt of a merge whose sign-off attested a report names that report and its hash.
  • keel hooks install after git config core.hooksPath .husky, or with a hand-written .git/hooks/pre-commit, exits non-zero, names what it would replace, and changes nothing. With --force it installs.
  • After another tool resets core.hooksPath (or unsets it), keel preflight and keel verify-dod wu|epic are red with keel hooks install as the fix, and keel check prints a warning but keeps its exit code.
  • cargo test and cargo clippy --all-targets -- -D warnings are green.

How the report is found

flowchart TD
  A[mr confirm wu|epic] --> B{sign_ready: checks 1-7 green?}
  B -- no --> R0[refused: sign last]
  B -- yes --> P{"[mr] report"}
  P -- none --> N{--report given?}
  N -- yes --> R1[refused: policy none attests nothing]
  N -- no --> S[sign: payload v2 without report lines]
  P -- required/optional --> O{--report given?}
  O -- yes --> H[hash it]
  O -- no --> F[candidates: docs.root html whose data-artifact has the level role]
  F --> C{how many}
  C -- one --> H
  C -- several --> R2[refused: lists them, fix: --report]
  C -- zero, required --> R3[refused: no wu-result / epic-result, fix: write it]
  C -- zero, optional --> S
  H --> S2[sign: payload v2 with report + sha256]
Report lookup and policy in keel mr confirm. Candidates for a WU are the docs changed in base..tip and present at the tip. An epic adds the untracked docs under docs.root, including ignored ones, because docs/.archive/ is gitignored.

Choices made here (reversible, owner may override)

#PointWhat was decided here
AHow to compute SHA-256Add the sha2 crate (RustCrypto). Git 2.50.1's hash-object has no --object-format option (checked with git hash-object -h), and the shell tools differ by platform (shasum, sha256sum). Values carry a sha256: prefix, so the algorithm is named in the data.
BSHA-256 scopeOnly the mr/v1 change_hash and report_hash (backlog B7 names exactly these). cr/v1 code_diff_hash and dod/v1 diff_hash stay git blob ids. They are unsigned bindings, and changing them would make every in-flight cr note stale.
CGuard on an unset core.hooksPathRefuse, as for a foreign one. This matches Trawler DEC-72 and catches a clone where hooks were never installed. Cost: test fixtures that run preflight or verify-dod wu|epic must install hooks first. The weaker alternative is to refuse only a foreign value and warn when it is unset.
DWhere the guard does not runverify-dod hook, verify-dod range (pre-push) and verify-dod commit skip it: the first two run from Keel's own hooks by construction, and the commit gate runs only inside the walk. check() stays guard-free, and only the keel check command warns.
Ekeel init -f and the hooksinit's -f (overwrite skills) does not imply hooks install --force. Replacing another tool's hooks is a separate, explicit act.
F[mr] report = "none" plus --reportRefused, because the policy says nothing is attested. A report already in a note is still re-hashed by check 8.
GWhat counts as "non-sample" hooksAny entry in <git-common-dir>/hooks/ whose name does not end in .sample. A foreign core.hooksPath is any effective value (local, global or system) other than Keel's canonical keel-hooks path.
HNew DEC idsMinted at commit 7, from the next free id after checking every live branch. The index says DEC-39 today, and W7 runs in parallel and mints a router DEC.
IRule-bearing textThe skill and template edits land as one owner keel mr commit (commit 8), staged and printed, never run by the agent.

Risks

  • Existing sign-offs go red. See open question 4. Mitigation: the WU result and the staged commands tell the owner to re-sign with the new binary any tip already signed before W2.
  • Fixture churn. Choice C (refusing an unset core.hooksPath) means tests/mr.rs, tests/verify_dod.rs and tests/cli.rs fixtures call keel hooks install before gate commands. Every later fixture git commit then runs Keel's pre-commit and commit-msg shims, using the test binary first on PATH. A fixture that commits on main after install would be refused, so the install goes after the fixture's base commit.
  • Fixture result doc. The tests/mr.rs fixture's <p>wu a: done</p> has no data-artifact, so the role lookup would not find it. It becomes a minimal <html data-artifact="wu-result"> doc, which is the one change to the "existing tests pass unchanged" claim.
  • Merge with W1/W11 on src/main.rs. W1 and W11 are already on the epic base (ef9ee75), so there is no pending conflict. W6 later shares the hook code (it depends on W2).
  • Lossy diff text. change_hash keeps hashing the diff text exactly as git() returns it today (lossy UTF-8, trimmed). Only the hash function changes, so every machine still hashes the same bytes.
  • This repo's own gate. Keel's checkout has core.hooksPath set to its keel-hooks, so guard D is green here. A worker in a fresh clone without hooks would be refused at preflight. That is the intended behaviour, and the fix line says so.

Not this WU

  • Chaining other tools' hooks (option C), a per-level report policy, or narrowing the epic-report candidates. These are follow-ups if the owner asks.
  • SHA-256 for cr/v1 and dod/v1 bindings, native SSH signing of rule-bearing commits (B7, stays backlog), and the notes fetch refspec (W6).
  • Re-recording Trawler DEC-72 in full: W5 does that. W2 only amends DEC-23, which already records the reversal.
