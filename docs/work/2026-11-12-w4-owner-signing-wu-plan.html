The roster after W4

One rule. A change is judged by the roster committed on what it lands on. Where that tree holds no roster yet, the roster the change itself carries judges it, and keel prints one line saying so. No keel command reads a roster from disk to decide who may sign.

The file format is unchanged (<tier>: <identity>, key: <identity> <keytype> <base64>); lines of a tier the judging policy does not accept still authorise nothing, and a malformed line is still an error. .keel/mr-allowed is rule-bearing in every project whatever rule_bearing lists, since Keel's template does not list .keel/. A roster change inside a branch never judges that branch's own merge: the target's roster does. So adding or replacing a signer needs a sign-off from a signer the target already lists.

The roster-change acknowledgement. When the range base..tip changes .keel/mr-allowed, keel mr confirm prints every added and removed roster line and refuses, writing nothing, unless --roster-change is passed. This is the one point where a roster edit made inside a branch meets the owner: the owner reads a result report, not the diff, and would otherwise sign a new signer in unseen. The flag is not recorded in the note; the signed change hash already binds the roster bytes.

The commit-level roster

A rule-bearing commit is judged by HEAD's committed roster, which is the branch before this commit. A commit that edits the roster is therefore judged by the old roster and cannot name itself into it. Only when HEAD has no roster (the commit that introduces it, or an unborn branch) does the staged copy count. What this is worth: it removes the disk file from the decision, so R14's write no longer helps. What it is not: a boundary. The trailer is typed text in every tier, --no-verify skips the hook, and rule_bearing itself is still read from the working tree (DEC-24, unchanged). The bound on a rule-bearing commit is that it sits inside a WU diff and an epic diff, each signed with the presence key and verified against the target's roster.

Owner setup (not code; the owner's hands only)

  1. Choose the key. Either a FIDO key (ssh-keygen -t ed25519-sk; every signature needs a touch), or a passphrase key that is never loaded into ssh-agent and is configured by its private path, not its .pub (every signature asks for the passphrase on the terminal).
  2. In the W4 worktree, once the code is there: cargo run -q -- mr setup --as vuluu --key <path>. It writes the line to .keel/mr-allowed, sets keel.signingkey in the shared git config, and proves the key with one probe signature.
  3. Commit it with the staged keel mr commit of owner commit A.

Keel cannot tell a presence key from a cached one, so this part of R14's fix is checked once, live (test plan), and stated in DEC-48 as the owner's standing duty.
