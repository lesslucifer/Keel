Decisions: workflow gates

Why the notes, the merge gate, the human sign-off, the code review contract and the doc tiers are the way they are. Check here before "fixing" anything that looks deliberate.

T2 · decisions · append-only · 2026-11-08 · Keel · DEC-13 – DEC-29, DEC-40, DEC-41, DEC-47, DEC-49 – DEC-52, DEC-54 · distilled from E-SEED (W2–W8 open points, rulings R2–R24), later epics as each record says

Append-only. A reversal marks the old record superseded by DEC-m and adds a new one. Check ids (1·notes … 8·manual-review) are the ones src/gate.rs prints.

Notes

DEC-13 · Schemas start at /v1, with no legacy readers

ContextTrawler's gate kept a reader for every schema it ever shipped (cr/v2…v5, design data inside cr/v3).
ChoiceEvery Keel note (test, doc, cr, mr, dod) starts at /v1, shares one identity block (tip, base, branch, committer, timestamp) and has no legacy readers. Until a release, a schema is changed in place (doc/v1 paths became changes). The identity has no epic/WU ids: the epic and WU are inferred from branch names, and 2·manifest only checks that each note's tip is the commit it sits on.
ConsequencesA note copied onto another commit is caught; a note meant for a different WU on the right commit is not.
LineageSeed plan; W2 scope; W3 open point 10; W8 open point 10.

DEC-14 · Evidence is derived from the tree, bound by git hashes

Choicekeel notes write computes range, identity, tiers and test counts itself; the agent supplies only a judgment (JSON on stdin for test, flags for cr). The cr binding is the git blob hash of git diff base tip -- code_paths, one shared function for writer and gate. Writing from main (an empty range) is refused.
Rejectedsha256 (diff_sha256): a new dependency for no gain while git's own object hash binds the tip anyway (hardening in backlog B7).
LineageW2 open points 1–3; Trawler DEC-44.

Merge gate

DEC-15 · One range resolver; configurable branch prefixes

ChoiceThe note writer and the gate resolve the target the same way: --target, else <wu_prefix><e>/… → <epic_prefix><e>, else branches.main. branches.epic_prefix / wu_prefix default to epic/ / wu/ and drive hook level detection and the pre-push range check. A tip that names no local branch (a bare commit id, HEAD on a detached checkout) is resolved before the naming rule: the epic of a wu/ branch that holds it, else the one epic/ branch that holds it; no holder or more than one epic refuses, asking for --target. main is never a guess for a WU. The note writer needs no such resolution: it always writes on HEAD's branch (owner ruling 2026-11-14, E-SEED3.W3). Merges into other branches are ungated.
RejectedTaking the first holder git prints; falling back to main when the tip is an ancestor of main; searching remote-tracking branches, since the checkout cannot measure what it does not have.
ConsequencesA WU's cr.base equals the merge-base its WU gate computes against the epic (it never could when the writer measured from main).
LineageW3 open points 5, 6; R4.

DEC-16 · The docs/infra exemption, and what it never covers

ChoiceA range is gated when any changed path is under code_paths (empty = everything is code). Otherwise it is exempt from test, cr and doc evidence and writes no receipt. Optional infra_paths globs can only narrow the exemption. Never exempt: check 8 (sign-off), the epic tracked-doc layout, and the lineage of a T3 doc the range archives (an archive commit is always docs-only, so exempting it would make the distillation check unreachable).
RejectedA config flag to exempt archive commits.
LineageW3 open points 2, 3; R3; R24; W8 open point 7; Trawler is_gated.

DEC-17 · keel check: where trees are proven

ChoiceRenamed from "gate0" to check everywhere (keel check, [check], keel-check-green), with no compatibility for [gate0]. It runs at preflight, on the merged tree of an epic → main merge, and on every pushed tree; a WU → epic merge checks notes only. Results are cached by tree content. The pre-commit hook enforces merge-only main and, since E-SEED3.W4, runs keel lint when the staged diff touches a code_paths path (lint only, never tests) and, with MERGE_HEAD present, runs the gate pre-merge-commit would have run instead of a separate lint.
ConsequencesTwo WUs green alone but red together are caught at the epic's preflight, its merge into main, or a push, not at the second WU merge. A non-HEAD pushed tree is proven in a scratch worktree whose cache is discarded.
LineageR2 (option a: spec reworded to match code); R5; W3 open point 8; W6 open point 9; Trawler DEC-74, DEC-11/54 (cache); E-SEED3.W4 (the commit hook's lint and merge gate).

DEC-18 · The epic walk and walk_waivers

ChoiceThe epic gate re-verifies every first-parent seam. A red seam is overridden only by walk_waivers: [{seam, why}] hand-edited onto the epic tip's cr note (git notes --ref=cr edit), matched by sha prefix, blank reason never waives. The epic tip itself is not walked (its epic-level checks cover it) and no rule restricts what the epic tip may be. A plain seam that changes no code and carries epic-range test and doc notes (each naming the epic's base, which is not the commit's parent: the archive commit) is judged on them over the epic range, by checks 1, 2 and 6 without the tracked-doc layout; a commit that changes code stays a standalone commit. The push of an epic branch skips plain commits already on main and judges its tip the same way when the tip carries epic-range notes; review and sign-off stay at the merge into main (owner ruling 2026-11-13, E-SEED3.W2).
RejectedA CLI flag for waivers; a rule that the epic tip must not be a code commit; running the epic review before the archive commit; a --tip flag for keel notes write; judging a code commit with epic notes over the epic.
LineageW3 open points 4, 7; R6; Trawler's walk.

DEC-19 · Notes sync is push-only

Choicepre-push pushes refs/notes/* (a failed sync only warns). Nothing configures a notes fetch: a fresh clone runs git fetch origin 'refs/notes/*:refs/notes/*' by hand. Fetch setup in init is deferred (backlog B6).
LineageW3 open point 9; R7.

Human sign-off

DEC-20 · Trust model: a local roster; "signed" means a listed key signed

Choice.mr-allowed lives at the worktree root, untracked (git-ignored via .git/info/exclude); every reader refuses while it is tracked, and the fix is to delete it and rebuild with keel mr setup. Tiers email / username / key, configurable via [mr] tiers (default all three). If an identity has any key entry, its notes must carry a verifying signature, whatever tier the note claims. Identities are limited to [A-Za-z0-9@._+-].
Accepted limitationAny process with SSH_AUTH_SOCK or filesystem access (including an AI agent) can sign with a loaded key or add itself to the roster. "Signed" proves a listed key signed this exact change, not that a human reviewed it. A passphrase-protected key is assumed and recommended; it only helps while the key is not loaded into ssh-agent.
LineageQ10; R8 (security review H1); W4 open points 1, 4, 5, 16; Trawler DEC-9, DEC-10.
AmendedBy DEC-47 (E-ROUTER3.W4): the roster is .keel/mr-allowed as committed on the target, never a file on disk; the untracked .mr-allowed is read by nothing.

DEC-21 · The signature payload

Choicessh-keygen -Y sign -n keel-mr over a versioned text: keel-mr/v1, level, base, tip, change hash (blob hash of the full diff), report path, report hash. Hashes are git object ids. The key comes from git config keel.signingkey (never user.signingkey). mr confirm self-verifies against the roster before writing. The verifier recomputes base, tip and change from the repo and trusts only the signed report hash, re-checked against the report's bytes.
RejectedTrawler's bare change_hash\nreport_sha256 (replayable onto another commit, range or level); sha256 via a new crate.
LineageW4 open points 2, 3, 6, 10; Trawler DEC-10.
AmendedBy DEC-40 (E-SEED2.W2): payload keel-mr/v2, the report lines only when a report is attested, change and report hashes sha256:<hex> via the sha2 crate, reversing the "sha256 via a new crate" rejection above.

DEC-22 · Sign last, strictly; check 8 at the boundary only

Choicekeel mr confirm refuses unless the tip passes checks 1–7 for its level (the epic walk included), so a human is never asked to sign a tip the merge would refuse. Check 8 runs in gate::run() on every top-level wu/epic run, never inside verify(): the walk re-enters verify() per seam and must not re-judge old seam sign-offs (the roster is local and mutable). Check 8 runs at pre-merge-commit only, not pre-push. The report is --report or the single changed *-result.html; reworking that is deferred (backlog B2).
LineageR10; R11; R13 (security review H4); W4 open points 8, 9, 11, 17; Trawler DEC-27, DEC-9/10 (boundary-only).
AmendedBy DEC-40 (E-SEED2.W2): the report is found by its data-artifact role under [mr] report; the *-result.html rule is gone. Correction found in W2: "pre-merge-commit only, not pre-push" is stale - pre-push also runs check 8 for every merge seam not already on the remote branch (the code is the truth); DEC-40's old-note exposure depends on it.
AmendedBy DEC-49 (E-CRCAP.W1): one exception to sign-last. A sign-off that waives the tip's review (--waive-review) does not need the tip's own cr note or checks 3–5 first; every other check must be green, and the waiver is written in the same act as the signature.

DEC-23 · The merge boundary judges by the target's policy and untracked hooks

Contextpre-merge-commit runs with the incoming branch already in the working tree. A branch could rewrite .keel/config.toml (H2) or ship a no-op .keel/hooks/pre-merge-commit that git would run for its own merge.
ChoiceThe hook loads the config from HEAD:.keel/config.toml (the target's committed policy; no committed config → refuse). Empty merge heads on a gated branch are refused (H3). Hooks are written to <git-common-dir>/keel-hooks/, untracked, with an absolute core.hooksPath; the hooks are thin exec keel … shims, so drift is small.
ReversesTrawler DEC-72 ("git runs the tracked hooks", relative tracked core.hooksPath, plus a guard refusing a checkout whose hooksPath is not its own). Keel did not carry that guard over; coexistence with other hook managers is settled by the amendment below.
LineageW4 open points 14, 15, 19; R14; commit 0412b3c.
Amended (E-SEED2.W2): coexistenceKeel runs alone, never alongside another hook manager. keel hooks install refuses (exit 1, changes nothing) when the effective core.hooksPath (any scope) is not Keel's canonical keel-hooks path, or, with none set, when <git-common-dir>/hooks/ holds any entry not ending in .sample; it names what it would replace, and --force replaces it. A re-install over Keel's own path is a no-op refresh; install and guard D compare paths component-wise with one test, so a trailing / is still Keel's path. keel init writes its files, then stops on that refusal; its -f never implies --force. Guard D (a DEC-72-style guard, UC-GATE-6): keel preflight and keel verify-dod wu|epic fail 0·hooks while core.hooksPath is unset or not Keel's; keel check only warns; verify-dod hook|range|commit skip it (they run from Keel's own hooks, or inside the walk).
Rejected (coexistence)Chaining the other tool's hooks (re-imports branch-controlled code into the gate); refusing only a foreign value and warning on an unset one (misses a clone where hooks were never installed). Cost accepted: a hook manager switched on later is caught at the next preflight or gate command, not when it happens.
Lineage (amendment)E-SEED.W9 plan open point 5 (options B + D); E-SEED2.W2 plan open question 5, choices C, D, E, G; owner ruling 2026-11-09; Trawler DEC-72 (guard).

DEC-24 · Rule-bearing commits: a trailer, not a signature; known gaps accepted

ChoiceA commit touching rule_bearing needs a listed Reviewed-By trailer (keel mr commit); the WU's mr/v1 signature covers the whole diff. Native git commit -S signing is deferred (backlog B7). rule_bearing entries ending in / are prefixes, others globs.
Accepted gaps(1) Permanent, not scheduled: the commit-msg hook reads rule_bearing from the working-tree config, so a transient uncommitted edit lets a rule-bearing commit land without a trailer, and nothing downstream re-checks trailers. (2) git commit --amend sees only newly staged changes; cherry-picks are checked like any commit.
LineageR9; R16; W4 open points 7, 12, 21; Trawler DEC-9.

DEC-40 · The result report is a configurable, role-found receipt; sign-off hashes are SHA-256

ContextThe sign-off always attested one report, inferred from a changed *-result.html: a project with no reports could not sign, a report with another name was missed, and an archived epic report was not found. The hashes were git SHA-1 blob ids.
Choice[mr] report = "required" | "optional" | "none" in the target's committed config, one policy for both levels, default required. The report is the doc whose root data-artifact carries the level's role (wu-result, epic-result; a collapsed doc counts for both), or --report <path>. Candidates, the same for both levels: html under docs.root changed in base..tip and present at the tip. No untracked or archived file is ever searched (owner ruling 2026-11-10): an epic sign-off passes --report <path> unless its result doc is committed in the epic's diff. Several candidates are refused with the list; none under required is refused before signing (FAIL / fix, no note); none with --report is refused. Check 8 reads the policy from the cfg it is given (HEAD's at the merge hook): required with no report in the note is red; a report in a note is re-hashed whatever the policy. The report is evidence like the notes: mr/v1 and dod/v1 both name it, nothing new replaces dod/v1. Payload keel-mr/v2, with the report lines only when one is attested. mr/v1 change_hash and report_hash are sha256:<hex> over the same bytes as before (diff text as git returns it; the report blob at the tip; the raw local file for an epic), via the sha2 crate. Note schemas stay mr/v1 and dod/v1, changed in place.
RejectedA per-level policy (the table form can be added later without breaking the string form); two automatic bounds tried on an untracked epic-report search under docs.root (gitignored docs/.archive/ included): "exactly one untracked epic-result" (from a checkout's second epic on, the archive holds several, and an epic with none of its own attested the one earlier report) and that search minus reports an mr/v1 note on a commit the base contains attests (review r2: a second raw-JSON note parser, a walk of every mr note per confirm, a scan of the whole archive, and its own "archived" definition beside notes::archived; it still counted reports signed elsewhere or not yet in the base); narrowing epic candidates by name or by a new epic-id attribute (new markup is rule-bearing skill text, and a tip given as a sha names no epic); bounding them by file mtime against the base's commit time (cp -p and touch move it, and it differs per machine); git hash-object for SHA-256 (git 2.50 has no --object-format there) and shell tools (differ by platform); SHA-256 for cr/v1 and dod/v1 bindings (unsigned, and changing them stales every in-flight cr note).
ConsequenceNo legacy reader (DEC-13): a pre-W2 mr/v1 note is red wherever a W2 binary re-verifies it - verify-dod wu|epic, the merge hook, and pre-push for an unpushed merge seam. Already merged and pushed seams are not re-judged. Owner rule: sign, merge and push each WU with the same installed keel; re-sign a WU signed but unmerged when the installed binary crosses W2. The usual epic sign-off names its report: epic close archives T3 docs out of git, and check 6 refuses a T3 doc tracked at the epic tip, so under the default tiers only a result doc outside the T3 globs (or a one-WU epic's collapsed doc before archive) is found without --report. Nothing in docs/.archive/ is ever picked by accident, whatever earlier epics left there. --report is checked as before: [mr] report = "none" refuses it, and the path must be readable (the blob at the tip, else for an epic the raw local file) or the confirm is refused.
LineageE-SEED.W9 plan (never started); R11; W4 open point 3 (backlog B7); E-SEED2.W2 plan open questions 1–4, choices A, B, F; owner ruling 2026-11-09; owner ruling 2026-11-10 (option A: no epic-report search) after review r2.
AmendedBy DEC-49 (E-CRCAP.W1): on a waived tip the keel-mr/v2 payload gains a last line review: WAIVED sha256:<hex> and mr/v1 gains waiver_hash; dod/v1 gains review and waiver. Without a waiver every byte is as before, so the header stays v2.

DEC-41 · Keel finds the repository from its working directory; git's local environment is never forwarded

ContextGit exports the variables of git rev-parse --local-env-vars to its hooks, and from a linked worktree GIT_DIR is absolute. On 2026-11-10 a git push from a linked worktree ran keel check, whose cargo test inherited that GIT_DIR: the test fixtures' git reached the real repository and set core.bare, an identity, a moved epic branch, a branch, a note and the installed hooks. The same inheritance made the pre-push scratch worktree check the hook's worktree instead of the pushed sha. Separately, keel mr confirm on a tip already merged into its target signed the empty range over the valid sign-off.
ChoiceEvery process keel spawns goes through one helper that removes the 15 names of git rev-parse --local-env-vars (the list is hardcoded; a test checks it covers the installed git's list, and a source scan checks every spawn in src/ uses the helper). The configured lint and test commands lose all 15. Keel's own git calls keep GIT_INDEX_FILE: git's commit hooks receive the index being committed (a temporary one for commit -a or a pathspec commit), and the commit-msg Reviewed-By check must read that one. Not stripped: GIT_CONFIG_GLOBAL, GIT_CONFIG_SYSTEM, GIT_CONFIG_NOSYSTEM, identity variables, GIT_REFLOG_ACTION - they select a scope or identity, not a repository. Every test spawn that can reach git goes through tests/common cmd(), which strips all 15, and a source scan enforces it. keel mr confirm refuses, writing nothing, when the merge-base of tip and target is the tip. The push check's scratch git worktree add and worktree remove strip GIT_INDEX_FILE, so a hook that pushes, or a shell that exported it, never writes the pushed tree into the caller's real index; keel's other git calls keep it, as above. Every test spawn in tests/common also sets GIT_CONFIG_GLOBAL=/dev/null and GIT_CONFIG_NOSYSTEM=1, so the suite reads no developer global or system config (backlog B10); a repository's own config still applies.
RejectedAsking git for the list at runtime (one more spawn per call, for nothing the coverage test does not catch); stripping GIT_INDEX_FILE in keel's own git calls too (a Reviewed-By bypass through commit -a); stripping the user's global/system config selectors (not repository-locating; the suite's isolation from ~/.gitconfig is set in tests/common (backlog B10)); making verify-dod red on an empty range (a merged tip is legitimately exempt there; only signing it is wrong).
ConsequenceGIT_DIR=/x keel … from an unrelated directory no longer reaches /x: keel runs inside the checkout it judges. The fix protects a push only once the fixed binary is the keel on PATH, since the hooks exec it; until then push from the main checkout (relative GIT_DIR=.git).
Incident recordThe empty-range sign-off happened to E-SEED2.W2. Its tip d40cb0d was signed and merged into the epic (9f9b15e), and then keel mr confirm wu ran again on that already-merged tip. Its mr/v1 note now reads base = tip = d40cb0d with the empty change hash: the note from the real sign-off is gone, and only the WU result and this record say what was signed. The merge itself went through the gate before the overwrite. Since W13, mr confirm refuses such a tip and writes nothing.

DEC-47 · The signer roster is committed, and the target's copy judges

ContextUnder DEC-20 the roster was the untracked .mr-allowed of whichever checkout ran the command, and .gitworktreecopy seeded it into every worktree. A worker session can write its worktree, so it could list itself, or rewrite [check] test to run keel mr confirm --as <owner> through keel check (backlog R14). Whoever wrote a checkout decided who may sign.
ChoiceThe roster is .keel/mr-allowed, committed; same line format and tiers as DEC-20. Every reader judges a change by the roster committed on what it lands on: check 8 at the merge hook by HEAD's, by hand by the resolved target's, at pre-push by the merge's first parent's; keel mr confirm by the target's (so a sign-off the gate would refuse is refused before signing); keel mr commit and the commit-msg hook by HEAD's. Where that tree holds no roster, the one the change carries (the tip's tree, or the staged index) judges and keel prints one bootstrap line; with none on either side nobody may sign. .keel/mr-allowed is rule-bearing whatever rule_bearing lists. A sign-off whose range base..tip changes the roster prints every added and removed line and is refused, writing nothing, without --roster-change; the flag is not recorded, the signed change hash already binds the roster bytes. keel mr setup writes the working file and authorises nothing until it is committed. Keel's own policy is tiers = ["key"] with a key that needs the owner's touch or passphrase (DEC-48); the template keeps all three tiers.
RejectedTracking .mr-allowed at the root (every checkout holds an untracked file of that name, so the first checkout of a branch that tracks it collides, and info/exclude still hides it); always main's roster (a roster change could not be used before it reached main, which this epic's own bootstrap cannot do, and a same-user shell can move the local main too); a disk fallback on a target with no roster (it keeps the read this decision removes); printing a roster change without refusing (a printed line scrolls past a pasted command); reading rule_bearing from HEAD in the commit-msg hook (the trailer stays typed text, so it bounds nothing more); refusing a signing key that is not sk- (a passphrase key outside the agent gives presence too, and Keel cannot see caching); key-only template defaults (a product decision outside a router epic).
ConsequenceA roster change inside a branch never judges that branch's own merge, so adding a signer needs a sign-off by a signer the target already lists. A commit that edits the roster is judged by the roster it replaces. A tiers flip takes effect on a target once committed there; merges already pushed are never re-judged, so push gated branches before flipping tiers or an unpushed identity-tier sign-off turns red at pre-push. The remaining gaps (a typed trailer, --no-verify, a same-user shell rewriting the target branch, notes deletion, a branch with no roster) are recorded in DEC-48. With no working signer left, the owner lands a roster by hand outside the gate, the same recovery the policy file has. keel mr setup refuses a roster it cannot read rather than rewriting it (W4 review round 1).
LineageE-ROUTER3 plan, W4 block, open points 2 and 5; E-ROUTER3.W4 plan open points 1–9, owner go 2026-11-12 on every default; backlog e-router-v2 R14; amends DEC-20; restates DEC-24's gap unchanged.

DEC-49 · A waived review is its own verdict, and only the owner accepts it

ContextA review the owner waived could only be written as PASS: E-SEED2.W12's tip, the E-SEED2 close and E-SEED2.W14/W15 say "reviewed, PASS" where the owner skipped the review (backlog B12). E-WMODE spawned a review session twice just to write such a PASS.
Choiceverdict: "WAIVED" with waiver: "<reason>" in cr/v1, bound to the code like a review. Check 3 accepts it with a non-blank reason and prints it; the walk carries a waived WU up; dod/v1 records it. The owner waives in the sign-off itself, in two steps (--waive-review "<reason>" previews, --confirm-waiver <code> writes the cr note and the sign-off together); the code is a hash of tip, base and the listing shown, so the owner confirms exactly what was shown. A waiver the tool wrote (the cap, DEC-50) is signed only with --accept-waiver <code>. The sign-off covers it: waiver_hash on mr/v1, and a signed payload line for key-backed signers; check 8 rebuilds it from the current note. One waiver writer (notes::waive) for every path: never over a PASS, a failed round of the same range kept whole, a review of another range or none marked unreviewed. Agents never stage the three flags. Every cr note is read through plumbing (notes list + cat-file), so no log.*, i18n.* or signature setting can drop or re-encode a row. The signed line covers the whole waiver, not the reason alone: the reason, the open counts, whether a review ran (unreviewed), the open findings and the walk waivers, so changing any of them after the sign-off turns check 8 red. The waiver and the sign-off land in one ref transaction: both, or neither. The cr writer takes no --reason with any verdict; the cap's reasonless form and the owner's at sign-off are the only two writers. A sign-off whose hash covers the reason alone was made by a Keel before E-SEED3; check 8 names that cause, and re-signing is the fix.
RejectedPASS plus a waiver field (an older keel would pass it silently; WAIVED fails safe there as "not PASS"). A separate CAPPED verdict (one more value every reader must know; the reason text already tells a cap from the owner's waiver). Print-only consent, or a bare flag (no proof the owner saw it). (a) a session records the owner's ruling with the WAIVED writer: the launcher lets only a review worker write cr notes (DEC-46), so it cannot run. A bare --confirm-waiver flag (could be typed on the first run, unseen).
ConsequenceSign-last has one exception (DEC-22 amended). The waiver hash binds the whole waiver: changing its reason, counts, open findings, walk waivers or review state after the sign-off fails check 8 (E-SEED3.W6). The cr and mr notes are two refs; since E-SEED3.W6 they are written in one ref transaction, so a failed sign-off leaves neither. The cr writer refuses --reason with every verdict (E-SEED3.W6, backlog B18): the cap's reasonless form and the owner's at sign-off are the only two waiver writers. Earlier PASS-by-waiver notes are not rewritten; B12 and B13 keep that history.

DEC-50 · The review follows a 5-round schedule the tool derives from the notes

ContextA review looped: each round found something, the fix reopened the whole WU. E-ROUTER3.W2 ran 7 rounds and E-SEED2.W12 was stopped by hand; the 3-round cap of 2026-11-11 lived only in the router's brief text.
ChoiceThe owner's schedule (plan comment 2026-11-12): rounds 1–2 review the whole range, rounds 3–5 only the code since the last reviewed commit; nits are fixed after the verdict under a fix-PASS; from round 4 importants with no blocker too; only a blocker earns round 5; a blocker in round 5 ends in the cap's WAIVED. The round is derived from the reviewed cr notes on the branch's own first-parent line (one rev-list, one notes list, one cat-file --batch), never typed; no new state, since gated branches are never rebased. Preflight prints and enforces it (0·review-cap); the writer enforces it, stamps round and scope, and writes the fix-PASS (--fixes). One function, review::then, decides what follows a round for preflight, the writer and every refusal. A narrow round still binds the whole range's code hash, so checks 4–5 stay one rule. [review] max_rounds is read from the target's committed config (default 5), so a branch cannot raise its own cap. The writer takes the round's lists (--findings, --refuted, --nits, --fleet) because a review session cannot run git notes add. Amendments made during W2: a commit that changes no code path carries a fix-PASS for the same round, even over a fix-PASS; a docs-only commit after a failed round fixes nothing; a second code fix from round 4 ends in the owner's waiver; a FAIL with nothing counted is recorded and needs a round (from round 4 or at the cap, the owner's waiver).
RejectedSchedule in skill text only (relies on the looping session's memory; E-ROUTER3.W2 shows it fails). A round number the agent types (notes are derived, UC-NOTE-1). Binding a narrow round to its narrow diff (a second binding rule). A new owner command per step (the sign-off is where the owner decides). A one-verifier check of each fix-PASS (a small round of its own). Letting fix-PASSes stack over new code (unreviewed code piles up with no reviewer and no owner step). A merge check on nit dispositions (DEC-26 kept).
ConsequenceThe merge check reads a fix-PASS as PASS; nobody checks that it only fixes the findings, but the owner sees each one and its files at sign-off. Leftover risk: a session that drops a failed round without writing its note escapes the count. From round 3, a fix that breaks code it did not touch is caught only if a reviewer follows the call path. An older keel accepts a fix-PASS as a plain PASS, so the schedule applies only once keel is reinstalled from main (E-CRCAP open point 11); the epic's own reviews applied it by hand.
Amended (epic code reviews 1–3)"Code changed since a round" (the fix-PASS carry-over, a second fix) and the scope from round 3 count only the branch's own changes, by the exact rule (owner ruling 2026-11-13): each first-parent commit of since..tip with one parent against that parent; a merge of two against git's own automatic merge of its parents (git --attr-source=<first parent> merge-tree --write-tree, conflict markers and all), so only what the merge commit changed by hand counts. Attributes come from the first parent's tree, the checkout the real merge was made on, never from the checkout running keel (round 4: an epic that marked a file -merge made the automatic merge conflict where the real one had been clean); $GIT_DIR/info/attributes applies to both alike; an octopus merge whole, against its first parent (the gate refuses one anyway). Needs git 2.40 or later (merge-tree --write-tree, --attr-source); an older git is refused with that reason, never guessed. The decision uses the paths' raw bytes; a path that is not UTF-8 is shown as "unknown (a path is not UTF-8; it is among the branch's own changes in <range>)", never decoded lossily (round 4); one renderer (notes::changed_text) writes preflight's changed: and the sign-off history's fix-PASS rows alike (round 5). notes::own_diffs builds the diffs, notes::diff_names lists their files (diff-tree --name-only -z, one per diff), and preflight prints the same argv with -p, one command per commit, oldest first, every argument outside [A-Za-z0-9/._-] single-quoted, so its changed: list is the files of the diff reviewers run; the sign-off history lists a fix-PASS's own files. Why: a plain git diff since tip counted what a back-merge of the epic (DEC-29) brought from another WU as this WU's fix (round 1); diff-tree --cc --name-only listed every file a merge result differs in from all parents (round 2); the -p --cc hunks still joined edits within three lines into one hunk, and a file git diffs as binary (-diff) has no hunk filter (round 3). Rejected: rev-list --no-merges (hides own code resolved inside a merge); --cc in either form (above). When keel cannot tell what changed (a git error), the writer and preflight refuse, never reading it as "changed" or "unchanged". The cr notes' batch read lives in notes.rs with every other note read. fix_diff_hash still hashes git diff <reviewed> <tip> (a record; no check reads it). The schedule's fields are typed on the note (notes::ScheduleFields): a fixes that is not a full commit name, or a round that is not a whole number, makes the note unreadable for every reader, the gate included; review::Schedule is the one place preflight and the writer read the schedule from.

DEC-54 · The doc check runs at the write, from a host plugin; a review or a merge is no substitute

ContextDEC-5 put the two doc checks in Claude Code's .claude/settings.json (PostToolUse and Stop). DeepSeek Harness (DSH) has no shell-hook surface: no host setting runs a command on a tool call or at turn end. So on DSH nothing ran keel verify-doc, and a broken doc surfaced at a review or never. DSH's tool pipeline is tools/pre-execute → tools/execute → tools/post-execute → tools/result, with agent/turn-stopping before an otherwise finished turn closes (read from the installed dsh-tools and dsh-agent API).
ChoiceThe trigger is the write, on any host. A host with shell hooks runs keel verify-doc <path> on each first-party write or edit and keel verify-doc over all docs at turn end; a host without them reaches the same two points through a plugin. tools/post-execute runs the per-path check after the bytes land and returns {kind:'block', feedback} with the problem lines on a red doc, so that write's result is a failure. agent/turn-stopping runs the whole-tree check and calls agent.steer() with the problems, so the turn takes another step instead of closing. Exit 0 is silent, and a draft is silent by construction; flipping to ready is the checkpoint. The check fails the write; it cannot prevent it. The gate stays facts-only: the merge reads the doc/v1 note and the report's bytes, never a document's form.
RejectedVetoing the write at tools/pre-execute: it can allow, deny or ask, but cannot rewrite arguments, so an edit would have to be re-run and validated by the plugin, and a veto loses the work. tools/result: observe-only, the outcome is immutable. Moving the check to the review or the merge: both are too late, and the merge never checked doc form. A project-side script on DSH: no hook surface to attach it to. Writing the plugin's code in this repo: it is a host package, so it lives in its own repo in the desktop-dsh project.
ConsequencesA red doc's bytes still land, and the cost is one fixing turn in the same turn. Without the plugin installed in the profile, nothing checks doc form in a DSH session, so the plugin is a profile dependency named by the install line, never a project file. keel-plan and keel-workflow stop naming one host's scripts as the trigger and state the no-substitute rule. The shipped skills are tested for that text (tests/init.rs::shipped_skills_put_the_doc_check_at_the_write_and_name_no_required_host).
LineageE-DSH plan open points 3 and 4, and "The plugin seam, read from the installed API"; E-DSH.W2 result; owner review round 2 (2026-11-14). Extends DEC-5 — the Claude Code hooks are unchanged.
