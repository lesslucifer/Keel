The WU plan for wu/E-ROUTERFIX/w5-epic-e2e. One hermetic test drives one worker's life, as the router sees it, through every seam W1–W4 changed.

T3 · WU plan · 2026-11-09 · Keel · off epic/E-ROUTERFIX 225101e · epic plan E-ROUTERFIX, W5 block and E2E plan

Why

The epic plan was written for one WU and named W1's launcher scenario as the epic e2e. The epic now has four WUs, each tested only at its own boundary: W1's argv test never sees the guard's settings wiring or a seeded worktree, W2's guard test never sees the launcher's -n, W3's test never spawns a worker, and W4's test runs in a synthetic repo with a sleep shim. Nothing proves the pieces compose into the flow the router actually runs.

Requirement

One test, tests/router.rs epic_e2e_router_drives_a_granted_worker_in_a_seeded_worktree_to_its_end, in a scratch clone of Keel's own tree with keel's hooks installed, creates a worktree that inherits .mr-allowed, then sends each router call through the clone's settings-wired guard and runs each allowed launcher command as given: the worker starts in plan mode with the fixed grant and deny lists and is named as the subscription addresses it, and wait reports it STALLED (by its transcript under a temp CLAUDE_CONFIG_DIR) and then EXITED.

Design

  • Reuse. The test lives in tests/router.rs beside the helpers it needs: the stub claude (extracted from launcher() into one function both use, unchanged in behaviour), field, age, WORKER_GRANTS/WORKER_DENIES. The clone and hooks steps follow tests/init.rs's W3 test.
  • The tree under test. After the clone, the working tree's copies of the epic's files (scripts/router-worker.sh, scripts/router-guard.jq, .claude/settings.json, .gitworktreecopy) are copied over the clone's. So the e2e judges the source being tested, not only the last commit, and a local breakage shows red.
  • One command string, judged then run. The router's Bash command is fed to the guard, and the same string, split on spaces (the guard admits plain words only), is what sh runs. No step runs a command the guard did not see.
  • No timing as synchronisation. The stub is held by a release file. wait's STALLED needs two quiet polls, and the transcript is aged 2 minutes past a 1-minute threshold, so any number of real ROUTER_WAIT_POLL=0.2 polls give the same line. EXITED follows the release whatever the timing.

Expected

  • The new worktree's .mr-allowed equals the main checkout's.
  • The settings-wired guard allows the router the spawn with --permission-mode plan, SendMessage {to: <name>, notify_when_idle: true} and wait <name> 1, and denies it cargo test, keel mr confirm … and a SendMessage carrying a message.
  • The launcher prints RUNNING … permission-mode=plan. The stub's argv holds exactly the grant and deny lists, --permission-mode plan and -n <name>.
  • wait prints STALLED name=<name> … since=<transcript> while the worker idles, then EXITED name=<name> once it is released.
  • Each of those behaviours, broken once locally, turns the test red.
