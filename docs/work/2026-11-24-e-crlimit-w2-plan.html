E-CRLIMIT.W2 · The rules name the review settings

The instructions agents follow describe the review schedule as your three settings, not as numbers.

T3 · WU plan · 2026-11-24 · Keel · its data file, 2026-11-24-e-crlimit-w2-plan.yaml, sits beside this page · the epic plan is here

The problem

The tool now runs the review schedule your project's settings give it. The instructions agents read still describe the old fixed schedule, round by round. An agent that follows them expects rounds the tool refuses. The architecture page and the config template repeat the old numbers too.

What you get

  • The review instructions state the schedule once, in terms of the three settings: the cap, the whole-work rounds, and the round from which only a blocker earns another.
  • The default values appear in one place only: a small table in that section, labelled as the defaults.
  • Every other instruction names a setting or points to that section. None states a round number.
  • The config template lists the three settings, switched off, each with what it decides. It points to the defaults.
  • The architecture page names the settings and carries no number.
  • Keel's own rules file gets a correct comment. It sets no value, so your defaults apply.

How you approve

  1. You confirm this plan. Nothing is edited before that.
  2. A worker edits the instruction files and stages only those. It shows you the staged change. It does not commit.
  3. You commit it, with your own rule-file commit.
  4. A fresh worker checks the new commit.
  5. A separate read-only reviewer reads the new text against the tool's real behaviour. A fix means a new staged change and another commit from you.
  6. The worker writes the result report. You sign and merge.

What it makes

Text only: three instruction files and their two reference pages, each in both copies; the config template; the architecture page; one comment in Keel's rules file. No code changes. The exact places and what each becomes are in the data file.

  • Both copies of each instruction file are identical.
  • A fresh project's config, as Keel writes it, is accepted, and gets the defaults.
  • The read-only reviewer finds the text matches the tool.
  • Keel's checks pass.
