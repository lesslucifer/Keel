E-CRCAP · Code review follows a fixed 5-round schedule, and a waived review says so

The problem

Two things go wrong today. First, a code review can loop without end. Each round finds something, the author fixes it, and the next round reviews the whole WU again and finds something else. E-ROUTER3.W2 ran 7 rounds before the owner stopped it by hand, and E-SEED2.W12 was stopped by hand the day before. Second, when the owner waives a review, the record still says PASS. Three merged tips say "reviewed, PASS" when the truth is "the owner skipped the review". This epic gives every review a fixed schedule that the tool enforces: fixes that only answer small findings need no new round, later rounds look only at the last fix, and round 5 is the last. A review that stops without passing is recorded as WAIVED, never as PASS.

A round that finds nothing is a plain PASS. "Record PASS" after a fix runs no reviewers: the tool writes the PASS on the fixed commit and records which round it answers.

W1 · A waived review is recorded as WAIVED B12

In short: when the owner waives a review, or the schedule's cap stops one, the cr note says WAIVED with the reason. The merge check accepts it and prints it. Sign-off shows it and needs the owner's explicit yes.

Mechanics:

  • keel notes write cr --verdict WAIVED --reason "<reason>" [--blockers n] [--importants n] writes the cr note with verdict: WAIVED, waiver: <reason>, and the same code hash as any review. An empty reason is refused. A reason on PASS or FAIL is refused.
  • The merge check's review step (check 3) accepts WAIVED and prints WAIVED 3·review: <reason>. The base and code-hash checks (4, 5) are unchanged, so a code change after the waiver still invalidates it.
  • The epic's walk over its merged WUs passes a waived WU and prints it. The dod/v1 receipt records review: WAIVED.
  • keel mr confirm on a waived commit prints the waiver and the review history, then refuses without an acceptance flag (working name --accept-waiver). With the flag, the signed text gains a line review: WAIVED sha256:<hash of the reason>. The sign-off check (check 8) rebuilds that line from the current note. Commits with no waiver sign exactly as today, so existing signatures stay valid.
  • Skill text: keel-code-review §5–§7 (an agent writes an owner waiver only on the owner's ruling), keel-workflow §3–§6.
  • Rule-bearing: skills/ and its .claude/skills/ mirror, in one owner keel mr commit that the worker stages and prints.
  • Not reviewed by any gate: that skill text and this WU's plan and result. The code (src/notes.rs, src/gate.rs, src/mr.rs) and tests/ go through the code review.

W2 · The 5-round schedule B8 · rounds owner 2026-11-12

In short: the tool knows which round a review is from the cr notes already on the branch. It tells the reviewer what to review (the whole WU, or only the last fix), writes a PASS after a fix that only answers allowed findings, and stops at round 5 with a WAIVED note. Nobody has to remember the schedule.

Mechanics:

  • Round number. A round is a reviewed cr note (PASS or FAIL, not a fix-PASS) on a commit of the branch's own line of history: first-parent commits of base..tip. One rev-list --first-parent and one git notes list; no new state. An epic counts only its own rounds, never its WUs'.
  • Preflight (keel preflight wu|epic) prints review round n of 5 and the scope. Rounds 1–2: the whole range. Rounds 3–5: <last reviewed commit>..<tip> on the code paths, which the skill passes to its reviewers as their diff. It refuses round 5 unless round 4 found a blocker, and refuses any round 6, with 0·review-cap.
  • The reviewed note (keel notes write cr --verdict PASS|FAIL) stamps round and scope (full, or since: <sha>). It still binds the hash of the whole range's code, so checks 4 and 5 are unchanged.
  • Fix-PASS (keel notes write cr --verdict PASS --fixes <reviewed sha>, working name). Allowed when that commit is an ancestor on the branch, carries the latest reviewed note, and its findings may be fixed without a new round: only nits in any round, or importants without a blocker in round 4 or 5. The note records fixes, the fix's own code hash, and the counts it answers. A fix-PASS on top of a fix-PASS is refused: a second fix needs a round.
  • The cap. When round 5 ends with a blocker, keel notes write cr --verdict FAIL answers that the cap is reached, and the skill writes the WAIVED note (W1) with a tool-fixed reason, review cap: 5 rounds, <n> blockers open. The owner accepts it, or not, at sign-off.
  • W1's sign-off listing adds each round, its scope and each fix-PASS.
  • Skill text: keel-code-review §1 (the scope comes from preflight from round 3), §2 (the new refusal), §5–§7 (the schedule replaces "loop until PASS"; the nit disposition fixed may now point at a fix-PASS), the keel-workflow check table, keel-router's review-worker brief row ("round n of at most 3" becomes the schedule). templates/config.toml's [review] comment changes, because the CLI now reads that section too.
  • Rule-bearing: skills/, .claude/skills/ and templates/, in one owner keel mr commit. Keel's own .keel/config.toml is not changed: the default applies.
  • Not reviewed by any gate: that text, the template and the WU docs.

W3 · What counts as a nit B8 · scope

In short: the review rules name two cases as nits, so they never fail a review: a missing test for a case the code already handles correctly, and a tidy-up of test helpers. The router's own extra reviews follow the same schedule. Text only, no code.

Mechanics:

  • The shipped rubric.md severity rows: if the code is right on an untested case, the missing test is a nit. If the code is wrong on that case, that is a blocker against the code, never against the test.
  • A test-harness tidy-up that changes no test's result (helpers, duplicated fixtures, hermeticity polish no test observes) is a nit. Whether the WU's own contract is tested stays a question for its test note.
  • keel-code-review §5 and §7: a nit never triggers a new round; it is fixed under a fix-PASS or waived on the note.
  • keel-router: its triage line, and its rule "re-review security paths until a round finds nothing above low", follow the 5-round schedule as text (open point 9).
  • Rule-bearing: skills/ and the mirror, in one owner keel mr commit.
  • Not reviewed by any gate: the whole WU. It changes no code, so it needs no test, review or doc notes, but it still needs the owner's sign-off. The router's read-only extra review reads the text.

Details

The rest of the plan is reference: acceptance criteria, contracts, scope limits, design choices, tests and where the knowledge goes at the close.

Acceptance criteria

  • A waiver: keel notes write cr --verdict WAIVED --reason "<ruling>" writes a cr note with the reason and the code hash. With no reason, it is refused.
  • The merge check on a waived WU prints WAIVED 3·review: <reason> and fails only on the missing sign-off. A code commit after the waiver invalidates it, as it invalidates a review.
  • Sign-off on a waived WU prints the waiver and the review history, and refuses without the acceptance flag. With the flag it signs, and the signature covers the waiver. Rewording the waiver, or turning a PASS into a waiver after signing, fails the merge.
  • An epic passes a waived WU in its walk and prints it as WAIVED. An epic's own review can be waived too (the E-SEED2 close case).
  • Preflight prints review round n of 5 and the scope: the whole range in rounds 1–2, only the changes since the last reviewed commit in rounds 3–5.
  • After a round with only nits, the author's fix gets a fix-PASS without a new round, and the merge check accepts it. The same holds for importants without a blocker in rounds 4 and 5. Any other fix-PASS is refused.
  • Round 5 runs only after a round 4 with a blocker. Round 6 never runs. A blocker in round 5 ends in a WAIVED note with the cap reason.
  • An epic counts only its own rounds, never its WUs'. Re-running a review on the same commit is one round.
  • [review] max_rounds in the committed config moves the cap. Unset means 5.
  • The rubric and skill name the two nit cases, and keep "the code is wrong on an untested case" a blocker. skills/ and .claude/skills/ stay byte-identical.
  • The epic test below passes through the real merge hook in a scratch repo.

Epic end-to-end test

epic_e2e_the_review_schedule_ends_in_a_fix_pass_or_an_owner_accepted_waiver in a new tests/review.rs, added by W2 (the last code WU). It builds a scratch repo in a temp dir, runs keel init with hooks there only, uses a test signer, and needs no network.

  1. An epic branch with a plan, and two WU branches with code, tests, result reports, and test and doc notes.
  2. WU A: round 1 finds only nits. The fix gets a fix-PASS, the merge check accepts it, it is signed, and the real git merge --no-ff into the epic passes the hook.
  3. WU B: rounds 1–4 fail (written with keel notes write cr --verdict FAIL, the only review output the merge check reads), round 4 with a blocker. Preflight prints the full scope for rounds 1–2 and the narrow one for 3–5. Round 5 fails with a blocker, and round 6 is refused.
  4. WU B ends in a WAIVED note with the cap reason. The merge check fails only on the missing sign-off. Sign-off without the flag is refused; with it, it signs. The merge into the epic passes the hook.
  5. The epic: its own review passes, its walk prints WU B as WAIVED, it is signed, and the merge into main passes the hook.
  6. Failure cases: a fix-PASS after a round-2 FAIL with importants is refused; rewording WU B's waiver after signing fails the sign-off check.

No test layer is waived. Lesson from E-SEED2.W15: the test runs the real merge through the real hook.
