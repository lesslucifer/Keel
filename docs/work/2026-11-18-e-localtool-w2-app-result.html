The nine answers

In short: the app reads and alerts; it never writes to git, keel or a session. Each answer gives one recommendation, then why. Facts in brackets, such as [F2], are in the sources table under Details. File and line references are to the code at e00f1ec.

Q1 · What runs where, and what may the window not do?

Recommendation: the main part does all the work: it runs commands, watches git, alerts you and keeps the project list. The window only shows. It runs with Electron's safe defaults, loads only the app's own pages, and asks the main part through about ten named requests. A request names an item the main part already knows, never a command, a path or a commit.

Why: the main part has Node and the window does not, and a bridge script is the one safe way between them [F1]. Electron's checklist asks for exactly this: isolation, the sandbox, no Node in the window, one method per request, a check of each request's sender, a content policy, and no navigation away [F2, F3]. So even a page that went wrong cannot run anything.

  • The window may not: read or write a file, run a command, open a web page, or pass free text to a command.
  • Requests, for W3 to size: the waiting list, the fleet, one epic, the projects, open an item's doc, copy an item's command.

Q2 · How does the app run keel and read its answers?

Recommendation: run keel's command line, one fixed command at a time, with no shell, and read its text. Ask keel for a machine-readable output later (keel change K1). Most data does not need keel at all: the notes are already JSON in git, and the app reads them directly (Q3, Q4).

Why: one judge. A Node binding would build a second copy of keel's checks into the app, and it could differ from the keel your git hooks run. The command line is what the hooks and you already use. Running a program without a shell keeps a stray character from becoming a command [F12].

  • Not a binding: rejected for the one-judge reason above.
  • The text today is stable enough to read: each failed check prints one FAIL <check> block (src/gate.rs l.497 prints the green line).

Q3 · How does the app show the gate without writing a receipt? (W1 point 5)

Recommendation: two sources. For what already happened, read the notes on the tip: tests, docs, review, sign-off and receipt. For "would it pass now?", run keel ci gate, which runs the same checks and writes no receipt. Later, give keel verify-dod its own no-receipt mode (keel change K2), so the app does not depend on a GitHub command W5 may retire.

Why: the gate writes its receipt in one place only: run stores it when green (src/gate.rs l.568). keel ci gate calls the same checks without that step (src/gate.rs l.578, its comment above says "writes no dod receipt"). So it is safe today. But its exit code is GitHub's: it stays green when only the review or your sign-off is missing (src/ci.rs l.48). The app must read its printed lines, not its exit code.

  • The app never runs keel verify-dod as it is: it writes the receipt.
  • Nor keel preflight: it runs lint and tests and writes a cache file (src/main.rs l.295).
  • Never --summary: it appends to a file.

Q4 · How does it read git, and how does it notice a change?

Recommendation: the git command, run without a shell and locked down. To notice changes, watch the git folder's branch and note files, wait a second for the burst to end, then re-read. Also re-read once a minute, in case the watch misses one.

Why: keel and every script read git with its command, so the app reads the same thing. Watching is quick, but Node says its file watching is "not consistent across platforms" [F13], so the minute check is the safety net. Today's router watch already works by checking every 15 seconds (scripts/router-watch.sh l.12).

  • Locked down: no inherited GIT_* settings, -c core.fsmonitor=false, --no-optional-locks, and --no-ext-diff --no-textconv on any diff. The worker facts already do this (scripts/router-worker.sh l.249 to l.252). Without --no-optional-locks, git status rewrites the index and can make a worker's commit fail [F15].
  • Worktrees: one list per project (git worktree list --porcelain). Branches and notes live in the shared git folder, so one watch covers every worktree.
  • No git library: it would be a second reader of the repository.

Q5 · What does it read from the sessions, and could it send the router a message later?

Recommendation: read three things, all read-only: Claude Code's session list (claude agents --json), each worktree's branch and tip, and the count of unread reports in the router's inbox. The watchdog and the app share one reading script (keel change K3), and each runs it: two readers, as W1 point 4 says. Sending the router a message waits for need n8. Then it must go by a way only you can use, never the inbox.

Why: the session list is Claude Code's documented way to read session state from another program [F16], and the watchdog uses it today (scripts/router-worker.sh l.212). The inbox is not safe for your messages: a worker can post there too, so the router could not tell yours from a worker's.

  • Session fields the app shows: name, folder, state (working, blocked, done, failed, stopped), status (busy, waiting, idle) and what it waits for [F16].
  • The app never consumes an inbox report: that is the router's receipt of it (scripts/router-inbox.sh l.194). It only counts them (status, l.216).
  • Sending later: Claude Code's channels [F18] or its per-session message socket [F17] are the candidates. How an outside program posts on the socket is not checked [F17].
  • DeepSeek Harness: the router has session tools there (list, status, output), but they are a host plugin's, not a program's (docs/architecture.html l.183). Its docs show no session list for an outside program [F19, F20]. The app reads sessions through one small adapter per host: Claude Code first, DeepSeek Harness when its docs show such a list.

Q6 · How does it alert you, and how does it stay quiet?

Recommendation: one macOS alert when an item first enters your waiting list, never again for that item. Items that arrive within a few seconds share one alert ("3 wait on you"). A click opens the app on that item. The app sends nothing to Telegram; the router keeps sending it, as today.

Why: an alert is tied to an item, not to a file change, so a burst of git writes gives one alert. Electron's alerts come from the main part and report a click [F6]. Telegram stays the router's, unchanged, until need n9 lets the app own both.

  • Quiet: no alert for an item that left before it was shown, and none at start for items you already saw. The app remembers which items it showed.
  • At your desk you may get both a macOS alert and the router's Telegram message for one event. That stays until n9.
  • On macOS an unsigned app's alert fails [F6]. Q8 and open point 1 cover the signature.

Q7 · How does it stay closed to workers?

Recommendation: the app opens no network port, runs only its fixed commands, and treats everything a worker can write as plain text. It writes only in its own folder. It adds nothing to any session: the router guard and the file guard stay as they are.

Why: a worker can write the git folder and the inbox: that is how it commits, writes notes and reports. So branch names, notes, commit messages, reports and transcripts are a worker's words. Shown as text, they cannot run. A worker can also change the git folder's settings, and one setting names a program git runs on git status. That is why the app turns it off, as the watchdog does (scripts/router-worker.sh l.249).

  • No port, no web server, no link scheme another program can call.
  • Text from git or a session is shown as text, never as a page. Control characters are blanked, as scripts/router-watch.sh does (l.60).
  • Commands: fixed arguments, no shell [F12]. A commit or branch is checked first, as scripts/router-watch.sh does (l.39 to l.44). keel, git and claude are run from paths set in the app, never from a repository.
  • keel runs only in the project's main checkout, never inside a worker's worktree.
  • The router guard (scripts/router-guard.jq) and the file guard (scripts/router-file-guard.sh) are not touched.

Q8 · What does Electron cost, and how do we keep it small?

Recommendation: accept the size, keep the app thin, and upgrade Electron at least every 6 months. Package with Electron Forge. Try a free signature on your own Mac first, and buy Apple's membership only if alerts fail without it. No automatic updates in the first build.

Why: Electron ships a new major version every 8 weeks and supports only the latest three [F4]. So a release falls out of support about 6 months after the next one replaces it. The latest today is 45 (2026-10-20) [F5]. Alerts need a signed app [F6]. Sharing the app beyond your Mac needs Apple's paid membership and notarization [F7, F8]. Electron's free update service needs a public GitHub repository and signed builds [F9]; your GitHub stays for releases, so it fits later.

  • Thin: no web server, no native add-on, no Rust binding (Q2), one window.
  • Size and memory: an empty Electron app is reported at 115 to 150 MB, but not from Electron's docs [F21]. Memory use is not checked [F22]. Neither backs an answer: you chose Electron knowing it is large.
  • Windows and Linux later: Electron runs on both [F10]. The scripts the app reads are shell scripts, so that port is its own epic.

Q9 · How does it handle many projects?

Recommendation: one project list per Mac, kept in the app's own folder. Each entry is the path of a project's main checkout that keel set up. Everything about a project is read from that project; the app stores nothing in it.

Why: W1's scope column splits state this way. A project's state is its git, its inbox and its config. Per Mac are the sessions, the alerts and the list itself. Electron gives each app a folder in Application Support [F11].

  • Per Mac: the project list, which alerts were shown, the paths to keel, git and claude.
  • Sessions are listed once per Mac, then split by project: a session belongs to the project whose worktree is its folder, as the watchdog decides today (scripts/router-worker.sh l.231).
  • One watcher per project. One running copy of the app [F11].
