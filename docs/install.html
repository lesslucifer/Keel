Installing Keel

Keel is one binary, keel. It carries the gate and the rules (the skills). There is no Claude Code plugin or marketplace entry. Unix only (macOS, Linux): the CLI and its hooks use sh and Unix file permissions.

1. Install the binary

Pick one channel (prebuilt binaries for macOS and Linux, arm64 and x86_64; stable releases only, from tags vX.Y.Z):

curl --proto '=https' --tlsv1.2 -LsSf https://github.com/lesslucifer/Keel/releases/latest/download/keel-installer.sh | sh   # shell installer, no Rust or Node needed
npm i -g @lesslucifer/keel                                                                                              # npm, global install
brew install lesslucifer/tap/keel                                                                                       # Homebrew
cargo install --git https://github.com/lesslucifer/Keel                                                                # from source, needs a Rust toolchain

The shell installer puts keel in $CARGO_HOME/bin (default ~/.cargo/bin). If that directory is not already on your PATH, the installer also edits your shell profiles. It adds a line that sources an env script to ~/.profile, ~/.bashrc, ~/.bash_profile, ~/.bash_login, ~/.zshrc and ~/.zshenv, and it writes ~/.config/fish/conf.d/keel.env.fish. To leave your profiles alone, run it as … | INSTALLER_NO_MODIFY_PATH=1 sh and add the directory to PATH yourself. Install npm globally: a project-local npm i -D leaves keel off the PATH that git and Claude Code hooks see. Confirm with keel --version, which prints keel <version> and a line saying it is the merge-gate CLI, not keel.so. Do not run cargo install keel: that is an unrelated crate.

Name clash. The npm package keel (keel.so) also installs a binary called keel. With both installed you get whichever is first on PATH, so typing keel init may run the other one. If keel init prints something unfamiliar, run which -a keel. Keel's keel --version prints a line starting Keel: merge-gate workflow CLI. When the first keel on PATH does not print it:

  • Keel's four gate hooks (pre-commit, commit-msg, pre-merge-commit, pre-push) refuse, naming the clash. post-checkout runs no keel. The harness hooks do nothing, as with no keel.
  • keel init warns only when Keel itself runs, i.e. when you start it by its full path (for example ~/.cargo/bin/keel init).
  • A Keel built before 2026-11-10 prints no such line, so it is refused too: upgrade it.

Fix a clash by putting Keel first on PATH.

2. Check PATH

Claude Code hooks see the login shell's PATH, so check that one:

sh -lc 'command -v keel'

Without keel on PATH the harness hooks exit 0 silently (they do nothing), and the git hooks refuse and tell you how to install.

3. Adopt a repo

cd your-repo
keel init
keel mr setup --as <identity> [--key <path>]   # the human owner only: writes .keel/mr-allowed
git add .keel AGENTS.md .claude/skills .claude/settings.json .codex .agents .gitignore
git commit --no-verify -m "keel init"   # once, to land the policy and the signer roster on main
keel hooks install                       # once per clone (hooks live in the git dir, untracked)

keel init writes the config, AGENTS.md, the six skills into .claude/skills/keel-*, a project-router template, the shared skill root .agents/skills (see below), .codex/hooks.json, and merges two hooks (PostToolUse Write|Edit and Stop) into .claude/settings.json, keeping every other key. The merged harness hooks call the scripts that hooks install writes into the git common dir, and exit 0 when they are absent, so editing in a clone that never ran hooks install still works. That clone is not gated, though: keel preflight and keel verify-dod wu|epic fail 0·hooks until it runs keel hooks install, and keel check warns. It also adds the worktrees directory ([paths] worktrees in .keel/config.toml, default .claude/worktrees/) to .gitignore.

DeepSeek Harness. keel init plants the shared skill root here: .agents/skills is a relative link to ../.claude/skills. A DeepSeek Harness session lists the six keel-* skills through it, and a git worktree checkout resolves the same link. A .agents/skills that is anything else, a real directory, a file or another link, is kept and reported, never replaced; a symlinked or non-directory .agents gets nothing planted and says why.

DeepSeek Harness plugins. Two host plugins exist and are installed as profile packages, never project files, so they install once per DSH profile and never into the repo. Run these two lines as printed:

dsh plugin --profile <name> add <path>/dsh-auto-review        # permissions: Always Auto Review decides each call
dsh plugin --profile <name> add <path>/dsh-worker-workspace   # a worker session rooted in one worktree

Auto Review is the permission preset every Keel DSH session runs under: a medium call runs, a high-risk call is denied, and a denial is final. The worker plugin gives the router a session per worktree whose report is its transcript. Their contracts are use cases: DeepSeek Harness; the reasons are DEC-55 and DEC-56.

The doc gate is planned, not installable. keel init's hand-off also prints a third line for dsh-doc-gate, but no such repo exists (checked 2026-11-14) and the name and line are placeholders, so that command cannot work: do not run it. The plugin is planned as backlog D1: The DSH doc-gate plugin, with its contract in DEC-54. Until it ships, nothing checks doc form in a DSH session — run keel verify-doc before you rely on a doc.

4. Upgrade

Install a newer binary, then re-run keel init in each project and commit the result. init records each skill file's SHA-256 in .keel/skills.lock when it writes the file. A file that differs from the new binary's copy but still matches its lock entry was never edited: init upgrades it without asking. The first upgrade after the lock arrives still asks about every changed skill file: no hash is recorded yet. For every other differing file, init asks Overwrite? [y/N] (default no) and says whether the file is committed or has uncommitted changes. Missing files are created without asking. Commit the lock with the skills. Files you added inside a keel-* directory are left alone and listed as extra.

Pass -f / --force to overwrite every differing skill file without asking. Scripts and CI must pass -f: without it init reads answers from stdin, treats end-of-file as "no", keeps the file and exits 0, so an unattended run never updates anything. -f only touches .claude/skills/keel-*; .keel/config.toml, AGENTS.md, .codex/hooks.json and project-router are project-owned and are never overwritten.

keel init and keel hooks install refuse to replace another hook manager: when core.hooksPath points elsewhere, or is unset and .git/hooks/ holds anything but *.sample files, init writes its files, then exits non-zero with Keel's hooks not installed. Keel runs alone; the owner decides, then runs keel hooks install --force (init's -f does not imply it).

Upgrading across the SHA-256 sign-off format (E-SEED2.W2): an mr/v1 sign-off written by an older keel no longer verifies. A WU or epic signed before the upgrade and not yet merged must be re-signed with keel mr confirm on its tip.

5. The GitHub App (Keel's own repository only)

Keel's own repository runs its flow on GitHub: GitHub runs the gate from main as required checks, you sign off by approving a pull request and GitHub merges it, a router bot pushes work branches and opens pull requests, and the router hears your comments and reviews (architecture: GitHub). keel init sets none of this up in another project. The bot is a GitHub App you own; nothing works until you do these steps once.

  1. Create the App. github.com → your avatar → Settings → Developer settings → GitHub Apps → New GitHub App.
    • Name: any free name, for example keel-router-lesslucifer. Homepage URL: https://github.com/lesslucifer/Keel.
    • Webhook: untick "Active". No callback URL, no "Request user authorization".
    • Repository permissions: Contents: Read and write (push), Pull requests: Read and write (open, ready, comment), Issues: Read and write (comments, the tracking issue), Checks: Read-only, Commit statuses: Read-only; Metadata: Read-only is set by GitHub. Add Workflows: Read and write only if the bot must push branches that change .github/workflows/ (GitHub refuses such a push without it). Everything else: No access.
    • "Where can this GitHub App be installed?": Only on this account. Then Create GitHub App.
  2. Note its ids. On the App's General page, the App ID (a number). The slug is the last part of its public page URL, https://github.com/apps/<slug>.
  3. Make its key. Same page, "Private keys" → Generate a private key. A .pem file downloads.
  4. Install it on this repository only. Left menu → Install App → Install next to lesslucifer → Only select repositories → Keel → Install. The page you land on is https://github.com/settings/installations/<number>: that number is the installation ID. An App created before its Issues, Checks and Commit statuses permissions were added needs them added under Permissions & events, then accepted on the installation (Settings → Applications → Installed GitHub Apps → the App → Review request).
  5. Place the key and the ids on your Mac. Nothing else may hold a copy or a hard link, and nothing inside any Keel worktree. The script refuses a key with more than one link, a key not mode 0600 or 0400, and a directory anyone else may write: 
    mkdir -p ~/.config/keel/router-gh && chmod 700 ~/.config/keel/router-gh
mv ~/Downloads/<the downloaded file>.private-key.pem ~/.config/keel/router-gh/app.pem
chmod 600 ~/.config/keel/router-gh/app.pem
printf 'app_id=%s\ninstallation_id=%s\napp_slug=%s\n' <APP ID> <INSTALLATION ID> <slug> > ~/.config/keel/router-gh/app.conf
  6. The router's shell. If the router session's shell runs in a sandbox, it needs api.github.com and github.com on its network allowlist and write access to ~/.config/keel/router-gh/run (the script's run dir, made on first use). Workers need neither: they never run the bot's scripts, and their sandbox cannot read the key directory.
  7. Optional: the router's allow lines. Without them each call asks for permission (or auto mode's classifier decides); the router guard bounds every call either way. In the router checkout's .claude/settings.json (rule-bearing: commit it with keel mr commit): "Bash(scripts/router-gh.sh push *)", "Bash(scripts/router-gh.sh pr-open *)", "Bash(scripts/router-gh.sh pr-ready *)", "Bash(scripts/router-gh.sh post *)", "Bash(scripts/router-gh.sh sync *)", "Bash(scripts/router-gh.sh issue *)", "Bash(scripts/router-gh-watch.sh *)".
  8. Recommended once, in the repository settings: Actions → General → "Fork pull request workflows from outside collaborators" → "Require approval for all outside collaborators". A stranger's pull request then runs nothing until you approve the run. The workflow's token stays read-only and holds no secret either way.

Who the router hears is committed in .keel/config.toml [github] commanders: numeric GitHub user ids (the owner, 5499546). A change there is rule-bearing.

Your sign-off by approval. The committed .keel/mr-allowed lists you as github: 5499546 lesslucifer (your numeric user id, then your login), and [mr] tiers names github. Your approval of a WU's or epic's pull request then signs it; the typed keel mr confirm still works. A roster change is rule-bearing and judged by the target's roster.

The repository settings, in order. Until step 5 nothing is enforced.

  1. Any time: Settings → General → Pull Requests: merge commits only (squash and rebase off); "Allow auto-merge" off until step 5.
  2. Any time: Actions → General: workflow permissions "Read repository contents"; Actions may not create or approve pull requests; fork approval for all outside contributors. Rules → Rulesets: the keel-tags tag ruleset (all tags; creations, updates and deletions restricted; bypass: Repository admin only).
  3. First after .github/workflows/keel-gate.yml reaches main, and before 2026-12-02: Actions → Policies, allow pull_request_target for .github/workflows/keel-gate.yml only. GitHub blocks that event by default in public repositories from that date.
  4. Check one pull-request run: "Keel gate" shows build, keel/ci, keel/gate, keel/docs, and the three checks sit on the pull request's head commit, not on main's. If they sit on main's, stop and tell the router.
  5. The keel-merge branch ruleset: the default branch and epic/**; no bypass; merge only; one approval with code-owner review; stale approvals dismissed; required keel/ci, keel/gate, keel/docs, keel/sign-off from GitHub Actions; up to date not required. Then "Allow auto-merge" on.
  6. GH_TOKEN=$(gh auth token) scripts/gh-settings-check.sh in a checkout of main, with an admin token: green.
  7. Pages: Settings → Pages, source "GitHub Actions"; Environments → github-pages, deployments from main only. The repository must stay public: the site builder reads it without credentials.

With the ruleset on, nobody pushes main or an epic, and only you merge. Never approve a wu/ pull request into main. What is still owed live is in backlog G10.
