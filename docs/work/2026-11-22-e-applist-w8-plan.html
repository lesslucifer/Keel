The problem

The app shows a bare, unstyled page. The list screens come next, drawn mostly by agents. Without a fixed set of colours and sizes, each screen would invent its own. Without a fast way to see a screen, each change would need a full app build.

What you get

  • The project screen: your project, where keel, git and claude are, Choose, the PATH's source and the test alert, in Keel's own look.
  • Light and dark, following your Mac. Your Mac's own font.
  • A browser view of any screen, filled with sample data. No app build.

How it works

  1. One small set of colours, spacings and text sizes. Nothing else can be drawn.
  2. A checker refuses any other value, and refuses a style pieced together while the app runs, because nobody could check it.
  3. The screen talks to the app's core in one place. A test or the browser view swaps in a stand-in that answers from sample data.
  4. Tests draw the screen against that stand-in, click its buttons, and check what was asked and shown.
  5. The stand-in never reaches the app you install; a test proves it.

What it makes

  • Keel's look as one config, and its checker.
  • The project screen, replacing the bare page.
  • The stand-in, the browser view and the screen tests. The usual checks stay as they are.

  • The browser view shows the project screen with sample data: none, one project, a missing tool.

  • In the app, Choose opens the macOS dialog and the test alert answers.
