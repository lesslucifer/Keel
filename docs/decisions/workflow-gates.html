Decisions: workflow gates

Why the notes, the merge gate, the human sign-off, the work process, Keel's own test suite and the local app are the way they are. Check here before "fixing" anything that looks deliberate.

T2 · decisions · current truth · 2026-11-18 · Keel · DEC-13 – DEC-25, DEC-29, DEC-40, DEC-41, DEC-47, DEC-57, DEC-59, DEC-70

Current truth: each record says what stands today, why, and what was rejected. A later decision that changes one is folded in and named. A record replaced whole keeps its id and one line. Ids are never reused; git keeps the history. Check ids (1·notes … 8·manual-review) are the ones src/gate.rs prints.

Notes

DEC-13 · Schemas start at /v1, with no legacy readers

ChoiceEvery Keel note (test, doc, cr, mr, dod) starts at /v1, shares one identity block (tip, base, branch, committer, timestamp) and has no legacy readers. Until a release, a schema is changed in place (doc/v1 paths became changes). The identity has no epic or WU id: they are inferred from branch names, and 2·manifest only checks that each note's tip is the commit it sits on.
WhyTrawler's gate kept a reader for every schema it ever shipped (cr/v2 to v5). A note copied onto another commit is caught; a note meant for a different WU on the right commit is not.

DEC-14 · Evidence is derived from the tree, bound by git hashes

Choicekeel notes write computes range, identity, tiers and test counts itself; the agent supplies only a judgment (JSON on stdin for test, flags for cr). The cr binding is the git blob hash of git diff base tip -- code_paths, one shared function for writer and gate. Writing from main (an empty range) is refused.
WhyWhat the tool can measure, an agent cannot type. Git's own object hash binds the tip already.
Rejectedsha256 (diff_sha256) for the cr binding: a new dependency for no gain (hardening in backlog B7). The sign-off's hashes are SHA-256 since DEC-40.

Merge gate

DEC-15 · One range resolver; configurable branch prefixes

ChoiceThe note writer and the gate resolve the target the same way: --target, else <wu_prefix><e>/… → <epic_prefix><e>, else branches.main. branches.epic_prefix / wu_prefix default to epic/ / wu/ and drive hook level detection and the pre-push range check. A tip that names no local branch (a bare commit id, HEAD on a detached checkout) is resolved first: the epic of a wu/ branch that holds it, else the one epic/ branch that holds it; no holder or more than one refuses, asking for --target. main is never a guess for a WU. The note writer needs no resolution: it always writes on HEAD's branch. Merges into other branches are ungated.
WhyA WU's cr.base now equals the merge-base its WU gate computes against the epic; it never could when the writer measured from main.
RejectedTaking the first holder git prints; falling back to main when the tip is an ancestor of main; searching remote-tracking branches, since the checkout cannot measure what it does not have.

DEC-16 · The docs/infra exemption, and what it never covers

ChoiceA range is gated when any changed path is under code_paths (empty = everything is code). Otherwise it is exempt from test, cr and doc evidence and writes no receipt. Optional infra_paths globs can only narrow the exemption. Never exempt: check 8 (sign-off), the epic tracked-doc layout, and the lineage of a T3 doc the range archives.
WhyAn archive commit is always docs-only, so exempting it would make the distillation check unreachable.
RejectedA config flag to exempt archive commits.

DEC-17 · keel check: where trees are proven

ChoiceThe command is keel check (config [check], status keel-check-green), with no compatibility for the old [gate0]. It runs at preflight, on the merged tree of an epic → main merge, and on every pushed tree; a WU → epic merge checks notes only. Results are cached by tree content. The pre-commit hook enforces merge-only main and runs keel lint when the staged diff touches a code_paths path (lint only, never tests); with MERGE_HEAD present it runs the gate pre-merge-commit would have run, instead of a separate lint.
WhyTwo WUs green alone but red together are caught at the epic's preflight, its merge into main, or a push, not at the second WU merge. A non-HEAD pushed tree is proven in a scratch worktree whose cache is discarded.

DEC-41 · Keel finds the repository from its working directory; git's local environment is never forwarded

ChoiceEvery process keel spawns goes through one helper that removes the 15 names of git rev-parse --local-env-vars (hardcoded; a test checks it covers the installed git's list, and a source scan checks every spawn in src/ uses the helper). The configured lint and test commands lose all 15. Keel's own git calls keep GIT_INDEX_FILE, because the commit-msg Reviewed-By check must read the index being committed; only the push check's scratch git worktree add and remove strip it. Not stripped: GIT_CONFIG_GLOBAL, GIT_CONFIG_SYSTEM, GIT_CONFIG_NOSYSTEM, identity variables, GIT_REFLOG_ACTION (they select a scope or identity, not a repository). Test spawns go through tests/common cmd(), which strips all 15 (a source scan enforces it) and reads no developer config (backlog B10). keel mr confirm refuses, writing nothing, when the merge-base of tip and target is the tip.
WhyGit exports those variables to hooks, and GIT_DIR is absolute from a linked worktree. A push from one ran keel check, whose cargo test inherited it: the fixtures' git changed the real repository. Signing an already merged tip overwrote its sign-off with an empty range. A push is protected once the fixed binary is the keel on PATH.
RejectedAsking git for the list at runtime; stripping GIT_INDEX_FILE in all keel git calls (a Reviewed-By bypass through commit -a); stripping the config selectors; making verify-dod red on an empty range (a merged tip is legitimately exempt; only signing it is wrong).

DEC-18 · The epic walk and walk_waivers

ChoiceThe epic gate re-verifies every first-parent seam. A red seam is overridden only by walk_waivers: [{seam, why}] hand-edited onto the epic tip's cr note (git notes --ref=cr edit), matched by sha prefix; a blank reason never waives. The epic tip itself is not walked, and no rule restricts what it may be. A plain seam that changes no code and carries epic-range test and doc notes (each naming the epic's base, not the commit's parent) is judged on them over the epic range, by checks 1, 2 and 6 without the tracked-doc layout; a commit that changes code stays a standalone commit. The push of an epic branch skips plain commits already on main and judges its tip the same way when it carries epic-range notes; review and sign-off stay at the merge into main.
RejectedA CLI flag for waivers; a rule that the epic tip must not be a code commit; running the epic review before the archive commit; a --tip flag for keel notes write; judging a code commit with epic notes over the epic.

DEC-19 · Notes sync is push-only

Choicepre-push pushes refs/notes/* (a failed sync only warns). Nothing configures a notes fetch: a fresh clone runs git fetch origin 'refs/notes/*:refs/notes/*' by hand. Fetch setup in init is deferred (backlog B6).

DEC-29 · Conflicted merges are handled by the workflow, not the CLI

ChoiceThe workflow skill says: resolve conflicts by merging the target into the work branch first, so the gated merge is clean. When MERGE_HEAD is present, pre-commit runs that same gate (into an epic the WU gate, into main the epic gate then keel check) instead of a separate lint, so a hand-finished merge behaves as the clean path git sends to pre-merge-commit. A merge commit is therefore allowed on main, where the merge-only rule refuses only non-merge commits (UC-GATE-1).
WhyFinishing a conflicted merge with git commit never runs pre-merge-commit; into an epic it once landed ungated until the epic walk re-checked the seam.

Human sign-off

DEC-20 · Trust model: a local roster; "signed" means a listed key signed

ChoiceThe roster is the committed .keel/mr-allowed (since DEC-47); the untracked .mr-allowed is read by nothing. Tiers email / username / key, configurable via [mr] tiers (default all three). If an identity has any key entry, its notes must carry a verifying signature, whatever tier the note claims. Identities are limited to [A-Za-z0-9@._+-]. Accepted limitation: any process with SSH_AUTH_SOCK or filesystem access (including an AI agent) can sign with a loaded key or add itself to the roster, so "signed" proves a listed key signed this exact change, not that a human reviewed it. A passphrase-protected key is assumed and recommended; it only helps while the key is not loaded into ssh-agent.

DEC-21 · The signature payload

Choicessh-keygen -Y sign -n keel-mr over a versioned text: keel-mr/v2, level, base, tip, change hash (the full diff) and, only when a report is attested, report path and report hash (DEC-40). Change and report hashes are sha256:<hex> via the sha2 crate. The key comes from git config keel.signingkey (never user.signingkey). mr confirm self-verifies against the roster before writing. The verifier recomputes base, tip and change from the repo and trusts only the signed report hash, re-checked against the report's bytes.
RejectedTrawler's bare change_hash\nreport_sha256: replayable onto another commit, range or level.

DEC-22 · Sign last, strictly; check 8 at the boundary only

Choicekeel mr confirm refuses unless the tip passes checks 1–7 for its level (the epic walk included), so a human is never asked to sign a tip the merge would refuse. One exception (DEC-49): a sign-off that waives the tip's review (--waive-review) needs neither the tip's own cr note nor checks 3–5 first; every other check must be green, and the waiver is written in the same act as the signature. Check 8 runs in gate::run() on every top-level wu/epic run, never inside verify(): the walk re-enters verify() per seam and must not re-judge old seam sign-offs (the roster is local and mutable). It runs at pre-merge-commit, and at pre-push for every merge seam not already on the remote branch. The report is found by its data-artifact role under [mr] report (DEC-40).
WhyA signature the merge would refuse wastes the human's step; the check at the boundary alone keeps old seams stable.

DEC-23 · The merge boundary judges by the target's policy and untracked hooks

Choicepre-merge-commit loads the config from HEAD:.keel/config.toml (the target's committed policy; no committed config → refuse), and refuses empty merge heads on a gated branch. Hooks are written to <git-common-dir>/keel-hooks/, untracked, with an absolute core.hooksPath; they are thin exec keel … shims. Keel runs alone, never beside another hook manager: keel hooks install refuses (exit 1, nothing changed) when the effective core.hooksPath (any scope) is not Keel's keel-hooks path, or, with none set, when <git-common-dir>/hooks/ holds any entry not ending in .sample; it names what it would replace, and --force replaces it. keel init stops on that refusal; its -f never implies --force. Guard D: keel preflight and keel verify-dod wu|epic fail 0·hooks while core.hooksPath is unset or not Keel's (UC-GATE-6); keel check only warns.
Whypre-merge-commit runs with the incoming branch already in the working tree: a branch could rewrite the config or ship a no-op hook git would run for its own merge.
RejectedTrawler DEC-72's tracked hooks (relative tracked core.hooksPath). Chaining another tool's hooks (it re-imports branch-controlled code into the gate); refusing only a foreign value and warning on an unset one (misses a clone where hooks were never installed). Cost accepted: a hook manager switched on later is caught at the next preflight or gate command.

DEC-24 · Rule-bearing commits: a trailer, not a signature; known gaps accepted

ChoiceA commit touching rule_bearing needs a listed Reviewed-By trailer (keel mr commit); the WU's mr/v1 signature covers the whole diff. rule_bearing entries ending in / are prefixes, others globs. Native git commit -S signing is deferred (backlog B7). Accepted gaps: (1) permanent, not scheduled: the commit-msg hook reads rule_bearing from the working-tree config, so a transient uncommitted edit lets a rule-bearing commit land without a trailer, and nothing downstream re-checks trailers; (2) git commit --amend sees only newly staged changes; cherry-picks are checked like any commit.

DEC-25 · W4 security review M3 and L1–L5 are not pursued

ChoiceNot triaged or tracked further.
WhyThe report holding their details is unavailable, and the owner accepted the risk.

DEC-40 · The result report is a configurable, role-found receipt; sign-off hashes are SHA-256

Choice[mr] report = "required" | "optional" | "none" in the target's committed config, one policy for both levels, default required. The report is the page whose data file beside it (<stem>.yaml, DEC-69) has an artifact carrying the level's role (wu-result, epic-result, as text or a list; a collapsed doc counts for both), or --report <path>; a page with no data file is never one, whatever tag it carries, and --report naming a data file is refused, naming its page. Candidates are pages under docs.root that base..tip changes, by the page or by its data file, with both files at the tip; no untracked or archived file is searched, so an epic sign-off passes --report unless its result doc is committed in the epic's diff. Several candidates, none under required, or none with --report are refused before signing. Check 8 reads the policy from the cfg it is given: required with no report in the note is red; a report in a note is re-hashed under any policy. The sign-off attests the page's bytes. Payload keel-mr/v2; change_hash and report_hash are sha256:<hex> via the sha2 crate. A waived tip adds a payload line (DEC-49).
WhyThe sign-off once attested one report inferred from a changed *-result.html: a project with no reports could not sign, and an archived epic report was not found. With no legacy reader (DEC-13), an old mr/v1 note is red wherever a new binary re-verifies it.
RejectedA per-level policy. Searching for an untracked epic report; narrowing by name, a new epic-id attribute or file mtime; git hash-object or shell tools for SHA-256; SHA-256 for the unsigned cr/v1 and dod/v1 bindings (it would stale every in-flight cr note).

DEC-47 · The signer roster is committed, and the target's copy judges

ChoiceThe roster is .keel/mr-allowed, committed, with the line format and tiers of DEC-20. Every reader judges a change by the roster committed on what it lands on: check 8 at the merge hook by HEAD's, by hand by the resolved target's, at pre-push by the merge's first parent's; keel mr confirm by the target's; keel mr commit and the commit-msg hook by HEAD's. Where that tree holds none, the roster the change carries judges and keel prints one bootstrap line; with none anywhere nobody may sign. The file is always rule-bearing. A sign-off whose range changes the roster prints each added and removed line and is refused without --roster-change. Keel's own policy is tiers = ["key"] with a key needing the owner's touch or passphrase (DEC-48); the template keeps all three.
WhyThe roster was an untracked file of whichever checkout ran the command, so a worker session could list itself, or rewrite [check] test to run keel mr confirm. Adding a signer needs a sign-off by a signer the target already lists; with none left, the owner lands a roster by hand. Remaining gaps: DEC-48.
RejectedTracking .mr-allowed at the root (it collides with every checkout's untracked file); always main's roster (a roster change could not be used before reaching main); a disk fallback; printing a roster change without refusing; refusing a key that is not sk-.

Workflow process

DEC-57 · Every follow-up names the work that takes it

ChoiceEvery follow-up names the WU, epic or backlog row that takes it, wherever it is recorded; a result report with none says none. The rule lives in the shipped skills (keel-workflow §2, keel-plan §3) and in UC-DOC-1. A done item is struck where it was recorded, not moved.
WhyA follow-up in a result report, a cr note or the backlog could name no destination, so nobody owned it. A review reads a destination and can refuse a flimsy one.
RejectedA gate on result reports: it cannot tell a real destination from an invented one. A tracker file: git is the registry.

Keel's own test suite

DEC-59 · Keel's suite is one test program run by plain cargo test

ChoiceEvery integration test is a module of tests/suite/, with tests/common included by path, so cargo test builds two programs (unit tests and suite) and shows every failure. layout::the_suite_is_the_only_test_program fails on any other test program, and on any .rs file under tests/suite/ that does not report itself through compiled!();. Every PATH a test hands a child starts with its git's own git-core directory (common::path()), so the xcrun shim never runs. A wait for something that must happen keeps the 10 s bound; a test that expects "never" passes a short one. The repos most tests start from are built once per process as templates (common::fixture) and copied with std::fs. Every test spawn's global git config is tests/common/gitconfig (it only turns off automatic maintenance). No thread cap; [check] test stays cargo test.
WhyA full cargo test took about 61 s (77 s in a worker's sandbox), spawn-bound, as eleven test programs run one after another; now about 28 s. Keel's own git calls are about 80 % of what is left (backlog B26); notify_owner's loopback tests still fail in a worker's sandbox (backlog R49).
Rejectedcargo-nextest as the required runner (Trawler's DEC-75): one program under cargo test measured the same (29.2 s against 28.8 s), and nextest is slower after the templates. A thread cap of 8 in .cargo/config.toml (about 4 % gain, not the 10 % set).

The local app

DEC-70 · A desktop app shows the flow and runs only the owner's commands; GitHub's flow is dropped

ChoiceThe app judges nothing. Keel's gate, notes and sign-off stay the one judge, in keel and its hooks. The app shows keel's and git's state and alerts the owner; it never runs keel verify-dod, keel preflight, keel notes write, a fetch or a push, and the terminal keeps working without it. Electron: a main part runs fixed commands without a shell, watches git and alerts; the window asks it by named requests that name an item, never a command, path or commit. It reads keel's CLI and the notes, never a binding of keel's code, opens no port, shows worker-written text as text, and runs keel, git and claude from paths set in the app. Only the owner's commands, by a button with a confirm: keel mr confirm (a WU, an epic), git merge --no-ff --no-edit (into an epic, into main) and keel mr commit with the message he types. Each button shows the full line and its folder, asks once in a main-part dialog, re-reads and checks every value from git, runs the line and shows keel's words; the same line works in a terminal. Beside these, only Attach (a terminal on a live session, writes nothing) and the owner's note posted to the router's inbox on his Send. Two sources: persistent data (docs, git, notes, run records, the inbox's files, the app's own files) is read from disk; router data (stages, questions, conflicts, live workers, alerts) comes from the router's update log, which the app only reads, gone at a router restart, each field with a default. The router writes the alert. GitHub's flow is dropped, reverted first: the checks, the sign-off by approval, auto-merge, the bot, the watch, the docs site and the settings check go by one revert of the five merges that brought them (E-GHREVERT, before any app epic), after the owner switches his GitHub settings off; the typed sign-off and its waiver options come back, and a task merges on his Mac. Releases (release.yml on a tag, no pull-request run) and his own pushes stay on GitHub. E-GHSETUP is closed unmerged: its "list what is missing first" goes to the app's "Add a project", its pinned install script to the release rows. By E-GHREVERT (the owner's ruling of 2026-11-19, on its W2 plan) no record replaces the flow's: its nine decision records are removed, with what they folded into older records, and its use cases and backlog page with them; every page reads as before the flow, plus what the revert keeps (backlog local-app A1). Their ids are never reused (decisions-index.yaml). The revert keeps keel reading the github tier and line, signing nothing, until E-LOCALTOOL and E-DOCSPLIT are on main; E-KEELFIX removes it. Five epics carry the app (backlog local-app A1 – A5); docs/local-app.html is their source, with keel's changes K1 – K15 (among them K2, a gate run with no receipt; K9, the commit hooks reading the committed rules; K14, K15, the update log). The username signs from the app, as DEC-48 left it; signing with a key is not designed.
WhyGitHub ran part of the flow (E-GHFLOW, E-GHFLOW2): heavy setup, one company, a push and a check run per step, and a pull-request page that was not where the owner wanted to read and approve; what waited on him came by Telegram, the terminal and GitHub mail. E-LOCALTOOL (2026-11-17 to 2026-11-19, ideas and draft screens, no code; archived, e.g. git show 90ee37b:docs/work/2026-11-19-e-localtool-w5-retire-result.html) designed the app. The owner's rulings: option B and Electron (2026-11-17); a button runs the command, overruling "the app copies it" (2026-11-18); two sources (2026-11-18); back to before GitHub first, signing back, E-GHSETUP closed (2026-11-19). Electron needs a major upgrade every 6 months and a signed app for alerts; whether a free signature is enough is decided at the first build. No use case yet: UC-APP-1 – UC-APP-6 are recorded when an app epic plans them.
RejectedReading and approving inside the app (option A, withdrawn: he reads in his browser, with htmldoc's comments). Tauri. A Node binding of keel's code (a second judge). The app copying the command to paste. A button on an alert (the confirm needs the full line in view). The app reading the sessions itself (claude agents --json): one reader, the router's watchdog. Switching the flow off and removing it in two later epics. Shrinking E-GHSETUP to releases.
