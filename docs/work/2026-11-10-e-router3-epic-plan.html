E-ROUTER3 · Router v3: two-way messaging, long-running workers, watchdog, clean launcher, owner-only signing

Epic plan for the router epic that absorbs backlog E-ROUTER v2 (R1, R3–R17, R19) along the grouping proposed there.

T3 · epic plan · 2026-11-10 · Keel · branch epic/E-ROUTER3 off main bfb3eb8 (renamed from epic/routerv3: open point 7)

Intent

Make the router a coordinator that can actually hold a conversation with its workers and stay awake on its own, and stop a granted worker from passing as the owner. Today the router can only subscribe to a worker's end, and in practice even that subscription is denied by the guard (R8). It cannot send a worker a clarification, it has no self-paced wake-up (R17), the launcher caps every run at $25 and starts a second Telegram poller per worker (R16, R7), and any launcher worker can sign a sign-off as the owner (R14). The owner ruled on 2026-11-10 that the guard's ban on router→worker messages is a defect, and set this epic next after E-SEED2, which closed at bfb3eb8. Why now: every multi-worker fleet since E-ROUTER has lost time to the one-way channel, and R14 makes the gate's human sign-off forgeable in every seeded worktree.

Expected result

  • A router session sends a running launcher worker a message with SendMessage, and the guard allows it. The worker answers, and the router receives the reply. A notify_when_idle subscription with the harness's real payload is allowed. tests/router.rs holds the captured payload as a fixture.
  • A follow-up round goes through router-worker.sh resume by default. The keel-router skill says so and tells an expired subscription to fall back to wait.
  • A worker stays alive between tasks: the router hands it the next brief with router-worker.sh send and closes it with stop. A watchdog worker messages the router every 5 min with one short sentence per worker saying what it is doing. The router itself runs no loop or timer (owner ruling 2026-11-11).
  • The launcher passes no --max-budget-usd. It refuses early, with a named reason, a worktree that lacks .claude/agents/worker.md. Two same-second launches of one name do not collide. A worker starts with no Telegram plugin.
  • A launcher worker that rewrites its worktree's .mr-allowed and [check] test cannot produce an mr/v1 note that check 8 accepts. A test reproduces the R14 attack and shows it refused.
  • scripts/router-guard.jq, scripts/router-worker.sh, scripts/router-watch.sh and .claude/agents/ are rule-bearing, so a plain commit touching them is refused without Reviewed-By.
  • The keel-router skill, project-router and decisions/router.html describe what the tooling does: R9, R10, R11, R13, R19 and the posture bullet are each either landed or struck.
  • The router e2e in tests/router.rs runs this flow with a stub claude: spawn, subscribe, message, resume, wait, and the forged sign-off refused.
  • Every row of e-router-v2.html is struck, re-pointed or marked accepted.

Non-goals

  • Shipping the router enforcement with keel init (R6 row 1). It stays per project (open point 3).
  • gh-backed watch kinds (release, CI run, htmldoc comments). They stay worker-run. The proposed W6 is dropped (open point 4).
  • OS-level isolation of workers from the owner (a separate user or a sandbox). R4 is re-recorded as an accepted risk, and the isolation is its upgrade path (open point 5).
  • The Keel product items re-pointed to E-SEED3 (the bare-SHA target inference, cargo fmt drift).
  • R2 (done) and R18 (obsolete).

Owner ruling 2026-11-11: no claude -p for workers or anything else. scripts/router-worker.sh spawn starts a worker as a native background session (claude --bg -n <name> --agent worker, with the policy's model and effort and the fixed grant). Probes come first: which flags --bg honours, workspace trust, what claude rm removes. Plan: W10 WU plan.

E-ROUTER3.W9 · A watchdog worker reports every worker's progress R17 owner 2026-11-11

A special native background session, agent type watchdog, started and stopped by the router through router-worker.sh watchdog start|stop <router-name> (session watchdog-<router-name>). It runs on Haiku (a watchdog_model entry in [router], an owner keel mr commit) with Claude Code's auto-compaction at 100k tokens, and is never restarted. Its tools are SendMessage and the native scheduler. The tick comes from the watchdog's own native schedule, every 5 min: there is no shell ticker. On each tick a read-only launcher command, watchdog facts, gives it one bounded fact block per live worker (state, quiet minutes, branch tip, the last few transcript items) and decides in code which workers are done (idle) or stuck (waiting on a permission prompt or any other non-idle, non-busy state, or busy with a transcript quiet for 15 min). The watchdog sends the router one SendMessage with one short sentence per worker, done and stuck workers first. This covers what W10's flow leaves open: a worker that goes idle without reporting, or never goes idle.

Owner ruling 2026-11-11 · backlog R17 · UC-ROUTE-1, UC-ROUTE-5, UC-ROUTE-6 · a new DEC (DEC-45: W10 lands first and takes DEC-44).

Tests with W10's stub claude: watchdog start runs one claude --bg on the policy's watchdog_model with --autocompact 100k and the 5-minute schedule in its prompt; watchdog facts prints one bounded block per live worker of this repository and marks an idle worker done, a worker waiting on a permission prompt stuck, and a busy one quiet for 15 min stuck; the watchdog agent file grants only SendMessage and the scheduler; the guard admits the two watchdog shapes and lets the watchdog message only the router. A live run logs at least two watchdog reports reaching an idle router, one sentence per worker.

E-ROUTER3.W8 · Router and worker scope; worktree and environment limits decided in its WU plan

Decided 2026-11-11 in the W8 WU plan and DEC-46: no worker pushes; the router creates and removes worktrees (worktree add|remove), one per epic and per WU branch; the review runs in a fresh --review worker; workers start on --setting-sources project,local --strict-mcp-config in Claude Code's Bash sandbox with a fixed deny list and no inherited GIT_*; resume is deleted; W3's remaining items are absorbed.

This WU settles, in its own WU plan, what the router does, what a worker does, and the limits each worker's worktree and environment run under. Each limit gets the checks and the setup that enforce it. Nothing is decided in this epic plan. The WU plan resolves the agenda below first (owner ruling 2026-11-10), and the code comes after.

  • Role contradictions. UC-ROUTE-2 has a worker push the epic branch, but briefs forbid pushing. The first WU worktree cannot be started, because the launcher spawns only into an existing worktree. The author runs keel-code-review on its own diff, against AGENTS.md. Nobody owns removing a worktree after its merge.
  • The environment workers inherit. Workers load the owner's user-level allowlist, hooks, plugins (the Telegram poller) and connectors. Candidate fix: --setting-sources project,local --strict-mcp-config, plus an explicit git grant.
  • Leaks a worker can cause. Inherited GIT_* variables (R19). Shared common-dir state: config, hooks path, notes, other branches. Branch drift inside the worktree. Writes outside the worktree (Claude Code's Bash sandbox is a candidate).
  • Live-probe setup for this epic. The router runs main's scripts, so this epic's probes need a router session in a scratch clone at the WU tip.
