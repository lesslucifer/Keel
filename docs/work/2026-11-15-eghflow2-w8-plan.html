E-GHFLOW2.W8 · Docs as web pages on GitHub Pages

One GitHub Pages site holds the docs of every live branch, so a plan or report is a link you open anywhere. Comments and diffs stay in htmldoc.

Ready v1 · 2026-11-15 · T3 · WU plan · Keel · off epic/E-GHFLOW2 6ea4d37 (landing 1) · epic plan: git show 738c795:docs/work/2026-11-15-eghflow2-plan.html (archived)

The problem

A plan or report is an HTML file. GitHub shows it as source, and a file on your Mac does not open on your phone. So you read docs only at your desk. You ruled on 2026-11-15: "ok, go with Pages".

What changes for you

WhenTodayAfter W8 is on main and Pages is on
You read a plan or reportA file on your MacA web page: https://lesslucifer.github.io/Keel/<branch>/docs/…
A pull request lists the docs it changedEach links to GitHub's source viewEach also links to its page
You comment on a docIn htmldoc, from the fileThe same htmldoc comments, from the page
An epic closesThe result report is a local fileIts report note (W3) is a page too
A branch is deleted—Its pages go at the next build

The pages are public, like the repository.

Example

  1. The bot pushes wu/E-GHFLOW2/w8-pages. "Keel gate" runs on it.
  2. When that run ends, the Pages workflow on main starts. It reads every live branch's docs/ from git and deploys one site.
  3. The bot's pull request lists this plan with a "page" link.
  4. You open the link on your phone. The plan renders with its diagrams and the htmldoc comment layer. You comment.
  5. The branch merges and is deleted. At the next build its folder is gone.

The work

A Pages workflow that runs from main after every "Keel gate" run builds one site in which each live branch's tracked docs/ files appear under <branch>/docs/ as regular files, each epic tip's report note appears as <branch>/docs/_report/report.html, relative links between docs resolve, a deleted branch's folder is absent, and no branch code runs; and the bot's pull-request body links each changed doc's page.

Expected

  • On a scratch repo with two branches, the builder writes each branch's docs under its own folder, byte for byte; links between docs resolve in the site; after a branch is deleted from origin, a new build has no folder for it.
  • An epic tip's report note renders at <epic folder>/docs/_report/report.html, and its links up to docs/ resolve. A WU or main tip's note is not published.
  • A symbolic link, a submodule, a dot or _report path, or a path or branch name outside the safe set is skipped with a log line, never written. A non-empty out dir is refused.
  • The workflow lock test pins the trigger, both jobs' permissions, the pinned actions, and that the build job checks out main only, with no credentials kept.
  • The bot's pull-request body links each changed doc's page.

Test plan

Integration (tests/suite/pages_build.rs): the builder on a scratch repo with a bare origin and a runner's clone: two branches' docs land in their folders; relative links resolve, checked by walking every href in the built site; a deleted branch's folder is gone on the next build; the report note renders for an epic tip only; links, submodules, dot paths, odd names are skipped; a non-empty out dir and bad arguments are refused. tests/suite/router_gh.rs: pr-open's body carries the page link for a changed doc. tests/suite/pages_workflow.rs: the workflow lock.

Unit: branch-to-folder naming, as a generated-input test through the builder's folder mode (pages-build.sh --folder <branch>): every accepted name maps to itself, every refused one prints nothing and exits 1. The builder is shell, so its unit is reached through the script, as router_gh_args.rs does for its argument checks.

Details

  • Facts used and their source. workflow_run: "GITHUB_SHA is the last commit on default branch", "GITHUB_REF is the default branch", it runs only if the workflow file is on the default branch, and runs at most three levels deep (GitHub's events page, read 2026-11-15). The actions, pinned by tag lookup with git ls-remote: actions/checkout v6.1.0 d23441a48e516b6c34aea4fa41551a30e30af803 (as keel-gate.yml), actions/upload-pages-artifact v5.0.0 fc324d3547104276b827a68afc52ff2a11cc49c9 (its tar uses --dereference --hard-dereference and drops dot files), actions/deploy-pages v5.0.1 368f82528645a54fb793d4d04e342629a3f51346.
  • Unverified until the first live run. That the github-pages environment's default rule admits the deploy (reasoned: its ref is main); that a fresh checkout at main with full depth holds every branch as refs/remotes/origin/* (as ci-gate.sh relies on for its base); that a deleted branch starts no "Keel gate" run, so its folder goes at the next push of any branch.
  • htmldoc and a public site. The doc ids are already public in the repository, and the htmldoc server takes comments without a key, so the site adds no new exposure. A doc's comments are keyed by its id, so a doc's comments show on every branch's copy, as on disk today.
  • Security review. The workflow holds a write token, so the router's independent review reads it before your commit, against DEC-63's list plus: no head code runs with a write token, no cache a pull request can write, every event value through env:.
