E-SEED.W10 — Release pipeline (GitHub Releases + npm + Homebrew)

Prebuilt keel binaries for macOS and Linux, published from one cargo-dist config: a tag-triggered GitHub Actions release, a shell installer, an npm wrapper package @lesslucifer/keel, and a Homebrew formula pushed to a tap repo. cargo install --git stays as the zero-infrastructure path.

v1 · 2026-11-07 · Keel · T2 WU plan · epic: E-SEED · depends on: W7 v2 CLI packaging · status: ready (dispatch does not wait on sign-off; the owner reviews asynchronously)

Requirement

Seed plan Q3 decided that adopters get the binary from "prebuilt binaries on GitHub releases + cargo install". After W7 v2, only the second half exists: cargo install --git https://github.com/lesslucifer/Keel, which needs a Rust toolchain and a full compile. This WU adds the first half, plus npm, because most adopting projects (TS/JS, Python) already have Node and no Rust.

Because W7 v2 put the skills inside the binary, a release is the whole of Keel: the gate and the rules ship together. Installing a release and running keel init is the complete adoption path. No plugin is involved.

Why after W7 v2: a release freezes the binary's init behavior (embedded skills, the settings merge, the upgrade prompt, the keel- names) into an artifact other projects depend on. Releasing earlier would ship skills under the old bare names and an init that cannot upgrade them.

One config generates the workflow, the shell installer, the npm wrapper and the Homebrew formula. The release is CI: a signal, never a gate (Trawler DEC-83).
PieceWhat it is
cargo-dist configGenerated by dist init (cargo-dist's CLI is now called dist), then trimmed. It sets ci = "github", installers = ["shell", "npm", "homebrew"], the Unix-only targets (open point 1), npm-scope = "@lesslucifer" so the package is @lesslucifer/keel, and tap = "lesslucifer/homebrew-tap" and publish-jobs = ["npm", "homebrew"] (open point 3). Verified against cargo-dist 0.34.0 (W10 implementation): the keys ci, installers, targets, npm-scope, tap and publish-jobs are valid as written. They live in the [dist] table of dist-workspace.toml (not Cargo.toml metadata), with cargo-dist-version = "0.34.0". dist init -y ignores -t and defaults to extra gnu and Windows targets, so targets was edited by hand. The Cargo.toml [package] needs repository (CI generation refuses without it), description and homepage (the Homebrew job warns without them); dist init also adds [profile.dist].
.github/workflows/release.ymlGenerated by dist, never hand-edited. On a v* tag it plans, builds each target, creates the GitHub Release with the archives, checksums and keel-installer.sh, then publishes npm and pushes the Homebrew formula to the tap repo. It is regenerated whenever the config changes.
npm package @lesslucifer/keelThe cargo-dist npm wrapper: a small package whose bin is keel and whose install step fetches the matching release binary for the platform. Installed with npm i -g @lesslucifer/keel, or per project as a devDependency (open point 6).
Homebrew formulaGenerated by cargo-dist as keel.rb and pushed to Formula/keel.rb in the tap repo lesslucifer/homebrew-tap on each release. Adopters run brew install lesslucifer/tap/keel (Homebrew drops the homebrew- prefix). It points at the release archives, so it needs the macOS and Linux targets already built. Settled in open point 3.
keel --versionNeeded for installer smoke checks and for telling Keel apart from keel.so's keel (W7 v2 open point 12). Today every command first resolves a repo root (repo_root() in run()), and no version arm exists. Add --version/-V before the repo lookup, printing keel <CARGO_PKG_VERSION> plus a fixed Keel marker line.
Version sourceCargo.toml version. The tag must equal v + that version, and dist refuses a mismatch. The first real release is 0.1.0, unless the owner bumps it first.
Install hintsOnce a release exists, docs/install.html (from W7 v2) lists the channels: shell installer, npm, Homebrew, and cargo install --git. Whether the in-binary hints (init's PATH warning, the hook shims) also mention them is open point 5.
Owner prerequisitesAn npm account that owns the @lesslucifer scope, and an NPM_TOKEN automation token stored as a repo secret. New (open point 3): the empty lesslucifer/homebrew-tap GitHub repo, and a HOMEBREW_TAP_TOKEN repo secret on lesslucifer/Keel. GitHub Actions needs write permission for releases on lesslucifer/Keel. Workers cannot do these steps.

Explicitly not this WU

  • crates.io publish. The crate name keel is taken by an unrelated crate, and the replacement name (for example keel-cli with [[bin]] name = "keel") is not settled. This does not block anything. Skipped for now.
  • Windows targets. The CLI is Unix-only (Unix permissions, sh hooks), as recorded in W7 v2. No *-windows-* target, no PowerShell installer, no MSI.
  • Docker image, and macOS code signing or notarization (open point 4). Homebrew is in scope (open point 3).
  • CI as a gate. The release workflow and any CI are signals (DEC-83). No PR-check workflow is added here.
  • Changing the binary name. It stays keel despite keel.so (owner decision 3, R25).
  • Any change to init, the skills or the gate beyond --version.

Expected result

Pushing a v0.1.0-rc.1 pre-release tag produces a GitHub pre-release with archives for the four Unix targets, checksums and keel-installer.sh. curl … | sh on macOS arm64 and in a Linux x86_64 container installs a keel whose keel --version prints the tag's version. npm i -g @lesslucifer/keel does the same once a stable tag exists. For Homebrew, the first stable release is the check: brew install lesslucifer/tap/keel installs a keel that prints the release version, and the tap repo holds the matching Formula/keel.rb. Corrected (cargo-dist 0.34.0, verified in the generated release.yml): a pre-release tag (v0.1.0-rc.1) creates only the GitHub pre-release with archives, checksums and keel-installer.sh. The npm and Homebrew publish jobs are skipped for pre-releases (publish-prereleases is off), so there is no @next npm dist-tag and no formula push until the first stable tag. Setting publish-prereleases = true would publish rc builds to latest, so it is not set.

Test plan

  • Integration (cargo test): keel --version exits 0 outside any git repo and prints CARGO_PKG_VERSION and the Keel marker. All existing tests stay green.
  • Config consistency (local, recorded in the WU result): dist plan lists exactly the configured Unix targets and the shell, npm and Homebrew installers, and the generated keel.rb references the right archive URLs and checksums. dist generate --check passes and dist generate leaves release.yml unchanged, which proves the committed workflow matches the config. dist build for the host target produces an archive whose keel --version is correct.
  • Dry release (manual, recorded): the pre-release tag flow from Expected result, on the real repo. Check that the rc tag produced only the GitHub pre-release (npm and Homebrew skipped). Delete the pre-release and its tag afterwards if the owner prefers.
  • Smoke per channel: shell installer (macOS arm64, Linux x86_64 container), npm global install, brew install lesslucifer/tap/keel (macOS arm64, after the first stable release, or against a hand-run tap push if the owner wants it earlier), and cargo install --git. Each is followed by keel init in a scratch repo and a check that .claude/skills/keel-workflow/SKILL.md exists.
  • Unit layer: the only Rust change is the --version arm, covered by the integration test above. No separate unit test.
