Keel — architecture

What Keel is at this tip: its commands, what setup installs, every policy key, the evidence, the router tools and the close.

T1 · 2026-11-14 · Keel · code at epic/E-SEED3 26f2069 (W1–W7 merged; W8 writes this page)

The shape

Keel is one binary plus the rules it writes into a repository. The binary serves the CLI and the git hooks. The repository holds the policy (committed) and the evidence (git notes, which travel with the code).

Work moves from the owner to a router to a worker in one worktree. A worker commits on wu/<epic>/<slug> or epic/<epic>. Each WU and then the epic is gated at its merge into its target; the owner signs last.

flowchart LR
  O["Owner"] -->|"signs, merges, pushes"| M["main"]
  E["epic/E"] -->|"epic gate"| M
  W["worker in a worktree"] -->|"WU gate"| E
  W -->|"writes"| N["refs/notes/*"]
  G["keel verify-dod"] -->|"reads"| N
  G -->|"reads"| C[".keel/config.toml at HEAD"]
  H["git hooks in the common git dir"] -->|"run"| G
  R["router"] -->|"launcher"| W
The gate reads committed policy and notes; the hooks are the enforcement.

Documentation has five tiers (skill keel-distill): T0 AGENTS.md, T1 this page and docs/install.html, T2 docs/use-cases/, docs/decisions/ and docs/backlog/, T3 docs/work/, T4 the code. This page is T1: it carries the shape and points at the T2 page that owns each rule. Where this page and the code disagree, the code wins; where the code and a written rule disagree, both are named in Where the code and the rules disagree.

Terms

EpicA user-visible change on epic/<slug>: one working unit or more, merged into main once.
WUA working unit: one independently shippable slice on wu/<epic>/<slug>, merged into its epic.
Gatekeel verify-dod at a merge boundary. It reads committed policy and notes, never an agent's word.
EvidenceThe notes a gate believes: test, doc, cr, mr, and the dod receipt the gate writes.
ExemptA range that changes no code_paths path. It owes no test, review or doc note; the sign-off still runs.

What setup installs

keel init is additive. A file it owns that already exists with other bytes is kept and reported; keel init -f overwrites only the skill files, never the policy, AGENTS.md or the host settings. It stops after writing the files when core.hooksPath points at another tool, or is unset while .git/hooks holds anything but *.sample files, because Keel never chains another tool's hooks.

The seven git hooks

HookWhat it enforces
pre-commitRefuses a non-merge commit on [branches] main. With MERGE_HEAD present it runs the gate pre-merge-commit would have run, because git skips that hook when a conflicted merge is finished by git commit. Otherwise, when the staged diff touches a code path, it runs keel lint (never tests).
commit-msgA staged rule_bearing path needs a Reviewed-By trailer naming a signer in the committed roster. Merge commits are skipped.
pre-merge-commitRuns keel verify-dod hook with the target's committed policy: into epic/* the WU gate, into main the epic gate and then keel check on the merged tree. Other targets are ungated; a back-merge of landed history passes; an octopus or an unknowable head is refused.
pre-pushkeel check on every pushed tree (in place for a clean HEAD, else in a scratch worktree); verify-dod range on main and epic/* updates; then pushes every refs/notes/* ref. A failed notes sync only warns.
post-checkoutSets merge.ff=false; copies .gitworktreecopy entries into a new worktree.
verify-doc-postThe host's per-write doc check: keel verify-doc <path>, fed back on red. Called from the host settings, not by git.
verify-doc-stopThe host's turn-end doc check: keel verify-doc over all docs. Called from the host settings, not by git.

Each installed hook is a short shim: it refuses when keel is not on PATH, refuses when the first keel on PATH does not print Keel's marker (another program named keel, or a build older than 2026-11-10), then execs the real command. The two host doc hooks exit 0 instead, so a missing or foreign keel never blocks an edit.

The skills lock

Before a write, init compares each shipped file with three things: what is on disk, what this binary carries, and the lock entry. Missing: create. Equal: leave. Differs but still matching its lock hash: upgrade silently, because Keel wrote those bytes. Differs and not matching: ask (default no), or overwrite with -f. A file inside a keel-* directory that this build does not ship is reported as extra and left alone. A symlinked or unreadable lock is never written through; init reports it and carries on. The lock is written whenever init writes a skill, or when one already exists, so a later upgrade can tell an unedited file from an edited one. A tree whose skills all match and that never had a lock is left untouched (Keel's own tree).

The config keys

.keel/config.toml is read at two different moments. The pre-merge-commit hook reads the copy committed at HEAD (the target), so a branch cannot change the rules that judge its own merge. By-hand commands (verify-dod, preflight, mr confirm) read the working tree's copy, and the review cap is read from the target's committed copy. The CLI parses a fixed set of keys and silently ignores unknown ones at the top level (the [docs.tiers] table is stricter: an unknown tier key is an error). The [review] modules/rubric and the [router] keys are never read by the CLI: the review skill and the worker launcher read them. This table names every key that exists in templates/config.toml or in the code that reads a config.

Five note kinds, all JSON in refs/notes/<kind>, all carrying the same identity block: tip, base, branch, committer, timestamp, and a schema string (<kind>/v1). Notes travel with the code because the pre-push hook pushes them; the gate never takes an agent's word for a fact it can read from a note.

The router tooling

The router is one coordinator between the owner and several workers. It never does the work itself. The tooling is in scripts/; the rules it implements are the keel-router skill plus the project's project-router skill. The enforcement split matters: on Claude Code the guard is a hook and fails closed; on DeepSeek Harness no guard plugin exists, so the skill is the only guard (backlog D2).

The epic close

An epic closes on its own branch, then lands on main. The code enforces the evidence at each step; the owner does the signing, the merge and the push. The exact order:

The T2 pages own the wording of these rules. The epic close lands the epic's amendments there: UC-GATE-3 and UC-GATE-4, UC-NOTE-1 and UC-GATE-2, UC-INIT-1, UC-REV-2/UC-REV-3, UC-MR-1 and UC-DOC-1; DEC-3, DEC-15, DEC-18, DEC-41, DEC-49, and a new DEC-57 for the follow-up rule. DEC-19 is not amended: it already records push-only notes. This page carries the shape those texts describe.

  1. Merge main into the epic if main moved. A back-merge into an epic is not a seam: the gate passes it.
  2. Distil: move each T3 working doc's durable truth into a T1/T2 doc, then git rm the T3 file and keep the file in the git-ignored docs/.archive/.
  3. On the archive commit, write the epic's notes: test/v1 with the e2e layer, and doc/v1 with one --distill line per archived T3 doc. Written with no --target while the archive commit is the epic tip, their range is the whole epic (merge-base(main, tip)..tip).
  4. Write the epic result report into docs/.archive/ (untracked), with data-artifact="epic-result" and a ready status; keep it on disk through the sign-off.
  5. Run the epic-scope code review on the tip; it writes cr/v1. A walk seam that is genuinely safe is waived in that cr note's walk_waivers, never with --no-verify.
  6. keel preflight epic <tip>: the checkout is the tip, the tree is clean, keel check is green, checks 1–2 pass, and the round is within the cap.
  7. keel verify-dod epic <tip>: checks 1–8. Before the sign-off the only expected red is 8·manual-review, the boundary being signed.
  8. The owner signs: keel mr confirm epic <tip> --as <id> --report docs/.archive/<date>-<slug>-epic-result.html. It writes mr/v1. Re-run keel verify-dod epic <tip>: check 8 now passes and the gate writes the dod/v1 receipt.
  9. The owner merges --no-ff into main. The pre-merge-commit hook runs the epic gate again and then keel check on the merged tree.
  10. The owner pushes main and the epic branch. The pre-push hook checks every pushed tree, walks the range on main and epic/*, and pushes the notes.

A close commit is judged by its epic-range notes (W2)

Check 7 (and the pre-push range walk) reads a plain first-parent commit in one of two ways. A commit is epic-range when every test or doc note on it names the epic's base (the merge-base of main and that commit) and that base is not its own parent. An epic-range commit is judged at the close level — checks 1, 2 (e2e) and 6, without the tracked-doc layout — when it is the pushed tip or it changes no code. A commit that changes code is judged at close level only when it is the pushed tip; inside the range it stays a commit. The first commit on an epic, whose parent is the epic base, is judged as a commit. Merge seams are judged as their WU tip; a merge whose second parent is already reachable from the mainline or the target is skipped as a back-merge; an octopus is refused.

That is what makes the archive commit pushable and walkable: it changes no code and carries the epic's notes. Writing those notes on the archive commit, not on the previous tip, is the whole point of the rule. A later code fix after the archive commit gets its own commit evidence; the archive commit itself keeps the epic's.

A bare tip is resolved, never guessed (W3)

A WU tip is measured against the epic its branch name names: wu/<e>/… gives epic/<e>. A tip that is not a local branch (a bare commit id, or a detached HEAD) has no name to read. The gate then looks at the local branches that hold it: one wu/ holder names its epic; otherwise one epic/ holder is the target. No holder, or two epics, is a refusal that names --target; main is never a guess for a WU. --target R always overrides, and the result must be a local branch. The branch-name derivation is shared (notes::target); the gate adds holder resolution (notes::target_from_holders) for a tip with no local branch. The writer has no holder rule, so write notes with the WU branch checked out.

They are rules, not gates. A gate can check presence and bytes; it cannot tell a real destination from an invented one, which is why that last rule is written down and not enforced.

What no gate reviews

  • Everything outside code_paths. Docs, skills, templates, .keel/, scripts/, AGENTS.md and the router guard are not code to the gate. Some are rule-bearing, so a commit to them needs the owner's Reviewed-By, but that trailer is typed text (DEC-47), no cr note is required and no test layer covers them.
  • A docs/infra-only WU or epic. Its whole range is exempt: checks 1–6 are skipped (an archived T3 doc still owes check 6's lineage), no test, review or doc note is required, and only the hooks guard, the owner's sign-off (check 8) and, at an epic tip, the tracked-doc layout still run. This page's own WU is that kind of range.
  • Whether a waiver's reason is true. The gate accepts any non-blank reason for a waived test layer; a review reads its quality, not the gate.
  • Doc depth and doc claims. verify-doc checks form: items, tags, the epic-plan word count, links and diagram label quoting. It cannot check that a sentence is right, and the Mermaid label scan is best-effort (backlog B21).
  • The dod/v1 receipt. The gate writes it; nothing reads it. Nothing notices if it is deleted.
  • Whether a follow-up names a real destination. The rule is in the skills; no gate can verify it.
  • The router guard on DeepSeek Harness. No hook surface exists there; the whitelist is a skill rule only, and the router must say enforcement is missing.
