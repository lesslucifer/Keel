What landed

Delivered. W1 did what its requirement said: init plants the shared root, and nothing else takes it away.

  • Init writes the six skills, then .agents/skills as a relative link to ../.claude/skills. The repository root now carries that link as one line.
  • A real directory, a regular file, an unreadable target or a link aimed somewhere else is kept and reported — never replaced, never printed as created.
  • A second run changes nothing: it reports unchanged .agents/skills (-> ../.claude/skills).
  • A git worktree add checkout carries the link, and it still resolves there, because the target is relative to the checkout.
  • The hand-off prints the three DSH profile install lines — Auto Review, worker sessions, doc gate — and says a plugin lives in the profile, never the project.

In a real repo, in steps

  1. A fresh repo runs keel init. The skills land in .claude/skills; then init makes .agents/ and prints created .agents/skills (-> ../.claude/skills).
  2. The same repo runs keel init again. It prints unchanged .agents/skills (-> ../.claude/skills), and a tree snapshot is identical before and after.
  3. A repo already has a real .agents/skills directory. Init prints kept .agents/skills (a real directory; not the shared root) and touches nothing under it.
  4. .agents is itself a link to ../shared. Init prints kept .agents/skills (.agents is a symlink -> ../shared; …), and ../shared stays empty — a relative target would resolve from nowhere else.
