Decisions: distribution and adoption

Why Keel is one CLI that carries its own rules, how a project adopts it, and how Keel itself is run.

T2 · decisions · current truth · 2026-11-18 · Keel · DEC-1 – DEC-12, DEC-38, DEC-53

Current truth: each record says what stands today, why, and what was rejected. A later decision that changes one is folded in and named. A record replaced whole keeps its id and one line. Ids are never reused; git keeps the history.

One CLI that carries its rules

DEC-1 · One project-agnostic Rust CLI, extracted from Trawler

ChoiceKeel (~/Documents/proj/misc/Keel, public GitHub repo) is a Rust port of Trawler's xtask code and tests, with every Trawler/cargo assumption moved into .keel/config.toml. One profile, every gate. Test counting by per-extension adapters (Rust, TS/JS, Python, Go) plus a config regex. Trawler itself moves onto Keel in a separate Trawler epic after Keel's first release.
WhyTrawler's workflow was hard-wired to one Rust repo; each new project would copy it by hand and drift. The config and the test adapters are now the only per-language surface.

DEC-2 · The rules ship inside the binary; no Claude Code plugin

ChoiceThe skills are embedded in keel (include_str!, one list in src/init.rs) and keel init writes them into the project's .claude/skills/keel-*, committed and versioned with the project's gate. Never user-level ~/.claude/skills. Skill directories carry a keel- prefix (avoids the built-in code-review collision); source directories have the same names as install directories. project-router stays unprefixed and project-owned. Keel's repo holds its skills twice (skills/ source, .claude/skills/ copy); a self-hosting test fails when they drift.
WhyA plugin means a second install step, a second version (plugin skills against the binary's gate) and rules the project does not control.
RejectedPlugin / marketplace distribution. Symlinking Keel's own .claude/skills/keel-* to skills/ (untested whether Claude Code loads symlinked skills).

DEC-3 · init never clobbers; skill upgrades ask per file

ChoiceProject-owned files (config, AGENTS.md, .codex/hooks.json, project-router): create if missing, otherwise keep and report. keel-* skill files: missing, created; differing, one [y/N] prompt per file on every run, TTY or not; end of input is N (keep, print "differs", exit 0); -f/--force overwrites without asking. .keel/skills.lock tells a hand edit from an upstream update: a file still matching its recorded hash upgrades silently; anything else (an edited file, no lock entry, a lock that cannot be read or written) asks, and -f overwrites and records. A lock that is a symlink is kept and never written through. Files no longer shipped or added by the user are reported as extra, never deleted. AGENTS.md is outside the upgrade flow. .gitignore lines are appended, never rewritten.
Whyinit must be idempotent and never overwrite an edited file unasked (UC-INIT-1), yet a re-run is also the skill upgrade path. CI and scripts must pass -f to update skills.
RejectedA three-tier --yes/--no/TTY design; a non-zero exit when a prompt cannot be answered.

DEC-4 · One AGENTS.md as T0; skills only in .claude/skills the skills-root line is replaced by DEC-53

Choiceinit writes a single AGENTS.md as the T0 file, no CLAUDE.md (Claude Code 2.1.277+ reads AGENTS.md when no CLAUDE.md exists; Codex reads it natively); it warns when a CLAUDE.md exists. No Codex skills parity. .codex/hooks.json is written as a real file calling the installed scripts (unguarded, as the template has it). The skills root is not .claude/skills alone: DEC-53 adds .agents/skills as a relative link to it, for DeepSeek Harness.
WhyOne T0 file serves both hosts. Claude Code does not read .agents/skills/, so that link is for DeepSeek Harness only.

DEC-5 · Harness hooks are merged into settings.json, guarded, fail-open

ChoiceA JSON merge, never an overwrite: a hook group is appended only if its exact command is absent anywhere under that event; invalid JSON is left untouched with a warning; key order kept (serde_json preserve_order, pulls in foldhash). Each command is guarded: it runs <git-common-dir>/keel-hooks/verify-doc-* only if present, else exits 0. The scripts themselves exit 0 when keel is not on PATH; git hooks fail closed instead. A committed settings file is inert until keel hooks install runs.
WhyWithout a plugin, the PostToolUse/Stop doc-verification hooks come from the project's own .claude/settings.json, which may already hold user settings. A missing binary never breaks a session (making the harness hooks loud is a one-line change).

DEC-53 · One shared skill root: .agents/skills is a relative link to .claude/skills

ChoiceInit writes the six keel-* skills once, under .claude/skills, then plants .agents/skills as a relative link to ../.claude/skills (relative, so another worktree resolves it). It plants only under a real .agents directory at the repo root: a symlinked, non-directory or unreadable .agents is kept with the reason printed. Anything at .agents/skills other than exactly that link (a real directory, a file, an unreadable link, a link aimed elsewhere) is kept and reported, never replaced, and the project gets no DSH catalog from init, which says so. The link rides the first commit. Init renders no per-host skill variant: the six skills are the same bytes for every host; the one per-host prose is the router's transport table (DEC-55). Replaces the skills-root line of DEC-4.
WhyDeepSeek Harness (DSH) reads skills from .agents/skills and never scans .claude/skills: a skill left there is absent from a worker's catalog. Probed 2026-11-14: through the link a DSH catalog listed all six skills, in the main checkout and in a worktree.
RejectedCopying the skills into .agents/skills (two trees that drift). A per-host variant rendered at init (N copies; a DSH tool rename means re-running init everywhere). An absolute link (dangles in a worktree, where workers run). Replacing a project's own .agents/skills. Keeping DEC-4's ban, which leaves DSH with no rulebook.

Install channels and release

DEC-6 · Install channels and the binary name

ChoiceToday: cargo install --git https://github.com/lesslucifer/Keel, the only hint the CLI prints (never cargo install keel). Prebuilt channels are built by DEC-38 (the first stable tag has not yet exercised npm and Homebrew; backlog B1). No crates.io publish. The binary stays keel: the PATH collision with the npm package keel (keel.so) is an accepted risk, stated in docs/install.html.
WhyAdopters get prebuilt binaries plus cargo install, and init prints the install line. The crates.io name keel belongs to an unrelated crate.

DEC-38 · Release pipeline: one cargo-dist config, tag-triggered, CI a signal

Choicecargo-dist (pinned in dist-workspace.toml) builds four Unix targets (macOS and Linux musl, arm64 and x86_64) and three installers: shell (into $CARGO_HOME/bin, no updater), npm @lesslucifer/keel, Homebrew formula in lesslucifer/homebrew-tap. .github/workflows/release.yml is dist-generated, never hand-edited: change the config, re-run dist generate. Any pushed tag matching **[0-9]+.[0-9]+.[0-9]+* triggers it; a tag matching no Cargo.toml version fails in plan. Pull requests do not run it (DEC-65); the owner's keel-tags ruleset (admin bypass only) guards tags. Only the owner tags a main merge commit whose push ran keel check. A prerelease tag (v0.1.0-rc.1) publishes a GitHub prerelease only (publish-prereleases off; tests/suite/release.rs asserts it). MIT licence; actions pinned to commits; Linux jobs on ubuntu-24.04 and ubuntu-24.04-arm (also locked by that test). Secrets by name only: NPM_TOKEN (granular, read-write, with expiry; scoped to @lesslucifer until the first publish, then @lesslucifer/keel; "bypass two-factor" set, else EOTP) and HOMEBREW_TAP_TOKEN (Contents read-write on the tap only; the tap needs one commit). If npm fails after the Release is live, fix the token and re-run failed jobs; never delete or re-push the tag. keel --version works outside a repo and names Keel; the git hook shims print the cargo install --git line and point at docs/install.html.
WhyAdopters without a Rust toolchain need a binary. Release CI is a signal, never a gate (DEC-11); .github/, dist-workspace.toml and Cargo.toml are neither code paths nor rule-bearing, so the router dispatches an independent review. Accepted risks (dist 0.34.0 hardcodes them; revisit at each dist upgrade, re-resolving the action pins): workflow-wide contents: write; the Homebrew job keeps the tap token on disk while running brew code; dist and rustup are piped from curl into sh with no checksum; the npm job runs end-of-life Node 20.x; github.ref_name is interpolated into run:; no tests run.
Rejectedallow-dirty: it turns every dist upgrade into a hand merge.

Adoption and defaults

DEC-7 · Unix only

ChoiceNo Windows support and no Windows work unit: the CLI uses Unix permissions, sh -c and #!/bin/sh hooks.

DEC-8 · Bootstrapping: the policy lands once, ungated

ChoiceFor adopters, init prints a one-time git commit --no-verify -m "keel init" on main. For Keel, E-SEED ran on branches without gates and W7 was the last ungated merge, carrying Keel's own init output; the owner then installs the hooks (install, push, keel init, refused-commit probe, keel mr setup). Rollback: git config --unset core.hooksPath. E-SEED's own seams carry no notes, so its epic gate needs walk_waivers on the record.
WhyAfter init, pre-commit refuses commits on main and the merge gate refuses a target with no committed config, so the config can land neither directly nor by merge.

DEC-9 · Config defaults and Keel's own policy

Choicecode_paths defaults to ["src/", "tests/"]; check commands are detected per language, otherwise a command that fails ("a gate that passes on nothing would be worse"). [paths] worktrees (default .claude/worktrees/) is gitignored by init so git add .claude cannot sweep in agent worktrees. The docs skeleton is directories only (no index docs: an htmldoc needs a server-minted id; no .gitkeep: a tracked T3 file). Keel's own rule_bearing adds skills/, templates/, .keel/, .claude/skills/, .claude/settings.json to the default, so init on Keel reports kept .keel/config.toml by design.

DEC-10 · Docs: HTML only; plans do not gate dispatch

ChoiceProject docs are HTML via htmldoc, never markdown (AGENTS.md and skill files are infrastructure). Every WU gets a plan doc for the record and for distillation, but a worker is dispatched once the doc exists and dependencies are met; the owner reviews plans and results asynchronously through htmldoc comments. Since DEC-69, a plan's or result's checklist lives in a YAML data file beside its page, named like it; keel verify-doc reads it, and the write hook passes on a written .yaml under docs/ as it does a page. Owner rulings during an epic go into an append-only rulings log, then into this knowledge base at close.
RejectedA per-WU plan-review gate before dispatch.

DEC-11 · What the extraction left out

ChoiceDeferred to later optional work: the design pack (design flow, component design, design-review, gate check 9; tied to a React registry), tally --fleet and debug serve (the fleet block stays optional on cr/v1), the Secure Enclave signer (any ssh-agent key signs). Never: CI as a gate (a signal only, Trawler DEC-83), legacy schema readers.

DEC-12 · Repo conventions: worktrees, and nothing unclosed on main

ChoiceThe main repo folder always stays on main; epic work happens in separate worktrees. No T3 doc, epic plan, or anything from an unclosed epic ever lands on main: an epic reaches main only at close, after its T3 docs are distilled and archived, as one epic merge. A file in another worktree is referred to the owner by full absolute path, never a relative link.
WhyEpics landing in sequence conflict on .claude/settings.json and .gitignore; take the settings that hold the router config and re-run keel init on top.
